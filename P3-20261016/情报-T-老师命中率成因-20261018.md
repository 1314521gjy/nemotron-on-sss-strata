## ② 老师的表是怎么做的

### 2.1 工具：`E:\strata\tools\make_profile.py`（110 行，全文已读）

- 输入：**① 基础 profile（默认 `data/expert-profile.bin`，随发行版发布）**；② 若干 **routing trace**（引擎跑 `--dump-routing FILE` 写出"a prompt typical of your use"的每层每位置 routed experts）；③ 不足 24,576 的用"每层轮转"补齐。

## ④ 判断 (a)/(b)/(c) 与建议

### 4.1 量化分解（把 43.3% → 96.5% 的 53.2 点拆开；A 级读数 + D 级线性分解）

| 项 | 点数 | 依据 |
|---|---|---|
| 我们实测 | 43.3% | R28/R34/R40 无 swap（A） |
| **(b) 表质量/相位**（表应给 67.4%，只拿到 43.3%） | **+24.1** | ③.1 + ③.3；根因=prefill 计数主导 + 缺 blk.88（②.3） |
| **槽位比例**（我们 27.9% → 老师 46.5%，按我们自己的分布） | **+16.5** | 67.4%→83.9%；VRAM 受每专家 2.95 MB 限制（D） |
| **(a) 路由浓度**（同 46.5% 槽：我们理想 83.9% vs 老师实测 96.5%） | **+12.6** | ③.1 vs 老师 [87]（D/A） |
| 合计 | **96.5%** | 与老师实测一致（分解是线性近似，非严格可加，标 D） |

- **(c) 口径：不是原因（≈0.01 点）**：老师 96.52%（uses）≈ 96.53%（distinct 推算，①）；但它有三个容易误读的点已在 ① 纠正：**decode 驻留 11,428（46.5%）** 而非 9,041；**统计只覆盖 decode verify window**（76 窗×48 层×33 entries），不含 prompt/MTP draft/token 路径；**9,041 是 prefill 借出 2,387 槽后的瞬时值**。
- **(a) 是结构性的、抄不来**：即使我们有一张完美的表、且把槽位比例提到 46.5%，我们的路由分布也只到 83.9%（老师 96.5%）；top-22/40 层 vs top-10/48 层 + 更平的逐层分布决定了这一点。老师的 36.8%（实为 46.5%）能到 96.5%，是因为它的 routing 极度集中：**46.5% 的专家覆盖 96.5% 的 uses**，且 profile 把槽按层间倾斜分配（155–342/层），再有每 4 轮 96 个的 adaptive 换入（818 次/76 轮）。
- **(b) 是主可修项**：24.1 点丢在"表 vs 负载不匹配"，其中可指出两条具体原因（②.3）：prefill 主导的计数、以及 blk.88 缺失。我们的自适应 swap 已验证能把这条差距缩小到 62.7%（R43/R44 臂）。

### 4.2 建议（若判定 (b)：我们自己的表怎么做）

1. **采集负载换到 decode 为主**（不改码即可先做）：用 3–5 条代表性 prompt（与 agent/问答/代码实际负载同族，如 alt prompt 类型），**prompt 尽量短（≤64 token）**、`--max-new 512~1024`，单请求顺序跑；目标 **2–5 万 decode token**（每 token 40 层×22 = 880 uses ⇒ 1.8–4.4 千万 uses，与现有 5.4 千万同量级即可）。prompt 占比降到 <10%，表就不会被 prefill 路由带偏。
2. **从空表开始收**：不要用 `p_master.txt` 作为 `--expert-profile` 起跑（否则 `save_profile` 写的是 `prior_+use_`，旧 prefill 计数会混进来，`engine.cpp:2020-2047`）；给一个**不存在的新路径**作 `--expert-profile` + `--expert-profile-write`（poly `main.cpp:943-944`；缺失文件会被 `read_profile` 当作无表，`engine.cpp:182-199`）。
3. **把 blk.88 采进来**：采集时开 `--draft`（`main.cpp` draft 默认开），让 draft 前向的 `moe(L,n_layer_,1)` 把它的 uses 计入 `use_`（`engine.cpp:2260`）；或者小改：profile 写盘时把 `n_layer_`（88）单独确认非零。
4. **（建议的小改）decode-only 计数**：`use_` 现在在 `moe()`（decode）和 `moe_rows()`（prefill）都加；加一个 `--profile-decode-only` 或在 `moe_rows` 记到 `prefill_use_` 不进 profile。这是 1 个计数点的小改，能保证 (1) 的短 prompt 方案之外也干净。
5. **验证（能变红）**：新表跑 alt prompt 64 token：
   - 期望 `experts from VRAM` ≥ **60%**（理想 67%）；若 <55% ⇒ 采集负载与评测负载仍不匹配（红），换 prompt 家族重采。
   - 期望 `decode: miss/token` ≈ 880×(1−0.60) ≈ **350**（当前 496.7）；若 >450 ⇒ 表没生效（查 profile 行数/装载日志）。
   - ids 45/45 逐位不变（改表只改"谁在 GPU 算"，poly 的 GPU/CPU 专家核已按 parity 测试过；仍以 ids 门为准），decode tok/s 应 ≥ 17（当前 15.7 无 swap、16.7 最好线程臂）。
   - 长跑 256 token 复核：命中率不应随长度掉（掉=表偏 prompt 首段）。
6. **可选**：把我们 swap 的力度对齐老师（老师 `adapt_every=4`、`adapt_swaps=96`、decay 0.7、gain>1.5 才换；我们 `--expert-swaps 64`、`--swap-ratio`/`--adapt-min-gain` 语义相近），R43/R44 臂已到 60.5–62.7%，说明自适应是有效的第二层保险。
7. **别指望补到 96.5%**：即使 (b) 修满，我们同槽比例上限 83.9%、当前槽比例上限 67.4%；(a) 的 12.6 点只有换更集中路由的模型/更多 VRAM 才能补。**能拿到的现实收益：命中 43.3%→~67%，CPU 专家 uses 496.7→~290/token，按 96 µs/miss 约省 20 ms/token（≈ 75ms 的 27%）——这是下一步最值得做的单点。**
