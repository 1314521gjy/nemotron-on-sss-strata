## §1 现状判定（读码 + 只读系统/进程）

### 1.1 专家 blob 是文件映射，不是 ReadFile/pread

- Windows：`CreateFileA(GENERIC_READ, FILE_SHARE_READ)` → **`CreateFileMappingA(h, …, PAGE_READONLY, 0, 0, nullptr)`** → **`MapViewOfFile(m, FILE_MAP_READ, 0, 0, 0)`**（`include\strata\artifact\gguf_reader.hpp:397-415`）；POSIX 走 `mmap(PROT_READ, MAP_PRIVATE)`（`:423`）。
- 专家指针（`L.exp_up/exp_down/exp_gate`）就是该视图内的偏移；CPU 专家读的就是映射页。poly 引擎只 include `artifact/gguf_reader.hpp`（`src\poly\runtime.hpp:6`、`expert_parity.cpp:14`），没有自己的文件读路径；`ReadFile`/`pread` 只出现在 program 线头文件与 pinned.hpp，poly 不用。

### 1.2 `STRATA_PIN_ARENA_GIB` 的 `cudaHostRegisterReadOnly` 不是"锁 CPU 页"

- 代码：`Engine::pin_expert_arena()`（`engine.cpp:1013-1060`）按**整层**调 `cudaHostRegister((void*)L.exp_up, up_len, cudaHostRegisterReadOnly)`（`:1040-1047`），目的是 `stage()` 直接从 mapping DMA（其上注释原文 `:1009-1012`："so stage() DMAs straight from the mapping instead of gathering it on the host"）。
- `ram_before` 检查（`:1017-1026`）是"给 page cache 留 8 GiB 头寸"的预算，不是锁页。
- **算术判红**：59.06 GiB = 15.5M 个 4KB 页；团队实测整个注册过程 **2–3 ms**（`R28-A3:82`：`pinned 40 layers (59.06 GiB) … RAM 76.4 -> 76.4 GiB free; took 2 ms`）。即便 100 ns/页也需 **1.55 s** ⇒ **物理上不可能逐页锁定**；RAM free 一字节没少也说明**没有 commit**。⇒ 该调用只建立 DMA 注册（读只读映射），**与 CPU 侧驻留无关**——lead 的判断这一半是对的。

### 1.3 关键被忽略的事实：引擎**已经**在做"加载后全量预触页"（默认）

- `Engine::load()` 里：遍历所有 MoE 层，把 **gate（若有）、up、down 的整层全量区间**放进 `spans`（`engine.cpp:1648-1654`）——即 **20,480 个专家 × 3.1 MB = 63.42 GB 全部**，不是只预热驻留的 5,721 个；然后起后台线程 `mapper_ = std::thread([...]{ map_pages(spans, map_quit_); })`（`:1675-1678`）。
- `map_pages()` 本体（`engine.cpp:163-179`，**在本次交付前就已存在**）：**逐 4KB 页读 1 byte**（`for (at += 4096) seen += s.first[at]`），每 16 MiB 查一次 quit；函数上方注释原文（`:163-168`）就是动机与标定：*"The mapped file's pages come into this process's page table as they are first read, a fault every few pages, and an expert read through those faults arrives at half the speed: **21.0 against 11.0 ms a token** … So one thread reads a byte of every page of the experts, once … the **100 GiB** of a model that the file cache holds take it **4 s**. What the cache does not hold is read from the disk here, not while a token waits."*
- ⇒ **候选 1（全量预触页）在本代码里不是候选，而是现状**。区别只在于：`map_pages` 只触 1 byte/页（映射进页表/工作集），且**没有完成日志**（无法从日志证明它跑完；但按注释标定 63.4 GB ≈ 2.5 s，远小于 load 的 11.4–12.9 s + prefill 2.4 s）。

### 1.4 运行期实测（A）：工作集峰值 67.1 GB，页确实驻留

- 空闲系统侧（08:39 我在 R34 起跑前采的）：`Win32_OperatingSystem.FreePhysicalMemory=85.5 GiB`；`\Memory\Standby Cache Normal Priority Bytes = 71,612.8 MiB`、`Standby Cache Reserve = 6,070.3 MiB`、`Modified Page List = 152 MiB`；**Standby ≈ 71.6 GiB ≈ 模型文件 70.1 GB** ⇒ 无进程时文件页在 RAM 的 standby 列表（可回收、**未锁**）。
- `R34-*` 全部臂的 **ids 与 T24a 逐位相同**（329 字节，`idsIdentical=True`）⇒ 改线程数是**无损**的。

### 1.5 缺页算术（判红支点）：165 ms 的 miss 不可能是逐页 fault

- 每 miss 读 3.0966 MB ⇒ **756 个 4 KB 页**；若逐页缺页，即便 0.5 µs/页也要 **0.38 ms/miss**，而实测最好 96.3 µs、最差 193 µs ⇒ **不可能是"每 miss 逐页 fault"**；再叠上"每 token 496.7 miss"更不可能。⇒ 页几乎全在（工作集/缓存）。
- 冷/热序列也无"先慢后快"：同配置同 exe 连跑 R28-A/A2/A3 = **124.5 / 141.3 / 144.7 µs**（后跑的更慢，噪声/热，不是缺页惩罚）⇒ 无磁盘冷页信号。

### 1.6 结论 + "能判红"的判定清单

**判定：专家页 = 文件映射页，加载时被 `map_pages()` 全量触过，运行期在进程工作集内（峰值 65.5 GiB）；未做任何真锁（无 VirtualLock/SetProcessWorkingSetSizeEx/QUOTA_LIMITS，poly 全量 grep = 0 命中）；但"未锁"在当前负载下没有造成可观测的缺页/换出代价。** 判红方法：

1. **代码反证**（我跑过的 grep，可重跑）：`src\poly` + `include` 全量搜 `VirtualLock|VirtualUnlock|SetProcessWorkingSetSize|SetProcessWorkingSetSizeEx|QUOTA_LIMITS`——**poly 侧 0 命中**（只有 program 线头 `include\strata\platform\memory.hpp:5`、`kernels\ngram.hpp:157` 与 `core\expert_source.hpp:711/730` 等，poly 不 include）。若哪天 poly 出现这些 API ⇒ 本判定红。
2. **运行期采样**（无 GPU 也可，脚本已现成）：`Get-Process <engine> | % WorkingSet64` 峰值；若 ≪ 63.4 GB ⇒ 页没驻留（红）；本机实测 67.1 GB ⇒ 常驻（绿）。R34 驱动每 0.9 s 采样正是这个仪器。
3. **磁盘/缺页反证**：decode 期间同时采 `\PhysicalDisk(_Total)\Disk Read Bytes/sec`、`\Memory\Page Reads/sec`；若 ≈0 ⇒ 无磁盘读（绿）。**未做**（要有人在跑引擎时采；R34 驱动可加两行）。
4. **P8 对照臂（已实跑，最硬的判据）**：同一 `--threads 8` 下，"先整文件预读 70 GB 再跑" vs 不预读：**15.83 vs 16.25/16.66 tok/s、103.2 vs 100.1/96.3 µs** ⇒ 预触页无正收益（差异在噪声内，且方向为负）⇒ 候选 1 判红（不成立）。
5. `QueryWorkingSetEx` 逐页统计需要 P/Invoke 小工具（未做，不必要：WS 峰值已足够）。

## §2 三个候选实现（按代价排序；★ 已按 §1 实测重估收益）

### 候选 1：加载后全量预触页（★ 已是现状；增强版）

- **改哪里**：`map_pages()`（`engine.cpp:169-179`）——现状是单线程、每页 1 byte、无日志。增强 = ① 用 **`PrefetchVirtualMemory(GetCurrentProcess(), n, WIN32_MEMORY_RANGE_ENTRY[], 0)`** 按 span 分批预取（Win8+，`windows.h`/`winbase.h`；每批 ≤1024 条；~25–35 行）；② 可选多线程（复用 `workers_` 4 条）把 63.4 GB 从 2.5 s 压到 ~0.7 s；③ 打日志 `prefetched_bytes/took_ms`（自证跑完，解决"mapper 无完成日志"）。
- **代价**：启动 +0–11 s（cache 命中 ~2.5 s / 全冷 ~11 s @5.7 GB/s）；运行期 0。
- **预期**：**0–3%**（P8 臂已证明≈0；现状 `map_pages` 已触过）。
- **风险**：无正确性风险；只占 page cache、启动变慢。
- **验证跑法**：1 跑 `--max-new 64` alt prompt（R34-P8 同型），读 `decode: cpu_us/miss` 与 decode tok/s。
- **判红**：`cpu_us/miss` 相对同线程 baseline 变化 **<3%** ⇒ 无效（红）；启动 +>10 s 且无收益 ⇒ 弃。★ 按 P8 实测：**已红**。

### 候选 2：真锁页（VirtualLock / 工作集配额 / pinned 副本）

- **改哪里**：在 mapper 完成后（`engine.cpp:1675-1678` 之后）新增 ~40–60 行：
  - 路线 A（轻改）：`SetProcessWorkingSetSizeEx(GetCurrentProcess(), min≈67 GiB, max≈67 GiB, QUOTA_LIMITS_HARDWS_MIN_ENABLE)` + 对每层每 span `VirtualLock(L.exp_up, up_len)`（40 层 × 2–3 span = 80–120 次）；需要 `ERROR_WORKING_SET_QUOTA`(1453) 处理与日志。
  - 路线 B（重改，~150–300 行）：把 14,759 个非驻留专家的 blob 用 `pread`/`ReadFile` 读进 **anonymous committed 内存**（`VirtualAlloc`+逐页写）或 `cudaHostAlloc`（真 pinned），再把 `L.exp_up/exp_down` 的指针改为间接表；必须避免 file cache 同时再占 63 GB（否则 96 GB 装不下两份）。
- **代价**：A 小（30–60 行 + 一次编译）；B 大（涉 `load_layer` 指针布局、`moe()/stage()/cpu_experts` 寻址、swap 源）。
- **预期**：**0–5%**——工作集已 65.5 GB 且 availMin 17 GB 无换出压力，锁页只能"防一个没被观测到的现象"；B 更无望（数据搬到 RAM 后仍受同样线程/内核效率限制）。
- **风险**：A：Windows 需提配额；**锁 63–67 GB 物理页**⇒ 仅剩 ~15–20 GB 给 OS/其它程序（availMin 已 17 GB），可能被系统拒绝/让桌面卡顿；B：RAM 耗尽/OOM，且要双份缓存或禁 file cache。
- **验证跑法**：1 跑；打印 VirtualLock 返回值与锁后 WS；读 decode-only `cpu_us/miss`。
- **判红**：`VirtualLock` 失败（配额）或 `cpu_us/miss` 不降（>3%）⇒ 红；**不建议花这一跑**。

### 候选 3：只预热"会被 CPU 访问"的 14,759 个非驻留专家（45.7 GB）

- **改哪里**：`engine.cpp:1607 fill_expert_cache()` 之后、`:1648-1654` 构建 spans 的地方——把"整层连续区间"改成**逐专家切片**：`for il, e: if (!L.slot[e]) spans.push({L.exp_up + e*L.gu_stride, L.gu_bytes}, {L.exp_down + e*L.d_bytes, L.d_bytes})`（非门控；共 14,759×2 个 span；~30–50 行，含 span 数上限/内存 ~240 KB）；mapper 传给 `map_pages` 不变。
- **代价**：小改 + 一次编译；启动 **省 0.7–3 s**（少触 17.7 GB），page cache 省 17.7 GB。
- **预期**：**0% 提速**（只是省资源；`map_pages` 触的是进程页表，多触 17.7 GB 不缺）；真正价值 = 把 17.7 GB RAM 留给未来"更大常驻/更少 swap"或给 pin 缓冲。
- **风险**：极低；span 数从 80 变 ~29k，`map_pages` 循环与 quit 检查逻辑不变（每 16 MiB 一查仍成立）。
- **验证跑法**：1 跑，加日志 `prefetched_bytes` 应 ≈ **45.7 GB**（不是 63.4 GB）；decode 不变。
- **判红**：若 `prefetched_bytes` 仍是 63.4 GB ⇒ 切片没生效（红）；若 decode 变差 ⇒ 有其它副作用（查 hot 页是否漏触）。

## §3 哪一条最可能把 21–23 GB/s 抬到 40–60 GB/s？

**答案：三条都不是；数据表明卡点根本不在驻留。** 理由链：

1. 驻留已达成（§1.4 WS 峰值 65.5 GiB、§1.3 map_pages 全量触、§1.5 缺页算术不成立、P8 臂 0 收益）。
2. 现在的 ~100 µs/miss（最好 96.3）折合 **1.538 GB/token ÷ 47.8 ms = 32.2 GB/s**（T8b），即**目前已是 32 GB/s，不是 21–23**；21–23 是 T24（24 线程）的 bad case。
3. 8→12→16 线程 `cpu_us/miss` = 100.1 / 99.6 / 99.5 **完全平台化** ⇒ 再加核/加带宽无效，瓶颈是**每线程的有效算力/取数效率**（≈11.0 MFLOP + 3.0966 MB per miss；96–100 µs ⇒ **110–114 GFLOPS**，8P 核 AVX2 Q4_K 的现实值）。
4. 要到 40 GB/s ⇒ CPU wall 38.5 ms ⇒ **~142 GFLOPS**（+25%）；60 GB/s ⇒ 25.6 ms ⇒ **~214 GFLOPS**（+90%）——只能靠 **CPU 专家内核变快**（更好的 Q4_K dequant/点积、软件预取、每 miss 更大 MLP）或**把一部分专家移到 GPU/PCIe**（团队 R26 长 prompt 臂 `--pcie-frac 0.4`：20.99→24.44 tok/s；R27 alt-prompt 臂 12.29→12.96），而不是"驻留/锁页"。
5. 若一定要在三候选里押一个：**押候选 3**（成本最低、无负面、为后续腾 RAM），**不押 1（已实测无效）、不押 2（上限 5% 且可能让系统不稳）**。

**⇒ 报告 lead：线 C 的下一步不是"真驻留"，而是把 R34 的 `--threads 8–12`（+23–34%，ids 无损）先落进交付配置，再做 `cpu_experts` 分段计时/内核提速；驻留方向可以关掉。**
