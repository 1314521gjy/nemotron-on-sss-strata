## §0 一句话结论

> ★★ **超级杠杆是【搬运机制】，不是【每 token 专家字节】。**
> **去重之后，两边一整个 prefill 搬运的专家字节几乎相等（我们 34.9–40.5 GB vs 它 40.8 GB）**；
> 真正的差是：**它按 16K–32K token 的 prefill-chunk 只搬一遍（2.49 MB/token），我们按 1024-token 调用每次都重搬一遍（16K prompt ⇒ ~34 MB/token，14×）**；
> 叠加**它有自己的流 + 双缓冲 + 全层一次批量拷贝（~34 GB/s 有效）**，我们 8.9 GB/s（同机可达 22）。

## §2 账 1：每 token 专家字节（**不是杠杆**）

**① 不设缓存、不做去重时（"top-k × 专家大小"）**
- 我们：40 层 × 22 × 3.0966 MB = **2,725 MB/token**
- 它：48 层 × 10 × 2.112 MB = **1,014 MB/token**（IQ3_S）/ 1,327 MB（NVFP4）
- ⇒ 比值 **2.7×** —— **这是"每 token 都重读一遍专家"的假想值，不是任何引擎的真实行为。**

**② 真实机制 = chunk 内去重（union）**
一个 chunk 内，同一专家被多 token 选中只搬一次 ⇒ 每 token 的搬运量塌缩成"该层非驻留专家的并集 / chunk 的 token 数"。

| | 我们的 700-token 调用 | 它的 512-token chunk |
|---|---|---|
| 非驻留专家 | 13,092 × 3.0966 MB = **40.5 GB**（实测 **34.87 GB**，86% 被用到） | 16,768 × 2.112–2.765 MB = **35.4–46.4 GB**（设计件口径 **40.8 GB**，60% 非驻留） |
| 每 token | **49.8 MB**（实测） | **79.7 MB**（40.8 GB / 512） |

⇒ ★ **同样一个短 prefill，我们每 token 搬得比它【少】1.6×**（49.8 vs 79.7）。
⇒ **top-22 vs top-10 的 2.7× 在去重后完全消失**（union 比值只有 40.5/35.4 = **1.14×**）。
**⇒ 问题 3 的答案：top-k × 专家大小不是杠杆。**

## §3 账 2：★ 真正的差 = **chunk 摊薄**（超级杠杆）

| chunk | 它每 chunk 搬运 | 它每 token | 我们（同长度 prompt）每 token |
|---|---|---|---|
| 512 | 40.8 GB（一次） | **79.7 MB** | 49.8 MB（赢） |
| 8K | **40.8 GB（同一批专家，仍只搬一遍）** | **5.0 MB** | ~34 MB（16 次调用 × 34.9 GB / 8192） |
| 16K | **40.8 GB** | **2.49 MB** | **~34 MB**（16 次 × 34.9 GB / 16384） |
| **比值** | —— | —— | **13.7×**（16K） |

**为什么它 8K 与 16K 的搬运量相同（设计件 `:1963-1964`）**：设计件自己的表就写着 **8K 与 16K 都是 40.8 GB** —— 因为一个 chunk 内每层的非驻留专家并集**早已饱和**（512 个专家、top-10，几百 token 就覆盖全部）。**chunk 越大，同一批字节摊到越多 token 上。**
**为什么我们会随调用数线性增长**：`moe_rows()` 的 staging 是**每个调用**做一次（`--prompt-batch` 1024 ⇒ 一个 16K prompt = 16 次调用），`staged_` 的复用只覆盖"上一次的最后一条 round"（`:2494-2497`），跨调用**不保持整层专家**。
⇒ ★★ **同一份 34.9 GB 的"层专家并集"，它按 chunk 搬 1 次；我们按 1024-token 调用搬 16 次。这 14× 就是超级杠杆。**

## §5 账 4：机制差异（它凭什么）

| 机制 | 它 | 我们 | 出处 |
|---|---|---|---|
| **搬运单位** | **整层、一次 `cudaMemcpyBatchAsync`**（每层一条拷贝记录） | **每层 17 轮 × 2 次 `cudaMemcpyAsync`**（sm=48；每轮 16 专家） | 设计件 `:1949`；本机 `:2450` |
| **缓冲** | **双缓冲 staging**，layer l 计算时 DMA layer l+1 的全部非驻留专家 | 单缓冲 `stage_`；只有"下一层早拷贝"走第二条流 | 设计件 `:1950`；本机 `:1673` |

## §6 ⇒ 一句话 + 杠杆排序

**超级杠杆 = "每 prefill-chunk 只搬一遍非驻留专家 + 与计算重叠"，不是每 token 专家字节。**

1. **★★★ 第一杠杆（10× 量级，长 prompt）**：把 staging 从**"每 1024-token 调用"**改成**"每 prefill-chunk 一次"**（它叫 streamed walk：整层 staging bank + 双缓冲 + 层间预取）。16K prompt 下每 token 搬运 **34 → 2.5 MB**。前提：`stage_` 要能放下"一层所有非驻留专家"（本靶 ~271 × 2.95 MB ≈ 0.8 GB ⇒ `--stage-mib ≥ 1024`）。
2. **★★ 第二杠杆（3×，短 prompt 也生效）**：轮内拷贝从 8.9 → **22 GB/s**（同机已证可达；见 `方案-轮内拷贝第二流-20261017.md` 的 A/B）并**与计算重叠**。**短 prompt 的同机上限 ≈ 34.9 GB / 22 GB/s = 1.58 s ⇒ ~440 tok/s**（现在是 145.6）。
3. **★ 第三（1.47×）**：专家格式（IQ3_S 2.11 MB vs 我们的 Q4_K_M 3.10 MB）—— **换格式会动数值契约，优先级最低**。

**★ 必须同时记住的上限**：**我们每 token 的 compute 是 673 µs**（`ln_correct`：470.8 ms / 700 token）。即使搬运完全摊薄（2.5 MB/token @22 GB/s = 0.11 ms/token），**长 prompt 也会被 compute 卡在 ~1,300–1,500 tok/s**。所以"10× 量级"要分两步：先拿搬运机制（到 ~1.3K），再动 compute。

## §7 未验 / 口径风险

1. **【口径】** 3.8-Flash 的 3,400–3,700 tok/s 是 **4K–64K chunk、Gen5** 的数；**512 token 的实测是 431 tok/s**。拿 145.6 对 2,300/3,400 会高估差距；同 token 数（512–700）对拍才是 3× 量级。
2. **【未核】** 它的每专家字节：几何算 **2.112 MB**（IQ3_S），设计件写 **2.77 MB**（NVFP4），而"7808 槽 / 22.79 GiB"反推是 **3.13 MB/槽**。三者不一致 ⇒ 本账用区间 **[2.11, 3.13] MB**，结论不变（union 比值 1.1–1.6×）。
3. **【未核】** 我们的 16K-prompt 每 token 34 MB 是"每调用搬同一并集"的保守估计（未跑）；实际可能因命中率随 token 数上升而略低。
4. **【未核】** 3.8-Flash 的 431/3,400 是否同一台机器（设计件的 5090 Gen5 假设）；我们机器是 4080S Gen4。
5. 本件**只读、零 GPU、未改码、未碰 `E:\strata`**。
