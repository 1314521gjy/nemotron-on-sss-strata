# A. `mamba2_scan`（0.845–0.872 s = compute 28.7%，最大单点）

## A0. ncu 出处已复核（不是"未验"）
- **盘上有**：`E:\视频\_flashnext\experiments\20261015-nemotron-on-strata\P3-20261016\计划-分环节定位杠杆-20261017.md:73` 记 ncu 读数：
  > Duration 38.62 ms · Grid `(128,1,1)×(64,1,1)` ⇒ **0.08 wave/SM** · **Achieved Occupancy 6.87%**（理论 79.17%）· **1 warp/调度器**（No-Eligible **98.67%**，每 75.4 cycle 发一条）· DRAM 0.84% · **Compute 2.98%** · IPC 0.04 · **最大 stall = 长记分板（L1TEX/global）60.6 cyc = 80.6%** · reg 47 · smem 4.11 KB · L2 命中 98.91% · **非合并 load 4.1/32 B、store 4.0/32 B（72% sector 未命中 L1TEX）**。
- **口径注意（重要）**：ncu 那跑 Duration **38.62 ms/层**，而 R13 nsys 是 **21.79 ms/层**（见 A1）⇒ ncu 是**旧/非 SMEM 版本**的读数（那时 state 在全局显存、每 token 走 strided load ⇒ 长记分板 80.6% 正是它）。**occupancy/stall 结论可用，Duration 不可当现配置读数。**
- ncu 的"理论 79.17%"是按 **static smem 4.11 KB** 算的；**漏算了 33 KiB dynamic smem**（见 A2）⇒ 理论的真实上限不是 79.17%。

## A2. 理论 occupancy 手算（C 级硬件规格：AD103/4080S = 80 SM、1,536 线程/SM、48 warp/SM、64K reg/SM、100 KiB smem/SM）
- 每 block：**2 个 warp**（64 线程）；regs 40×64 = 2,560；smem = 4,112 + 33,024 = **37,136 B**。
- 逐项上限：regs 65,536/2,560 = 25 blocks；warp 48/2 = 24；threads 1,536/64 = 24；**smem 102,400/37,136 = 2 blocks（瓶颈）**。
- ⇒ **每 SM 最多 2 blocks = 4 warps = 8.33% 占用率上限**。
- 但实际 grid 只有 **128 blocks / 80 SM = 1.6 blocks/SM** ⇒ **≈3.2 warps/SM = 6.7%** ——与 ncu 的 **6.87%** 吻合（差 0.2 pt 来自尾块/调度）⇒ **6.87% 的算术原因闭环**。

## A3. 6.87% 的根因（按权重，A）
1. **暴露的并行度只有 8,192 线程**（`n_head=128 × head_dim=64`），而 GPU 可跑 ~163,840 线程 ⇒ 只有 **5%**；grid 128 blocks 是硬伤（0.08 wave/SM）。**这是主因。**
2. **每线程沿 t 串行 6,791 步**（`kernels.cu:2572` 的 `for (t…)`），每步还要等 128 个状态更新后才算 `sumf`（`:2585-2597`）⇒ 串行依赖链长。
3. **warp 数不足以藏延迟**：ncu `No-Eligible 98.67%`、`1 warp/scheduler`、长记分板占 80.6% ⇒ 延迟受限（非带宽：DRAM 0.84%、Compute 2.98%、L2 命中 98.9%）。
4. **smem 33 KiB/块把上限压到 8.33%**（不是当前主因，但会挡住"加 grid"后的收益——加 blocks 后仍是 2 blocks/SM）。
5. 非 SMEM 版本另加"state 非合并 load 4.1/32 B"（`:2592-2596` 逐线程 `sp[st]`）⇒ ncu 的长记分板来源；现配置 SMEM 已去掉每 token 的全局 state 读写。

## A4. 三个改法（预计提速 / 工作量 / 数值风险）
| # | 改法 | 预计 | 工作量 | 数值风险 |
|---|---|---|---|---|
| **1（推荐先做）** | **d_state 切给 warp 协作 + state 入寄存器**：block 256 线程=8 warp，一个 warp 管一个 `(head,i1)`，32 lane 分摊 128 states（4 个/lane，寄存器）；每 token 各 lane 更新自己的 4 个 state（**无跨 lane 依赖**），`__syncwarp` 后**按 st 顺序**归约累加写 y | **2–4×**：21.8 ms → 5–10 ms/层 ⇒ 0.87 → **0.22–0.4 s**（墙 +5~8%，D）；grid 可升到 **1,024 blocks ×256 线程**（占用率 ~25–50%） | 中（~100–130 行重写 kernel + parity），无新 scratch | **可做到逐位**（state 递推顺序不变；y 累加保持 st 序 ⇒ 与现实现同序）⇒ 对 Δp=0 友好；若放弃有序归约则 drift ~1e-7 |
| **2** | **token 分块两遍 scan**：T 分 C 块（1,024 tok/块），pass1 各块零初值算块末状态（并行）、块间串行合成（C=7 步）、pass2 真初值重算 | 与 #1 叠加再 **1.5–2.5×**；单独也 2–3×（D）；总 0.87 → **0.15–0.25 s**（墙 +8~12%，D） | 高（~200–250 行 + 块边界 scratch ≈ 29 MB + parity） | **非逐位**（递推重结合，drift ~1e-7）；需容差门（ids 硬 + 逐层 rel ≤1e-5，见 `正确性判据-mamba2scan改动-20261017.md`） |
| **3** | 只把 state 从 smem 挪到寄存器（腾掉 33 KiB） | **单做≈0**（grid 仍 128 blocks ⇒ 6.9% 不变）；**只是 #1/#2 的前提** | 小 | 无 |
- **明确不做**：`__launch_bounds__`/unroll 调参（grid 限制，没用）；照搬上游 `gdn_rec_chunked`（**Mamba2 ≠ GDN**：Mamba2 是 `s_t=a_t s_{t-1}+b_t` 的**逐通道标量递推**，GDN 是 WY 表示/分块矩阵形式；**代码不可搬，只可搬"分块并行 + 对拍"方法**——与 `情报-E-prefill计算结构对拍-20261018.md:164` 一致）。
- **对拍台**：`正确性判据-mamba2scan改动-20261017.md` 已写好两套判据（①state→shared "不许变" 可做 kernel memcmp · ②切维分块 "允许变但有界"），直接复用。

# B. FP16/BF16 prompt 路径（compute 侧"唯一真候选"的复核结论：**不建议移植**）

## B1. 我们现在走什么（A）
- **dense，量化的**：`engine.cpp:2031-2034` → `Mmq::quantize` + `mmq_->mul`（**int8 MMQ**，llama.cpp ggml-cuda 的 `mul_mat_q`；nsys 里 `mul_mat_q<(ggml_type)12>` 等）。
- **dense，F32/BF16 的**：`engine.cpp:2019-2028` → **`gemm_f32`（cuBLAS SGEMM，FP32）**，实现 `src/poly/kernels.cu:2082-2102`（`cublasSgemm` :2094 / `cublasSgemmStridedBatched` :2098；小形状走自写 `gemm_small_kernel` :115）。
- **MoE（prompt，流式专家）**：`engine.cpp:2687/2696`（cached 路径）、`:2771/2780`（tile 路径）、`:2858/2863/:2873/:2879`（staged 路径）→ 全是 **int8 MMQ**（`mq_`/`mq2_`/`mq_tile_` 为 q8_1 激活）。
- **链接面**：`strata-poly` 链 `strata_poly_mmq`（`CMakeLists.txt:1803-1805, 1829`）= `src/poly/mmq.cu` + `src/prefill/ggml_cuda_host.cu` + ggml `quantize.cu` + `mmq-instance-*.cu`；**没有 `gemm.cu`**（`gemm.cu` 属 `strata_prefill`，`CMakeLists.txt:612`，我们没链）。

## B2. 上游 FP16 路径的数据流（A，`UP/` 只读）
- `UP/docs/QUANTS.md:37`：Q4_K 的 **CUDA prompt 默认 = "FP16 path"**；MMQ 要 `STRATA_MMQ_KQ=1` 才开。
- `UP/docs/QUANTS.md:43-44`："FP16 path = prompt 的专家**反量化成 FP16 再用 BLAS 乘**；**每个专家读成 ~10 MB FP16**"。
- `UP/include/strata/prefill/gemm.hpp:1-6`：权重在 device 上是 BF16 / 或**从 GGUF block 反量化进可复用 scratch（`dequant_bf16`）**；激活取 BF16；**cuBLAS tensor-core GEMM**。
- **DQ=2 环**：`UP/src/prefill/prefill.cpp:315` `constexpr int DQ = 2; // dequantized-expert ring (FP16 gate/up + down)`；`:1307` 每份 `dq_gu[i] = 1280×2560 uint16`（=6.55 MB）、`dq_d[i] = 2560×640 uint16`（=3.28 MB），**i<2** ⇒ 环 ≈ **19.7 MB device**。
- ⇒ **关键事实：上游 DMA 在飞的仍是 Q4_K 原字节**；FP16 环是**反量化 scratch（小、常驻）**，不是把 FP16 搬过 PCIe。

## B3. 若移植到我们 poly：最小改动面（file:line 级）
1. **Q4_K→FP16 反量化 kernel**：我们链接面里**没有** ggml 的 `dequantize.cu`（`CMakeLists.txt:1803-1805` 只含 `quantize.cu`）⇒ 需 ①把 ggml `dequantize.cu`（或 `dequantize_row_q4_K` 的 CUDA 版）加进 `strata_poly_mmq`，或 ②自写 Q4_K 反量化 kernel（Q4_K super-block 结构，~60–80 行，放 `src/poly/kernels.cu`）。**这是最大的一件新代码。**
2. **FP16 环**：按我们几何（up=1024×2688=2.75M w、down=2688×1024=2.75M w；Q4_K 半帧 1.548 MB ⇒ 反量化 FP16 = 5.5 MB/半帧，整专家 **11 MB**，与上游 "~10 MB" 一致）；DQ=2 环 = **2×5.5 + 2×5.5 = 22 MB device**，在 `alloc()` 里加（`engine.cpp:1670` 一带）+ reserve 预算 +2.2 MB 级别。
3. **FP16 GEMM 入口**：新增 `mmq_f16(...)`（cuBLAS **HGEMM**，`cublasGemmStridedBatchedEx` with `CUDA_R_16F`/`CUBLAS_COMPUTE_32F`；我们代码里已有同 API 的现成调用可抄：`kernels.cu:2059` 的 warm-up）~50–80 行；把 `engine.cpp:2858/2863/2873/2879`（staged MoE）与 `:2687/2696/2771/2780`（cached/tile）换成"反量化 → mmq_f16"。
4. **旗标**：`STRATA_PROMPT_F16`（默认 0），默认路径保持逐字节不变（AGENTS.md 的 opt-in 规矩）。
5. **数值门**：ids 45/45 硬门 + **pos0 probs 容差**（上游自己写"changes the prompt's rounding"，`CMakeLists.txt:78` ⇒ **不可能逐位 0**）+ `poly_expert_parity` 对 CPU 参考；另加"端到端变快但 kernel 份额降"的读数链检查（`正确性判据-mamba2scan改动-20261017.md` 的总口径）。
6. **是否要 ncu/对照跑**：要。**至少 2 跑 A/B（同窗）+ 一起 ncu**，否则无法判"FP16 GEMM 是否真比 int8 MMQ 快"。

## B4. 收益判断（D，带算术）
- **DMA 字节不变**（Q4_K 在飞；见 B2）⇒ 45.1 GB 不变，**不额外吃 PCIe**。
- 但额外两条 VRAM 流量：反量化写 FP16 环 + FP16 GEMM 读环；量级 = 每次专家使用 11 MB 写 + 11 MB 读（**VRAM，不是 PCIe**），按 ~2 TB/s 约 (14,566 次×22 MB)/2e12 ≈ **160 ms**（D）。
- **算力上限**：AD103 的 FP16 稠密 TC ≈ **165 TFLOPS**（C，lead 口径），**int8 TC ≈ 2× = 330 TOPS**（C）⇒ FP16 路径的**峰值只有 int8 的一半**；我们 MMQ 的 MoE 有效吞吐按 FLOPs 反推 ≈ **65.7 TFLOP MoE / 0.30–0.36 s（MMQ MoE 份额，B5）≈ 180–220 TFLOPS 等效**（D）⇒ 已接近 int8 峰值的一半以上，**FP16 要反超需要效率翻倍**，没有理由。
- ⇒ **收益区间：−10% ~ −30%（更慢）**；不值得作为 compute 杠杆。**若 lead 仍想要 GEMM 侧杠杆**，性价比更高的是"dense F32/BF16 走已存在的 cuBLAS 混合精度"（`gemm_f32` 现在纯 SGEMM FP32，`:2094/2098`），而不是专家流。

## B5. 顺带：`mul_mat_q type12` 的 0.912 s（R13 trace；R10 报 0.844 s）里 dense/MoE 各多少（D，按 grid 形状）
- **MoE（专家组）**：`grid=(1728,1)` 116 次 0.206 s + `(2268,1)` 47 次 0.083 s + `(2940/3024/3780)` 43 次 ~0.015 s ≈ **0.30 s**（+ type14 的 0.048 s 几乎全是 MoE ⇒ 合计 **~0.35 s**）。
- **dense/shared**：`grid=(7830,1)` **40 次 0.277 s**（一 MOE 层一次，判为共享专家/大 dense 投影）+ `grid=(80,1)` 432 次 0.012 s + `(432,1)` 40 次 0.016 s ≈ **0.31 s**。
- **其余** ~0.28 s 分散在多种 grid（本件未逐 launch 对到 call site）⇒ **标"未查到精确归因"**；要精确须把 kernel correlationId 对到 `cudaLaunchKernel` 的调用栈/线程（nsys 未采 callchain）。
- ⇒ **type12 里 MoE ≈ 0.35 s、dense/shared ≈ 0.31 s、未归因 ≈ 0.28 s**（D，±30%）。

# 推荐顺序（给 lead 定）
1. **先做 A 的改法 #1**（d_state 切 warp + state 入寄存器，**目标逐位 0**）：收益 0.6–0.65 s（墙 +5~8%），工作量中，数值风险可控（可做逐位），且**有现成两套判据与对拍台**（`正确性判据-mamba2scan改动-20261017.md`）。
2. A 的改法 #2 视 #1 效果再定（非逐位，需容差门）。
3. **B 不做**（FP16 专家路径预期 −10~−30%）；若要做 GEMM 方向，先给 MMQ 做一次 ncu 拿效率，再谈 dense 混合精度。

# 未验 / 未查到
1. ncu 读数出处已查到（`计划-分环节定位杠杆-20261017.md:73`），但它是**旧/非 SMEM 版本**（38.62 ms 对当前 21.79 ms）；**现配置的 ncu stall 分解未测**。

5. A 的提速是 D 级外推，**未实跑**；改法 #1 的"可逐位"依赖归约保序实现，**未验**。
