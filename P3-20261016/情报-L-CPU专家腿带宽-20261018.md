- **状态**：**达成**（① 访存模式 ② 内存类型判定 ③ 老师对照 ④ ≤3 条可执行改动 + 最可能一条）。

## §0 一句话结论

**21.4 GB/s 大概率不是"DDR5 只用到 1/3"的纯带宽读数，而是三件事叠加**：① **口径**——`144.7 µs/miss` 若取自 `cpu_us/miss`（= CPU 腿**墙钟**，`main.cpp:786`），它把该层 GPU launch/交接的时间也算进去了（代码里另有 `cpu_busy = wall − launch_ms` 才是纯 CPU，`engine.cpp:2448-2449`、`main.cpp:792`）；② **并发被 SMT/混合核拆掉**（本机 **i7-13790F：16 物理核/24 逻辑核**，`--threads 24` ⇒ 23 worker + 调用线程，默认 `--host-core off` 时**一个线程都不钉**，`threads.hpp:184,198,232`，24 线程压 16 核、barrier 等最慢的 E 核）；③ **访存/计算形态碎**（每行一次间接 `vec_dot`、无 prefetch、无多行 unroll、AVX2-only，任务只有 24–37 KB）。内存类型是"GGUF 文件映射 + cudaHostRegister"，但 **pin 只用 3 ms、RAM free 不变**（59 GiB/1550 万页不可能 3 ms 触完）⇒ 物理页未真正锁定，读的是 **page cache 文件页**——这是第二种可能解释（未验）。

## §1 ① 访存模式（代码事实，A 级：本机源码）

| 项 | 读到的实际 | `file:line` |
|---|---|---|
| 一个漏专家的数据布局 | **3 段各自连续**的 blob：gate 1,548,288 B、up 1,548,288 B、down 1,548,288 B（行宽：`gu_row = row_size(gu_type, n_embd=1024) = 576 B`；`d_row = row_size(d_type, n_ff=2688) = 1512 B`） | `cpu_experts.cpp:178-181`；行宽公式 `ggml_row_size`；专家帧字节 `pair_D_pb6912.log:3-82`（756.0 MiB/512 专家） |
| 线程切分 | **按行块切、跨全部专家并行**（不是"一专家一线程"）：gate/up 每任务 `kRowsPerTask=32` 行 × 2 矩阵 ⇒ **36.9 KB/任务**；down 每任务 `kRowsPerDownTask=16` 行 ⇒ **24 KB/任务**；任务数 = `n_runs × ceil(n_ff/32)`（decode 每层 ~5.6 个漏专家 ⇒ ~470 个任务） | `cpu_experts.cpp:22-23, 216-224, 254-259` |
| 内层循环 | 每任务：`for r in 32 rows { for i in uses { vec_dot(gate_row); vec_dot(up_row); } }` —— **每行一次间接函数指针调用**（`tg->vec_dot`），行与行之间无 unroll | `:225-249`（gate/up）、`:260-264`（down） |
| prefetch / NT / AVX | **无 `_mm_prefetch`、无 non-temporal load、无 AVX-512**（本机 CPU 无 AVX-512，老师日志 `dec-pool2.txt:1` 同结论）、**无多行 unroll**；用的是 ggml-cpu 的通用 `vec_dot`（AVX2 路径） | 全文 grep：`_mm_prefetch` 0 命中；`cpu_experts.cpp:232-233, 264` |
| 每线程一次读多少 | 每任务 36.9 KB（gate+up）或 24 KB（down），随后换下一个 (expert, row-block) —— **远小于 L2/L3，不会造成"重复搬运"，但流太短**，硬件预取器与 MLP 都拉不满 | 同上 |
| 内存复用 | 同一 expert 的多 use（spec 窗口内多 token）**按行共用一次读取**（`for i in [i0,i1)` 在行循环内层）⇒ 无按 use 重复读权重 | `:228-233` |

**⇒ 访存模式一句话**：每个漏专家是 **3 段连续 blob**，按 **行块（32/16 行）跨专家并行**；不是整专家一线程——并发性够，但**任务碎 + 每行一次间接调用 + 无 prefetch/unroll**，单线程 MLP 低。

## §2 ② 专家数据在宿主端到底是什么内存（读码 + 日志，A 级）

| 问题 | 答案 | 证据 |
|---|---|---|
| 是 VirtualAlloc+VirtualLock 吗 | **不是** | `pin_expert_arena()` 全程只有 `cudaHostRegister((void*)p, n, cudaHostRegisterReadOnly)`，无 VirtualAlloc/VirtualLock：`engine.cpp:1013-1051` |
| 是 malloc 后触页吗 | **不是** | 专家源指针来自 **GGUF 文件映射**：`GgufFile` "mmap the file and parse header… read in place"（`include/strata/artifact/gguf_reader.hpp:6,10,359`），Windows 用 `MapViewOfFile`（`:408`），Linux `mmap(PROT_READ, MAP_PRIVATE)`（`:423`）；`engine.hpp:3` "The engine reads the GGUF in place" |
| 是文件映射且没锁页吗 | **是文件映射；锁页"注册成功"但可疑** | `pin up layer 1: 756.0 MB -> no error (0)`（`pair_D_pb6912.log:3-82`）⇒ 注册返回成功；**但** `pinned 40 layers (59.06 GiB) of 88, 0 refused; RAM 74.8 -> 74.8 GiB free; took 3 ms`（`pair_D_pb6912.log:83`）⇒ **3 ms 不可能把 1550 万页触进物理内存、RAM free 一字节没少** ⇒ 注册当下**没有**把 59 GiB 锁成常驻物理页 |
| 那 CPU 读的是什么 | **page cache 的文件页**；引擎有专门的 `map_pages()` 线程"每页读一次"预热（注释明说"so a prompt does not fault"）：`engine.cpp:1675-1677`（mapper_ 线程起于 load，pin 在 `:1765`）、`engine.hpp:503` 注释 | 同左 |
| 有没有互相矛盾的观察 | 有：prefill 的 **direct DMA 达 23.2 GB/s**（队长 nsys）说明这些页对 DMA 可用（pin 生效）⇒ 最可能是"注册了 device 映射、但页在注册时未全部常驻，按需 pin/页缓存命中"的混合态。**本件不下定论，列判别法**（§5-U2） | —— |

**⇒ 内存类型一句话**：**GGUF 文件映射（mmap/MapViewOfFile，in place）+ `cudaHostRegister(ReadOnly)` 注册**；不是 VirtualAlloc+VirtualLock、也不是 malloc。**pin 的 3 ms 与 RAM free 不变说明 59 GiB 页并未在注册时全部常驻 ⇒ CPU 读的是 page cache 文件页**——若页被回收/预读不足，21.4 GB/s 就有了"第二种解释"。

## §3 ③ 对照老师：只抄"读法"（C 级：老师源码/日志）

| 维度 | 老师怎么做 | 我们怎么做 | 差异是否值得抄 |
|---|---|---|---|
| **worker 的核** | **只钉物理核**：`physical_cores(bool skip_first)` 用 `GetLogicalProcessorInformationEx(RelationProcessorCore)`，每个物理核取第一个逻辑处理器；注释原文："hardware_concurrency() returns LOGICAL… pinning one worker to each of the first N would put two workers on each physical core and **halve the bandwidth the expert kernel is bound by**"；`skip_first` 把 0 号核留给 host 自旋 | **默认不钉任何线程**（`--host-core off` ⇒ `plan_threads` 不建 workers 列表，`threads.hpp:184,/198,/231-234`；`pin_worker_thread` 拿到 -1 ⇒ no-op）；`--threads 24` ⇒ 23 worker 压 16 物理核（8 P 有 HT + 8 E） | **★ 最该抄** |
| **任务切分** | 每个 phase 的**全局行区间连续切给每个 worker**（`mrows_/mtasks_`：`g0 = mrows_*i/mtasks_`，一个区间**可跨专家**），每线程一条长连续流 | 每任务 = (专家, 32 行块)，跨专家但**每块只 37 KB**，线程在专家间跳 | ★ 该抄（长流 vs 碎块） |
| **内核** | 自写 AVX2 整行内核：`s2_expert_gu_rows` / `_down_rows`（及 `_multi`），按行区间整块算：`src/kernels/cpu/expert.cpp:484,494,522,536`；类型特化 AVX2：`iq_avx2.cpp`(23 KB)、`q2_avx2.cpp` | ggml-cpu 通用 `vec_dot` 函数指针，**每行一次间接调用**（`:232-233,264`） | ★ 可抄结构（不必抄代码） |
| **相位计时** | pool 把 wait_park / drain / re-park 三段分开计时（`pool.hpp:141-151`），并印出 `pool phases wait-park … drain … re-park`（`dec-pool2.txt:84`） | 只有 `cpu_ms` 总和（`engine.cpp:2448-2449`），无相位拆分 | ★ 该抄（仪器） |
| **内存类型** | **同样是 mmap+pin**：`expert arena: cudaHostRegister PORTABLE ok; large pages refused… using 4 KB pages`（`dec-pool2.txt:28-30`），"loaded 46.84 GiB" | 同样 GGUF 映射+pin | **不抄**（不是差异所在） |
| **线程数** | 老师那次 decode 只用 **3 个线程**（`dec-pool2.txt:31-32`：tasks/phase 9、participating threads 3、2 pool workers + host）就拿到 1.14 routed 漏专家/层、133 µs/漏专家（≈2.03 MB/133 µs ≈ 15 GB/s **单线程量级**） | 我们 24 线程、21.4 GB/s 聚合——**按每线程算我们反而更慢**，说明"线程多"没转化成带宽 | —— |

**⇒ 老师的快不是"CPU 池强"**：它是 **物理核钉死 + 每 phase 连续行区间 + 自写整行 AVX2 内核 + 只 3 线程**；它的 CPU 池在 decode 里只处理 ~1.14 个漏专家/层。我们能抄的是**读法**（核钉/连续流/整行内核），不是它的池实现。

## §4 ④ ≤3 条可执行改动（每条：改哪 → 预计 → 风险 → 怎么验/判红）

### 改动 1（零改码，先做）：**先把口径分开，别把 launch 当带宽**
- **改哪**：不改；**读**新打印的两行（已经在树里）：`decode: cpu_us/miss`（= wall，`main.cpp:786`）与 `decode: cpu_busy_us/miss`（纯 CPU，`main.cpp:792`）；对照 `engine.cpp:2448-2449`（`cpu_busy = wall − launch_ms`）。
- **预计**：若 `busy/wall < 0.7` ⇒ **21.4 GB/s 是假口径**，71.9 ms/token 里有一大块是 **GPU launch/交接**在 CPU 腿里的投影（`launch` 作为 gate 相位的 task 0 跑在 worker 上，相位墙钟等它）；改法应是把 launch 提前/移出（重叠），而不是访存优化。若 `busy ≈ wall` ⇒ 走改动 2/3。
- **风险**：无（只读计数）。
- **怎么验/判红**：读那两行；**判红**：若 3 跑里 `cpu_busy_us/miss` 与 `cpu_us/miss` 相差 <10%，则本条"口径"分支作废，改向 2/3。

### 改动 2（最可能的一条）：**worker 只钉物理核 + 按物理核数定线程**（~40 行，改 `threads.hpp` 默认策略 + `cpu_experts.cpp` 不变）
- **改哪**：`src/poly/threads.hpp:231-234`（workers 列表现在取**所有逻辑 CPU**）→ 改为 `physical_cores()` 每核取**第一个逻辑处理器**（`threads.hpp:64-95` 已有该表）；worker 数上限 = 物理核数 − host 核；`--host-core off`（默认）也启用该策略（或加 `--pool-physical`，默认开、`off` 回旧）。`engine.cpp:1646`（threads=usable_cpus()=hardware_concurrency）→ 默认取物理核数。
- **预计（D 级推算）**：本机 16 物理核、单核 AVX2 流式读 ~15–25 GB/s；若 16 核都进有效并发，聚合理论 60–90 GB/s（DDR5 双通道实收 ~60–70）⇒ CPU 腿 71.9 ms **→ ~30–40 ms/token**，decode 13.36 → **~22–28 tok/s**；若 `busy` 证明大半是 launch，则本条只拿其中一部分。
- **风险**：中低——**只挪线程、不改算术**（`threads.hpp:18-20` 自己写明"Pinning changes where a thread runs, never what it computes"）；唯一风险是核数**变少**（24→16）后若某相任务数 <16 会略欠并行（gate 相任务数 ~470，足够）。
- **怎么验/判红**：跑同一 decode；读 `cpu_busy_us/miss`、`cpu_us/miss`、`decode tok/s`、ids/`--top-probs`；**判红**：ids 不是逐位同（不应发生）；或 `cpu_busy_us/miss` 不降而 tok/s 反降 ⇒ 退回 `--host-core off`。

### 改动 3：**把"碎行块"改成"连续长流 + 多行 unroll + prefetch"**（~60–100 行，改 `cpu_experts.cpp`）
- **改哪**：`cpu_experts.cpp:216-224`（gate/up 任务=当前 (expert, 32 行) 块）→ 改为老师式的**全局行区间**（每个 worker 一条 `[mrows*i/n, mrows*(i+1)/n)` 连续区间，跨专家）；`cpu_experts.cpp:22-23` 粒度 32→64/96 行、down 16→32 行；内层 `:225-249` 每 4 行 unroll（4 个独立 `vec_dot` 同时进流水）+ `_mm_prefetch(gate/up/down + 下一行, _MM_HINT_T0)`；down `:260-264` 同样。
- **预计（D）**：单线程 MLP/预取改善，单线程吞吐 +20–50%；与改动 2 叠加后目标向 40–60 GB/s（老师同机单线程量级 15 GB/s × 16 核远高于此，受 DDR5 实收限制）。
- **风险**：**数值**——按行独立计算、累加顺序不变（每行 dot 的 K 顺序不变）⇒ 预期 ids/`--top-probs` **逐位同**；若末位漂按类 E 门处理（静默窗口比 probs）；**不改** `by/run` 排序与输出聚合顺序。
- **怎么验/判红**：`cpu_busy_us/miss`（主读数）、`decode tok/s`；ids 45/45 + `--top-probs` 逐位；**判红**：ids 漂 或 `cpu_busy` 不降。

**备选（第 4，只改参数）**：`--pcie-frac` 已在本树落地（`engine.cpp:2192-2414`），扫 0 / 0.15 / 0.3，用 `cpu_us/miss` 与 `pcie=` 计数定 share，把这条腿的 1.54 GB/token 分一部分到 GPU 的空闲期；按老师实测 share 很小（0.16 distinct/layer），不宜期待大值。

## §5 最可能的那一条 + 未验

**最可能的一条 = 改动 2（worker 只钉物理核 + 按物理核数定线程）**：
- 证据最硬（A 级本机拓扑：**i7-13790F 16 物理/24 逻辑**；A 级代码：`--host-core off` 时**一条线程都不钉**、workers 列表含全部逻辑 CPU；C 级老师注释与实现：SMT 兄弟会"把 expert kernel 的带宽砍半"、其 worker 只钉物理核）；
- 改动小、**零精度风险**（只挪线程）；
- 若改动 1 证明 `cpu_busy ≈ wall`，那 21.4 GB/s 是真实 CPU 腿速率，这条就是把 24 逻辑线程变成 16 个真正不互抢的流的最直接办法。
- **最不确定**：`144.7 µs/miss` 究竟取自 wall 还是 busy；若 busy 远小于 wall，则"21.4 GB/s"整个命题要撤回，最大杠杆变成"把 launch/交接从 CPU 腿里移走"。

**未验清单**：
- **U1**：lead 的 144.7 µs 是 `cpu_us/miss`（wall）还是 `cpu_busy_us/miss`——树里两行都有（`main.cpp:786,792`），本件无法从盘上判（需要那次跑的输出）。
- **U2**：59 GiB 专家页**是否真正常驻**。判别法（30 秒，零 GPU）：① 跑 decode 时看首 token 与稳态的 `cpu_us/miss`（首 token 明显更高 ⇒ 页首次触/缺页）；② Windows 任务管理器/`GetProcessMemoryInfo` 看进程 WS 与系统可用内存（若映射页被回收，WS 不会含 59 GiB）。
- **U3**：本机 DDR5 实际带宽与单核流式上限（未测；需一次内存基准，属 GPU 窗口外的 CPU 小测）。
- **U4**：`--threads 24` 是那次 alt-prompt 跑的实际值（计划 §0 未写命令行）；若实际是别的值，改动 2 的"23 worker"要按实调。
- **U5**：老师 pool 的 36.32 GB/s 是 6 核开发机上的数字（`pool.hpp:80-82`），不是本机，不能当我们的天花板读数。
