### 2.3 判定（回答三问）

1. **"我们的 0.4 ms/token 在算什么？"** = **全程 CPU 专家总时间 ÷ 总 token 数（含 6792 个 prompt token）**，不是 decode 口径。证据：分母 `stats_.tokens` 在 `read()`/`eval()` 都累加（`engine.cpp:3339` 读 prompt 的每 call `call.m`；`:3260` eval）。⇒ **0.4 ms/token 与老师 7.159 ms/token 不可比**（老师分母 = 76 个 decode positions）。
2. **"为什么只有老师的 1/18？"** —— **这是假象，方向反了**：
   - 老师每个 decode token 只把 **≈55 个专家**交给 CPU（0.93 distinct×1.14 routed / 48 层，命中 **96.52%**，`dec-pool2.txt:71/:87`）；
   - 我们命中 **51.7%**（`R13-P1`）⇒ 48.3% × (top-22 × 40 MoE 层 = 880) ≈ **425 专家/token**（≈7.7× 老师）；命中最高的短 prompt 跑（69.3%）也有 ≈270 专家/token；
   - 短 prompt 反推：R15c（217 prompt + 64 decode）`CPU 10.8 ms/token × 281 tokens ≈ 3.04 s`，其中 prefill 占比很小 ⇒ **decode CPU ≈ 40–47 ms/token**（D，按 64 decode tokens 摊）；除以 ~270 专家 ≈ **0.15–0.17 ms/专家**，与老师的 7.159/55 ≈ **0.13 ms/专家 同量级**（D）。
   ⇒ **我们的 CPU 侧不是"池子没弄好"，是"分给 CPU 的专家数多 5–8 倍"；根因是命中率/常驻率（G1），不是池实现（G3）**。
3. **"GPU 与 CPU 真并行还是串行？切分/combine/互等？"**
   - **并行**：同一层内 GPU cached 专家的 kernel 由 CPU 池的一个线程发（`meanwhile`），与其余 CPU 专家的计算并发（`engine.cpp:2136-2137/2255-2257`）；swap 上传（`swap_st_`）也与 decode compute 并发（§3）。
   - **切分**：硬切分——`L.slot[e]` 有 ⇒ GPU，无 ⇒ CPU（`engine.cpp:2108-2116`）；**decode 没有可调比例，`--cpu-share` 不生效**。
   - **combine**：GPU 侧 `add_scaled` 累加；CPU 结果 `h_cpu_`（pinned）→ 层末 `moe_add()` 的 `axpy(...,true,st_)` 在 GPU 上加（`engine.cpp:2264-2267`）。
   - **互等**：每层头等 router logits（`cudaEventSynchronize(ev_)`，`:2082`）；层末 GPU 和要等 CPU 的 `axpy` 完成；**层间无流水**（CPU 算完才进下一层）⇒ 当前 decode 的串行点 = "每层 CPU 专家 + 层末 combine"。

⇒ 老师的 decode **不是"PCIe 搬 vs 算"的边搬边算**：它 decode 期没有大搬运（命中 96.5%），它的"边"是 **GPU 验证窗 ↔ CPU pool ↔ host 门铃** 三条时间线的重叠。

### 3.2 我们这边（A 源码）

**每 token（当前配置：`--no-draft --lookup 0` ⇒ 单 token eval）序列**：

1. `eval(&t,1,true)` → `run()`（`engine.cpp:2976`）：**入口 `cudaStreamSynchronize(cs(st_))`**（`:2991`）；`follow(1)` 记账/发起 swap（`:2992`→`:1369-1409`）；专家上传线程 `follow_loop()` 在 **`swap_st_`** 上做 `cudaMemcpyAsync`（`:1158-1172`、`:1341-1358`），完成事件 `s->done` 由 `follow()` **非阻塞查询**（`:1379`）⇒ **swap 上传与 decode 计算真重叠**（日志 `swapped into VRAM ≈ 2,000 / 45 token ≈ 44/token`）。
2. 每层：`layer()`（`engine.cpp:3102-3108`）→ `up()`（router 核 + D2H logits，`ev_` 记录 `:3040`）→ `moe()`：**`cudaEventSynchronize(ev_)` 等 router logits**（`:2082`，每层一个硬同步点）→ host `route()`（`:2103`，R13 已单遍）→ GPU cached 专家的 launch（`:2138-2244`，st_ 流）+ CPU 专家（`:2255`）**并发** → `moe_add()` 的 H2D+axpy（`:2264-2267`）→ `tail()`。
3. **ring/预取不参与 decode**：`ring2_`、`up_`、`cp_`、`stage()` 的 ring 分支只在 `moe_rows()`（n≥32 的批路径）里（`engine.cpp:2883/2889/2926-2942`；`moe_rows` 起点与 `batched()` 门见 `:2305/:1877` 一带）；decode 走 `moe()`（`:2071-2261`），**没有"下一层预取"**。

**可重叠窗口清单**：
- ✅ 已有：`swap_st_` 专家上传 ∥ decode compute（`--expert-swaps` 是唯一旋钮，`engine.cpp:1159`）；
- ✅ 已有：同层 CPU 专家 ∥ GPU cached 专家（`meanwhile`）；
- ❌ 没有：下一层专家/路由预取（decode 路径无 ring/无 double buffer；`ring2_` 只服务 prefill）；
- ❌ 没有：router D2H 与上一步计算重叠（每层 `cudaEventSynchronize` 是串行点，`:2082`）；
- ❌ 没有：KV 搬家（KV 常驻，64 MiB 级）。

⇒ **回答"我们 decode 的边搬边算"**：**只有 expert-swaps 那一条真重叠**（≈44 专家/token，量小）；**ring/多流在 decode 不参与**；真正的 decode 时间结构是"每层：等 router → CPU 专家（关键路径）∥ GPU cached 专家 → combine → 下一层"，**没有跨层流水**。老师 decode 的"边搬边算"是 GPU 验证 ↔ CPU pool ↔ 门铃三线重叠，性质不同。

## §6 D0-3：**模型是否自带 MTP —— 有（A 级实据）**

**证据（GGUF 头解析，零 GPU）**：
- shard1（39.7 GB）KV：`nemotron_h_moe.block_count = 89`、`nemotron_h_moe.expert_used_count = 22`、**`nemotron_h_moe.nextn_predict_layers = 1`**、`general.architecture = nemotron_h_moe`（51 个 KV 键）。
- shard2（30.4 GB，328 tensors）里 **`blk.88.*` 共 18 个张量**，其中：
  - **4 个 nextn 张量**：`blk.88.nextn.eh_proj.weight`、`nextn.enorm.weight`、`nextn.hnorm.weight`、`nextn.shared_head_norm.weight`；
  - 以及 **一整个 MoE 层的权重**：`attn_q/k/v/output`、`ffn_gate_inp`、`ffn_up_exps`、`ffn_down_exps`、`ffn_up_shexp`、`ffn_down_shexp`、`ffn_latent_up/down`、norms 等。
⇒ **block 88 = 第 89 层 = MTP/nextn 层（nextn_predict_layers=1），模型自带、且在 GGUF 里**（A）。运行时 `n_layer_ = 89 − 1 = 88`（`engine.cpp:699`），与运行日志"88 layers"一致。

**poly 侧支持链（A 源码，全已实现）**：
- 检测：`engine.cpp:697-711` —— `nextn_predict_layers==1` 且存在 `blk.{n_layer_}.nextn.eh_proj.weight` ⇒ `block_=gg_`；`draft_ = block_ && !nextn.embed_tokens && !nextn.shared_head_head` ⇒ **我们的 GGUF 没有 embed_tokens/shared_head_head ⇒ draft_ = true**（前提：`opt_.draft && window != 1`）。
- 加载：`engine.cpp:1535`（`n_all = n_layer_ + (block_layer_?1:0)` = 89 层都 load）、`:1634-1646`（4 个 nextn 权重）。
- 前向：`engine.cpp:3653-3673`（`draft_step`：draft_input → block_attend → MoE → head）、`draft()`（`:3675-3693`）。
- 验证/回退：`main.cpp:432-485`；`engine::window()/keep()`（`:3503-3620` 区间）。
- **当前被 `--no-draft` 关掉（`main.cpp:852`，交付配置在用）**。

**`E:\strata-data\mtp\rt\` 是什么**：老师 3.8-Flash 的 MTP 运行时（`dense.bin` 116 MB、`experts.bin` 708 MB、两个 `draft_vocab.bin`）；`dense.txt` 里的形状（fc_embedding 2560×2560、hc 10240、self_attn q 12288…）是 **Qwen3.8-Flash 的几何** ⇒ **对 Nemotron 不可用**；我们不需要它（MTP 在 GGUF 内）。

**结论**：**有，模型自带 1 层 MTP；poly 已具备加载/验证代码；当前只是被旗标关着**。**未验**：在 Nemotron 上从未跑过（正确性/接受率/是否触发 `check_draft_block` 限制——NemotronHMoe 无 override，基类为空 `engine.hpp:304`，理论无阻；但 `draft_step` 的 MoE/attention 路径在 latent+非门控专家上未测）。

## §8 参数分组建议（4 组打包，供"分组暗组验证"，**不做 OFAT**）

> 依据：`P3\计划-decode专项-20261018.md:41-63` 的四组，本席按代码事实调整并注明追加 A/B 的落组。

**G1 驻留组（决定 decode 的 CPU 专家数/搬运字节）**
- 包：`--vram-reserve-mib {3000→2500/2600/3500}` × `--expert-profile-write`（跑一轮 256-token 再读回，替代每跑冻结的 p_run.txt）→ 命中率↑
- 机制自证：`experts from VRAM %`（51.7% 基线）+ `swapped` 次数 + 峰值。
- **追加 A 的核心落在这里**：decode 的 CPU/GPU 切分是命中率决定的（§2.3-2），不是 `--cpu-share`。G1 是"把 CPU 工作量降下来"的唯一现役手段。
- 待移植（不进首轮）：per-layer 配额、resident-cpu（`--resident-budget-gib` 风格）。

**G2 投机组（一次搬运算多 token —— 潜在最大单项）**
- 包（**零改码首轮即可测**）：`--draft`（去掉 `--no-draft`）× `--window {4,8}` × `--lookup {0,3}`；模型 MTP = 内置 blk.88（§6）。
- 判据用 `KP-STRATA-0016`（每轮吐出 token + 墙钟，不用接受率）；质量门 ids/Δp/256-token 体检。
- 待移植：`--spec`/`--mtp` 程序线专用机制不需要（poly 自有 window 实现）；`STRATA_DEC_BATCH` 另议。

**G3 并行组（CPU/GPU 同算 —— 本席建议把追加 A 明确落这里，但注明它只在 G1 抬高命中率后才有意义）**
- 包：`--threads {12,24,48}`（默认 24）×（可选）`--any-node`；**不打包 `--cpu-share`（decode 不读，只会误导）**。
- 理由：decode 的并行是真的（GPU cached ∥ CPU 专家），但**CPU 侧专家数由 G1 定、CPU 侧完成时间由 --threads 定** ⇒ "同算"= **G1×G3 的交互**，第一轮建议 **G1 bundle 与 G3 bundle 分开测 ON/OFF，第二轮测 G1×G3 交互**（与计划件 §3 的"两两交互"一致）。
- 备注：老师 pool 的 affinity/host-core/aux-cpus/pool-tasks 在我们代码里**不存在**（§4 末），首轮不要假装有。

**G4 布局组（搬运粒度与 decode 的"边搬边算"）**
- 包：`--expert-swaps {0,32,64,128}` × `--tail-skip {0,N}`（有损，须质量门）——这是 decode 唯一现役重叠旋钮（`swap_st_` 上传 ∥ compute，§3.2）。
- 明确不打包：`--stage-ahead`/`--stage-mib`（**已确认只救 prefill**，`KP-UNI-0250`），`STRATA_STAGE_RING2`（prefill only，`engine.cpp:2926` 在 `moe_rows`）。
- 追加 B 的落组：**decode 没有 ring/无下一层预取**（§3.2），所以"边搬边算"在 G4 里只能测"swap 上传 ∥ compute"这一条；**更深的 decode 流水（下一层 CPU 专家预取/双缓冲）需要改码**，不进首轮，标"需编译"。

**组间交互（第二轮，必测）**：G1×G2（驻留高时 MTP 收益是否变小）、G2×G3（MTP+CPU 池）、G1×G3（命中率×线程数，追加 A 的正面测试）。
