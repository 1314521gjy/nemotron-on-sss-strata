## §0 三问速答

**① NIM 卡在两条上，主因是显存、次因是卡型**：
- **显存**：这模型 **NVFP4 ≈ 75 GB**（BF16 249 GB）；NIM 官方配置 NVFP4 = **1×B200 / 1×H200 / 2×H100**，BF16 = 2×B200 / 4×H200 / 8×H100（[NIM 模型卡](https://docs.api.nvidia.com/nim/reference/nvidia-nemotron-3_5-super-vl-120b-a12b)，本机 `情报-V` E5 已核）。**32 GB 装不下 75 GB；2×4090=48 GB 也不够**；且 4090（Ada, sm_89）**无原生 NVFP4**，只能回退 BF16 249 GB ⇒ 更不可能。
- **卡型**：NIM 的 verified-GPU 列表是**数据中心卡**（A100/A10G/B200/B300/GB200/GH200/H100/H200/L40S 等），**没有 GeForce/RTX 消费卡**；NIM 多卡要求**同型号受支持 GPU + 受支持 profile**（[NIM for LLMs 支持矩阵 2.0.2](https://docs.nvidia.com/nim/large-language-models/2.0.2/reference/support-matrix.html)）。
- ⇒ 准确说法不是"没有 B300"：**H200/L40S/A100 也支持**；我们卡的是"**75 GB > 32 GB（且 2×4090 48 GB 仍不够）**" + "**消费卡不在支持清单**"两条同时成立。

**② 我们的 KV 不是 BF16，是 F16；@16384 只有 128 MiB（含 MTP 块 144 MiB）；量化不值得**：`n_kv=2 × head_dim=128 × 2(K+V) × 2 B = 1 KiB/层/token`；8 个 trunk attn 层 → **128.0 MiB**，加 blk.88（MTP 块自己的 KV）→ **144.0 MiB**。对照"48 层全 attn" = **768 MiB（6×）**。Q8 只省 64 MiB ≈ **21 个专家 slot（0.36%）**，Q4 省 96 MiB ≈ 31 slot（0.54%）⇒ **<300 MB 判据 ⇒ 不值得**。mamba state = **164.7 MiB（fp32）**；窗口快照 `snap_` 最多 3×164.7=494 MiB（window>1 时；本次交付 window=1 ⇒ 0）。

**③ 结构针对性优化 Top-3**：**T1 GPU 侧 routing（sigmoid+bias+top-22）**（预填 −0.2~0.35 s / decode −2~4 ms/token，最值得）＞ **T2 Hybrid prefill CUDA graph + shared expert 独立流**（预填 +3~8%）＞ **T3 mamba-state 感知的 window/spec 管理**（tok/s 0~+2%，但**可能修掉 MTP 的 ids 漂**；state bf16 省 82 MB）。**"mamba 段与 MoE CPU 腿跨层重叠"不可行**（残差链）；**40 mamba 层整段图化**只在先有 T1 后才有意义（非 MoE 段只有 40 段、32 段仅 1 层）。

## §1 ① NIM：卡在哪（显存 vs 卡型，带数字）

### §1.1 NIM 硬件支持（C）
- NIM for LLMs 的 **Verified GPUs** 列表（2.0.2 支持矩阵）：`A100-SXM4-40GB / A100-SXM4-80GB / B200 / B300-SXM6-AC / GB200 / GH200-144G-HBM3e / H100-80GB-HBM3 / H100-NVL / H200 / H200-NVL / L40S / A10G / GH200-480GB`——**数据中心卡，无 GeForce/RTX 4090/4080S**（URL：https://docs.nvidia.com/nim/large-language-models/2.0.2/reference/support-matrix.html）。
- 通用说明（同站 supported-models）："Any NVIDIA GPU should be, but is **not guaranteed** to be able to run this model … multiple, **homogeneous** NVIDIA GPUs with sufficient aggregate memory, compute capability >= 7.0 (8.0 for bfloat16)"（https://docs.nvidia.com/nim/large-language-models/1.8.0/supported-models.html）——"不保证"= 消费卡不在验证清单，且多卡必须**同型号**。
- 例外产品是 **NIM for RTX**（面向 RTX AI PC 的微服务），但它只覆盖小模型（7B~30B 级），**不含 120B**；且需 WSL/RTX 驱动栈（本机未验）。

### §1.2 这个模型的 NIM 配置与显存（C）
| 精度 | NIM 官方 GPU 配置 | 模型权重体积 | 32 GB | 2×4090 48 GB |
|---|---|---|---|---|
| **NVFP4** | **1×B200 / 1×H200 / 2×H100** | **≈75 GB** | ✗ | ✗（48<75） |
| BF16 | 2×B200 / 4×H200 / 8×H100 | **≈249 GB** | ✗ | ✗ |
- 出处：NIM 模型卡 https://docs.api.nvidia.com/nim/reference/nvidia-nemotron-3_5-super-vl-120b-a12b（本机 `回执\IA-20261018-官方引擎与可借鉴项目.md` E5 已逐条抄）；体积：[orcarouter 部署成本文](https://www.orcarouter.ai/zh-TW/blog/nemotron-3-5-super-vl-deployment-cost)（"BF16 249 GB vs NVFP4 75 GB；BF16 4×H100 或 NVFP4 一张 H200/单台 DGX Spark"）；[Unsloth 文档](https://unsloth.ai/docs/models/nemotron-3.5-super-vl) 给 NVFP4 GGUF 的"est. minimum memory 96GB"档（含 KV/上下文余量）。
- **NVFP4 的硬件门槛**：原生 NVFP4 计算需 Blackwell（B200/B300/GB200/sm_100/120）；H200 走 NVFP4 也是官方 profile 支持的（NIM 列表），但 **RTX 4090（Ada）没有 NVFP4 内核**；NIM 的 unraid 社区文档明确 "nvfp4 unsupported → 回退 bf16"（https://github.com/PikkonMG/unraid-docker-templates/blob/main/docs/NVIDIA-NIM_SINGLE.md）。

### §1.3 判定（回答"是卡型还是显存"）
1. **显存是硬约束**：NVFP4 75 GB > 32 GB；**2×4090=48 GB 仍不够**（且没有 4×4090 的 NIM profile）。
2. **卡型是第二道门**：GeForce 不在 NIM verified 列表；NIM 多卡要求同型号数据中心卡；NVIDIA 不对消费卡发 NIM profile。
3. **结论**：**两条同时成立**；即使借到 4×4090=96 GB，也**不是 NIM 支持配置**（消费卡 + NVFP4 不支持 + 非验证 GPU）。**32 GB 单卡无任何官方 recipe**；"单 Spark（128 GB）/单 H200"是官方 NVFP4 档（C）。

## §2 ② 我们的 KV：类型 / 大小 / 量化价值

### §2.1 类型与分配（A，读码）
- **KV 是 F16，不是 BF16**：`const size_t row = n_kv_ * head_dim_ * sizeof(uint16_t)`（`PolyStrata\src\poly\nemotronhmoe.cpp:206`）；`B.keys/B.vals = kv_alloc(row, 1)`（`:212-213`）；写入口 `store_f16_at/store_f16`（`:318-322`）。
- 每层每 token 的 KV 字节 = `n_kv(2) × head_dim(128) × 2(K+V) × 2 B = 1,024 B`；`card_row_bytes = n_attn_ × 1,024`（`:255`）。
- `kv_alloc`：`all = ceil(max_context/per) × bytes`（`engine.cpp:904-913`）；`--kv-grow` 时按行增长（`engine.cpp:920-940`，`kKvGrow`），`max-context 16384` 到顶。
- **层数**：GGUF `attention.head_count_kv` 数组 89 项，非零 = `[7,16,25,36,47,58,69,78]`（8 个 trunk attn）**+ blk.88（MTP 块）**（本机 GGUF 解析，A）；`n_attn_` 在 `kAttn || kAttnMoe` 时自增（`nemotronhmoe.cpp:147`）⇒ **trunk 8 层；开 draft 时 MTP 块也占一份 KV**。

### §2.2 大小（A 计算）
| 项 | 公式 | @16384 |
|---|---|---|
| trunk 8 个 attn 层 | 8 × 1,024 B × 16,384 | **128.0 MiB** |
| + blk.88（MTP） | +1 × 1,024 × 16,384 | **+16.0 MiB = 144.0 MiB** |
| 对照：48 层全 attn | 48 × 1,024 × 16,384 | **768.0 MiB（6×）** |
| **mamba state（40 层，fp32）** | 40 × (channels 10,240 × 3 + 8,192×128) × 4 B = 43,171,840 floats | **164.7 MiB** |
| **窗口快照 snap_**（window>1） | `snap_places_ ≤ 3 × rec_n_`（`engine.cpp:2778-2790`） | **≤494.1 MiB**（本次交付 `--no-draft --lookup 3` ⇒ window=1 ⇒ 0） |

### §2.3 量化价值（判据：<300 MB ⇒ 不值得）
- **KV Q8**：128→64 MiB，省 **64 MiB = 20.7 个专家 slot**（每 slot 3.0966 MB）≈ 0.36% 驻留；**KV Q4**：省 96 MiB ≈ 31 slot（0.54%）。
- attention 只有 8 层、且 GPU kernel 忙度 decode 段仅 2–4%（情报-Y 的 nsys 读数）⇒ **attention/KV 不是瓶颈** ⇒ **KV 量化不值得**（换来的入住率 <0.6%，还要动 attention 内核 + class-E）。
- **mamba state bf16**（外部做法：SGLang cookbook 有 `mambaDtype=bfloat16` 旋钮，见 §3-T3）：省 82 MB ≈ 26 slot（0.45%）；state 读写量 40 层×4 MiB×2 = 320 MB/token → 160 MB/token，按 736 GB/s 省 ~0.22 ms/token（0.3%，D）；**收益也小**，且是数值精度改动。
- **真正大的 VRAM 项不是 KV**：是**窗口快照 494 MiB**（window>1）与 MTP 权重 626 MB；要省 VRAM 应动这些，不是 KV。

## §3 ③ 模型结构（40 mamba + 8 attn + 40 MoE）⇒ 针对性优化

### §3.0 结构事实（本机 GGUF 解析，A）
- `block_count=89`（88 trunk + 1 MTP），`nextn_predict_layers=1`；`feed_forward_length` 非零 41 块（40 trunk MoE + blk.88）；`head_count_kv` 非零 9 块（8 trunk attn + blk.88）。
- **MoE 层索引** = `[1,3,5,8,10,12,14,17,19,21,23,26,28,30,32,34,37,39,41,43,45,48,50,52,54,56,59,61,63,65,67,70,72,74,76,79,81,83,85,87,88]`；**mamba 40 层**、**attn 8 层**。
- **非 MoE 段**：40 段（32 段长 1、8 段长 2，共 48 层）⇒ 任意相邻两个 MoE 层之间**最多 2 个**非 MoE 层。**这条数字决定"整段图化"的上限**（见 §3.2）。

### §3.1 T1（最值得）：**GPU 侧 routing**（Nemotron 专用 sigmoid+bias+top-22）
| 项 | 内容 |
|---|---|
| 机制 | 现在：每 MoE 层把 512 个 router 分数 **D2H 整批**（预填时每层 13.9 MB）→ host 24 线程算 sigmoid+bias+top-22+归一化 → 再开始搬专家。外部：**gating 全在 GPU 的 ggml 图上做**（llama.cpp `build_moe_ffn`：`llama-graph.cpp:1949-2050`，sigmoid 分支 `:2045-2047`；本机 pin `E:\llama-cpp-pin`）；SGLang PR #44518 更专门为 Nemotron 加了 **"opt-in M=2–16 Triton router inside the existing fused-gate operator (`SGLANG_SM120_MTP_ROUTER_TOP22`)"**，device 算术不变。 |
| 出处 | https://github.com/sgl-project/sglang/pull/44518（body）；`E:\llama-cpp-pin\src\llama-graph.cpp:1949-2050`；我们自己的对拍件 `IA-20261018-prefill结构对拍.md`（"最值得搬的一条是 GPU 侧 routing，对得上 40 个层边界气泡 0.400 s：每 MoE 层 D2H 整张 13.9 MB 分数 + 24 线程 sigmoid/bias/top-22"） |
| 我们可行性 | **中**：新增一个"512 选 22（sigmoid+bias，scale 5.0，weights_norm）"的 GPU kernel；D2H 从 512 floats/token 降到 22 ids+weights（预填 6912 token：13.9 MB/层 → ~0.7 MB/层，40 层共省 ~0.4 s 的 PCIe/同步）；host 只等 ids 再发 staging（doorbell 仍需 host，但不再算 top-k）。 |
| 预期量级 | **prefill −0.2~0.35 s（+6~10%）**；**decode router_wait 7.7 ms/token 中可砍 2~4 ms（+3~6% per-token）**（D，输入：`IA-20261018-prefill结构对拍` 0.400 s 气泡；R49 ledger `router_wait=981.7 ms/127 轮=7.7 ms/token`）。等级 **D**（推算）。 |

### §3.2 T2：**Hybrid prefill CUDA graph + shared expert 独立流**（SGLang PR #44518 的 Nemotron 专用项）
| 项 | 内容 |

| 机制 | SGLang PR #44518 body 原文："**Hybrid prefill CUDA graphs for Nemotron on SM120, with shared experts overlapped on one explicit stream**"——把混合 prefill（mamba SSD + attn + MoE + shared expert）整段图化，shared expert 单独一条流与主图重叠。对照 llama.cpp：**整模一张 ggml 图**（`E:\llama-cpp-pin\src\llama-context.cpp` `build_graph` 在 `:2476`、`ggml_backend_sched_graph_compute_async` `:2539`），没有我们这种"每层 host 往返"。 |
| 出处 | https://github.com/sgl-project/sglang/pull/44518；`E:\llama-cpp-pin\src\llama-context.cpp:2476,2539` |
| 我们可行性 | **中低**：整图化要求**没有 host 决策**；我们的 MoE 层 host routing 会把图打断（所以 T2 依赖 T1）。折中版：**只图化 48 个非 MoE 层组成的 40 个段**——但 32 段只有 1 层、8 段 2 层 ⇒ **只能合并 8 个层边界**（48 层 → 40 段），收益有限；要真正整图必须先做 T1。 |

### §3.3 T3：**mamba-state 感知的 window/spec 管理**（外部已踩过同一类坑）

### §3.4 需求列出的四个问题（逐条）
| 问题 | 答案（带数字/出处） |
|---|---|
| mamba state 常驻/重算 vs 存显存 | **我们已经在 VRAM 常驻**（fp32 164.7 MiB，`nemotronhmoe.cpp:199-201` + `engine.cpp:2778-2783`）；"重算"不可行（每 token 都要全 40 层 state）；外部可借鉴的是 **bf16 state**（SGLang cookbook `mambaDtype=bfloat16`，URL 见上/下）与 **state 形状按配置算**（vLLM `nemotron_h.py`）；收益小（82 MB/0.45%、带宽 −0.3%）。 |
| 40 个 mamba 层能否整段图化 | **理论可以**：llama.cpp 就是整模一张图（`llama-context.cpp:2476`）；但我们的图被 **40 个 MoE 层的 host routing** 打断，**非 MoE 段只有 40 段（32 段 1 层、8 段 2 层）** ⇒ 不做 T1 时只能省 8 个层边界；**先做 T1 才值得整图**。 |
| mamba 段与 MoE CPU 腿重叠 | **跨层不可行**：残差链（层 i+1 输入=层 i 输出，MoE 在链上）⇒ GPU 不能提前跑下一层的 mamba。**唯一可重叠的是同一 MoE 层内"GPU 常驻专家 ↔ CPU miss"**（我们的 `moe()` 已做）；或**去掉路由 host 往返（T1）让 CPU 腿更早启动**。老师 A770 的"重叠 CPU pool 与 GPU"是其 GPU 工作更重的结构（`情报-Y` 读的 `A770_SPEED_SPEC.md:688-714`），**不能按字面搬**。 |
| 8 层 attn ⇒ KV 精度换 slot？ | **不值得**：KV f16 @16384 只 128 MiB（含 MTP 144 MiB）；Q8 省 64 MiB=21 slot（0.36%）、Q4 省 96 MiB=31 slot（0.54%）⇒ **远小于 <300 MB 判据**；attention 不是瓶颈（nsys decode GPU busy 2–4%，`情报-Y`）。 |

- **U6**：T1/T2 的百分比是 **D 级推算**（输入：0.400 s 预填气泡、R49 的 7.7 ms/token router_wait；外部 PR 未给 Nemotron prefill 单独数字）；**需 1 跑实验**（先用 GPU 侧 routing 的 ncu/nsys 对比 profile）。
