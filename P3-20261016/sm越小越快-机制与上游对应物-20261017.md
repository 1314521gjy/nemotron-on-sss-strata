# `--stage-mib` 越小越快：机制判读 + 上游 `strata` 的对应物 + "我们没开的功能"逐条评估 — 2026-10-17

- 席位：`scheduler` · **只读**（读码/读文档/grep）：**未跑 GPU、未改码、未抢窗口**。
- 触发（2026-10-17 需求）：**`--stage-mib` 越小越快，需对照 strata 的做法、差异与未启用功能**
- **★ 一句话结论**：
  **① "越小越快"的主因是"预取/流水粒度"（B），不是"stage 抢 arena"（A）—— 且 A 的**上限可以被算出来（整条曲线只值 ~2.4 点命中），足以在 builder 的读数里**一刀分开**（判读表见 §1.3）。**
  **② 上游【没有 `--stage-mib` 这个旋钮】—— 它的缓冲是"按槽数/按 pack 导出"的（`STAGE = 8` 槽 · `ring_slots()` 由 pack+pinned 比例定），不是"用户可调的 MiB 数" ⇒ 所以"为什么不一样"的答案是：我们多了一个上游没有、且同时管两件事的旋钮。**
  **③ "stage 的替代品"不是 `--prefill-head-alias`（方向相反）—— 上游根本没有这类替代品；真正值得搬的是三条【策略】而不是【构造】（§3.6）。**

## §1 问 1：「越小越快」的机制到底是哪一条

### 1.1 两个候选**都真实存在**（读码，A）

| 候选 | 机制 | 出处 |
|---|---|---|
| **(a) stage 抢 arena** | `stage_` 在 `alloc()` 里分配，而 `alloc()` **早于** `fill_expert_cache()`（`:1487` → `:1489`）⇒ **stage 每大 1 MiB，arena 少 1 MiB** ⇒ 常驻专家少 ⇒ 命中低 | `engine.cpp:1668-1670` · `:1487-1489` · `:1043` |
| **(b) 预取/流水粒度** | `per_round = stage_bytes/(slot_down + d_bytes)`（**一层分几轮**，`:2342`）· `L.ahead` 上限 `= stage_bytes/(2·gu_bytes + d_bytes)`（**一层预取几个**，`:1255`）⇒ stage 越大 ⇒ 预取越多、轮越少 | `:2342-2345` · `:1255` |

### 1.2 ★ 代数：把两个候选的**预期量级**算出来（本靶，A）

本靶常数：`one_expert = slot_down + d_bytes = 3,096,576 B = 2.9531 MiB` · `2·gu_bytes + d_bytes = 4.4296 MiB` · 每对专家占 arena `3.0966 MB`；**1 MiB arena = 0.338 对 = 0.00165 of 20480 ⇒ 1 MiB ≈ 0.165 点命中**（每 100 对 ≈ 0.49 点）。

| `--stage-mib` | 实际 `stage_bytes_` | `per_round`（专家/轮）⇒ **一层轮数** | `L.ahead` 上限 | **Δarena vs 2048** | **(a) 能解释的 Δ命中** |
|---|---|---|---|---|---|
| 64 | 64 MiB | 22 ⇒ **~24 轮** | 14 | +1448 MiB | **+2.4 点** |
| 128 | 128 MiB | 43 ⇒ ~12 轮 | 29 | +1384 | +2.3 点 |
| 256 | 256 MiB | 87 ⇒ ~6 轮 | 58 | +1256 | +2.1 点 |
| 512 | 512 MiB | 173 ⇒ ~3 轮 | 115 | +1000 | +1.7 点 |
| 768 | 768 MiB | 260 ⇒ **2 轮** | 173 | +744 | +1.2 点 |
| 1024 | 1024 MiB | 347 ⇒ **2 轮** | 231 | +488 | +0.8 点 |
| **2048（默认）** | **1512 MiB**（被 `n_expert×one_expert` 夹住） | **512 ⇒ 1 轮** | 341 | —— | —— |

**⇒ 关键量级对比（A 级算术）**：**整条曲线（2048 → 64）里，(a) 至多值 +2.4 点命中**；而**实测速度从 125.6 → 367（+192%）**。
⇒ **⇒ (a) 不可能解释这条曲线**（除非命中真的升了 ≥10 点，那是**另一个机制**在起作用，见 §1.4 的"悬崖"）。

### 1.3 ★★ 判读表（**接住 builder 正在同报的 `arena 对数` 与 `命中率`**）

| 观测（builder 的读数） | 判 → **(a) 主因** | 判 → **(b) 主因** | 怎么用它 |
|---|---|---|---|
| `sm↓` ⇒ **arena 对数** | 必按 **线性**升：`Δ对数 ≈ Δstage_bytes(MiB) × 0.338` | **同一线性**（这条对 (a)(b) **无鉴别力**，只用来**验证 stage 与 arena 的 1:1**是否成立） | 若实测斜率 **≠0.338** ⇒ **先怀疑"该档被夹住了 / 有别的分配在变"** |
| `sm↓` ⇒ **命中率** | **必须显著升**（整条曲线 **+2.4 点** 上限；**sm 2048→64 到不了 5 点 ⇒ 若实测升 ≥5 点，(a) 之外还有机制**） | **基本不动** | ★ **这是主判据** |
| `sm↓` ⇒ **速度** | 只能解释 **≤2.4 点命中所对应的那一小部分** | 能解释 **+192%** | 把"速度增益"与"命中增益"**并列报** |
| **只看 `sm=64` vs `128`（新扫的两点）** | Δarena = 64 MiB ⇒ **Δ对数 ≈ 22 ⇒ Δ命中 < 0.2 点** | 轮数 24 → 12、预取上限 14 → 29 | ★ **这一对最干净**：**若速度差（实测 367 vs 352 ≈ 4%）远大于命中能解释的（<0.2 点）⇒ (b)** |
| **下限 = `one_expert`（2.9531 MiB）** | 再降只多 **~21 对（0.1 点）** ⇒ **速度应持平** | 轮数 → **1 专家/轮（最细粒度）**、预取上限 → **0 或 1** | ★ **若降到 2.9531 MiB 仍继续变快 ⇒ (b) 成立且"越细越好"** |

**⇒ 判读规则（写死，供报告用）**：
- **(i)** 命中率沿曲线**几乎不动（≤2–3 点）** ⇒ **(b) 主因**；报告里**不许**把速度增益归给命中。
- **(ii)** 命中率**大幅上升（≥5 点）且与速度同步** ⇒ **(a) 之外还有机制**（可能是 §1.4 的悬崖，或 stage 抢的不只是 arena）。
- **(iii)** **两者兼有 ⇒ 必须分开写**（"其中 ≤2.4 点归容量、其余归粒度"）。

### 1.4 ★ 一个必须排除的"第三机制"（**A 级旁证的边界**）
我们已有一条**运行级**旁证：`sm=768` 的 arena = **7144 对** vs `sm=8192`（被夹到 1512）的 **6892 对** ⇒ **差 252 对 = 744 MiB = 1512−768** ⇒ ① **stage 与 arena 1:1** ✅；② **`sm>1512` 被夹** ✅；③ **而那一对的命中率恒 97.1%**（**`sm` 扫描里**）⇒ **(a) 在那一档里不显形**。
⚠️ **但**：`sm=64` 时 arena 可能已经**大到把"该层全部专家"装下**（触到"缓存不驱逐/装满"的另一侧）⇒ **命中率会出现台阶**。**⇒ 若 builder 在 `sm≤128` 看到命中率突然跳一大截（≥5 点），那不是 (a) 的连续效应，而是触到了容量悬崖 ⇒ 必须单独标注**（这与"内存超配/装满"是两件事）。

## §2 问 2：上游 `strata` 的对应物 —— **它有缓冲，但"不是可调 MiB"**

### 2.1 读码事实（A，我们 clone 的 `strata` 引擎）

| 件 | 原文/事实 | 出处 |
|---|---|---|
| **ring 的形态** | 「the routed experts are grouped by expert: resident ones are read from the VRAM tier, **the others streamed from the host arena through a pinned ring on a copy stream**」 | `include/strata/prefill/prefill.hpp:6-8` |
| **★ 有一个固定的小 ring 常量** | `constexpr int STAGE = 8;  // host->device expert staging ring (chunks below stream_all_min())` | `src/prefill/prefill.cpp:122` |
| **★ 大的 ring 是"按 pack/pinned 比例导出"的** | 「The streamed ring: **384 slots** when (nearly) every streamed expert is DMA'd from pinned RAM —— measured on Q2_0, 8192-token chunks: **96 slots 1153 tok/s, 384 1294** … **the host copies are the limit and the bigger ring only takes cache slots**. `STRATA_PREFILL_RING` overrides.」 · 「slot count is **derived from the pack**（`ring_budget_slots`）；Q2_0 仍是 1024（fused）与 384」 · `g_ring_override`（#340，layer split）· `g_ring_budget`（#583，"auto chunk 扫描的字节预算 ring"） | `src/prefill/prefill.cpp:214-230` |
| **★ ring 越大 ⇒ 占缓存槽越多（= 与我们的 `stage` 抢 arena 同构！）** | 同上原文：「**the bigger ring only takes cache slots**」；且实测 **"one chunk the smaller ring only slowed it"**（RTX 5070 4K：Coder −15%、IQ3_S −5%、IQ3_XXS −2%） | `:214-230` |
| **VRAM 侧：优先借专家缓存槽** | 「The same with caller-owned device buffers（**the prompt path borrowing expert-cache slots**）」 | `include/strata/prefill/gemm.hpp:24` |
| **一个专家要么来自缓存槽、要么来自 ring 槽** | 「a **cache slot or a ring slot**, no gather」 | `include/strata/prefill/moe_fused.hpp:11`、`moe_fused_iq.hpp:5` |
| **★ 借以外还"自己分配"（hybrid）** | 「The prompt path **borrows cache slots 1 to N** (slot 0 stays). **Whatever does not fit there is allocated by the prompt path itself**, which makes a "hybrid" layout.」 | `docs/PREFILL_HEAD_ALIAS.md:34-37` |

### 2.2 ⇒ 判定
1. **上游【有】过路缓冲，但形态是"槽"**：**`STAGE = 8`**（小 chunk）+ **`ring_slots()`**（大 chunk，**由 pack 与 pinned 比例导出**，`STRATA_PREFILL_RING` 可覆盖）。
2. **上游【没有】"按 MiB 可调的独立 stage 缓冲"这个旋钮** ⇒ **⇒ "为什么我们和它不一样"的答案**：**我们把上游"按规则导出的槽数"暴露成了用户可调的 `--stage-mib`，于是多了一个旋钮；而这个旋钮同时管两件事**（一轮几格 + 预取几个）⇒ **它的最优值必须按本靶几何重新定**（我们测出 768–1024，且**实测越小越快、下限 `one_expert`**）。
3. **★ 而且上游【也承认这条代价】**：**"the bigger ring only takes cache slots"** = **ring 越大 ⇒ 占的缓存槽越多** ⇒ 与我们的 **(a)** **同构**；**上游实测也有最优窗口**（Q2_0：96→384 变快；IQ3_S（host 拷贝成瓶颈）：**96 → 256 反而更慢**）⇒ **"缓冲大小该多大"在两个引擎上都是"要按几何/带宽测出来的"，不是常量**。

## §3 问 3：我们没开的（上游）功能逐条评估 —— **哪个是 stage 的替代品？**

### 3.1 `--prefill-head-alias`（**头号假设**；A/C）
- **它是什么**（原文）：「Two large VRAM users never work at the same time… the head's VRAM holds prompt buffers while a prompt is read, and the head is read back in before the first generated token」；**具体**：启动后**把输出头卸载**（`417 MiB` for IQ3_XXS），**专家缓存按"头也算空闲"重算**（**749 槽 instead of 508**），**prompt 路径借缓存槽 1..N，溢出的自己分配（hybrid）**，chunk = **2048/1536/1024/512 中装得下的最大者**（`docs/PREFILL_HEAD_ALIAS.md:31-37`）。
- **我们有没有对应物**：**无此旗标**（poly 42 旗标全表已核）。
- **★ 能不能搬 / 为什么"方向相反"**：**它给的是"prompt 侧更多空间 ⇒ 更大的 chunk（512→2048）⇒ prefill 256→583 tok/s（+125%）"** —— ★★ **这是"chunk 越大越快"，与我们"`stage` 越小越快"** **不是同一件事**：
  - **上游的 chunk** = 一次吃多少 token（对应**我们的 `--prompt-batch`**，且我们 canonical 已用 **1024**，**方向一致**）；
  - **我们的 `--stage-mib`** = **过路缓冲/预取上限**（**上游没有这个可调旋钮**）。
  ⇒ **所以 head-alias 不是 `stage` 的替代品**（它替代的是"让 prompt 路径拿到更大缓冲/更大 chunk"）。
- **★ 而作者自己在 Open questions 里给了对我们最有用的一句**：「**A larger card already gets a large chunk without the flag, so we expect the gain to be smaller there**」⇒ **在 32 GB 卡上它的收益本就小**。
- **改动面（只评估）**：**大** —— 要在 prompt 前后 **unload/load 输出头**（受测中位数 **255 ms/次**）+ 重排 prompt 路径（20 ms）+ 处理 **CUDA graph 抓到了头地址**（作者用"地址变了就重启引擎"兜）+ **要求 `--mtp`/单卡/无 `--batch`/无 layer split/`--prefill auto`**（`:48-50`）。
- **代价（作者实测，C）**：**短读变慢**（1–64 fresh：**671 → 1,311 ms**；65–512：1,703 → 2,453 ms），**长读才回本**（513–2,048：4,062 → 3,331；2,049–8,192：15,206 → 6,876）；**decode 期 0 MiB 空闲 ⇒ WDDM 下危险**（`:52-72`）。

### 3.2 `docs/KV_PREFETCH.md`（C）
- **它是什么**：**下一层 attention 的 KV 上传在本层计算时进行**（opt-in）。
- **对应物**：**无**（我们 `cover()` 按 ctx 增长**惰性映射**，没有"层间 KV 预取"）。
- **可搬性**：**理论可搬**（我们有 event 习惯，`ev_free_/ev_ahead_`）；**收益口径 = prefill 时间 −5.3%(32K) / −4.1%(64K)**（作者读数，C）⇒ **中等**；**改动面**：中。

### 3.3 `docs/BATCHING.md`（`--batch/--slots`，PR #559）（C）
- **它是什么**：**多请求同批** —— 每窗带**每个会话一个 token** ⇒ **共享专家只读一次**（跨请求摊销）。
- **对应物**：**无**（我们单请求串行；`--serve` 一次一请求）。
- **可搬性**：**不能**（改动面**很大**：调度 + 每请求状态 + 与 `--prompt-cache` 交互）；**且收益来源与我们的问题不同**（我们是**单请求 prefill**）。

### 3.4 `docs/BATCHED_DMA.md`（C）
- **它是什么**：一个 verifier group 的独立专家上传走 `cudaMemcpyBatchAsync`（CUDA **13.0+**，opt-in `STRATA_DMA_BATCH=1`）。
- **对应物**：**部分有** —— 我们的 `stage()` 是**逐专家 memcpy**（`engine.cpp:2156-2185` 一带）⇒ **形态同源**。
- **可搬性**：**可搬，但作者自己写明**「**This is an experiment to reduce host submission overhead, not a demonstrated increase in model tokens per second**」⇒ **别指望它**；**改动面**：小。**收益前置**：得先证明"我们的上传次数是瓶颈"（**未测**）。

### 3.5 `--kv q8_0`（`98d1947`）（C）
- **它是什么**：KV 量化到 **Q8_0**（VRAM 减半）；**上游这条只挂在 `qwen35`**（另件已核）。
- **对应物**：**无**（我们 KV 恒 f16）。
- **可搬性**：**可搬**，但**我们已量**：`--max-context 8192` 时 **KV 只有 64 MiB** ⇒ **省不出肉**；**只在长上下文才值得**（`b9aef4f` 那条 1M 上下文里它才有意义）。**改动面**：小–中。

### 3.6 ★ 结论：**没有"stage 的替代品"；值得搬的是三条【策略】**
| 排序 | 搬什么 | 为什么 | 代价/改动面 |
|---|---|---|---|
| **1** | **★ 把 `stage_mib` 从"用户给的 MiB"改成"按几何导出的默认"**（上游先例：`ring_budget_slots` **按 pack 导出**、`STRATA_PREFILL_RING` 可覆盖） | 我们的 `--stage-mib 2048` 默认**落在平台外**（实测 −36%）；上游从不要求用户填一个 MiB 数 —— **它的缓冲是导出的** | **改默认值 + 一条导出规则**（小） |
| **2** | **`KV_PREFETCH` 的思路**（下一层 KV 上传藏在本层计算下） | 与我们 `--stage-ahead` **同一思想、不同对象**（我们藏**专家**、它藏 **KV**）⇒ 长上下文时会变重要 | 中 |
| **3** | `BATCHED_DMA`（**只有在"上传确实碎"时才做**） | 作者自认**未证 tok/s 提升** | 小 |
| — | ~~`--prefill-head-alias`~~ | **不是替代品**（它是"给 prompt 更多空间/更大 chunk"，方向与"降 sm"相反；且大卡收益小、短读变慢） | 大 |

## §4 问 4：能变红的判据（**给头号假设 `--prefill-head-alias`**）

**⇒ 可判别预测（写死）**：
1. **★ 方向**：**若 head-alias 真是"借头缓冲给 prompt 侧"，它的收益应当与"给 prompt 侧更多空间"同向**（例：**与"升 `--prompt-batch`"或"降 `--vram-reserve-mib`"同向**），**而与"降 `sm`"** —— **不必然同向**（因为 `sm` 管的是**过路缓冲/预取粒度**，不是 chunk）。
2. **★★ 一刀切开（若将来真做等价物）**：**在 `sm=2048` 与 `sm=64` 两臂各开/关"借缓冲"** ——
   - **若收益随 `sm` 增大而增大** ⇒ 它**替代的是"stage 与 arena 争空间"这件事** ⇒ **可以部分替代降 sm**；
   - **若收益与 `sm` 无关**（两臂同幅）⇒ **它只是"给 prompt 侧独立空间"** ⇒ **解释不了 367 vs 170**（因为 367 vs 170 是**同一 `--prompt-batch`、只改 sm** 得到的）。
3. **★ 最硬的一条（免改码，直接推翻）**：**367 vs 170 发生在【同一个 chunk 大小】（`--prompt-batch 1024` 不变）** ⇒ **凡是"只改 chunk/只省显存"的机制，原理上都解释不了它** ⇒ **⇒ `--prefill-head-alias` 若"只是省显存、不改流水粒度"，就【不可能】是我们这条曲线的替代品**。
4. **正控/负控**：若将来给 `poly` 做"借头/借 KV"的等价物 ⇒ **必须同时报 `per_round`（一层几轮）与 `L.ahead` 上限**；**若这两个数没变而速度变了 ⇒ 那才是"省空间"的贡献**；**若 `per_round` 变了 ⇒ 说明改的是粒度**（那就不是 head-alias 类的东西）。

## §5 未验 / 边界
1. **【A】** §1 的公式与常数、§2 的全部 `file:line` 与原文、§3.1 的原文与读数 —— 均**读码/读文档实测**（作者读数标 C）。
2. **【D】** §1.2 的 `per_round`/`L.ahead` 上限是**公式代入本靶几何**（**未跑**）；**一层轮数** 按 `round_` 构造**近似估算**（n_cached/n_ahead 随跑变）。
3. **【D】** §1.4 的"容量悬崖"是**待验**（builder 的 `sm {8,16,32,48}` 扫描 + 命中率同期读数**正好能判**）。
4. **【C】** §3 的收益数字全部是**作者自报**（另一台机 8 GB / 8,151 MiB RTX PRO 2000 Laptop）。
5. **【未核】** 我们的输出头（`output_`）**有多大**（决定"借"能借出多少 MiB）；`ring_budget_slots` 的**导出公式细节**未逐行读。
6. 本件**未改码、未编译、未跑 GPU**；未跑重 CPU/磁盘扫描。
