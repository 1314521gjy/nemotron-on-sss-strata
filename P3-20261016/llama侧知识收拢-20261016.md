## §0 结论速览（一屏）

1. **★ 最值钱的是"口径三坑"**（§1）：同一台机、同一个模型，**`llama-bench`(合成 prompt) 与 `llama-cli`(真实 prompt) 对 prefill 给出相反结论**（43.95 vs 16.5 t/s）⇒ **口径本身是主变量**；且 **`llama-cli` 本版默认进对话模式**、**本版无 `-no-cnv`** ⇒ 单次补全必须用 **`llama-completion.exe`**。
2. **`--n-cpu-moe` 是 U 形，峰值在 N≈24**（11.86 t/s），**再压小 N 反而掉到 3.90** ⇒ 原因是 **N=24 时显存已近满（32156 / 32759 MiB）⇒ 再小就是超配**；**判据必须用 `nvidia-smi` 显存读数，不许靠 tok/s 反推**。
3. **同口径（真实 prompt / 单次补全）下：我方引擎 prefill ~1.5×、decode ~3.7×**（§6）。
4. 供应链：**`api.github.com` 匿名已被限流** ⇒ 走 **非 API 三条路**（§3）。
5. 运行时：**本机 13.3 的 cudart/cublas DLL 能配 13.4 的包**，**不必新下 cudart**（§4）。

## §1 ★★ 口径三坑（本件最值钱；对表纪律由此来）

| # | 坑 | 实测证据（A） | 处置 |
|---|---|---|---|
| **1** | **`llama-bench`（合成 prompt、可重复、带 ±散布）vs `llama-cli`/`llama-completion`（真实 prompt）给出相反结论** | bench `-p 700 -n 45 -r 3`：**N=24 pp700 = 43.95 ± 0.42**（`P3_llm_full_n24.log`）；而 cli 真实 prompt：**`[ Prompt: 16.5 t/s | Generation: 5.9 t/s ]`**（`P3_llm_cli_n24.log` 末行）⇒ **差 ~2.7×** | **对表必须钉一个口径**；**"合成口径"只能当"上界/合成参考"，不许进结论** |

- **真实口径**：llama 23.9 vs 我方 36.3 ⇒ **我方快 ~1.5×**。

## §2 ★★ `--n-cpu-moe` 的 U 形 + 显存超配（判据：看显存，不看 tok/s）

**扫描（小测 `-p 8 -n 8 -r 1`，A）**：

| N | 27 | 26 | 25 | **24** | 23 | 22 | 21 | 20 | 18 |
|---|---|---|---|---|---|---|---|---|---|
| pp8 t/s | 10.80 | 10.98 | 11.49 | **11.86** | 11.58 | 8.93 | 9.58 | 6.47 | **3.90** |

- **N 从 27 往下压，到 24 见顶；再往下 DROP**（N=18 只剩 3.90 = 峰值的 1/3）。
- **机制（A，用显存读数定死）**：**N=24 时显存峰值已近满：32156 / 32759 MiB** ⇒ **再压小 N 就是"要的比实有的多" ⇒ 超配 ⇒ 掉速**。（N=27…18 **全部能加载、无 OOM** ⇒ 不是 OOM，是超配。）
- **★ 引擎自身的原生证据（A，支持同一机制）**：`engine.cpp:988-993`
  > "The cache takes what is free but for a reserve. … **Under Windows a card that is asked for more than it has does not refuse: memory moves to the system's, and an answer came at 13 tokens/s where it comes at 30.**"
  ⇒ **"超配不报错、启动正常、只有速度崩"是 poly 引擎已记录的行为**，与 llama 侧 U 形后半段同因。
- **⇒ 判据（能变红）**：**用 `nvidia-smi` 的显存读数（峰值 / 余量）判定是否超配**；若只看 tok/s 会把"超配"误读成"模型/配方不行"（`KP-NIFER-0036` 同族；库内已有 `KP-ENGSPEED-0007` / `KP-UNI-0222` 覆盖同一族）。
- **★ 反常要如实报**：**"N 越小（越多专家上卡）越快"这个先验在本机不成立**——**N=24 是峰值，不是 N=18**。

## §4 运行时复用：**不必新下 cudart**

- 包是 **cuda-13.4**，但本机 `E:\llama-cpp\` 的 **13.3** 三个 DLL **能配**（同类同名）：**`cudart64_13.dll` · `cublas64_13.dll` · `cublasLt64_13.dll`**（A：本机存在性已核）；另有同源 `cudart-llama-bin-win-cuda-13.3-x64.zip`。
- ⇒ **处置**：只读**拷**这三个 DLL 进解包目录即可；**不要**去下 13.4 的 cudart 包（省一次下载）。
- ⚠️ **若日后换 CUDA 大版本（13.x → 14.x）⇒ 必须重新配 DLL**（同名规则只在小版本内成立）。

## §6 0 点结论本体（**同口径**；含全部口径警示）

**口径（钉死）**：同 prompt 文件（≈700 token，llama 侧实测 **709 tokens**）· **单次补全** · **无投机/MTP** · `-c 4096 -fa on -t 16` · 各取 3 跑中位。
- llama 侧用 **`llama-completion.exe`**（因 §1-3）；我方用 `--max-new 45 --no-draft --lookup 0` + **冻结 profile** + **预热 1 跑丢弃**。

| 量 | **llama.cpp（N=24）** | **我方引擎** | 谁快 |
|---|---|---|---|
| **prefill t/s** | 26.45 / 21.37 → **中位 23.9**（**两次差 19%**） | **36.3 / 37.2 / 35.4 → 中位 36.3** | **我方 ~1.5×** |
| **decode t/s** | 6.61 / 6.68 → **中位 6.65** | **24.88 / 25.78 / 24.03 → 中位 24.88** | **我方 ~3.7×** |
| 生成 | 44 runs（`n_predict 45`） | **45 (stop) ×3** | 同口径 ✓ |
| **装载时间** | **41.9 s / 37.4 s** | **9.4 / 9.7 / 9.5 s** | 我方 ~4× |
| **显存峰值** | **32156 / 32146 MiB**（32759 上限 ⇒ 近满） | **29837 MiB** | 我方低 ~2.3 GB |

**★ 不对称必须写明（不是运气）**：llama 侧 **24 层专家留在 CPU/RAM**（`--n-cpu-moe 24`），而我方 **8010 / 20480 专家常驻 VRAM（39.1%）+ profile 学习排序** ⇒ **我方胜得符合机制预期**；反过来 llama 的 N=24 已近满显存（§2）⇒ **它也没有更多腾挪空间**。

**★ 警示（不许省）**：
1. **llama 侧 prefill 两次差 19%**（26.45 vs 21.37）⇒ **该口径的 prefill 自带 ~±10% 噪声** ⇒ **1.5× 这个倍数在临界上**，别当精确值。
2. **两侧 KV/ctx 实现不同**（我方 `max_context 8192` 的 KV = 8 KiB/token；llama `-c 4096`）⇒ **decode 绝对值慎比**（decode 对 KV 尺寸/换入更敏感）。
3. **我方对照数取自当日早批**（非同期同窗口）⇒ **跨批有环境漂移风险**；且**我方 §6 的 36.3 与早批 `g0q/g0r` 的 19.8–25.8 口径不同**（早批 `--max-new 64` + 未喂 profile + 未预热）⇒ **两个数不许混引**，主因**未验**。
4. **合成口径 `llama-bench pp700 = 43.95` 只能当"llama 上界参考"，不许与真实口径混着比**（§1）。

## §7 可复现命令（照敲级）

**前置**：① 解包到 `E:\llama-cpp-upstream\`；② 从 `E:\llama-cpp\` **只读拷** 3 个 13.3 DLL；③ prompt 文件放 **ASCII 路径**。

```powershell
# ── llama 侧：N 扫描（小测）────────────────────────────
llama-bench.exe -m <model-00001-of-00002.gguf> -ngl 99 --n-cpu-moe 24 -fa on -t 16 -p 8 -n 8 -r 1
#   ⇒ 读表里的 pp8 / tg8 两行；N 从 27 往下扫到 18

# ── llama 侧：正式读数 ────────────────────────────────
llama-bench.exe -m <model-00001-of-00002.gguf> -ngl 99 --n-cpu-moe 24 -fa on -t 16 -p 700 -n 45 -r 3
#   ★ 本版不收 -c（ctx 由 -p/-n 定）

# ── llama 侧：真实 prompt 单次补全（★不用 llama-cli）──
llama-completion.exe -m <model-00001-of-00002.gguf> -ngl 99 --n-cpu-moe 24 -fa on -t 16 `
  -f C:\tmp\prompt700.txt -n 45 -c 4096
#   末两行 = "prompt eval time = … / 709 tokens ( … tokens per second)" 与 "eval time = … / 44 runs"

# ── 显存读数（判"是否超配"只看这个，不看 tok/s）─────
nvidia-smi --query-gpu=memory.used,memory.total --format=csv,noheader

# ── 我方：同 ids 单次补全（★每次跑前冻结 profile）────
cp <母本 p_master.txt> <p_run.txt>
strata-poly.exe --model <model-00001-of-00002.gguf> --tokens <long_ids.txt, 700> `
  --max-new 45 --prompt-batch 8 --cpu-share 0.55 --expert-swaps 64 --tail-skip 0 `
  --threads 24 --vram-reserve-mib 2500 --no-draft --lookup 0 --expert-profile <p_run.txt>
#   预热 1 跑丢弃 → 3 跑取中位；读 "prompt 700 tokens X tok/s" 与 "loaded in X s"
```
