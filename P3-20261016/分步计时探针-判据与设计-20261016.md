## §2 ★★ 计时手段：**最小侵入方案**（观测掩盖律优先）
**铁律（本节最重要）**：
> **不许因为计时而改变被测时序。** ⇒ **凡是"要让 host 等卡"的手段一律禁止**（`cudaStreamSynchronize` / `cudaEventSynchronize` / `cudaDeviceSynchronize`）。
> **理由**：`dbg()` 那条路（`engine.cpp:1827` 的 `cudaStreamSynchronize`）**已被我们判为掩盖竞态**（观测掩盖律 §4），**不能在探针里重犯**。

| 手段 | 改时序？ | 判定 |
|---|---|---|
| **host `Clock`/`std::chrono` 包住【host 自己在做的事】**（如 `cpu_experts()` 调用、`stage()` 的 host 拷贝循环、`moe_router` 的 host 段） | ❌ **不改** | ✅ **首选**（引擎已有 `Clock`/`ms_since`，`:1909/:2082/:2239`） |
| **`cudaEventRecord`**（只**入队**、不阻塞 host），**在 run 末尾** `cudaEventElapsedTime` 一次性算差 | ❌ **不改** | ✅ **可用于"卡上区间"**（如 up / 激活 / down 各段） |
| **`cudaEventElapsedTime` / `EventQuery` 在【中途】调用** | ✅ **会**（隐式同步） | ❌ **禁止中途算**；**只在末尾** |
| **`cudaStreamSynchronize` / `cudaEventSynchronize` 新增到探针里** | ✅ **会** | ❌ **禁止**（= `dbg()` 的错） |
| **复用引擎【已有的】阻塞点**（`:1910`/`:2169`/`:2250`，本来就是 host 等卡）包一层 `Clock` | ❌ **不改**（那三处**本来就阻塞**） | ✅ **`route_wait` 就是这么做的**（`:1909→:1911`） ⇒ **照抄这个模式** |
| **探针记录用 host 原子自增 + 定长 ring（thread_local），run 末一次 flush** | ❌ **不改** | ✅（与投递探针同法） |

⇒ **⇒ 组合方案（我的建议）**：
- **host 段**：`Clock` 包（零新增同步）；
- **卡上段**：**每层少量 `cudaEventRecord`**（8–12 个/层），**全部在 run 末算**；
- **粒度**：**默认只按层汇总**（不按 token），避免 event 数量爆掉。

## §3 判据 + 负控（**能变红**）
### 3.1 正控（**已知会变大的量**）
| 臂 | 预期 | 变红条件 |

### 3.2 **加总闭合**（★ 必须先写清【闭合区间】= 口径三要素）
> **闭合区间 = 「从第一层开始」到「最后一层结束」之间**（**排除装载、嵌入、输出采样、teardown**）。
- **判据**：`Σ(分步) / (区间墙钟) ∈ [0.85, 1.00]`（**残差上限 15%**）。
- **依据**：探针会漏掉小项（同步空隙、launch 开销）+ event 自身开销 ⇒ **留 15%**。
  ⚠️ **若把装载/teardown 也算进去，残差会到 80%+（装载 ~10 s vs decode ~2.4 s）⇒ 那条闭合毫无意义** ⇒ **区间必须写死在结论同一行**。
### 3.3 负控（**散布上限**）
- **同配置重跑 ≥2 跑**（**弃预热跑**，见修订 11）⇒ 各步**占比**的 **MAD-σ**；
- **判据：`MAD-σ(占比) ≤ 10%`**（与修订 11 同门限，便于记忆）；**>10% ⇒ 不判**，先补跑/查环境。
- ★ **与 V4 配套**：**连续 3 轮不合格 ⇒ 转治环境，不再改判据**。

## §7 ★★ CUDA graph 口径（**外部剖面/对照的硬约束**；队长 2026-10-16 令 + 我的限定）

> **为什么单列一节**：本靶的"找杠杆"依赖外部剖面（nsys / ncu）。而本引擎**每层录一个 CUDA graph 并重放**（`engine.hpp:65 graphs = true`；注释原文 *"a token's fixed launches are recorded once, a CUDA graph a layer, and replayed"*）⇒ **关掉 graph 就是换一个被测对象**，剖面读数不再代表被验收的跑法。**与 §2 计时铁律（不得因观测改时序）同族**。

### 7.1 口径前提（**写死**）
- **一切 nsys / ncu 剖面，一律在 `graphs = true`（默认，`engine.hpp:65`）下取**。
- ★ **"关 graph"不作允许手段** —— 它改的是被测对象本身（launch 结构、每个 kernel 的发射路径、可能的重叠链），**不是观测手段的开关** ⇒ 关 graph 得到的份额**不能**用来判定"开着 graph 时的瓶颈"。
- ⇒ 若某工具/教程要求"先关 graph 才测得到 kernel"，**该工具在本靶不适用**，须换法（见 §7.2）。

### 7.2 对照手段：**nsys 的 CUDA-graph 追踪开关两档对照**（**不关 graph**）
- **手段**：nsys `--cuda-graph-trace=<值>`（2024.6.2 支持；**值名我未在本机核 `--help`** ⇒ 标 **C**，执行前请 builder 用 `nsys profile --help | grep cuda-graph` 钉死**实收值**）。
- **两档语义**：一档把 graph **展开成逐 kernel 事件**（可得 kernel 份额），一档**只记 graph 节点**（只得节点粒度）。**两档都在 `graphs=true` 下跑**（这是与"关 graph"的本质区别）。
- **判据**：**两档的 kernel 份额分布应一致**（同配置、**只换 tracer** ⇒ 被测计算没变）。
- **不一致 ⇒ 结论**：**明显不同 ⇒ 判其中一档"漏 kernel"**（这是 `KP-UNI-0015` 的**可判形式**）⇒ **取不漏的那档**，并在结论里**写明判定过程**（哪档漏、凭何判漏）。

### 7.2.1 ★ 我的限定（**必须写，否则会误判**）
> **两档必须同一种"展开语义"** —— **要么都展开成 kernel，要么都只记 graph 节点**。
> **若一档展开、一档不展开 ⇒ 份额不同是【预期的】，不构成"漏 kernel"**（比的是苹果 vs 橘子）。
> ⇒ **报"两档份额"前，先在结论同一行写明两档各自的语义**。

### 7.2.2 可判门限（**能变红**）
- **每档各 ≥2 跑、弃预热跑**（复用修订 11）；
- **比"份额中位"**（不是绝对时间 —— 见 §7.4）；
- **每项（每类 kernel 的份额）两档差 ≤3 点** ⇒ 通过；
- **>3 点** ⇒ **先查是否口径不同（§7.2.1）；口径确认相同才判"漏 kernel"**。
- ★ **负控**：两档若**连"总量级"都对不上**（如某档少了 40% 的 kernel 实例），**先怀疑其中一档根本没采到 graph 内 kernel** ⇒ 用**引擎自带机制计数**交叉印证（§7.3），**不许单方面采信 nsys**。

### 7.3 交叉印证（**判据条目**）：nsys 份额 与 引擎机制计数**要能对上故事**
引擎自带机制读数（`main.cpp:716-723`）：`CPU experts ms/token` · `route_wait ms/token` · `swapped`（次数）· `loaded in`。
| 引擎读数大 | nsys 应看到 | 方向相反 / 量级差 **>2×** 时 |
|---|---|---|
| **`CPU experts ms/token` 大** | host 侧 / CPU 段 / **同步空隙**份额大 | ⇒ 报"两者不可互证" |
| **`route_wait ms/token` 大** | GPU **空闲**、等 event 多 | 同上 |
| **`swapped` 次数大** | **拷贝 / stage 类**份额大 | 同上 |
| **`loaded in` 大** | **启动段**同量级 | 同上 |

- **判据**：**任一方向相反，或量级差 >2× ⇒ 报「两者不可互证」**，**不许单方面采信 nsys**。
- **"对不上"本身有信息**：可能是 **nsys 漏 kernel**（§7.2），**也可能**是**引擎计数口径不同**（例：`route_wait` **只量 3 处已有阻塞** `:1910/:2169/:2250` ⇒ 它**不覆盖全部等待**，对不上是**预期**而非矛盾）⇒ **先归因口径，再判采信**。

### 7.4 口径纪律重申（**写死在结论里**）
- ★ **只报份额，不报 profiler 下的绝对时间** —— 剖面本身改时序/加开销（与 §2 铁律同源）⇒ **profiler 下的 `tok/s` 与墙钟时间不可用作性能结论**，只用作**份额**。
- （此条引自队长令，**我未见 `run-nsys.cmd` 原件** ⇒ 标 **C/转述**；但与我 §2 的独立结论**同向**，故采纳。）

### 7.5 CUDA graph 对 §3.2「加总闭合」的影响（**一处要澄清**）
- **`graphs=true` 下**，"卡上段"的 kernel **在首次录制时发生、之后每 token 是 replayed** ⇒ **若按"每次 kernel 发射"计份额会错**（graph 重放不等于逐 kernel 重发）。
- ⇒ **§3.2 加总闭合的区间**仍须**排除首次录制那一跑**（**该跑入预热、弃掉**，与修订 11 一致）；**闭合只在"已录好的重放跑"上算**。
- **本项我未核**（没跑过 nsys、没数过 graph 重放的 kernel 事件数）⇒ **首轮请 builder 报"首跑 vs 重跑"的 kernel 事件数是否量级一致**；不一致 ⇒ 说明 graph 重放确实改变了事件计数，**闭合区间须再收紧**（**改动留痕**）。
