## §1 若 **§1 成立**（跨流 event/wait 有缺口）

> 缺口位置（我读码标的唯一可疑点）：**`mine && kept == r` 分支**（`engine.cpp:2371-2372` "// the buffer has it"）**不做任何 `ev_ahead_` 等待**。我此前的推理认为它**被传递性覆盖**（写它的那次调用已在 `r==0` 等过）—— 若 R0/R1 判 §1 成立，说明**那条传递性推理有洞**。

### 候选 F1-a（首选）：在 `r == kept` 分支补一次显式等待
```cpp
// engine.cpp:2371 一带（"the buffer has it" 分支）
} else if (r == kept) {
    ck(cudaStreamWaitEvent(cs(st_), (cudaEvent_t) ev_ahead_, 0), "expert staging");
}
```
- **改动面**：**1 处**（+1 行）。
- **为什么首选**：**把隐含前提变成显式依赖** —— 不再依赖"上一次调用等过"这条传递性推理（正是我标的不确定处）。
- **速度代价**：`cudaStreamWaitEvent` 在事件**已完成**时只是主机侧入队（µs 级），且**每轮最多一次** ⇒ **可忽略**；**不改变重叠语义**（只是让依赖显式）。
- **副作用 / 环风险（★ 必读）**：
  - 现有依赖是**双向**的：`up_` 等 `ev_free_`（`st_` 记于 `:2390`）、`st_` 等 `ev_ahead_`（`up_` 记于 `:2191`）。**补 F1-a 不新增环**（同向多一个消费者）。
  - ⚠️ **但必须保持语义**：`up_` 等的是**上一轮**的 `ev_free_`（`:2189` 在**本轮 `stage()` 之前**、且 `ev_free_` 是**上一轮 `card()` 末尾**记的）。**若误把它改成"等本轮的 `ev_free_`"，就形成 `up_→st_(本轮)→...→st_ 末尾记 ev_free_ → up_` 的环 ⇒ 死锁**。⇒ **改 F1-a 时不要碰 `:2189`**。
  - ⚠️ **单事件 `ev_ahead_` 的语义**：若 `up_` 在同一 `st_` 序列里被**重记两次**，等待的是"最近一次"。F1-a 会**把这条隐含前提显式化**（每次用 buffer 前都等最近一次写入）—— **这正是它的价值**。

### 候选 F1-b（更彻底，改动面中等）：`ev_ahead_` 改成**每轮一个**（小数组）+ 记录轮号
- **改动面**：~4 处（建 N 个事件、按轮记录、按轮等待、析构）。
- **收益**：彻底消除"单个事件被重记"的隐含前提；**不需要**传递性推理。
- **代价**：多 N−1 个事件对象；代码复杂一点；**速度代价仍可忽略**。
- **风险**：若轮数可变（`n_round` 由 `stage_bytes_` 推出，`engine.cpp:2251` 一带）⇒ 数组要按**最大轮数**分配（或用池）⇒ 引入新的边界条件 ⇒ **比 F1-a 更容易出错**。

### 候选 F1-c（不推荐，仅作对照）：`stage()` 一律在 `st_` 上做（即 `--stage-ahead 0` 的代码等价）
- **收益**：确定性**天然成立**（没有跨流写入该 buffer）。
- **代价**：**失去重叠** —— 正是我们在追的机制（问3）⇒ **不能作为修法**，但**是"§1 是否成立"的一个现成对照臂**（`--stage-ahead 0`）。

**⇒ §1 的小结**：**首选 F1-a（1 行）**；**唯一的真风险是误改 `:2189` 造成环**（保持"等上一轮的 ev_free_"语义即可避免）；**改动前先用 `--stage-ahead 0` 做对照臂**确认"是不是这条路径"。

## §2 若 **§2 成立**（`L.slot` 由 `cudaEventQuery` 的时序决定）

> 机制（A）：`follow():1303-1316` 对每个 `kSent` 的 swap 做 `cudaEventQuery(s.done)`；**`NotReady ⇒ continue`**（`:1306-1307`）；**只有 arrived 才 `layers_[s.il].slot[s.e] = s.slot`**（`:1309`）⇒ **"谁在卡上"是时间的函数** ⇒ 而 decode 的"谁算"由 `L.slot[e]` 硬定（verifier 证）⇒ **数值漂**。

**★ 先报一条现成的**：**我们其实已经有一个"确定性模式" = `--expert-swaps 0`**（`start_swaps` 在 `:1093` 直接 return ⇒ **不建 follower 线程、永不发布新槽**）⇒ 若 R1 判 §2 成立，**"确定性 vs 性能"的取舍已经是一个现成旋钮**（无需新码）—— 这既是**兜底**，也是**确定性的上界对照臂**。

### 候选 F2-a（发布不等时序）：`follow()` 里把 pending 换入**等它到再发布**
- 形态：`:1306` 的 `cudaEventQuery` → **`cudaEventSynchronize`**（或函数头统一同步所有 `kSent`）。
- **改动面**：1 处。
- **速度代价 ★ 真实且可能显著**：`follow()` 是**热路径**（`:2469` 每 token/窗口一次，单 token 时 `written=1`）⇒ 把"后台换入"变成"**前台等待**"（等一个专家 blob 的 H2D 拷贝，量级 ms）⇒ **会把换入省下的时间还回去**。⇒ **这是它没有用 `Synchronize` 的原因**；改成它**几乎注定变慢**。
- **风险**：中（性能回退）；且未验"到底慢多少"。

### 候选 F2-b（★ 我认为性价比最高）：**"冻结窗口"** —— 发布只发生在**调用边界**
- 形态：`follow()` 拆成两部分：**"收集已完成"**（读 `Query`，**不发布**）与 **"发布"**（在 `read()/eval()` 的**调用边界**统一把已完成的槽写进 `L.slot`）。
- **语义**：**"在一个 decode 步（一次 `eval`）内，`L.slot` 不变"** ⇒ 同一 prompt 两跑，只要**边界处**的集合相同，**整个调用内的"谁算"就相同** ⇒ 数值可复现。
- **改动面**：中（`follow()` 拆分 + 调用点对齐；`read()`/`eval()` 各一个发布点 ⇒ ~3–4 处）。
- **速度代价**：**小** —— 换入**仍在独立流上跑**（重叠保住），只是**发布粒度变粗**（本步内不生效、下一步才生效）⇒ 驻留集合的**收敛慢一点点**（最多晚一步），远小于 F2-a。
- **风险**：① "调用边界"的定义必须与 `read()/eval()` 严格对齐（否则漂到跨调用）；② 与 `plan_ahead`/`staged_` 的交互要复核（发布点变了 ⇒ `staged_il_` 的重置时机要跟着看）。
- **★ 为什么它比 (i) 好**：**它保住了"边算边搬"（重叠）**，只把"何时生效"变确定 —— 与既定机制（问3）不冲突。

### 候选 F2-c（显式确定性旗标，留作 A/B 与交付档）
- 形态：`--deterministic`（默认关）：= **不动 residency 的实现**，只**冻结**它（例如等价于 `--expert-swaps 0`，或冻结 `recent_` 衰减）。
- **改动面**：极小（若等价于现有 `--expert-swaps 0` ⇒ **0 处代码**，只写文档；否则 ~1 处）。
- **速度代价**：等于**放弃换入的收益**（本线未量化，但 `--expert-swaps 64` 是默认值 ⇒ 作者认为它有用）。
- **风险**：低；**但它是"降级"，不是"修好"** ⇒ 应标明"确定性优先档"，与 F2-b（二者兼得）并列。

### 候选 F2-d（让"谁算"不依赖驻留）—— 两条极端
| 变体 | 形态 | 速度代价 | 改动面 | 风险 |
|---|---|---|---|---|
| **d1 一律 CPU**（miss 不搬） | ≈ `--expert-swaps 0` + `--stage-ahead 0` | **最慢**（放弃把 miss 搬进来） | 0（现成旗标组合） | 低 |
| **d2 一律 GPU**（miss 都搬进来） | 需容量 ≥ 全集 | **我们 40% 容量下不可行** ⇒ 必然换页 ⇒ 反而触发 **−75%**（§VI-2 实证） | —— | **不可行** |
⇒ **d1 可作"确定性上界"对照臂；d2 判不可行**（除非先解决容量）。

## §3 若 **R1/R2 都判"不是"**（R3 ⇒ 两条都不是）：下一刀查哪

**备选嫌疑（我读码时标过、未排除）——"从非主线程向 `st_` 投递"的两处**：
1. **`moe()` 的 `launch` 由 Worker 线程执行**（`engine.cpp:2033` 把 `&launch` 作为 `meanwhile` 传进 `cpu_experts`；`cpu_experts.cpp:213` 在**任务 0** 里执行它）⇒ **该线程向 `st_` 投递**，而**主线程同时在跑 CPU 专家任务**（`Workers::run` 的调用者也参与）。我静态读到**缓冲不重叠**（`launch` 用 `g_/h_/q8_/d_/stage_`；CPU 专家用 thread_local + 读 `h_x_` + 写 `h_cpu_`）—— **但这是"读一遍"的结论**。
2. **`Behind` 线程跑 `card()`**（`:2399`；`Behind::go` 起 `std::thread`，`:247-248`）⇒ 与主线程的 `cpu_experts` 并发；同样**只有一个线程向 `st_` 投递**。
⇒ **下一刀的探针**（零 GPU 可设计，跑由 builder）：**打印每次 `launch`/`card` 的线程 id + 轮次**，看是否出现"两个线程交替向 `st_` 投递"或"同一缓冲被两线程触碰"。
