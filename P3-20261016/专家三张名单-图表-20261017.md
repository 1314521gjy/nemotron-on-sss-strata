## §2 四条逐条核（出处）

### 2.1 ① 的名单怎么定：**是 profile 前 N 名**（启动时），decode 期会动

- 排序键：`const double used = (prior_[i] + use_[i]); cands.push_back({..., used / bytes})`（`engine.cpp:1086`）。启动时 `use_=0`，Nemotron 所有专家 `bytes` 相同 ⇒ **降序 = profile 计数降序**。
- 取法：`for (cand) if (c.bytes <= room) { room -= bytes; taken.push_back(c); }`（`:1120` 一带）⇒ **前 7,388 名**（由 `arena` 大小决定；`--expert-cache auto` 实测 7,388）。
- **tie-break**：`stable_sort` 的比较器在 value 相等时按 `a.e < b.e`（专家号），**不是按层**（`:1092`）。
- **decode 期**：`follow(written)` 在 `written>0` 时按 `recent_` 换人（`:1350-1380`）；**prefill（written=0）直接 return**（`:1371`）⇒ **一次纯 prefill 期间，① 就是 profile 前 N 名，不换**。

### 2.2 ③ 是谁决定搬哪些：`group_` + `round_` + `per_round`

- 只搬**本次调用路由到、且 `L.slot[e]==nullptr`** 的专家（`count_[e]>0 && !L.slot[e]`），外加 `plan_ahead` 的预取（`L.ahead`，按 prior 排序）。
- `per_round = stage_bytes_ / (slot_down + d_bytes)`（`:2456`）：sm=48 ⇒ `48 MiB / 2.953 MiB = 16`；sm=1024 ⇒ `346`。
- 每轮拷贝量：**16 专家 = 2 × 24.77 MB**（up 段 + down 段），与 nsys 的 1,358 次 × 24.77 MB 完全吻合。
- 边界：`stage_bytes_ = max(min(stage_mib<<20, n_expert×one_expert), one_expert)`（`:1738`）⇒ 上限 `512 × 2.953 MiB = 1,512 MiB`。

### 2.3 ② 是否覆盖 ① 和 ③ 的全部来源

| 问 | 答 |
|---|---|
| 覆盖 ③ 的**全部**可能搬运源吗？ | **只有"前 K 层"**（层序前缀）。`STRATA_PIN_ARENA_GIB=59.1` ⇒ **40/40 层全覆盖**；`=8` ⇒ 只覆盖 **5/40 层**（12.5% 的搬运走直接 DMA，其余仍走 host gather）。 |
| 覆盖 ① 的来源吗？ | **源是同一批 GGUF 页**，但 ① 的拷贝发生在**启动时**（`fill_expert_cache()` 早于 `pin_expert_arena()`）⇒ 钉住对 ① 的加载**没有加速作用**，只对之后的 ③ 有效。 |
| 40 层是否包含全部 20480 个专家？ | **是**：40 MoE 层 × 512 = 20,480 = 全部 routed experts（**不含** MTP/draft 块的专家——它在 `layers_` 之外，若计入则是第 41 层、+1.4766 GiB）。 |
| ② 是"拷贝一份到内存"吗？ | **不是**。`cudaHostRegisterReadOnly` 锁的是 **mmap 的同一批文件页**；不新增 59 GiB 副本，但**这些页从此不可回收**。 |

### 2.4 ★ 账：② 总量 vs 本机空闲

| 项 | 数 | 来源 |
|---|---:|---|
| 专家源总量（40 层） | **59.06 GiB** | 40 × 1.4766 GiB；代码注释也写 "a full 40-layer pin (59.1 GiB)"（`:1004-1005`） |
| （若计入 MTP 第 41 层） | 60.54 GiB | 与队长口径 **60.5 GiB** 吻合 ⇒ **60.5 是"41 层"口径**，但 `pin_expert_arena()` 只遍历 `layers_`（实测日志 "88 layers: 40 moe"）⇒ **实际最多 59.06 GiB** |
| 本机 RAM | 总 **95.8 GiB** · **可用 76.2 GiB** · commit 可用 98.1 GiB | 本机实测（`GlobalMemoryStatusEx`，2026-10-17 19:5x） |
| 全钉 40 层后剩余 | **76.2 − 59.06 = 17.1 GiB** | 派生 |
| 稠密权重还要的页缓存 | ~6.6 GB（70.03 GB 文件 − 63.43 GB 专家） | 文件大小实测 |
| 8 GiB 安全线 | 代码规则：`ram_before < budget + 8 GiB` ⇒ **拒绝**（`engine.cpp:1006-1011`） | **合理**：全钉后仍有 17.1 GiB；扣掉稠密 ~6.2 GiB ⇒ 净余 **~10.9 GiB**，高于 8 GiB 线 |

**⇒ 结论：**
- **`STRATA_PIN_ARENA_GIB=59.1` 可行**（当前 76.2 GiB 空闲下，规则要求 ≥67.06，满足；钉后剩 17.1 GiB）。
- **8 GiB 安全线是合理的**（代码原本 16 GiB 会"free RAM 一漂移就拒绝整 40 层"，注释原文）；但**建议第一跑用 52 GiB（35 层 / 51.68 GiB，钉后剩 24.5 GiB）**做安全档，再上 59.1。
- ★ **覆盖度是重点**：8 GiB 只覆盖 5/40 层（12.5%），**要拿到"消灭 host gather"的全部收益必须 ≥59.1 GiB**；中间档按 `floor(n/1.4766)` 层线性覆盖。

## §3 未验 / 风险

1. **【未验】** 钉住后的收益：pinned 层 `stage()` 变成"每专家 2 次小 DMA"（3.1 MB/次）；nsys 显示小拷贝有固定成本 ⇒ **未必等于 host gather 的节省**，需 builder 实测。
2. **【未核】** 40 层之外若还有 MTP MoE 层（`nextn`），它未被 `pin_expert_arena()` 覆盖（`layers_` 只含 88 层主模型）。
3. **【未核】** `cudaHostRegisterReadOnly` 在 Windows + 文件映射页上的长期稳定性（失败是响亮的，但需跑久一点看）。
4. **【口径】** 队长说的 60.5 GiB ≈ 41 层；本件按代码路径按 **59.06 GiB（40 层）** 计，两者差 1.48 GiB。
5. 本件**只读、零 GPU、未改码、未碰 `E:\strata`**。
