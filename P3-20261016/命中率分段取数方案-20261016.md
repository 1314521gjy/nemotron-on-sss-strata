# 命中率分段取数方案（prefill vs decode）— 2026-10-16

- 席位：`scheduler`（引擎后端-调度）· **只读**：未改码 / 未编译 / **未跑 GPU**。**本件只出方案与时序，不执行**（GPU 归任务令的 llama 0 点）。
- 任务来源：队长——把「命中率是混合口径」从**假设**推到**可判**，并给**最小钩子**与**判据量级**。
- **★ 本件先纠-3（第三次更正，证据优先）**：我上一件 §4-4 的机制（"prefill 主导、把 66.2% 拖低"）**错了**。**真机制是：批路径的命中根本不在那个比值的分子里**（见 §2）。结论方向"66.2% 不是 prefill 数"仍成立，**机制必须换**。

## §0 结论速览

1. **★ 现成**：引擎**已经在数** prefill 段的命中——`stats_.batch_cached / batch_staged`（`engine.cpp:2367-2368`）——但**从来不打印**（全仓 grep 只有：字段定义 `engine.hpp:137`、累加 `engine.cpp:2367-2368`、多引擎合并 `:1780-1781`）。
   ⇒ **最小钩子 = 把这两个已有的数打出来**（不新增任何状态、不改语义）。
2. **两段命中率的定义（都可算）**：
   - **prefill 命中** = `batch_cached / (batch_cached + batch_staged)`（批路径，**行加权**）
   - **decode 命中** = 现有 `gpu_experts / (gpu_experts + cpu_experts)`（`main.cpp:722`）
3. **判据量级（D）**：两段之差**应达 20–45 点**（视 staged 口径，见 §4），**远超红臂 ±3 点** ⇒ **能变红**。若实测差 ≤5 点 ⇒ H0 成立（命中率与阶段无关）⇒ 推翻本方案的前提。

## §1 读码定死：哪个计数器属于哪条路径（A 级）

| 路径 | 触发条件 | 计数去向 | `file:line` |
|---|---|---|---|
| **批路径（prompt batch, MMQ）** | `batched(L,n) = mmq_ && L.mmq && n ≥ 32` | **`batch_cached`（行）+ `batch_staged`（行）** | `engine.cpp:1877` · **`:2366-2368`**（`rc = bounds[n_cached]`；`rg - rc`） |
| **批路径的 CPU 份额** | `cpu_share != 0` 且有 spare 专家 | **`cpu_experts`（+`cpu_ms`）** | `:2457-2463` |
| **非批单 token 路径 `moe()`** | `n < 32`（decode 常态） | `gpu_experts += n_cached` / `cpu_experts += n_host` | `:1958-1959` |
| **card 路径（全在卡上）** | `card = n < 32 && card_moe(n)` | `gpu_experts += m*n_used_` | `:2675` · 记录版 `:2701` |
| **主打印（`once`）** | 每次 `--tokens` 跑完 | `experts from VRAM %.1f%% = 100*gpu/(gpu+cpu)` | `main.cpp:715-722` |
| **主打印（`--serve` DONE 行）** | 每请求 | 同上，取 `now - before` 的**请求内增量** | `main.cpp:660-668` |

**⇒ 口径判定（A）**：
- **批（prefill）路径只往 `batch_cached/staged` 记**，**分子 `gpu_experts` 里没有它**；
- 而 **`cpu_experts` 有批路径的贡献**（`:2463`，CPU 份额）
- ⇒ **`experts from VRAM %` 是"混合口径"且偏向 decode**：分子≈decode 的卡上命中，分母≈decode + 批路径 CPU 份额。
- **★ 所以 prefill 段的命中率从来没有出现在任何打印里** ⇒ 想分段，**必须加一行打印**（不能靠现有输出反推）。

## §2 ★ 纠-3：撤回"prefill 主导拖低"，换成"prefill 被排除在分子外"

| | 旧机制（**作废**） | **新机制（采信，A 级读码）** |
|---|---|---|
| 主张 | 1024-token 批几乎触到全层专家 ⇒ prefill 命中低 ⇒ 把总量拉低 | prefill 的命中去向 `batch_cached/staged`，**不进** `gpu_experts` ⇒ **它压根不进那个比值** |
| 后果 | 66.2% = 低 prefill + 高 decode 的混合 | 66.2% ≈ **decode 段（含 `--serve` 的请求内 decode）**的命中；prefill 的成绩**未知** |

**这条同时解开一个旧怪象（A + 读码）**：
- **t16（`dump_t3_fix.log`，`--dump` ⇒ `rows_=1`，`engine.cpp:1591`）**：**全部 token 走非批路径** ⇒ 命中 ≈ **容量比**（40.6% 实测 vs 39.9% 容量，t16 §4）✓
- **G0'（`--prompt-batch 1024`）**：prefill 被排除 ⇒ 66.2% **不该**等于容量比 39.1% ✓（实测 66.2% ≫ 39.1%，**正说明它是 decode 的高命中**，缓存里装的是 profile 选出的**热点**专家）
- ⇒ **t16 的 40.6% 与 G0' 的 66.2% 不可直接比** —— **两者是不同阶段的口径**。（这属于 D5 同族：不标口径并排即造假数）
- **G1「命中 +9.7 点而墙钟不动」（队长提的旧怪象）**：在新机制下**有解**——那 9.7 点是 **decode 口径**的变动，而墙钟由 **prefill 的搬运/暂存（`stage_`、`batch_staged`）** 主导 ⇒ **一个不改墙钟的指标在动**。**该解释仍是 D 级假说**，须用 §3 的方案验（这正是本件存在的理由）。

## §3 分段取数方案（★只出方案，不执行）

### 方案 A（**首选**）：打印已有的两个计数器（最小钩子）
- **改动面**：**1 处、纯增加**——在 `main.cpp:716-724` 的 summary 行**之后**再加一行，或复用 `DONE` 行（`:660-668`）。
- **建议门控**（与既有 `STRATA_ROUTE_TAIL_SKIP`/`STRATA_PROBE_XQ` 同风格）：`STRATA_PHASE_STATS=1` ⇒ **默认输出逐字不变**，可一键 revert。
- **打什么**：`batch_cached` · `batch_staged` · `tokens`（三个都在 `Stats` 里，`engine.hpp:137`；`tokens` 在 `:2760/2789/2868/3013/3131` 累加）。
- **得到**：
  - `prefill_hit = batch_cached / (batch_cached + batch_staged)`（**行加权**）
  - `decode_hit = gpu_experts / (gpu_experts + cpu_experts)`（已有）
- **为什么这是最小钩子**：**零新增状态、零语义改动、零性能影响**（一次 `fprintf`）；且 `batch_cached/staged` **本来就在**，只是没人看。

### 方案 B（**零改动**，但只能拿 decode）
- 两次跑：`--max-new 0`（或 1）与 `--max-new 64`，**同一 prompt、同一冻结 profile**；用 `DONE` 行的**请求内增量** `hits/experts`（`main.cpp:664-668`）反推 **每个 decode token 的命中**。
- **拿不到 prefill**（`batch_cached/staged` 不打印）⇒ **本方案的 B 只能验证 decode 侧，不能分段**。
- 用途：**不占新窗口即可复核"66.2% 是 decode 属性"**（若每 decode token 的命中≈66% 且与 `--max-new` 无关 ⇒ 支持新机制）。

### 方案 C（★方案的**负控**，能与 A 交叉验证）
- 跑一档 **`--prompt-batch 8`**（<32 ⇒ **全部非批路径**，`engine.cpp:1622/1877`）：
  - 此时 `batch_cached/staged` **应当为 0**，而 `gpu/(gpu+cpu)` **应当回落到 ≈ 容量比**（预测 ~41–44%，见 `batch-arena-命中配比-20261016.md` §3）。
  - **若 batch=8 时 `batch_cached>0` ⇒ 方案 A 的路径归属判断错**（能变红）。
  - **若 batch=8 时命中仍 ≈66% ⇒ "批路径被排除"这条机制错**（能变红）。
- 这条**同时**给出"升/降 batch 会不会改变那个 print 出来的命中率"的直接答案。

### 时序（都不执行，供 builder/verifier 排窗口）
```
① 冻结 profile（D4）：cp <母本> p_run.txt
② 同窗口：--no-draft --lookup 0（D6）；一次一个 GPU 作业
③ 跑 A 档：--prompt-batch 1024 --tokens <固定长 prompt> --max-new 64   ⇒ 读 prefill_hit / decode_hit
④ 跑 C 档：--prompt-batch 8  同 prompt 同 max-new                    ⇒ 期望 batch_cached=0 且命中≈容量比
⑤ 红臂：③ 重复一次，两个比值各须在 ±3 点内（跑法纪律 §4）
⑥（增强，非必需）--expert-swaps 0 重跑 ③ ⇒ 把"swap 的贡献"从 decode 的 66.2% 里剖出来
```
- **不需要**改判据、不需要新 exe（若用方案 B）；方案 A 需**一次编译**（改动 1 行 + 环境变量）。

## §4 判据与负控（能变红）

**★ 先钉死口径（否则并排即造假数）**：`batch_staged` 的行**算不算命中**？两种都要报：
- **口径-1（staged = miss）**：`prefill_hit = batch_cached/(batch_cached+batch_staged)` —— 它衡量"**是否提前驻留**"。
- **口径-2（staged = hit）**：`(batch_cached+batch_staged)/(batch_cached+batch_staged) = 100%` —— 它衡量"**是否在卡上算**"（暂存的专家最终也在卡上算）。
- ⇒ **两个数一起报**，并写明"staged 是把专家**拷进 `stage_` 后在卡上算**（`engine.cpp:1668-1670`、`:2375-2443`）"。

| 假设 | 内容 | 预期（D） | 判定 |
|---|---|---|---|
| **H0** | 命中率与阶段无关 | \|prefill_hit − decode_hit\| **≤ 5 点** | ⇒ **§2 的机制被推翻**，命中率是"容量/热度"属性 |
| **H1** | 两段不同（本方案预期） | 口径-1：prefill ≈ **容量比 39–44%**，decode ≈ **60–72%** ⇒ 差 **≈20–33 点**；口径-2：prefill = **100%** ⇒ 差 **≈30–40 点** | ⇒ **§2 机制成立**；且解释 G1 怪象 |
| **红臂** | 同配置重跑 | 两个比值各 **±3 点**内 | 超出 ⇒ 该跑不合格（D7 `s_round` 口径），**不是**"两段不同" |

- **负控（该判据能变红）**：**H0 是可测的**——若两段真的差不多，方案 A 会直接显示差 ≤5 点 ⇒ **不是只会变绿**。方案 C 亦各自带红臂（见 §3）。
- **分辨率声明**：命中率是**行加权**（`bounds[]` 的行数，非专家实例数）；decode 是**专家实例**加权。⇒ **两者单位不同**，比"差几点"时**必须写明是行还是实例**（这是本判据最容易出错的地方）。

## §5 与既有纪律的关系 + 给 verifier 的提醒

- **D5 同族（必须新增一条口径律）**：**任何跨 `--prompt-batch` / 跨 `--dump` 的"命中率"比较，都是口径不一致**（prefill 的算法在两种配置下不同：batch≥32 走 `batch_*` 且**不进** `gpu/(gpu+cpu)`；batch<32 与 dump 全部进）。⇒ 建议 verifier 在判据里加：**报命中率必须同时报 `--prompt-batch` 与是否 `--dump`**。
- **D4**：本方案的 prefill/decode 两比值都依赖驻留集合 ⇒ **必须冻结 profile**（否则比值漂）。
- **D6**：一律 `--no-draft --lookup 0`（草稿会改 decode 的 token 数，直接影响 decode 侧加权）。
- **D7**：`s_round` 用 **prefill** 主读数；本方案的 prefill_hit 与 prefill 墙钟**同段**，天然成对。
- **观测掩盖律（§1）**：**方案 A 的 print 本身不是同步点**（不在 `dbg()` 路径上、不插 `cudaStreamSynchronize`）⇒ **不会改变被测行为**；但方案 C 的 `--prompt-batch 8` 会改行为（那是**故意的**，用来做负控）。

## §6 未验 / 缺口（如实列）

1. **【D】H0/H1 的预期量级是模型推算**，非实测；口径-1 的"prefill ≈ 容量比"假设"一批 1024 token 几乎触到全层专家"未独立验证（可用 `batch_staged` 与 `n_expert_` 的关系反查：若 `batch_staged/batch_cached` 的比值 → 提示触达面）。
2. **【D】`cpu_share` 在 1024-token 批下是否真会取走一部分**（决定 `cpu_experts` 里批路径的占比）未验；`cpu_share < 0` 时按 `share_[size]` 自适应（`:2465-2467`）。
3. **【D】`stats_.tokens` 的语义**未逐条核（`:2760/2789/2868/3013/3131` 五处累加，含批与单 token 两路）⇒ 若要按 token 归一，需先核分母。
4. 本件**未改码、未编译、未跑 GPU**；方案 A 的 1 行改动**归 builder**，判据归属**归 verifier**。
5. **G1 怪象的"新解释"仍是假说**（D）⇒ 只有 §3 的方案 A/C 跑完才算验。
