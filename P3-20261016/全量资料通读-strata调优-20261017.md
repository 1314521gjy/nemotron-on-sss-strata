## §2 决定 prefill 速度的因素（逐条带数据）

### 2.1 ★★ 第一因素：**host 拷贝（约 1.57 s）是主项，PCIe 被藏在它下面**

对 `prof-warmup-base`（2168.7 ms）做完整分解（全部原文数字）：

| 分项 | ms | 占 |
|---|---:|---:|
| **host gather（15535 专家从 host arena → pinned）** | **1581.2** | **72.9%** |
| PLE | 340.9 | 15.7% |
| 借槽回填（"2387 lent slots refilled"） | 208.7 | 9.6% |
| 余量（DMA/计算/其它） | 37.9 | 1.7% |

- 同样的分解在 `plemmap`：1862.8 = 1568.0 + 39.6 + 209.5 + 45.7。
- ★ **派生**：15,573 专家 × 2.047 MB（=4.55 GiB/2387 槽的平均）≈ **31.9 GB**；host 1.568 s ⇒ **20.3 GB/s 的 host 拷贝**。**PCIe 的 ~32 GB 传输被压在这 1.57 s 之下**（"DMA" 全部异步）。
- ★ 对比我们：nsys 里 H2D **3.83 s** 是墙钟主项（74%），host 填充与 DMA **交替**而非嵌套 ⇒ 我们把两者都付了。

### 2.2 ★★ 第二因素：**PLE 的 IO 方式**（prefill 的最大可调方差）

| PLE ms | 预填 tok/s（同 6792/chunk 6912） | 来源 |
|---:|---:|---|
| **2.1**（`--ple-io ram`，但启动锁 RAM 41.2 s） | **3497.8** | `…B1-resple.log:36` |
| **39.6 / 46.1**（`--ple-io mmap`） | **3646.0 / 3633.2** | `…B4/B2-plemmap.log:37` |
| 124 / 223 / 253 | 3084 / 3146 / 2815 | `prof-m6-ours` / `ilrows` / `kvA-warmup` |
| 317–388（常态） | 3084–3186 | `…A1/A2-base` |
| **741 / 926 / 1007** | **2629.9 / 85.9 / 2411.7** | `pf0.35.txt:50` · `stats-0140-nopool.txt:46` · `kvA-m4-int8.txt:50` |

- **派生**：PLE 从 ~350 → ~40 ms，prefill 从 2169 → 1863 ms（**−306 ms = +16.4%**），与 PLE 差（310 ms）**逐毫秒对上** ⇒ **这批 6792-token 跑的方差几乎全是 PLE**。
- `--ple-io ram`：PLE 2.1 ms，但 "PLE table locked in RAM in **41.2 s**"（启动代价）+ 12+ GiB 常驻；且腾出的 VRAM 多给 1,123 个专家槽（resident 10126 vs 9003）。
- `--ple-inflight 1024`（pleinflow）：PLE 327.7，与 base 持平。

### 2.3 chunk 大小与"借槽"

| chunk | borrow | 借槽回填 | 现象 | 来源 |
|---:|---:|---:|---|---|
| **256** | 815（1.55 GiB） | 71.2 ms | 220 token ⇒ 421 tok/s | `trace-tiny.log:45-50` |
| **6912** | 2387（4.55 GiB） | 208.7 ms | 6792 token 的最佳 chunk | `prof-warmup-base.txt:45-49` |
| **8192** | 2563（4.88 GiB） | 223.6 ms | 32767 token = 4 chunks ⇒ **streamed 62844 = 4× 单 chunk** | `trace-long32k.log:45-50` |
| `auto:32768` | — | — | 仅 arm 存在，**未在长 prompt 上实测**（那次 prompt 只有 6792） | `arm-exe-pref32k.json` |

- **`--prefill auto` 的规则（原文）**："the largest chunk up to 8192 whose buffers the expert cache can lend; auto:16384 / auto:32768 (or STRATA_PREFILL_AUTO_MAX) allow bigger ones"（`abba-pf1.00.txt:141-143`）。
- **借槽不占额外 VRAM（原文链条）**：`expert cache 11428 slots` → `prompt path borrows 2387 cache slots (4.55 GiB)` → prefill → `2387 lent slots refilled in 208.7 ms`。借的是**已有 cache 的槽**，用完回填。
- ★ **派生（对我们最重要）**：4 个 8192-chunk 把同一批 ~15.5K 专家搬了 **4 遍**（62844）。若能用 32768 的 chunk，同样 prompt 只搬 **1 遍** ⇒ **搬运量 4× 下降**。这就是"chunk 摊薄"在他们自己数据里的直接证据。

### 2.6 `--pcie-frac`（**decode 侧**的旋钮，不是 prefill 的）

- 效果行原文：`pcie experts  0.16 distinct experts per layer read over PCIe (share 90/256 of the misses)` @0.35 · `0.37 … 128/256` @0.50 · `0.49 … 166/256` @0.65 · `1.00 … 205/256` @0.80 · `1.68 … 256/256` @1.00。

## §5 坑 / 悬崖（原文）

1. **no-token-graph / no-pool**：`89.3 / 85.9 tok/s`（resident **0**、streamed **24576**）⇒ **一掉就是 30×**。来源 `stats-0140-notokengraph.txt:47`、`stats-0140-nopool.txt:46`。
2. **PLE 波动**：同一配置 PLE 253–1007 ms（4×）⇒ prefill 2.4–3.2k。**需要多次取中位，不能单跑定案**（ABBA 文件存在的原因）。
3. **`--ple-io ram` 的 41.2 s 启动**：为 2 ms 的 PLE 付 41 s 冷启动，不值得做交互；适合长驻服务。
4. **大页被拒**：`large pages refused … using 4 KB pages`（37 处）——本机 TLB 走 4 KB，**host gather 的 1.57 s 可能受此影响**（未量化）。
5. **AVX-512 缺失**：`this CPU has no AVX-512: the expert kernels run on AVX-2`（40 处）——CPU 专家/池的上限。
6. **cache refused**：`0 admitted, 6283 refused, cache 100.0000% full`（decode 统计）——cache 满时的拒绝计数，不是错误。
7. **cuBLAS grouped GEMM 试过丢掉**：`faster in isolation, slower inside the engine: 770 vs 790`（`bench-summary.txt` "Tried and dropped"）。
8. **MTP 在 chat C=1 反而慢**：`MTP slower than plain at C=1 on chat (82 vs 98.5 tok/s)`（设计件 `:357`）。
9. **`--prefill auto:32768` 不会在小 prompt 上生效**：chunk = min(auto, prompt)，只有 6792 token 时仍是 6912（§1）。
