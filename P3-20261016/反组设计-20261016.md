- 席位：`scheduler`（引擎后端-调度）· **只读**：未改码 / 未编译 / **未跑 GPU**。
- 任务来源：队长（上一版反组 `--expert-cache 11000` **本引擎无此旗标**；改 `--vram-reserve-mib 256` 后**反而 prefill +7.5%** ⇒ 不是反组）。要四件：① 读码定死 `--vram-reserve-mib` 如何决定 arena + 核账；② 真反组候选与预期；③ 附则纪律（反组自证）；④ `--no-gpu-experts` 能否当反组。

## §1 读码定死：`--vram-reserve-mib` 如何决定 arena（A 级，当前树实读）

### §1.1 三个作用点（不是只有一个）

| # | 位置 | `file:line` | 机制 |
|---|---|---|---|
| ① | **加载期 arena 上界** | `engine.cpp:1001-1003` + **`:1043`** | `reserve_mib_ = max(opt, 256)`（显式）或 `default_reserve_mib()`；`reserve = reserve_mib_<<20`；**`arena = min({all, free_b − reserve, …})`** ⇒ **reserve 直接从 free_b 里扣** |
| ② | **运行期保底** | `engine.cpp:1169` | `keep = (显式 reserve 或 ram_tight) ? reserve_mib_ : max(reserve_mib_/2,128)` ⇒ **显式大 reserve ⇒ 运行期"要留这么多空"** ⇒ `free < keep/2` 时 `shrink_cache()`（`:1170-1173`） |
| ③ | **KV 扩张时的裁切** | `engine.cpp:553-556` | `quarter = reserve/4`；`free_b < more + quarter` ⇒ `shrink_cache(cut)` ⇒ **reserve 越大，KV 增长时越早裁专家缓存** |

⇒ **结论**：显式调大 reserve，**不但缩小初始 arena（①），还让运行期更早/更多地砍缓存（②③）**——三处**同向**，方向明确（都朝"缓存更小"）。

### §1.2 核账（A 级自洽）

- 加载期线性：**Δarena = −Δreserve**（`:1043` 的 `min` 在 `free_b − reserve` 这一项上直接生效）。
- 每对专家字节 = **3,096,576 B = 3.0966 MB**（up 1,548,288 + down 1,548,288；t16 实测，A）。
- 专家池满额需求 = 20,480 × 3.0966 MB ≈ **59.06 GiB**。
- **差分律（线性上界）**：**+1000 MiB reserve ⇒ −1000 MiB arena ⇒ −338 对 ⇒ −1.65%（of 20480）**。
- 队长实测核账：`2500 → 256` 多让出 **2244 MiB = 2.19 GiB ≈ 2.2 GB** ✅（与队长一致）。

### §1.3 ★ 但"每 MiB 换点数"实测只有线性的 ≈1/4（**D 级，待验**）

> ### ⚠️ 更正（2026-10-16 晚，本席加；原文保留不改）
> **本节结论作废**：这里的"线性模型"取的是**覆盖曲线斜率**（≈5.2 点/1000 MiB），**口径错**。
> 该比的是**容量比**：`+1000 MiB / 59.06 GiB 的专家池 = 1.65 点/1000 MiB`（`Δarena=Δreserve`、3.0966 MB/对、20480 对）。
> 实测 1.29 点/1000 MiB ÷ 1.65 = **0.78，不是 0.25** ⇒ **线性容量模型基本成立，不存在"1/4 衰减"**。
> 另一处前提也错：**G0' 的 arena 实测是 23.1 GiB / 8010 对**（`g0r_1.log:3`，A），**不是 6–7 GiB**。
> 详见 **`batch-arena-命中配比-20261016.md` §2、§4-4**（本更正即该件纠-2）。

把 §2 覆盖曲线的斜率（≈**15.5 命中点 / 1000 对**）乘差分律（0.338 对/MiB）⇒ **线性预测 ≈ 5.2 点/1000 MiB**。
但队长实测 `2500 → 256`（−2244 MiB）只换来 **+2.9 点** ⇒ **≈ 1.29 点/1000 MiB** ⇒ **实测斜率约为线性预测的 1/4**。

**含义 / 候选因（未定，写"可能"）**：
1. 让出的 MiB **没有全进专家 arena** —— `--prompt-batch 1024` 的 scratch / KV / 其它分配会吃掉一部分（与 t16 §VI-1 候选因 (a) 同源）；
2. `2500 → 256` 这对**可能**叠了 D4（profile 跨运行耦合）造成的读数漂 —— 若该对**未冻结 profile**，2.9 点里有多少是 reserve、多少是 profile，**分不开**；
3. 命中率曲线本身**上凸**（越往高越平，见 §2：2048→4096 只 +4.7 点）⇒ 边际点/对在变小 ⇒ 折半效应。

⇒ 因此**容量臂的预期只能给"区间"**，**必须靠自证判"够不够反"**（§4）。这也正是 §1.3 存在的理由：**别再用线性模型拍脑袋定 reserve 数值**。

## §4 附则纪律（队长第 ③ 件）：**反组必须自证它是反组**

> **规则**：反组跑完后，**先看机制读数是否朝预期大幅变**；**没变 / 反向 / 变化小到落在噪声内 ⇒ 判"该臂不是反组"，换臂重来**（**不是**判"整轮作废"，也**不是**判"结论成立"）。

**自证门限（必须能变红）**：
1. **主门限（机制）**：`experts from VRAM %` **相对 `G0'`(66.2%) 掉 ≥ 10 点**（⇒ ≤ 56.2%）。
   - 红臂（负控自检）：**同配置重复一次**，两次命中率差 **> 3 点** ⇒ 判"读数不可信"，**加跑取中位**，**别**把漂当"掉"。
2. **辅门限（机制，方向）**：`CPU experts ms/token` **显著上升**（D7 口径：判"显著" = `> max(2·s_round, 5%)`）。
3. **墙钟**：**prefill tok/s**（主读数，D7）相对 `G0'` 掉 **≥ 5%**。
   - ⚠️ **decode 不作主读数**（D7：decode 只 ~45 token ≈ 3 s，`s_round` 实测 70.6%）。
4. **任一不满足 ⇒ 该臂不是反组 ⇒ 换更硬的一档**（不是作废）。

**配合既有纪律（改不了本件的口径，交叉引用）**：
- **D4（冻结 profile）**：每跑前 `cp <母本> p_run.txt`，跑后 `--expert-profile p_run.txt` ⇒ **否则命中率变化分不清是 reserve 还是 profile 泄漏**（§1.3 候选因 2）。
- **D5**：读数行必带 `N tokens (length|stop)`；长度不等 ⇒ 该对退回不比较。
- **D6**：反组与 `G0'` 比**一律** `--no-draft --lookup 0`（与正确性跑法一致），否则草稿接受率逐跑变，**2× 漂**盖过 reserve 效应。
- **D7**：每跑前**预热跑丢弃**；`s_round` 由 **prefill** 重算；`s_round > 10%` ⇒ **判环境不合格，停手不出结论**。
- **N.1**：窗口证据（`tasklist` / `nvidia-smi` 两行）**原样写进 log 头**。

## §5 ★ `--no-gpu-experts` 能否当反组？（队长第 ④ 件）

**能，且是最硬的主反组 —— 但它是"另一类"，不能与容量臂混用。**

**读码（A 级）**：
- `if (!opt_.gpu_experts || n_moe_ == 0) return;`（`engine.cpp:995`）⇒ **`--no-gpu-experts` ⇒ 根本不给专家建 arena**（连 `:1043` 都不走）⇒ 整套"卡上专家缓存"机制 **整体关闭**。
- 同时 `:1114` 同款早退；`:1622` `L.mmq` 里 `opt_.gpu_experts` 为假 ⇒ **mmq 批路径也关**。
- `main.cpp:836` `a == "--no-gpu-experts"` 置 `o.gpu_experts = false`（接线确实存在，A）。

**判定**：
| 维度 | 结论 |
|---|---|
| **方向** | ✅ **必然反向**：`experts from VRAM %` **按构造 = 0%**；`swapped into VRAM` = 0；`CPU experts ms/token` **必然大涨** ⇒ **自证自动通过** |
| **能否作"容量梯度反组"** | ❌ **不能** —— 它**不是"缓存变小"，是"缓存没了 + 数值路径整个换了"** |
| **数值路径** | ⚠️ **会变**：专家全走 CPU = ggml **Q8_K**（`cpu_experts.cpp:174`），而卡上走 **Q8_1**（`engine.cpp:1889`）⇒ **与 `G0'` 不是同一数值路径** ⇒ **禁用它与 `G0'` 比"正确性/逐位等价"**（只能比**速度方向**） |
| **归类** | **第二类反组 / 极端臂**（"整套 GPU 专家特性 OFF"）——比"缓存更小"**是更强的 claim** |

⇒ **用法**：`--no-gpu-experts` 当**主反组**（证明"卡上专家这条机制确实在贡献速度"）；**容量梯度**另用 **R2 的 reserve 臂**（同数值路径、只压容量）。两臂**分别自证**，**别写成同一组**。

## §6 风险与红线

- **R1｜红线：常规跑法要求 `--vram-reserve-mib 2500`**；反组用大值 = **独占窗口下的故意配置** ⇒ **必须写进 log 头**（N.1），并明确"本跑不是常规基线"。
- **R2｜★ 静默退化（危险）**：`if (free_b <= reserve) return;`（`engine.cpp:1004`）⇒ **reserve 若超过加载时可用的 `free_b`，函数直接返回、`exp_` 为空 ⇒ 引擎静默退化成"专家全 CPU"**（形似 `--no-gpu-experts`，**但你以为在测"容量"**）。⇒ `--vram-reserve-mib 20000` 极可能踩此坑。**自证门限恰好能抓它**：命中率→0 且 `CPU ms` 暴涨 ⇒ **判"退化"而非"容量反组"** ⇒ 换更小 reserve。**跑前应先自证能加载**（log 头看 arena/命中行），**若挂 ⇒ 用较小 reserve**。
- **R3｜一次一个 GPU 作业**（跑前核 exe sha、清 `.obj`）；**窗口归队长统一分配**（N.2：check 不根治 TOCTOU）。
- **R4｜`--vram-reserve-mib` 的效果跨机器/跨 ctx 会变**（§1.3 衰减与 scratch 占比有关）⇒ **换 `--prompt-batch` / `max_context` 就要重算预期**。
