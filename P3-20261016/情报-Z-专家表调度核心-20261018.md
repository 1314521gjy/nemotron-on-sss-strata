- **两版源码**：T = `E:\strata`（老师侧 0.1.40.2，`dec-pool2.txt:42`）；U = `upstream-0.1.44.1`（v0.1.44.1）；bare clone `C:\sp3\upstream-hist\strata.git` / `polystrata.git`；全量 clone `E:\strata\.git`。

## §3 `--reorder` 到底是什么

### 3.1 它只在**工具层**，引擎没有这个旗标

- **U 树** `tools/make_profile.py`：有 `--reorder`（参数 `:98-100`）；实现 `rank_profile()`（`:86-112`）；文首 docstring 自述："默认顺序 = base 的全部 → trace 频次降序 → 补齐；**base 只被追加、从不被重排，而 shipped base 已排满 24,576 ⇒ 普通 `--base` 下 trace 是 no-op**；`--reorder` 让 trace 对先排、base 再补；`--no-base` 丢掉 base"（`:8-13`）。
- **T 树（0.1.40.2，老师实际跑的版本）`tools/make_profile.py` 没有 `--reorder`**（110 行版本：参数只有 `--base/--no-base/--out/--n-layer/--n-expert`；`git log --all -- tools/make_profile.py` 显示 `90d32517` 在 2026-10-03 才加，晚于 0.1.40.2）。
- **引擎侧没有 `--reorder`**：两树的 `reorder` 命中都是无关 kernel（T：`gr.cu`/`session.cpp`/`dequant_bf16_test.cpp`；U：同 + `nvfp4_avx2.cpp`/`sampler_parity.cpp`/`elementwise.hpp`），**没有表重排的运行时开关**。

### 3.2 commit `90d32517`（2026-10-03）的 diff 说明它修的是什么

```
tools/make_profile.py builds the ranking as the base's order, then the trace's pairs, then the fill.
The base is only appended to, so --base can never move a pair the base already ranks - and the
shipped data/expert-profile.bin ranks all 24,576 pairs, which makes a trace a no-op:
    wrote ...: 24576 ranked pairs (24576 from the base, 0 from the traces, ...)
Add --reorder: rank the trace's pairs first (most frequent first), then let the base fill the rest,
then the fill.  The default is unchanged. ... On this host's coding trace the same command now puts
5,808 trace pairs first.
```
diff 内容：新增 `rank_profile()`，把排序拆成 `trace_pairs → base → fill` 三段；`--no-base`/`--reorder` 都让 trace 先排（U `make_profile.py:92-105`）。**这证明 `--reorder` 原本的意图就是"让工作负载的 trace 决定 rank 前缀"**，而之前因为 base 完整覆盖而静默失效。

### 3.3 它重排的是"槽位/准入顺序"，不是"派发/获取顺序"

因为引擎对表的消费是**按 rank 前缀取前 `slots` 个**（C4/C6）：
- `--reorder` 改变 **rank 前缀集合** ⇒ **谁驻留**（slot 集合）+ **`open_sized` 打包顺序**（C5）+ **U 的成本模型/peer 填充读到的前缀**（U1/U2）+ **`--expert-cache N` 截断语义**（C3）。
- 它**不改变**：decode 的 verify/CPU pool 派发顺序（routing 顺序）、prefill 流式顺序（层/expert id 序）、门铃/ring 顺序、adaptive 候选（usage 计数）。

与 `--dump-routing` 的配合（U `make_profile.py:18-21` 文首）：`--dump-routing FILE` 写出一次运行的 `(layer, k, k 个 expert id, k 个 weights)` 记录；`read_trace()`（`:47-58`）按 `(layer, expert)` 累计频次；`rank_profile()` 按频次降序。**老师 0.1.40.2 的 run 早于 `--reorder`，没有用它**（`dec_pool2:19` 用的就是 shipped `data/expert-profile.bin`）。

## §6 结论表 + 缺哪 3 个机制（按 收益×改动量 排序）

| 表的消费点 | 老师怎么用 | 我们怎么用 | 差距 | 若补齐预计收益 |
|---|---|---|---|---|
| 驻留资格（前缀） | 前 `slots` 个 rank = GPU 可算；非表内 decode 永 CPU miss（C6） | 全局 top-N 按 counts（P2） | 机制等价，**表质量差**（prefill 污染+缺 blk.88） | 命中 43→60+（R43/R44 已证） |
| 容量/打包 | `min(slots,profile.size())` cap；native 按 pair 大小 `open_sized`（C4/C5） | 按空闲 VRAM 定槽、无 per-pair 打包（统一 2.95 MB） | 我们 GGUF 专家等大 ⇒ 打包收益≈0；cap 无影响 | ≈0（本模型） |
| **prefill 借槽** | 表存在才借；借 **cache 尾部低 rank** 给 prompt 缓冲；chunk auto 6912；读完 refill（C7） | **无**（独立 staging/ring2） | **缺整个机制** | 释放 ~1.8 GB 给 cache（+~600 槽 ≈ +2-3 命中点）+ prefill chunk/延迟；**不依赖命中率** |
| 多卡放置预测 | U1：rank 前缀当覆盖曲线做 layer-split auto / peer 条带 | 单卡无 | N/A（单卡不需要；U1 自己也有 94.9% vs 69.2% 的预测误差） | 仅多卡 |

### 缺的 3 个机制（按 预期收益 × 改动量 排序）

1. **表→prefill 借槽 + `--prefill auto`**（T 树；`generate.cpp:1619/2455-2492/2511-2535/3112-3152/3484-3559`）
   - 为什么：**不依赖命中率**的"表驱动调度"——用"最低 rank 的驻留槽"换 prompt 缓冲，读完 refill；顺带把 `--prefill auto` 的 chunk 从 2048 拉到 6912（老师日志 `chunk auto 6912`、`prefill 2265.6 ms / 2997.9 tok/s`、`refill 213 ms`）。
   - 我们的收益估算：poly 现用 ~2 GiB staging + 1.5 GiB ring2 自管；借槽可把其中一部分转为 cache（+~600 槽 ≈ +2-3 命中点），并可能缩 prompt 路径缓冲；**改动中-大**（poly prefill stage/ring 与 cache 地址不共享，需借出/relayout/refill 契约），**风险中**（refill 正确性、prompt 与 decode 互斥窗口）。
2. **表→学习闭环（U3 `rank_learned_profile` 语义）**（`expert_cache.cpp:141-168/170-207`；`generate.cpp:10364-10367`）
   - 为什么：把"实际驻留 + 实际热度"写成新 profile（resident→heat→prior-rank），**下次启动即用**；老师 r2prof A/B（`abba-r2profile.ps1`）与 `8cb26e6`（+5..64% decode，均值 +21%）证明表质量就是解码速度。
   - 我们：已有 `save_profile`（每 10 s + 退出）但**混了 prefill 计数**、无 rank 语义；**改动小**（profile 写出前按"decode-only 计数 + resident 优先"排序即可），**收益**：命中 43→60+（R43/R44 已证自适应可回捞 17–19 点；持久化后从第一个 token 就生效）。
3. **表→离线 trace/策略回放**（`--dump-routing` + `bench_eviction`/`profile_oracle`；commit `49c50f4`）
   - 为什么：`--dump-routing` 记录每层每位置 routed ids；用 trace 回放可以**零 GPU** 比较"槽数/每层配额/淘汰策略/fill 顺序"的命中率（老师工具：fill-only/LRU/LFU-decay/oracle）。我们的 p_master 已是计数版，但没有"回放任意策略"的能力。
   - 改动小-中（加一个 dump-routing 与一个小回放脚本），**收益**：把"一跑一猜"变成"离线选参数"，对 decode 是间接但确定的收益。

**特别标出（用户要的"不需要高命中率也能提速"的机制）**：
- **prefill 借槽**：与 decode 命中率无关，纯 VRAM 调度（老师 refill 213 ms、chunk 6912、2997 tok/s prefill）。**这是表作为"调度核心"的真正实例**。
- **RouterLookahead（U 树，不是表）**：用 **下一层 router 权重** 提前 `warm` 文件页、`ForesightSwap::predict` 预拷 VRAM 槽（`expert_source.hpp:241-246`、`expert_source.cpp:2220-2458`、`foresight_swap.hpp:1-107`），**提前量在"当前层计算时"**；它不需要命中率高——它把 miss 的等待藏到计算后面。**这才是"预取调度"核心，且我们完全没有**（poly `lookahead/foresight` 0 命中）。
