## 0c. RAM 判决（reviewer §9 并入）

- **闭合，余 ~20.8 GB**：up 31.71 + sidecar 31.71 + token 0.30 + housekeeping ~1.5 + OS ~10 ≈ **75.2 GB**；pin 预算 29.53+29.53+8 = **67.06 GiB ≤ 96** ✓。
- **冷页风险**：up 靠**保留 map_pages 的 up span** 预热；**sidecar 必须 touch/prefault**（反例：R57-E1 不 touch ⇒ decode 1.59 tok/s、`router_wait=104.9 ms/token`）。⇒ **D4 的 load 末尾 fault-in 是硬要求**，且 fault-in 后 avail 降幅 <28 GiB ⇒ 报错退出（F1 教训）。
- **现状 95.13 GB**（up+down+sidecar）⇒ 必须 **跳 down（D6a :2312）** 且 **pin 只 up（D4）** 才闭合。

## 1. 改动清单（D1–D9）

- MMQ 的 down 路径 = `Mmq::mul` → `mul_mat_q_case<GGML_TYPE_IQ4_NL>` → 每 tile 分三步：
  `ggml_cuda_mmq_load_tiles_iq4_nl`（把**行主序**权重块解码进 shared memory）→ `vec_dot_q8_0_q8_1_dp4a`（**算术主体**）→ `write_back_dp4a`。
- loader 读的是 `bxi = x + kbx0 + i*stride + kbx` 的 `bxi->qs`（16 B）与 `bxi->d`，即**单个行主序块**，无跨块/跨行状态 ⇒ **只要给它的每块 16 B + fp16 d 与原字节相同，下游算术逐位不变**（R58 已证同机制在 mmvq 上成立；inverse(T)==GGUF 已证 2 专家全字节 0 差）。
- **但"T 原生 MMQ loader"不划算**：一个行主序 16 B 块在 T 里散在 **32 个神经元**的 512 B 块里（每个只给 1 nibble）⇒ 每块要 32 次跨 cache-line gather。全 prefill 每次约 14.5K 专家 ⇒ gather 流量 ~160 GB/prompt（正常 ~22 GB），prefill 会崩。
- **正确做法（方案 P）**：MMQ **一行不改**；prefill staging 时把 T 块**在 GPU 上反变换成 row-major**（纯字节置换 kernel，~40–60 行），MMQ 读到的字节与今天**完全一致** ⇒ **位精确由构造保证**。代价：每专家 1.55 MB 的 GPU 内置换流量，~14.5K 专家/次 = **22 GB/prompt**；按 4080S 显存带宽 ~700 GB/s ⇒ **~30 ms/prompt**（prefill 3.5 s 的 <1%）。VRAM：需要一个与 staging down 区同大的临时区（或原地分块置换；见 D2b）。

## 2. 与 R57b 立项的差异（必须写进交接）

1. **MMQ T 原生内核不做**（原 D2）：改为 **GPU 反变换 + MMQ 原样**。理由：T 原生 loader 是 32-neuron gather，每次 prompt ~160 GB 额外流量（8×），会把 prefill 收益吃光；反变换只 22 GB（~30 ms）。
2. **D0 时序切换不需要**：Stage D 下 GGUF row-major down **从加载起就不读**，sidecar 在 load 时 pin 即可（R57 已证 `cudaHostRegister` 不 prefault ⇒ **load 后必须显式 fault-in 一遍 sidecar**，放在 load 末尾、fill 之前，一次性 27 s 左右——这是 Stage D 的固定启动成本，需在交接件写明）。
3. **decode 位精确**：R58 已 PASS（GPU mmvq T 内核 == row 内核逐位）；**prefill 位精确**：由 D2a 的 byte-parity 保证（MMQ 输入字节相同 ⇒ 下游全同）。
4. **RAM**：up pin 29.53 + sidecar pin 29.53 = 59.06 GiB（与今天相同），GGUF down 不再驻留/不再读 ⇒ 96 GB 闭合。
