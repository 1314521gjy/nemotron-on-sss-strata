## §1 A. device 侧路由 + 门铃 + 整图

### 1.1 老师怎么做（file:line）

**真实编排（一轮 verify window，U 树代码 + T 树日志）**：
1. **起手**：`pre[0]` 先发（`core/session.cpp:658` 注释 "pre[0] IS LAUNCHED BEFORE THE LOOP SO EVERY ITERATION HAS THE SAME SHAPE"；`:672-681` launch）。
2. **每层 poll 环**：host 读 **mapped pinned 的 volatile `h_seq`**，每轮**必须**调一次 `cudaEventQuery(probe)`（`:686-713` 注释："THE DRIVER CALL IS NOW A FALLBACK, NOT THE MECHANISM"、"the device's write to mapped pinned memory becomes host-visible only when the driver is entered"）；看到 ring 或图结束才退出；`rings_mid_graph` 计数（`:716`）；`待ring` 计时进 `ms_to_ring`（`:717-719`）。
3. **GPU 半段先发**：ring 后立刻 `hits(Launch)`（`:727-730` 注释 "THE GPU'S HALF GOES FIRST, SO IT RUNS WHILE THE CPU DOES ITS HALF"，只 enqueue 不 wait）。
4. **CPU pool**：host 用 doorbell 发布的 `h_x_f/h_ids/h_weights` 跑 CPU 专家（`:732-733`）。
5. **combine/copy**：CPU 结果拷回 pinned→device（`:649-654` 起；`:735-740` 注释 "COMBINED BY LAYER l, NOT BY l+1"）。
6. **下一层**：发 `post[l]`、`pre[l+1]`；一层两张图（T 树 `core/session.cpp:186-187`："TWO GRAPHS PER LAYER, SPLIT AT THE ROUTER. `pre` ends with the doorbell rung; the host then runs the CPU pool… `post` combines those experts"）。
7. **门铃本身**：`core/layer.cpp:370-385`：`moe_route()` 在捕获序列里把 `x/ids/weights` 写进 mapped pinned，**最后写 ring**（"THE RING IS LAST, so a host that sees it knows every byte above is in place"）。
8. **device 表 vs host 表**：device plan 只在**整层专家都驻留**的 token graph 里"decided on the device"（T `generate.cpp:2358/2391/2401`：`token graph hit path: 11428 resident experts, decided on the device`）；verify window 的 GPU/CPU 分配仍由 **host 生成 plan 并写 mapped**（`expert_source.cpp:284-367`），GPU 图内 `wait_flag_ge(flagA/flagB/flag)` 等 plan/PCIe/CPU rows（`verify.cpp:558/587/595`）。`res_patch`/`d_res` 只在异步 tier（`STRATA_ADAPT_NOWAIT=1`/`LAG>1`）时才需要补丁（commit `3f2db5e2`；`generate.cpp:1373-1395` 定义 `adapt_nowait/adapt_lag/adapt_overlap`；`:8726/8745/8811-8815` pending/apply/gate）。
9. **账本**：`generate.cpp:13931-13940` 打印 `wait for rings / pool / host / commit ms/round` + CPU experts distinct/routed —— 老师 24.31 ms/round 里的 12.378 就是第 2 步的等环时间。

**哪些 device、哪些回 host**：
- **device**：router GEMM + top-k；doorbell 写 mapped（ring 最后）；GPU 半段（常驻/PCIe 专家）；combine；`pre[l+1]`；整驻留 token graph 时的专家选择。
- **host**：poll 环（每层一次 driver entry）；CPU pool（miss 专家）；把 CPU 结果写回 device；建/发布 plan（非整驻留时）；发 post/pre；commit/采样。
- **无法去掉的 host 往返**：CPU pool 需要路由结果（ids/权重）→ 必须等环；combine 需要 CPU 结果 → 必须回 host。**老师也不是"一张图到底"**，而是"每层两张图 + host 环"。

### 1.2 我们现在的做法

- **host 路由**：`NemotronHMoe::route()`（`nemotronhmoe.cpp:409-462`）：每 token 每层 512 次 sigmoid + bias + 选 top-22（n_used_=22）+ 归一化——由 `moe()` 在 host 调用（decode 的 `moe_router(L,1)`；draft 的 `moe_router(L,1)` `engine.cpp:4678`）。
- **GPU 只做 router GEMM**：`Engine::moe_router`（`engine.cpp:2867-2880`）里 `router_scores()`（GPU `lin`）→ latent_down（GPU）→ quantize → `copy2(rl_, h_rl_, …)` **D2H 拷 512 floats/层**；随后 `cudaEventSynchronize(ev_)` 等 router（decode `:2897`；prefill `moe_rows` 同类 `:3469`）。R49 打印 `router wait 7.2–9.1 ms/token`（**含 prefill 的 route_wait 污染+分母含 prompt**，decode-only 真值未验；lead 给的 7.7 ms/轮 是 decode-only 口径，B）。
- **逐层 host launch**：MoE 段 **不在图里**——`moe()` 的 cached 专家用 `native_mmvq_slots`（`engine.cpp:3082/3093/3123` 等 host 发射），每层 ~15 次发射；只有 per-layer `heads`/`shared`/`tail` 三张图（`engine.cpp:4018-4028`）。
- **device plan 不存在**：`moe_card()` 要求门控专家，非门控直接 `return false`（`engine.cpp:3275`）；`d_slots_`（`engine.cpp:2556`）在 decode 不用。
- 现状：命中 41.2–57%（R49/R34），miss 516.9/token（R49），**永远不全驻留**。

### 1.3 差异的后果

1. **host 每层做 route+plan+launch**（40 层/token）⇒ host 在 CPU 池之外还有固定开销；teacher 的 top-k 在 device 上算完直接写 mapped，host 只读结果。
2. **我们每层一次 D2H（512 floats）+ event sync**；teacher 用 mapped doorbell（device 直接写 host 可见内存，ring 立即读），**少一次 copy 调用**。
3. **我们 MoE 段掉出图**（每层十几到几十个 host 发射）；teacher 的 GPU 半段在 **post 图**里一次 launch。
4. **但**：teacher 的"整图/device plan"只对**全驻留**成立；我们 41–57% 命中永远走 host plan + CPU pool，**这条最"成熟"的骨架对我们的现实 regime 不适用**。teacher 自己在 verify window 里也要 host 建 plan（`expert_source.cpp:284-367`），所以"把路由搬上卡 + 一张图"最多只能复制它的**非整驻留形态**（device top-k + doorbell + 两层图），不能拿到 token graph 的整图红利。

### 1.4 要不要模仿 / 怎么改 / 预期 / 风险

- **要不要模仿：有条件——只模仿"device top-k + mapped doorbell"一小步；不模仿 device plan/整图（我们 regime 用不上）。**
- **怎么改（范围）**：
  1. 新增一个 fuse 路由 kernel：sigmoid+bias+top-22+归一化，**直接写 mapped pinned `h_rl_/h_ids_/h_w_`**（或写 device 后一次 copy 到 mapped），替代 `copy2(rl_,h_rl_)` + host `route()`；
  2. host 只读 mapped 的 ids/权重（一次 `cudaEventSynchronize(ev_)` 保留，语义同 ring）；
  3. 可选：把 GPU 半段（cached 专家）与 `moe_shared` 一起 capture 进 `post` 图（`engine.cpp:4018-4028` 的 `replayed` 机制已有，扩到 `moe()` 的 cached 分支，需 non-gated `native_mmvq_ids` 支持——现在的 `moe_card` 门控限制要放宽）；
  4. **不动** `up_↔st_` 四处事件配对（红线）；不动 prefill 的 staging/ring。
- **预期（重估）**：省 host 0.44M sigmoid+top-22 ≈ 0.9–1.8 ms/token（D，按 5–10 ns/次），省 40 次 D2H+event 的一部分（~0.2–0.6 ms）⇒ **+1~4%（D）**；把 cached 专家图化再加 ~1–3 ms/token ⇒ 总共 **+3~7%（D）**，达不到老师水平（老师瓶颈是 24.3 ms 的 pool/ring 编排，不是 host 路由）。**此前 +8~12% 的估计偏高**。
- **风险**：高——① `up_↔st_` 四事件配对红线（一碰就回滚）；② device top-k 必须与 host `route()` 逐位一致（sigmoid/bias/tie-break/normalize 顺序），否则 ids 漂；③ 图捕获与 staging 缓冲动态地址、`at_/tok_` 每 token 变化（现有 head/shared/tail 图已经踩过）；④ 调试面大。**不是今天。**

**如果只能选一条先做：A 不选**——它最贵、风险最高，且我们 41–57% 命中使它的"整图/device plan"主体不可用，只剩 +3~7% 的边缘收益。

## §2 B. resident 补集 + 交换架构（及其 RAM 推演验证）

### 2.1 老师怎么做（file:line）

- **resident RAM 模式**：把"GPU cache 装不下的专家"（**complement**）从 `experts.bin` 拷进一块**紧凑 pinned RAM 副本**一次，此后 decode/prompt 不再读文件（`generate.cpp:6960-6966`："the experts the GPU cache does not hold are copied from experts.bin into RAM once, so no decode or prompt step reads the file"）；`--resident-budget-gib` 限 RAM（`:6960-6973`、`:6967-6968` "exchanges experts between the GPU caches and the resident RAM copy only"）。
- **交换**：adaptive swap 把 RAM 副本里的 `in` 传进 VRAM 里 `out` 的槽；旧路径把 `out` 的字节 **memcpy 回 `in` 原来的 RAM 位置**（`docs/DETAILS.md:168-169`："the RAM copy keeps holding exactly what the GPU does not"）；`EXCHANGE_ROTATE` 把这次 host copy 变成"缓冲所有权轮转"（`docs/EXCHANGE_ROTATION.md`；`exchange_storage.hpp:14-120`；`expert_source.cpp:3265-3323/3371-3439`；commit `fa1d1d1e`——但注意它只在**有 resident 补集**时启用）。
- **老师实际 pin 多少 RAM**：它的 dec-pool2 run 用的是 **expert arena**（不是 resident 模式）：日志 `dec-pool2:26-30`：`expert arena read unbuffered … loaded 46.84 GiB at 2.64 GiB/s`；`:28` **`cudaHostRegister PORTABLE ok` 长度 50,295,996,416 B ≈ 46.84 GiB**；也就是说**该 run pin 了全部 expert 集**。resident 模式的**设计**只 pin 非 VRAM 的补集：老师 cache 11,428/24,576 ⇒ 补集 13,148 个专家 × ~1.9 MB ≈ **~25 GB**（D 级估算；`dec-pool2:34` 的 11,428 槽、`:19` 的 24,576 pairs）。
- **arena 模式的特殊性**：arena 里每个专家都在 RAM（pageable 或部分 pinned 副本，从不移动），adaptive 轮没有 exchange、没有 RAM move（U `generate.cpp:9028-9031`）⇒ 老师的 dec-pool2 run 根本不用 exchange/rotation。

### 2.2 我们现在的做法

- `pin_expert_arena()`（`engine.cpp:1261`；`STRATA_PIN_ARENA_GIB=59.1`）：把 **40 个 MoE 层的整段 expert 映射**用 `cudaHostRegisterReadOnly` 注册（R28-A3:82：`pinned 40 layers (59.06 GiB) of 88, 0 refused; took 2 ms`）。
- **但这不是"锁 63.4 GB RAM"**：`情报-M` 已证——`cudaHostRegisterReadOnly` 是 DMA 注册，不 commit/不锁页，3 ms 完成、`RAM free` 不变；真正占 RAM 的是 `map_pages()`（`engine.cpp:163-179`）**逐 4KB 页 touch 全部 expert 映射**，把 63.4 GB 读进 page cache/工作集（`情报-M`：R34 采样 WS 峰值 **67,101 MB ≈ 65.5 GiB**；无进程时 Standby Cache ≈ 71.6 GiB）。
- **pin 的实际作用**：让 prefill 的 `stage()` 能 **直接从映射 DMA 到 VRAM**（`engine.cpp:3325` `if (pin)` 分支，`:3325-3330` 附近的 `cudaMemcpyAsync(dst+at, L.exp_gate…, HostToDevice)`）；没有 pin 的层退回 host gather（先前实测 pin 让 prefill **+53.7%**，backlog A 段）。
- **decode 的 CPU 读取**：miss 专家从映射读（page cache），**不需要引脚**；swap 的源也从映射 memcpy 到 pinned 缓冲再 H2D（`follow_loop` `engine.cpp:1926-1958`），**不依赖 pin**。

### 2.3 验证 lead 的推演："光改 pin 省不出 RAM"——**成立（但要把机制说清楚）**

1. **pin≠RAM**：改 `STRATA_PIN_ARENA_GIB` 只改"哪些层可 DMA 直拷"，**不改变页缓存占用**；要省 RAM 必须同时**停掉 `map_pages` 对非驻留页的预热**（代码改动），否则 63.4 GB 仍会被 touch 一遍。
2. **63.4 GB 的每一块都有读取用途**：非驻留 42.5 GB 是 **CPU miss 读取**（373–517 miss/token × 3.0966 MB = 1.16–1.60 GB/token）+ **prefill staging 来源**（每 prompt 流式 ~41 GB，R28-A3:90 `prefill staging 28,664 / 41.33 GB`）+ **swap-in 来源**；驻留 20.9 GB 是 **VRAM fill 来源**（`fill_expert_cache`）+ 被换出后重新成为非驻留时的读取来源。⇒ **稳定态工作集趋近 63.4 GB**，不是 20.9 GB。
3. **RAM 账**：96 GB 机器上，若加 31.7 GB sidecar：非驻留页 ~42.5 + sidecar 31.7 + dense mmap ~6.7 + OS/其他 ~10 = **~91 GB**（余 ~5 GB，且换页抖动风险）；若用老师 resident 模式（紧凑补集 42.5 GB 提交、VRAM 驻留 20.9 GB 不进 RAM、文件页缓存可丢），仍是 **42.5+31.7+6.7+10 ≈ 91 GB** ⇒ **arena/resident 补集都只有 ~3–5 GB 余量**；而 housekeeping（staging pinned 2 GiB、KV/pinned 缓冲、swap 交换缓冲）会吃掉它。
4. **代价**：① 停暖后冷页读盘 ~5.7 GB/s（团队 host gather 4.98/5.66 GB/s），若 373 miss/token 中有 10% 冷页 = 116 MB/token ≈ 20 ms/token；② prefill 失 DMA 直拷（+53.7% 的那条路）⇒ prefill 明显变慢；③ 换出/换入要写 RAM 位置（teacher 的 copy path），或上 EXCHANGE_ROTATE（`fa1d1d1e`）——但那要求紧凑补集 + 等大 blob。

**结论（验证 lead）**：**"只 pin 驻留专家 + 非驻留走映射"省不出 RAM**——省 RAM 的必要条件是"把非驻留读取从页缓存改成紧凑提交副本/或接受冷读"；**这只有 Stage D（resident 补集 + exchange 架构）能提供**，且余量只有 ~3–5 GB、还要付 prefill 退化与冷读风险。**Stage D 是 sidecar 的唯一解（在有意义的 RAM 节省意义上），但它不是今天该做的事。**

### 2.4 要不要模仿 / 怎么改 / 预期 / 风险

- **要不要模仿：有条件（先验证，后決定 Stage D）**——若 sidecar 的收益被重新证明值得，则必须做 Stage D；否则不值得。
- **怎么改（先做一次实验，零改码的部分）**：① `STRATA_PIN_ARENA_GIB=20`（只 pin 前 ~13 层，其余走 host gather）跑一次 prefill+decode，量 `--prompt` 的 prefill 退化与 decode 命中/CPU 腿（**注意**：`map_pages` 仍会预热全部页，所以这次实验只量"pin 作用的损失"，不量 RAM 节省）；② 若第一步损失可接受，再改代码：`map_pages` 跳过非驻留专家页、`pin_expert_arena` 只注册驻留集（或做 Stage D 的紧凑补集）。
- **预期**：decode 本身 **0 收益**（CPU 读速取决于页是否在 RAM，不取决于注册）；潜在收益=为 sidecar 腾 31.7 GB（但 sidecar 收益未证）；代价=prefill 退化/冷读风险（D 级）。
- **风险**：高——冷页读盘、prefill 退化、RAM 只余 3–5 GB、sidecar 本身已被判不可用（需重新论证）。

**如果只能选一条先做：B 不选**——它省不出 RAM 的推演成立；唯一出路 Stage D 是数百行、~3–5 GB 余量、前置实验未做，今天动它风险最高、收益最不确定。

## §3 C. MTP 专属驻留（老师把 512 个 MTP 专家单独常驻 VRAM 675 MiB）

### 3.1 老师怎么做（file:line）

- MTP 块自己的 512 个 routed experts **整块加载到独立 VRAM**（`mtp.cpp:138-151`：`---- the 512 routed experts, one blob each`；`cudaMalloc(&experts_, bytes)`；`bytes = g.n_expert * BLOB`）；前向只从这块常驻区取 top-10（`mtp.cpp:389-399`：`moe_group_resident`/`moe_grouped_s2`）；draft head 用 106,299 行子集（`:258-274` 建 `dhead_`；`:424-432` `nv = sub ? n_dvocab_ : n_vocab_`）。日志：`dec-pool2:23` `strata mtp: draft layer loaded, 836 MiB of VRAM (experts 675, dense 111)`；`:47` `draft head over 106299 tokens (212.9 MiB)`。
- 结果：MTP draft 每 token 都走完整块（attention+MoE+shared+head），但 **MoE 全在 GPU 常驻区**、无 CPU/cache 查询（情报-R）；draft 链每步只是一个小图（`capture_step`，`mtp.cpp:500-511`），按概率门提前停链。

### 3.2 我们现在的做法

- **blk.88（MTP 块）的 512 专家和主干共用同一个 cache**（`fill_expert_cache` 全层共享计数器，`engine.cpp:1076-1166`）；而我们的 profile（`p_master.txt`）**只有 40 个 trunk MoE 层、没有 layer 88 的计数**（情报-W：40 层、20,275 pair；layer 88 0 行）⇒ **blk.88 专家 prior=0，永远排在最后、不驻留**（除非 swap 偶然换入）。
- **开 MTP 的实际后果（A 级日志）**：R48-P1/P2/P3（`--expert-profile=p_decode.txt`、`--expert-profile-write`、`--max-new 512`、draft 默认开；`C:\sp3\run_R48_P*.cmd`）：`miss/token=673.6/677.8/708.2`、`experts from VRAM 34.8/32.9/25.6%`、decode **12.62/12.34/12.57 tok/s**；对照 R49-L（`--no-draft --lookup 0`）：`miss/token=516.9`、`from VRAM 41.2%`、decode **10.92–15.18 tok/s**（噪声大，含 15.18 离群）。⇒ **当前 MTP-on 的 miss 比 no-draft 多 157–191/token**（draft 的 22 routed experts/层 × 3 步基本全 miss），这与 `情报-R` 的"draft MoE 每 token 一次完整层、head 全词表 440 MB"一致。
- **MTP 被收口 opt-in 的原因（lead 给）**：MTP 吃 VRAM ⇒ 主驻留 **−212 槽** ⇒ ids 漂。**根因分析**：要么 ① MTP 占 VRAM 导致主 cache 少 212 槽（主模型专家 GPU/CPU 分配变化 ⇒ 舍入路径变化 ⇒ ids 漂）；要么 ② draft 取到的主 cache 专家在 CPU/GPU 之间移动造成 draft 不确定性。两者都可以通过"**MTP 专家不占主 cache**"同时消除。
- **R43 的 `--draft-vocab` −8.4%**：现在不能进交付，因为它改的是 draft head 行数（省 draft head 读），但 draft MoE 的 miss 仍在；且 draft 仍吃主 cache。

### 3.3 仿老师：给 MTP 512 专家一个**不占主 cache 的常驻区**

- **尺寸**：老师 675 MiB 是因为它的 blob ≈1.9 MB（675 / 512）；我们的 expert blob = **3.0966 MB**（GGUF 静态：1585.447 MB/层 ÷512）⇒ 需要 **512 × 3.0966 MB = 1.585 GB**。
- **显存来源（不牺牲主 cache 的方案）**：
  1. **prefill staging/ring2 借槽**：`--stage-mib 2048` 的 stage buffer ≈2 GiB + `STRATA_STAGE_RING2=1` 的第二 round buffer ≈1.5 GiB（`dec-pool2` 式的第二缓冲；我们 R28 日志 `STRATA_STAGE_RING2: the second round buffer is 1512 MiB`）⇒ **情报-Z 的 "表→prefill 借槽"** 机制可以把它在 decode 期间让给 MTP 常驻区（prompt 时再收回）；
  2. **缩 `--stage-mib`**（2048→512 省 1.5 GiB；prefill 会慢，需 A/B）；
  3. 若都不动，则只能从主 cache 拿 512 槽（−512/6,745 ≈ −7.6% 主 cache，命中 −~2 点、miss +~17/token ⇒ +2.3 ms/token），**抵消 MTP 收益，不建议**。
- **怎么改（范围 ~30–80 行）**：
  - `fill_expert_cache()`（`engine.cpp:1076`）里为 `n_layer_`（blk.88）预留 512 个 slot（**单独计数、不参与主 top-N**；或建独立小 arena 1.585 GB）；`moe()`/`draft_step` 走现成 cached 分支即可（非门控专家走 `native_mmvq_slots`，`engine.cpp:3082-3123`；不需要 `moe_card`）。
  - profile 采集把 88 层计入（`情报-Z` #2：`use_` 在 `moe()` 的 draft 前向也会加，`engine.cpp:2260`），或专用 `--draft-vocab` 缩减 head；
  - 显存来源改为 stage/ring2 借槽（复用 `情报-Z` 的 borrow 结论），或先 `--stage-mib 512` 试验。
- **预期**：draft 的 CPU 腿去掉（3 draft × 22 routed × ~50-60% miss × ~0.13 ms ≈ **~4–5 ms/round**，≈1.5–1.9 ms/token）；主 cache 不动 ⇒ 主模型算术不变 ⇒ **ids 门有望过**；MTP 的 spec 收益（3.05/3.20 token/round，R40）才有机会真正兑现。**净效果 D 级 +5~15%**（若 MTP 的 spec 收益兑现；最差 ±0），并且能把 R43 的 `--draft-vocab` 臂（−8.4% 收益）重新拉回正收益后进交付。
- **风险**：中低——① VRAM 来源（stage/borrow 未实现则先缩 stage，prefill 慢）；② draft 的 MoE 从 GPU cached 路径算，与之前 CPU 路径的数值不同（但 verify 用主模型 logits，greedy 的接受/回退保证输出 ids 与 no-draft 一致；需 ids 门实测）；③ 不碰 `up_↔st_` 红线；④ blk.88 的 512 专家与主模型专家类型相同、kernel 现成。

**如果只能选一条先做：选 C**——唯一"改动小（30–80 行）、不碰主 cache/主算术、直接解 MTP 的 ids 漂根因、且能把已测到的 spec 收益（R40 3.05/3.20 token/round、R43 draft-vocab −8.4%）转正"的一条；A 太贵且主体不可用，B 省不出 RAM。

## §5 判决

- **如果只能选一条先做：C（MTP 专属驻留）**。理由：改动最小（30–80 行）、不碰主 cache/主算术（ids 门有望过）、直接去掉 draft 的 CPU 腿（~1.5–1.9 ms/token）与 MTP 吃槽根因，并可把已测到的 spec 收益（R40 tokens/round 3.05/3.20）与 R43 的 `--draft-vocab`（−8.4%）重新拉正；A 的"整图/device plan"在我们 41–57% 命中下用不上、只剩 +3~7% 的昂贵边缘；B 已证"光改 pin 省不出 RAM"，Stage D 是 sidecar 唯一解但代价/风险最高，应先做零改码的 pin 实验再谈。
- **顺序**：C（今天/本轮，改 fill 预留 + 显存来源试验）→ A（若 C 后 decode 仍差，做 device top-k 小仿，别做整图）→ B（只在 sidecar 被重新论证值得时做 Stage D，先跑 `STRATA_PIN_ARENA_GIB=20` 实验）。

## §6 查无 / 未验（明写）

1. **`STRATA_VERIFY_DEVICE_PLAN` 的完整实现未逐行读**（U 树有 `ver.set_adapt_gate`/device plan 相关；本件只读到"整驻留 token graph decided on the device"的 T 树证据 `generate.cpp:2358/2391/2401` 与 verify window host plan `expert_source.cpp:284-367`）。
2. **R49 的 `router wait 7.2–9.1 ms/token` 含 prefill `moe_rows` 的 route_wait 污染且分母含 prompt**（`engine.cpp:2897` decode、`:3469` prefill 都累加；`main.cpp` 打印除 `st.tokens`）⇒ decode-only 真值未验；lead 给的 7.7 ms/轮 是 B 级口径。
3. **B 的冷页读盘损失未实测**：`373–517 miss/token × 3.0966 MB = 1.16–1.60 GB/token`；若 10% 冷页 ≈ 116–160 MB/token ÷ 5.7 GB/s ≈ 20–28 ms/token（D 级外推，未跑）。
4. **老师 resident 模式的补集大小 ~25 GB 为估算**（24,576−11,428=13,148 × ~1.9 MB/blob，blob 大小取自 `dec-pool2:12` "largest blob 2.66 MB" 与 46.84 GiB/24,576≈2.0 MB 的组合，未逐 blob 算）。
5. **C 的显存来源（stage/ring2 借槽）在 poly 尚未实现**；`--stage-mib 512` 的 prefill 退化未测；MTP 专用驻留后 ids 能否过门、draft 的 GPU cached 路径与 CPU 路径数值差对接受率的影响均未实测。
6. **`fill_expert_cache` 对 blk.88 的当前处理未逐行确认"是否被排除"**：它遍历 `layers_`（含 blk.88？`n_layer_` 层）；但 `p_master` 无 88 层计数 ⇒ prior=0 ⇒ 排在最后；是否因 slot 大小不同（`slot_bytes` per layer）而永远装不进需实测（本件按"不驻留"处理，R48-P 的 miss 数据支持）。
