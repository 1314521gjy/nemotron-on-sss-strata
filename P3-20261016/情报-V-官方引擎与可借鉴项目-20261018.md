## §0 三句结论

1. **"500+ tok/s" 不是 NVIDIA 官方博客里的绝对数字**：NVIDIA 官方 blog 只给相对值 **"up to 5× higher throughput"**、**没有写 500/600 tok/s 的绝对值**（[NVIDIA blog](https://developer.nvidia.com/blog/nvidia-nemotron-3-5-super-vl-powers-specialized-agents-with-multimodal-reasoning)，本件全文已读）。绝对值出现在四处：**LMSYS/SGLang 官方博客的 NVIDIA 图表标题 "over 600 TPS … on Baseten endpoint"**（[lmsys blog](https://www.lmsys.org/blog/2026-10-15-nvidia-nemotron-3-5-super-vl/)）；**Blackbox AI 实测：单 B300、30 条 ~10k token prompt、单请求 521 tok/s、10 并发 218 tok/s/请求**（[xenospectrum 转述](https://xenospectrum.com/en/nvidia-nemotron-super-vl-enterprise-agents/)）；**THU 服务实测：单 H100 NVL 544 tok/s**（[THU](https://llmapi.service.thu.edu.tw/news/191?lang=zh-Hant)）；以及 SGLang **RTX PRO 6000 单卡 243.9 tok/s（含 MTP）**。
2. **官方推荐引擎 = NIM（打包 vLLM / SGLang / TRT-LLM 三选一）+ Dynamo（多卡调度）**：NIM 模型卡明确列 **vLLM · SGLang · TensorRT-LLM**；NVIDIA blog 的部署段落只推荐 **NIM + Dynamo**；**NIM 的 GPU 配置表：NVFP4 = 1×B200 / 1×H200 / 2×H100；BF16 = 2×B200 / 4×H200 / 8×H100**（xenospectrum 转述 NIM 文档）——**没有一张 32 GB 消费卡的官方配方**（与 `Nemotron历史版本调研` 的负面结论一致）。**MTP 在 SGLang 有官方 cookbook（EAGLE，5 steps / 6 drafts；低延迟档 3 steps / 4 drafts），在 vLLM 是 LiLiCorr/DFlash 草稿模型路线，TRT-LLM 的 MTP 集成未查到公开文档（未验）**。
3. **git 上已出现大量同题项目，最值得抄的不是"更大引擎"，而是同病相怜的"小卡跑 120B"项目**：`helgard-orlm/nemotron-super-8gb`（**RTX 5060 8 GB 跑同族 120B NVFP4，7.3–7.6 tok/s**，专家 NVMe→RAM LRU→GPU 流式 + **prefetch + ReLU² 零跳过**）、`plotarmordev/...TensorFold`（1×DGX Spark，**18 个无损引擎 patch，+20.6%**）、`sfxnz/...DGX-SPARK`（vLLM + LiLiCorr，**单 Spark 1 用户 48 tok/s、32 并发 189 tok/s**）。**我们 16.2 tok/s 与官方 500+ 的差距 ~32×，其中硬件/驻留占大头（见 §4），但"ReLU² 零跳过"是唯一可能在我们机器上把 CPU 腿字节砍掉 ~1/3 的机制级抄点。**

## §4 ④ 结论：官方最快路径、差距判断、TOP-3 可借鉴

### §4.1 官方最快路径
| 路径 | 硬件 | 配置 | 读数 |
|---|---|---|---|
| **NIM + Dynamo（数据中心）** | B200/B300（NVFP4 1×B200 / 1×H200 / 2×H100） | NVFP4 + MTP/LiLiCorr + KV-aware routing/offload | **单 B300 单请求 521 tok/s**（Blackbox AI）；Baseten endpoint **>600 TPS**（100k 输入）；16×B200 下 50 tok/s/用户、8× 用户数 |
| **SGLang 单卡** | **RTX PRO 6000** 单卡 | NVFP4 + EAGLE MTP（5 steps/6 drafts）、v0.5.21 | **243.9 tok/s**（官方图注） |
| **vLLM 单 Spark（社区最优实测）** | 1×DGX Spark GB10 | NVFP4 + LiLiCorr 7 drafts、32 并发 | 单用户 **48 tok/s**、32 并发 189 tok/s、接受 4.5–5.7 |
| **llama.cpp/GGUF（我们的路）** | 8 GB RTX 5060（同族 NVFP4 流式） | 专家 NVMe 流式 + LRU + ReLU² 跳过 | **7.3–7.6 tok/s**（helgard）；我们 4080S/Q4_K_M/32 GB **16.2 tok/s** |

### §4.2 差距判断：**硬件/驻留是大头，引擎是第二**
- 我们 16.2 vs 官方 521 = **32×**；拆：
  - **显存容量/驻留**：B300 288 GB HBM ⇒ 120B NVFP4（~75 GB）**整模常驻**；我们 32 GB + 59 GiB 专家库 ⇒ **只有 28% 命中，CPU 腿 71.9 ms/token**（交接 §9.4）。
  - **带宽**：B300 HBM3e ≈ 8 TB/s vs 4080S GDDR6X ≈ 736 GB/s ≈ **10.9×**；单请求 decode 是带宽/延迟受限 ⇒ 硬件项直接差一个数量级。
  - **算力/精度**：NVFP4 tensor core（Blackwell）vs FP16/int8（Ada）≈ 数倍。
  - **引擎机制**：MTP（Blackbox 实测 **198→492 = 2.5×**）、continuous batching（32 并发 189 tok/s）、fused MoE、整图/门铃、KV offload —— 这些我们缺或判死，合计最多再差 **1.5–2.5×**。
- **我们的"天花板"算术（A 级输入）**：CPU 腿 = `miss/token(496.7) × 3.0966 MB = 1.54 GB/token ÷ 32.2 GB/s = 48 ms` ⇒ **理论上限 ~21 tok/s**；现 16.2 = 天花板的 **77%**。⇒ **在我们这张卡+这个驻留率下，"引擎再优化"最多到 ~21，加 ReLU² 零跳过（−~37% CPU 字节）可到 ~30–33；要 500+ 必须换硬件（HBM 容量/带宽 + FP4）**。
- ⇒ 回答用户："**官方 500+ 是 B200/B300 级 HBM + NVFP4 + MTP 的口径，不是 32 GB 家用卡口径；我们的差距 ~90% 在硬件/驻留，~10% 在引擎（MTP/批处理/融合内核）**。"

### §4.3 TOP-3 可借鉴（能落到 `PolyStrata\src\poly`）
1. **ReLU² 零跳过（helgard-orlm/nemotron-super-8gb）**：同族模型实测 **92.5% 的 ReLU² 中间神经元=0**，把 down 矩阵按神经元重排（纯字节置换，文件同尺寸）后**只读活列**；他们此招 +12%（在 8 GB 流式引擎上）。落到我们：**CPU 专家 down 相（每 expert 1.548 MB 的一半）按 32/16 粒度只读非零块**——先测我们 Q4_K_M 的激活稀疏率（1 跑），若 >80%，CPU 腿字节可砍 ~1/3 ⇒ decode 16.2→22–26 tok/s；改动在 `cpu_experts.cpp` down 循环 + 离线重排专家库（59 GiB，一次 ~分钟级，同 helgard 的 2.5 min 经验），**无需新 GPU kernel**。
2. **MTP small-M 执行 + Mamba2 变长验证（SGLang PR #44518 + vLLM PR #53036）**：MTP 的 verify 是 **M=1–6 的小 M**，上游专门做 "small-M execution" kernel；vLLM 还专门做 "varlen Mamba2 decode for adaptive verification"（我们 40 层 Mamba 与 MTP 冲突的同题）。落到我们：MTP 重启（交接 §10.6-1 隔离非确定性）后，把 verify 的 attention/MoE 内核按 M≤6 特化、并核对 Mamba state 在变长验证下的处理，避免 R40 的 "miss/token +35%" 式回退；**需 1 编译 + 多跑**。
3. **跨层专家预取（helgard NS_PF=4，~72% 命中的 next-layer router 预测）**：把"下一 MoE 层的 router 作用在当前输入"预测专家，未命中部分在 GPU 工作时预读；他们据此把 NVMe 读藏在 GPU 后面。落到我们：我们已有 `pcie-frac`/`expert cache`/`map_pages`，缺"预测"（`情报-P`：lookahead/foresight 全 0 命中；老师 0.1.40.2 也没有、0.1.44.1 才有）；可实现为 **CPU 腿运行时预取下一层候选专家到 pinned RAM / staging**，与 CPU 计算重叠 ⇒ 减少 32 GB/s 腿的等待；**零 GPU 可先写方案，1 编译 + 2 跑验证**。

（备选第 4/5：llama.cpp PR #29807 "去掉 mamba2_scan 后的冗余 CUDA 拷贝"——我们 40 层每层都有；llama.cpp issue #27717 "`--n-cpu-moe` + MTP 草稿加载崩溃"——我们开 MTP 前必须核；unsloth PR #9872 "offload planner"——我们 pcie 份额/驻留的手工配比可借它做自动规划。）
