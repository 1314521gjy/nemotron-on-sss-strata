## §3 四问逐答（计划 §2 线 C）

### Q1：40 层 mamba2 在 batch=1 怎么跑？128 步串行链？smem？每层 µs？

- **kernel**：`mamba2_scan_kernel<true>`（SMEM 版；`kernels.cu:2554-2610`），启动配置 **`<<<n_head, head_dim, smem>>>`**（`:2925-2927`）。
  - 几何（GGUF 实测，`nemotronhmoe.cpp:78-89` 读键）：`ssm.inner_size=8192`、`ssm.time_step_rank=128`、`ssm.state_size=128`、`ssm.group_count=8`、`ssm.conv_kernel=4` ⇒ `head_dim = d_inner/n_head = 8192/128 = **64**` ⇒ **grid 128 blocks × block 64 threads = 8,192 线程**（每 block 2 个 warp，占用率很低）。
  - **"128 步串行链"的真实含义**：每个线程负责一个 (head, value-dim) 元素的 **`d_state=128` 个状态值**，在一次 kernel 内**串行循环 st=0..127**（`kernels.cu:2578-2597`：`for st` 里 `state = state*sdA + sB[st]*x_dt; sum += state*sC[st]`）；**不是跨时间步的 128 步链**——decode 每 token 每状态只更新一次，串行维度是 **d_state**，不是 sequence。
  - **SMEM**：`need = head_dim × (d_state+1) × 4B = 64×129×4 = **33,024 B ≈ 32.25 KiB**`（`< 48 KiB`，无需 opt-in；`kernels.cu:2908-2930`）。SMEM 版把每个线程的 128-float 状态行"load once/store once"（`:2566-2569/2608-2609`），全局状态流量 = **4 MiB 读 + 4 MiB 写 / 层**（8192×128×4B）。
  - **每层 µs：未验**。读数推算：8 MiB @ 700 GB/s ≈ 11.4 µs，加 xbc/dt 读、低占用率与发射 ≈ **15–25 µs/层**（D）；40 层 ≈ **0.6–1.0 ms/token**（相对 75 ms 可忽略，但需打点证实）。
- 旁证：R14b 把 warp/tree 版 kernel **试过并输了**，现树里 warp/micro 路径被 `#if 0`（`kernels.cu:2612-2674/2784-2906`），生产就是 SMEM 版（`:2907-2931`）。

### Q2：每 token 发射多少 kernel？CUDA graph 覆盖整段 decode 吗？哪里掉出图？

- **每层"到 router 为止"约 30 个 kernel**：源码注释原文 *"the same launches every time, some thirty a layer up to the router, and they cost this thread more than the card"*（`engine.cpp:3200-3202`）⇒ 88 层 ≈ **2,640 kernel/token**（在 `heads`/`shared`/`tail` 图内）。
- **MoE 的 routed-expert 发射不在图里**：`moe()` 内的 `native_mmvq_slots`(gu)/relu2/quantize/`native_mmvq_slots`(down)/`add_scaled` 是 host 直接发射（`engine.cpp:2256-2419`，其中 `launch` lambda 由 CPU worker 执行）；按 cached≈9.6/层、kSlots=8 ⇒ 2 组 ×5 kernel = 10，加 memset/axpy/latent(2)/axpy/tail ≈ **每层 ~15 host 发射 ⇒ 40 层 ≈600 kernel/token**（host 直接可见）。
- ⇒ **总量级 ≈2,600（图内）+ 600（图外）+ lm_head ~3 ≈ 3,200 kernel/token**；**host 侧发射调用 ≈ 216 次图启动（88 heads + 40 shared + 88 tail≈216）+ ~600 次 MoE 直发 ≈ 820 次/token**（读码推算）。
- **graph 覆盖**：只有 **per-layer 的 `heads` / `shared` / `tail` 三张图**在 `L.fixed` 时录制（`engine.cpp:3211-3226`；`L.fixed=true` 见 `nemotronhmoe.cpp:150`）；**整段 `whole` 图不成立**——`whole` 要求 `card_moe()` 全命中且用 `moe_card()`（`:3329-3365`），而 **`moe_card()` 对非门控专家直接返回 false**（`:2489 if (!L.gated) return false`；Nemotron 是非门控），所以 `card=false`、`whole=false` ⇒ **每个 MoE 层的 expert 段都掉出图**；`lm_head` 另有一张 `tail_` 图（`:3413-3429`，仅 `n==1 && want_logits`）。
- 每 token 的 host 同步点：**eval 入口 `cudaStreamSynchronize(st_)`**（`:3168`）；**每层一次 `cudaEventSynchronize(ev_)` 等 router**（`:2157`）；eval 末 logits 后再一次 `cudaStreamSynchronize`（`:3432`）。

### Q3：CPU experts 11.1 / router wait 6.6 是串行还是能重叠？有没有重叠机会？

- **数值纠正**：真实 decode CPU = **71.9 ms/token（R28 实测）**，不是 11.1（那是含 prompt 的稀释值）；**router 等待的 decode-only 真值未验**（打印被 `moe_rows` 的 prefill 部分污染，`engine.cpp:2157` vs `:2681`）。
- **层内**：有重叠——`moe()` 把 GPU cached 专家的发射交给 CPU 池的**一个线程当 `meanwhile`**执行（`engine.cpp:2252-2257` 注释、`:2430-2432` `cpu_experts(..., hand_over ? &launch : nullptr)`、`cpu_experts.cpp:211-213`），CPU 其余线程同时算 CPU 专家；`--pcie-frac` 的拷贝也在自己的流上（`:2260-2273`，默认 0 不跑）。
- **层间**：**不重叠**——`router wait（每层头）→ CPU 专家 → moe_add(axpy) → moe_latent → tail（下一层）` 全在单 host 线程顺序推进（`engine.cpp:3366-3374`），下一层的 `ev_` 等待要等本层 CPU 专家结束后才到；⇒ **CPU 腿就是关键路径**，GPU（≈8 ms 的 HBM 需求）大部分时间在空等。
- 结论：**"CPU 11.1 + router 6.6 能否藏进 GPU"这个问法本身要改**：是 GPU 藏在 CPU 后面（已发生），不是 CPU 藏在 GPU 后面；真正可挖的重叠是 **跨层的 CPU 专家与下一层 GPU head 流水**（需改码：moe_add 的依赖决定了要双缓冲残差/延迟提交；大改）。

### Q4：稠密权重每 token 读多少字节？理论下限？

**静态字节（A：GGUF 张量表按类型 payload 求和）**：
- 总 tensor 载荷 **70.095 GB**（= 两 shard 文件 39.73+30.37 GB）；其中 **专家 65.003 GB**、**dense 4.267 GB**、**lm_head(output.weight Q6_K) 0.440 GB**、token_embd 0.302 GB（每 token 只读 1 行）、MTP block 0.083 GB（只在开 draft 时用）。
- **每 token 稠密读取** = mamba-dense 2,475.68 MB + attn-dense 161.65 MB + MoE-dense（含 shared expert/latent/router/attn）1,629.47 MB + **lm_head 440.40 MB** = **4,706.8 MB ≈ 4.707 GB**（token_embd 行可忽略）。
- 加上 **cached 专家 383.3 × 3.0966 MB = 1,186.8 MB** ⇒ **VRAM 侧总流量 ≈ 5.894 GB/token** ⇒ **理论下限 5.894/0.864 = 6.82 ms @864 GB/s（4080S 峰值）**；按实测有效 ~700 GB/s ⇒ **8.42 ms**。
- 但 **CPU 侧还有 496.7 × 3.0966 MB = 1,538 MB/token 从宿主 RAM 读** ⇒ 按 DDR 实测/有效 ~70 GB/s ⇒ **理论下限 ≈22.0 ms**；按 R28 实测的 CPU 有效带宽（1.538 GB / 65.3 ms = **23.6 GB/s**）⇒ **65.3 ms**。**⇒ decode 的真实下限由 CPU 侧决定（≈22 ms/token ≈ 45 tok/s），不是 GPU 的 6.8–8.4 ms。**

**事件 vs 墙钟（写死）**：
- **必须 CUDA event**：GPU 段的时间/空隙——eval 总 GPU 时间、`--no-graphs` 臂的逐层 GPU 时间、namba scan µs、lm_head。原因：host 墙钟在 GPU 异步处会读成"0 或噪声"。
- **墙钟足够**：`route`、`build`、`cpu_experts`、`launch`、每层 host 推进——这些是 **host 关键路径**，且 R28 已证明 host 就是瓶颈；时钟开销 ~40 ns/点。
- **不能在图内加 event 而不改图**：`heads/shared/tail` 是 capture 出来的，往里塞 `cudaEventRecord` 会改变 capture 结构（并可能改变时序）⇒ **图内逐层 GPU 时间只能靠 `--no-graphs` 臂或 nsys**，且必须证明 `--no-graphs` 的 ids 与图臂逐位相同（图只改发射打包，不改算术——`engine.cpp:3200-3214` 注释；需要跑一次 ids 门）。

## §6 未验 / 边界（明写）

1. **R28-A3 是 `C:\sp3\sp_pcie1.exe` 的读数**（非当前交付 exe）；命令行带 `--expert-swaps 0`，与交付配置（`--expert-swaps 64`）不同 ⇒ 命中率 43.3% vs 交付 51.7%；**绝对值需在交付 exe 上复核**（同一 decode-only 计数器）。
2. **mamba2 每层 µs 未验**（仅推算 15–25 µs/层）；**per-layer GPU 时间未验**（图内无事件）。
3. **decode-only router 等待未验**（打印被 prefill 的 `moe_rows` 累加污染，`engine.cpp:2681`）。
4. **CPU 专家内部分相（quant/up/quant/down）未验**；CPU 腿是 compute 还是 memory bound **未判**（有效 23.6 GB/s vs ~84 GFLOPS，二者都可能；需 P1 的 4 阶段计时）。
5. **`--pcie-frac` 的实际可用性**：源码里存在（`main.cpp:881/945-947`；`engine.cpp:2198-2273`），但本计划不碰；若未来想用它救 CPU 腿，**1.538 GB/token 走 PCIe @23GB/s = 67 ms**，不划算（除非与 GPU 重叠且分批，需另算）。
6. **laptop/不同 exe 的 `L.fixed`、图录制次数**可能不同；本件按当前工作树（`nemotronhmoe.cpp:150 L.fixed=true`）。
7. 计划 T4 目标（≥20 tok/s = 50 ms/token）：按 §3 Q4 的 CPU 下限 **≈22 ms/token（45 tok/s）** 是可达理论上界（若 CPU 腿达到 RAM 满带宽、且 GPU 残差被压到 <5 ms）；但当前 CPU 腿 65 ms 距该下限 **3×**——**先修 CPU 腿（命中率/CPU 内核效率/线程配置）才谈 20 tok/s**。
