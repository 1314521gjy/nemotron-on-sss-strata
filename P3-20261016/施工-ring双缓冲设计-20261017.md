## §0 一句话方案

> **N=2 个 round 槽（每槽 341 专家 = 1,007 MiB；两槽共 2,014 MiB，比现 `stage_` 1,477 MiB 多 +502 MiB）+ 提前一层预取（软件流水）+ 每槽一对事件**；mmq 的批布局**不变**（仍然"up 数组 + down 数组"），所以算术应与今天**逐位同**；旗标 `STRATA_STAGE_RING2`（默认 0）。

## §1 上游 ring 是什么（抄什么、不抄什么）

- **语义（`prefill.cpp:132-134`，原文）**：*"from this chunk size on, every non-resident expert of every layer streams in a fixed order through a ring_slots()-slot ring (nearly all 512 are routed at such a chunk), so the copy engine keeps working through the attention halves instead of waiting for each layer's routing."* ⇒ 三个要点：**固定顺序**、**N 槽**、**拷贝引擎在 attention 段继续干活**（不等每层 routing）。
- **槽数（`:292-314`）**：`STRATA_PREFILL_RING` 覆盖；否则 pinned-share 规则 = pinned ≥0.9 时 **384**（fused 1024）/ 走 host 拷贝时 **96**；cap 512/1024（`:257-259`）。实测依据（`:214-217`）：Q2_0、8192-token chunk，**96 槽 1153 tok/s → 384 槽 1294**（"the next layer's experts arrive during its attention half"）。
- **分配（`:1922-1926`）**：ring 是 `ring_slots × MAXBLOB` 的**一整块**分配（owned）或每槽一次 `take`（borrowed）。
- **槽间纪律（`prefill.cpp:422-458`，stager 侧）**：host 缓冲 ring `kRing=16`（`STRATA_STAGER_RING`），第 j 个 job 落到 `j % kRing` 槽，**该槽只有 `j − kRing` 的 DMA 完成事件之后才复用** ⇒ "每槽一事件"的范式。
- **不抄什么（关键适配）**：上游每槽 = **一个整 expert blob**（`MAXBLOB`，IQ3_S 2.54 MiB → 199 槽），因为它的融合 MoE 用**逐专家指针**。我们的 staged MMQ 需要"**up 数组（stride `gu2`）+ down 数组（stride `d_bytes`）**"的连续批布局（`engine.cpp:2746-2747` 两处 `mmq_->mul(stage_…, gu2, m, …)` / `mmq_->mul(stage_ + down_at, …, d_bytes, m, …)`）。照抄 per-blob ring 会逼出 host repack ⇒ 等于放弃 pin 直 DMA（今天 44.58 GB 全走 `cudaHostRegisterReadOnly` 直搬）。⇒ **适配为 round-slot：一槽 = 一个 round 的 up+down 两段**。

## §2 槽位方案（回答 1）

| 项 | 方案 |
|---|---|
| N 槽数 | **N=2（乒乓）**。预取深度 = 1 层：copies 341 专家 ≈ 1.084 GB ÷ 17.7 GB/s ≈ **61 ms/层**，compute ≈ **62 ms/层** ⇒ 2 槽即可把 ahead 拷贝藏进上一层 compute；N=3 只多一层 lookahead、多 1,007 MiB，无必要（若实测有缺口再加） |
| 每槽大小 | **341 专家**（= 现 `plan_ahead` cap，见 `engine.cpp:1317`）= 341×3,096,576 B = **1,055,932,416 B = 1,007 MiB**（+`kTail`/256B 对齐） |
| 与 `stage_` 1.477 GiB 的关系 | **ring 开时 `stage_` 退役**：改分配 2 个槽（2,014 MiB vs 现 1,477 MiB，**净 +502 MiB**）；flag 关时仍分配旧的 1,477 MiB 单缓冲，路径逐字节同今天 |
| VRAM 可行性（R2a 实测） | 峰值 30,004–30,165 MiB / 32,760 ⇒ 余量 2,595–2,756 MiB；+502 MiB 后余量 ≈ **2,093–2,254 MiB** ⇒ **预期不掉驻留**（两列仍要实测同报） |
| 槽内容 | 每槽 = `[m×gu2][pad(m×gu2)][m×d_bytes]`，m≤341；round 1（others ≤171）写回同一槽（round 0 kernel 之后，同流顺序保证） |
| 何时不用 ring（回退） | `n < stage_ahead`、`--stage-ahead 0`、或任何 round 的 m > 341（例如无 ahead 的 512 专家 round）⇒ 该 call 退回旧单缓冲路径，并打一行自证（不静默） |

## §3 ★ event 纪律：四件套改前/改后逐行（回答 2）

**改前（当前工作树；一套"全局"配对）**

| # | 行 | 语句 |
|---|---|---|
| ① | `engine.cpp:2407` | `ck(cudaStreamWaitEvent(cs(up_), (cudaEvent_t) ev_free_, 0), "expert staging");` |
| ② | `engine.cpp:2409` | `ck(cudaEventRecord((cudaEvent_t) ev_ahead_, cs(up_)), "expert staging");` |
| ③ | `engine.cpp:2737` | `ck(cudaStreamWaitEvent(cs(st_), (cudaEvent_t) ev_ahead_, 0), "expert staging");` |
| ④ | `engine.cpp:2785` | `ck(cudaEventRecord((cudaEvent_t) ev_free_, cs(st_)), "expert staging");` |

**改后（两个槽各一套；s1 = 本层 round 0 读的槽，s2 = 1−s1 = 下一层预取写的槽；`s1` 每层翻转）**

| # | 位置 | 改后语句 |
|---|---|---|
| ①′ | 原 `:2407` 处（预取灌槽） | `ck(cudaStreamWaitEvent(cs(up_), (cudaEvent_t) ev_free_[s2], 0), …);` |
| ②′ | 原 `:2409` 处 | `ck(cudaEventRecord((cudaEvent_t) ev_ahead_[s2], cs(up_)), …);` |
| ③′ | 原 `:2737` 处 | `ck(cudaStreamWaitEvent(cs(st_), (cudaEvent_t) ev_ahead_[s1], 0), …);` |
| ④′ | 原 `:2785` 处（位置不变：本层所有读 s1 的 round 之后） | `ck(cudaEventRecord((cudaEvent_t) ev_free_[s1], cs(st_)), …);` |
| ⑤（新） | `moe_rows(L)` 的 `card()` 末尾、④′ 之后 | **prefetch 下一层**：若 L+1 是 moe 且 ahead 开启且 ≤341：`plan_ahead(L+1)`（在 read 期间 `L.slot` 不变 ⇒ 与 routing 无关、可提前算）→ 对 s2 执行 ①′②′ → 置 `prefetched_il_=L+1`。下一层 `moe_rows(L+1)` 看到 `prefetched_il_==il` ⇒ 跳过旧的"早拷贝"分支，只保留 ③′ 的等待 |

- **为什么语义仍然闭合（可复核的论证）**：每个槽只有两类动作——`up_` 写（ring 预取）与 `st_` 读（round 0/1 的 kernel）。两条规则：**写槽 s 前等 s 的最后一个读者（`ev_free_[s]`）；读槽 s 前等 s 的写完（`ev_ahead_[s]`）**。
  - 槽交替 ⇒ 同一个槽两次使用之间隔一整层（≈60 ms）：`ev_free_[s]` 记在"读 s 的最后一个 kernel 之后"，`ev_ahead_[s]` 记在"拷贝全部入队之后" ⇒ **读者看不到半份数据、写者不覆盖活读者**；
  - 跨流依赖仍是单向：`up_` → `st_` 与旧的 ①→③ 同类；`ev_free_` 的旧"保护单缓冲"语义被"每槽 `ev_free_[s]`"**精确接替**（旧的是 1 个缓冲 1 对事件，新的是 2 个槽 2 对，规则同构）；
  - round 1（others，≤171）写回 s1：发生在 round 0 kernel 之后、同一条 `st_` 流上，顺序不变，无新事件；
  - 唯一新增的"跨层"动作是 ⑤：它等的是 s2 的旧读者（L−1 的 ④′，早已记录），所以**可以在 L 的 kernel 还在跑时就开始拷贝** —— 这就是上游"copy engine keeps working through the attention halves"的落地。
- **`kept/mine` 逻辑**：单 call 下 `mine=false`；prefetch 命中时等价于"early 已完成"⇒ round 0 走 ③′ 等待、不拷。多 call（生产 prompt >8192）同样按"下一层"推进；call 边界用成员 `ring_slot_` 记住下一槽。

## §4 确定性判据（回答 3）

- **预期**：本方案**不改批布局**（同 ahead 列表 341、同 `per_round` 341 ⇒ 同 `round_`/bounds/mq 批次）⇒ **ids 45/45 且 `--top-probs` 逐位同（max|Δp|=0）**；与 A3 的 `max|Δp|=1.405e-3`（那刀改了批形）不同。
- **门（照 lead 口径）**：ids 45/45；`--top-probs 8` 的 **max|Δp| ≤2e-3**；**同 config 对照**（同 exe 旗标关 vs 开各 ≥3 非-probs 跑，decode 3 跑中位不许掉 >3%）；1 对 top-probs 跑（A0p/A1p 模式）给 max|Δp|。
- **负控（能变红）**：旗标关 ⇒ 必须回 **wall 5.01 s / DMA 28,792 / 44.58 GB / 驻留 5,890 / ids 45/45**（同 sha 配对）。
- **建议加验证旗标** `STRATA_STAGE_RING2_CHECK=1`：每到 round 0 前 `cudaStreamSynchronize` 并断言槽事件序（抓"事件记早/记晚"的静默错值；**只用于验证，不用于性能读数**）。

| 风险 | 后果 | 防法 |
|---|---|---|
| 事件记早/记晚（③′ 早于拷贝完成 / ④′ 早于最后读者） | **静默错值**（不崩） | `RING2_CHECK` 旗标 + ids/top-probs 门 |

## §9 未验

1. **未落码、未编译、未测**（本件零 GPU）。
2. 上游 per-blob ring（199–1024 槽）与我们的 round-slot（2 槽）**不同构** ⇒ 上游的 tok/s 数字不可直搬；本件预期是从 A3 实测 + 边际速率推的（D 级）。
3. VRAM 余量来自 1 Hz 外部采样（6 窗），短峰可能漏；双缓冲实际峰值必须落码后实测。
4. 多 call（生产 prompt >8192 token）下 ring 的收益未建模（本靶 6792 单 call 是主场景）。
