# `--stage-mib` 语义 + `--stage-ahead` 的门：读码定死 — 2026-10-16

- 席位：`scheduler` · **只读**：未改码、未编译、未跑 GPU。
- 触发（实测 A，队长扫档）：`--stage-mib` **2048 ⇒ prefill 125.6** · **768 ⇒ 170.2** · **1024 ⇒ 170.0/172.6** · **1536 ⇒ 125.1**（命中 97.1% 不变、decode ~60 不变）；`--stage-ahead 1024` ⇒ **13.6–15.0（−88%）**、命中跌到 **9.0%**、加大 `--stage-mib` 救不回来。

---

## §0 一句话结论

1. **★ `1536` 不是"回落"，是"撞上限"**：`stage_bytes_` 被 **`n_expert_ × one_expert = 1512.0 MiB`** 夹住 ⇒ **`--stage-mib ≥ 1512` 全部是同一个值**（1536 与 2048 同值，实测 125.1 vs 125.6 **正落在噪声内** ✓）。⇒ **那张表要按"两个平台"读**（≤1024 一族 ~170 / ≥1512 一族 ~125），**不是"窗口 + 回落"**。
2. **★ `--stage-ahead 1024` 的"崩"不是崩，是"门没开"**：门是 **`n >= stage_ahead`**，而 **`n` = 本次 eval 调用的 token 数**，我们的 prompt ≈ **700** ⇒ **700 < 1024 ⇒ `ahead=false` ⇒ 根本没进重叠** ⇒ 落到 `G2a` 那一支（13.6 / 命中 9.0% / CPU ms 67）**完全吻合**；**加大 `--stage-mib` 无用** ⇒ 因为**门在缓冲之前**。
3. **两个默认值的论证依据都是"另一类卡/另一类模型"** ⇒ 又一条"别人的数字不能照搬"（§3）。

## §1 `stage_mib` 的语义与"越大越差"

### 1.1 分配（A）

```cpp
stage_bytes_ = std::max(std::min((size_t) opt_.stage_mib << 20, (size_t) n_expert_ * one_expert), one_expert);  // engine.cpp:1668
stage_ = dmalloc(stage_bytes_ + 256 + kTail, "the expert staging buffer");                                      // :1670
```
- `one_expert = max over moe layers of (L.slot_down() + L.d_bytes)`（`:1625`）⇒ 本靶 = **1,548,288 + 1,548,288 = 3,096,576 B = 2.9531 MiB**（`专家取数几何审计-20261016.md:47-48`，A）。
- ⇒ **上限 = 512 × 2.9531 MiB = 1512.0 MiB** ⇒ **`--stage-mib ≥ 1512` 全部等价**。
- ⇒ **★ 实测吻合**：`1536`（>1512 ⇒ 夹到 1512）与 `2048`（同样夹到 1512）给出 **125.1 / 125.6** ⇒ **同值**。

### 1.2 这个缓冲既是"过路缓冲"也是"预取窗口"（A，两个用途各一处）

| 用途 | 公式 | 出处 |
|---|---|---|
| **过路**：一层分几轮算 | `per_round = stage_bytes_ / (gu2 + L.d_bytes)`（`gu2 = L.slot_down()`） | `:2342` |
| **预取**：一层预取几个专家 | `L.ahead.resize(min(#非缓存, stage_bytes_ / (2*L.gu_bytes + L.d_bytes)))` | `:1255`（`plan_ahead`） |

**代数（本靶，非门控：`gu_bytes = d_bytes = 1,548,288`、`slot_down() = gu_bytes`、`one_expert = 2.9531 MiB`）**：

| `--stage-mib` | 实际 `stage_bytes_` | **`per_round`（一层几轮）** | **`L.ahead` 上限（预取几个）** |
|---|---|---|---|
| **2048 / 1536** | **1512 MiB** | **512 ⇒ 一层 1 轮** | **341** |
| 1024 | 1024 MiB | 347 ⇒ **2 轮** | 231 |
| 768 | 768 MiB | 260 ⇒ **2 轮** | 173 |

- `round_` 的构造（`:2343-2345`）：`[n_cached]` → 若有 ahead 则 `[n_cached+n_ahead]` → 之后每 `per_round` 加一个 ⇒ **默认（1 轮）时 `round_.size()-1 = 1`**；768/1024（2 轮）时 **= 2**。
- 每轮之间的搬运靠 `ev_free_`（`:2442`）/`ev_ahead_`（`:2426`）配对 ⇒ **轮数 ≥2 才有"轮间流水"**。

### 1.3 ⇒ 机制候选（**B/D，我不采信队长的猜；给出可判别实验**）

> **首选候选（结构可读）**：**默认（≥1512 MiB）把"整层"塞进一轮 ⇒ `n_round = 1` ⇒ 没有轮间流水**；小缓冲（768/1024）把一层拆成 **2 轮** ⇒ **第 2 轮的搬运被第 1 轮的计算藏住** ⇒ 更快。
> **★ 能变红的判别实验（零成本、只加两档）**：扫 **`--stage-mib 1200` 与 `1400`**（都在 1024 与 1512 之间）
> - **1400 也 ≈170** ⇒ 阈值靠 **1512** ⇒ **"整层合一"这件事**才是变差的原因（clamp 说成立）；
> - **1400 ≈125** ⇒ 阈值**更低** ⇒ 是"缓冲越大越差"的连续机制（另有原因，需再查）。

**★ 一并排除一个候选（有实测负控）**：**"挤了别的分配/arena 变小 ⇒ 命中降"** —— `stage_` 在 `alloc()` 里分配（`:1670`），而 `alloc()` **早于** `fill_expert_cache()`（`:1487`→`:1489`）⇒ **stage 每大 1 MiB，arena 少 1 MiB**（这条是真的）。**但实测命中 97.1% 不变**（1512→768 差 744 MiB = 251 对 = **1.2% of 20480**）⇒ **远不足以解释 26% 的速度差 ⇒ 这条被实测排除**。

## §2 ★ `--stage-ahead` 的"门"：为什么默认 1024 等于关闭

### 2.1 门的原文（A）

```cpp
const bool ahead = opt_.stage_ahead > 0 && (n >= opt_.stage_ahead || shared_ahead_);   // engine.cpp:2197
```
- **`n` = 本次 `moe_rows(L, il, n)` 的 token 数**（即**一次 eval 调用的 token 数**，不是 prompt 总长、不是 batch 上限）。
- **`shared_ahead_`**：**只在"一次读多个调用"的层主序路径里整段置真**（`:2935` 置真 → `:2944/:2996/:3001` 复位），其**用途就是**"一个多调用读里，**连最后一个短的调用也照走重叠**"——与 help 原文「**in a read of several calls and this many tokens every call does**」逐字对应。

### 2.2 ⇒ 我们那次跑走的是哪条路（A）

- `read()` 的分流（`:2855`）：`if (n_calls == 1 || !mmq_ || all_cached() || n < opt_.stage_ahead) → 逐调用 eval()`。
- **我们的场景**：prompt ≈ **700–709 token**、`--prompt-batch 1024` ⇒ **`n_calls == 1`**（700 一次装得下）⇒ **走逐调用 eval()** ⇒ `moe_rows` 里的 `n = 700`。
- ⇒ **`--stage-ahead 1024`：`700 >= 1024` 为假、`shared_ahead_` 也为假 ⇒ `ahead = false` ⇒ 一次预取都不做** ⇒ 与 `--stage-ahead 0`（`G2a`）**同一条路** ⇒ **拿到同一组数**：**prefill 13.6 / 命中 9.0% / CPU ms 67** ✓✓（**实测逐项吻合**）。
- ⇒ **`--stage-ahead 128`：`700 >= 128` 为真 ⇒ `ahead = true`** ⇒ 预取生效 ⇒ 126.0 ✓。
- ⇒ **"加大 `--stage-mib` 救不回来" 的原因**：**门在缓冲之前**（`:2197` 的 `ahead` 一旦为假，`:2234-2243` 整段预取都不执行，`stage_bytes_` 不参与）⇒ **不是缓冲不够，是根本没走那条路**。

**⇒ 结论**：**默认 `--stage-ahead 1024` 对"单调用 + 短于 1024 的 prompt"= 关闭**。这不是"崩"，是**默认值的适用域与本机口径不相交**。

**★ 能变红的预测**：**换 ≥1024 token 的 prompt 再跑 `--stage-ahead 1024`** ⇒ 应当出现重叠（prefill 跳到 ~125+）；**若仍 13.6 ⇒ 我的"门"判读错**。

### 2.3 命中为何跌到 9.0%（A/机制）
`ahead=false` ⇒ `n_ahead=0` ⇒ `L.ahead` 空 ⇒ **一层的非缓存专家只能"路由后拷"或交 CPU**；`--cpu-share` 默认 <0（按 `share_[]` 自适应）⇒ **大量专家落到 CPU** ⇒ 打印的 `gpu/(gpu+cpu)` 跌到 9.0%、`CPU experts` 涨到 67 ms/token ✓（与 `G2a` 的两个读数**同时**吻合）。

## §3 ★ 两个默认值的论证依据（**又一条"别人的数字不能照搬"**）

| 默认 | 源码注释原文 | 依据是谁的 | 对我们 |
|---|---|---|---|
| `stage_mib = 2048` | 「the buffer the experts that are not cached pass through: **by default about what a layer of Q2_K experts leaves out of the cache**, and never more than a layer's experts take」（`engine.hpp:51-53`） | **另一类模型（Q2_K）** 的"一层漏出量" | 本靶是 **Q4_K/IQ4_NL、512 专家** ⇒ **不适用**；且实测默认（夹到 1512 = 整层）**正好落在慢的一侧** |
| `stage_ahead = 1024` | 「**with 8 GB of VRAM was the faster of the two up to about 1,000 tokens**」（`engine.hpp:54-58`） | **另一类卡（8 GB）+ 约 1000 token** 的经验 | **本机 32 GB、prompt ≈700** ⇒ **默认恰好落在"关闭"一侧** |

⇒ **⇒ 记一笔**：**两个默认值的论证依据都是"别的卡 / 别的模型"**（同族：`KP-NIFER`/`KP-UNI-0242` 那条"别人的数字不能照搬"）。

3. **【D】** §2.2 假定 prompt 为一次调用（`n_calls==1`、n≈700）—— 与 help/实测吻合，但**该次的 `n_calls` 未从 log 直接读到**（可从 `PP` 行数间接验证）。

# §5 ★ 更正（本席自纠，2026-10-16 晚；**原文保留**）

**触发**：大队长补扫出 **6 点曲线** —— `768→170.2` · **`1024→169.8`** · `1200→145.8` · `1400→128.0` · `1536→125.1` · **`2048→125.6`**。

**⇒ §1.3 的"两个平台"读法与首选候选被否**：
- 我早先只有 4 点（768/1024/1536/2048），据此判为**"两个平台"**（≤1024 快 / ≥1512 慢），并把**"默认整层合一 ⇒ 无轮间流水；小缓冲拆 2 轮 ⇒ 更快"**列为首选候选。
- **新增的 1200 与 1400 落在两者之间且单调下降**（145.8 / 128.0）⇒ **是"连续机制"，不是台阶** ⇒ **"轮数台阶"说的预测不成立 ⇒ 该候选作废**。

**改判（现采信，B/D）**：**`stage_bytes_` 越大 ⇒ `L.ahead`（预取名单上限 = `stage/(2·gu_bytes + d_bytes)`）越大 ⇒ 预取量超出"可隐藏窗口"⇒ 多出来的搬运摊在关键路径上** ⇒ **随 `stage_bytes_` 连续变慢**。

**§1.1/§1.2 中仍然成立的部分（不撤）**：
- ✅ **上限 1512 MiB 的夹取**（`n_expert_ × one_expert`）—— **`1536` ≡ `2048`**（实测 125.1 vs 125.6，**相等**）。
- ✅ **`stage` 与 arena 1:1 抢**（运行级旁证：`sm=768` arena **7144 对** vs `sm=8192`（夹到 1512）**6892 对** ⇒ 差 **252 对 = 744 MiB = 1512−768**）。
- ✅ **主因不是"抢显存"** —— 该扫描里**命中恒 97.1%** ⇒ arena 少 252 对解释不了 36% 的速度差。

**待验（能变红）**：若"预取失衡"说成立 ⇒ 在 `sa` 固定 128 时 **`--stage-mib` 取 512 应持平或更慢**（ahead 太小 ⇒ 后段只能路由后拷）⇒ **只扫 512 一点即可判**。
