### §1.1 核心段（`:688-714`，逐字）
```
### GPU utilization: the GPU is mostly IDLE during decode (major finding)

`gputop` (the Xe counterpart to intel_gpu_top) CAN be read for the engine if the
engine process is user-owned. `sycl/serve/strata-sycl.sh` runs the container as
root (no `--user`), so `gputop` cannot attribute it; a temporary copy adding
`--user <uid>:<gid>` made the engine user-owned and readable. During a 700-token
decode (240-token prompt) the A770's compute engine (ccs) sampled:

    0%  0%  4.1%  14.8%  41.4%  2.8%  0%  8.5%  65.0%  84.3% ...

— i.e. **mostly 0-20%, spiking occasionally**, mean over the run ~20%. The GPU is
**not saturated during decode**. (1 Hz sampling and ccs attribution make this
coarse, but the many 0% samples during an active generation are unambiguous.)

This **overturns the "ms_wait = GPU compute" reading** in the hypothesis above.
`ms_wait` is the host waiting for the GPU's layer ring, but the ring is late
because the GPU is **stalled on the CPU/handoff**, not because it is busy. So the
decode window is dominated by **per-layer host<->GPU synchronization and the CPU
expert pool, not GPU kernels** — consistent with every kernel measured standalone
being minor. The path to 20 tok/s is therefore to **cut the per-layer handoff
latency / overlap the CPU pool with the GPU**, not to optimize kernels.

Next empirical step (cheap, needs no profiler): quantify the handoff cost by
measuring round-trip latency of the doorbell (ring -> host -> flag -> GPU) on this
`xe`/PCIe-3.0-x4 card and how much of the window is idle GPU time, then decide
the architectural change. This is now the primary direction; WP4/WP5 (kernel
optimization) are closed as mis-targeted.
```

### §1.2 决定性结论段（`:734-761`，逐字摘）
```
### Per-stage breakdown obtained (decisive): the CPU pool handoff dominates
...
`waitA`/`waitB` are the GPU **spinning for the CPU expert-pool flags**;
`copy+combine` is the CPU results copied to the GPU and combined. Together they
are **~87% of the window**; every actual GPU kernel is small (tens of ms). This
independently confirms the gputop ~20%-busy finding.

**Definitive conclusion:** A770 decode here is limited by the **CPU expert pool
and its per-layer host<->GPU handoff**, not by GPU compute. WP4/WP5 (kernel
optimization) are closed. The path to 20 tok/s is architectural: cut the
per-layer handoff latency and/or overlap the CPU pool with GPU work. (Note the
absolute stage numbers are inflated and `NOCHECK` distorts the pipeline, so the
next step is an *honest* profiler — fix the eager payload path — to size the real
handoff cost before designing the change.)
```

## §2 ② 它说的是哪种"占用"

| 说法 | 指什么 | 是本文陷阱吗 | 依据 |
|---|---|---|---|
| **"GPU utilization: the GPU is mostly IDLE during decode"** | **GPU 计算引擎利用率**：`gputop` 的 **ccs（compute engine）busy%**（≈ intel_gpu_top / nvidia-smi 的 util%） | **是（主句）** | `A770_SPEED_SPEC.md:688-700`（"ccs sampled … 0-20%, mean ~20%, not saturated"） |
| SM occupancy / register occupancy | 每 SM 的 warp 槽占用（kernel 级） | 否（但同族："More registers can reduce occupancy; an accepted flag alone is not evidence of a speed improvement."） | `A770_SPEED_SPEC.md:188` |
| 显存占用（VRAM occupancy） | 显存被占了多少 | 否（同族："VRAM occupancy alone is not a throughput measurement."） | `AMD_HIP.md:129` |
| 功耗/温度撞墙 | power/thermal throttle | **不是**（A770 文档里没有这个说法；它测的是 ccs busy%；温度只出现在 bench README 的旁记） | `A770_SPEED_SPEC.md` 全文（本件 grep 无 throttle/power 论述） |

⇒ **需求所指的"GPU 占用"= GPU 利用率（util%），不是 SM occupancy、不是显存占用、不是功耗墙。**

## §3 ③ 机理（为什么"占用高"不是目标）

原文给的机理链（`:688-714` + `:734-761`）：
1. **GPU 不是算不过来**：decode 期间 ccs 采样**多数 0–20%**、均值 ~20%。1 Hz 采样粗，但**活跃生成期间大量 0% 样本是无歧义的**。
2. **GPU 在等**：`ms_wait`（host 等每层 ring）里的 ring 迟到，不是因为 GPU 忙，而是因为 **GPU 卡在 CPU/交接上**。
3. **交接是什么**：host 每层等 GPU 的 ring（doorbell），再跑 CPU 专家池，再把 CPU 结果 copy+combine 回 GPU；eager 分段表显示 **`waitA`/`waitB`（GPU 空转等 CPU 池的 flag）+ `copy+combine` 合计 ≈ 87% 的窗口**，真正 GPU kernel 只有几十 ms。
4. **结论**：**"提高 GPU 占用"（更大 kernel、更高 occupancy、更忙的 GPU）不会缩短墙**——墙是**串行的每层交接**。所以原文把 **WP4/WP5（kernel 优化）关闭为 mis-targeted**，路径改成"**cut per-layer handoff / overlap CPU pool with GPU**"。
5. **这本身就是一次"撞墙"的记录**：文档先写了"`ms_wait` = GPU 计算"的假设（`:537-543`、`:559-561`、`:575-576`），后由 gputop 实测**推翻**（`:702` "This overturns…"）——**先相信占用/等待刻度的解释、后来发现看错了对象**，正是需求所指的"陷阱"。

## §4 ④ 我们今天有没有撞到同类（对照 lead 的四个拐点 + 我们自己的 A 级读数）

### §4.1 首要证据：我们的 GPU 在 decode 期间几乎空闲（A 级）
- **nsys 现有 trace**（`C:\sp3\nsysR13.sqlite`，32,442 个 kernel 记录，来自 `run_R13_NSYS_20261018.cmd` = `sp_ring2.exe` decode 45 token）：
  - 全程 kernel busy = **16.5%**（union of kernel intervals / trace span 19.7 s）；
  - 预填后按 500 ms 分箱：`38, 3, 4, 4, 4, 3, 4, 4, 2 %` ⇒ **decode 期间 GPU kernel busy ≈ 2–4%**（其它 bin 是预填/加载）。
  - 注意口径：nsys 的 kernel busy 不含 copy；但即使加上 copy，也远到不了"忙"——**我们的 decode GPU 利用率比 A770 的 ~20% 还低一个量级**。
- **R49 三相账**（`C:\sp3\R49-L1-20261018.log:223`，A 级）：每 token 墙 **65.9 ms** = cpu_pool **49.1** + router_wait **7.7** + host/launch **3.4** + commit **5.6**；`cpu_pool = 1.53 GB ÷ 31.1 GB/s`（纯带宽）。
  ⇒ **墙 = CPU 专家腿 + 每层交接**，GPU kernel 只占墙的 ~3%（≈1.7–2.6 ms/token 的常驻专家 kernel + attention/mamba），**与 A770 文档同一结论**："不是 GPU 计算，是 CPU 池和交接"。

### §4.2 四个拐点 = 四个"占用/并行↑但更慢"的同型陷阱（A 级）
| 拐点 | 读数（A） | 同型教训 |
|---|---|---|
| **threads 16 → 24** | 16.23–16.40 → **12.65 tok/s（−22%）**；`cpu_us/miss` 96.3–100.1 → **127.9–156.6**（交接 §8.2） | "并行单元越多越好"错：23 worker 压 16 物理核（SMT/混合核超订），**CPU 侧 occupancy↑ 反而慢** |
| **reserve 3000 → 2400** | **−15.4%**（`cover()` 在 KV 增长时 `shrink_cache()` 吃掉刚填的槽；reserve 2400 的 quarter 只剩 600 MiB）R18/R22 | "驻留槽越多越好"错：显存占用↑ ⇒ 尾部被切 ⇒ 命中与 decode 双降 |
| **窗口 depth 3 → 7** | R45 depth7：兑现 41%、**miss +147%** ⇒ **−59.9%**；R46 depth3：**−2.4%** | "每轮 token 越多越好"错：窗口内被拒 token + draft 块 MoE 全进 CPU 腿 ⇒ `miss/token` 暴涨 |
| **pcie 0.35（分流比例）** | R39：direct/frac0.35 绝对值 **0.0%**（机制 +16.9% 但被 CPU 腿吃掉）；dma/frac0.35 仅 +5.6%；frac 0.8 **−13.3%** | "把更多活推给 GPU（让 GPU 更忙）越好"错：每层串行交接没变，净收益≈0 |
| （附加）accepted 代理 | `--expert-swaps 64`：命中 41.2→62.2%、miss −35.9%，但 per-token 只 **+3.5%** 且确定性全失（交接 §10.3） | "命中率↑=更快"错（同一代理指标陷阱） |
| （附加）tokens/round 代理 | `--lookup 3`：p6792 +77%（模板），异构 alt **−2.8%**（交接 §9.5） | "tokens/round↑=更快"错（只在模板负载成立） |

### §4.3 我们自己的"kernel 优化"也已被同一堵墙挡回（与 A770 关闭 WP4/WP5 一致）
- R36（CPU 行内核/VNNI）：ids 位同但 decode **−1.1%**（窗口内 uses 段长 ~1.2，省不回来）；
- R41（CPU MLP 预取/unroll）：`cpu_us/miss` **130.9 → 132.6/133.7（未降）**、per-token **+0.2%/+1.6%（反升）** ⇒ 判红。
- ⇒ **改 kernel/占用（CPU 或 GPU 侧）不改变墙**；墙是"CPU 腿字节 + 每层交接"。

### §4.4 一个必须说的边界（避免把 A770 结论无脑外推）
- A770 是 **Intel Arc/SYCL、PCIe 3.0 x4、CPU 池 ~36 ms vs GPU ~123 ms** 的特定配置；**老师 0.1.40.2 在 4080S 上的 q38 日志相反**：`verify window wait for rings 12.102` vs `pool 2.930 ms/round`（`C:\sp3\q38_perf.log:46`，45 token 短跑）⇒ 那个 regime 里 GPU 半段是大头。**结论是"看 regime，不看 util 数字"**——这恰是原文的教训，而不是"GPU 永远空闲"。

## §5 ⑤ 可操作结论（对下一步：专家表 / ReLU² / host+commit 打点）

1. **判据层面（立刻可做，零 GPU）**：把 **GPU util% / SM occupancy / 显存占用 / 命中率 / tokens-per-round** 正式列为"**只解释、不验收**"——验收只看 **ms/token + ids**。我们已有的 `验收\decode判据表-v2-20261018.md` 的 D1/D5 已是速度+质量，建议加一行显式禁令（依据：`A770_SPEED_SPEC.md:688-714`、`AMD_HIP.md:129`、`A770_SPEED_SPEC.md:188`）。
2. **方向排序与这条教训一致**：
   - **先做 CPU 腿字节（ReLU² 零跳过）**——它直接砍 `cpu_pool` 的 49.1 ms（占墙 75%），与原文"cut the CPU expert pool / handoff"同向；比任何"让 GPU 更忙"的改动都值。
   - **然后做 host+commit/每层交接打点**——我们 host/launch 3.4 + commit 5.6 = **13.7% 墙**；原文/老师 §8.6 的"GPU 侧路由 + 整图/门铃"正是这条（消 6.6 ms router wait + 逐层 launch）。**做之前先有"honest profiler"**（A770 的教训：他们的 stage 表被 host stamp 放大、eager 路径坏，必须先修仪表）——对应我们的 `情报-K §5 P1 打点`。
   - **专家表**：按 **ms/token** 判，不按命中率（R43 的 −8.4% 来自 draft head 字节，不是命中率；R22 S3 命中 +2.4pp 只 +0.7%）。
3. **不要做**：为"提高 GPU 占用"改 kernel/加 occupancy/加批量（A770 WP4/WP5 closed；我们 R36 −1.1%、R41 反升；pcie 分流"让 GPU 更忙"已测 0%~+5.6%）。
4. **可加一条自检**：任何新机制，先问"它缩短的是 CPU 腿、交接、还是 GPU kernel？"——三者中只有前两者是我们今天的墙（R49 账）。

## §6 未验 / 边界
- **U1**：A770 结论是 **Intel Arc/SYCL + PCIe 3.0 x4** 的实测（`A770_SPEED_SPEC.md:694-700`），**不是 NVIDIA 三卡**；老师 0.1.40.2 在 4080S 的 q38 短跑（`wait for rings 12.1` vs `pool 2.9`）是**另一个 regime**。本件用"占用/等待不是目标"这层**方法论**，不外推"GPU 永远空闲"。
