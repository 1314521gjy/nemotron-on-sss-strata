## 4. ★ 最该补的一条：1.6 + 1.7（RouterLookahead + ForesightSwap）

### 为什么之前被我否掉，现在为什么该做
- 我引用的本机结论是"**预取是延迟工具，完美预测只改 miss <0.1%**" —— 它的前提是**预取不改字节总数**（只是提前搬）。
- 但在我们这个 regime 里，**预取会改"miss 走哪条腿"**：预取命中 ⇒ **CPU miss 变 GPU hit**，CPU 腿的 1.16 GB/token 直接少掉那一部分。
- **前提 = 有空闲 VRAM 槽放预取来的专家** —— 我们恰好缺。
- **但有一条路**：decode 期间 `stage_` + `ring2` 的 **3 GB 是闲置的**（prefill 专用）⇒ 当 **decode 预取缓冲 ≈968 槽**。

### 形态（可落地的设计）
```
每层 l：
  ① 用本层 MoE 输入 h 喂「l+1 的 router 权重」 ⇒ 预测 l+1 的 top-22（便宜：一个 512-d 点积）
  ② 把预测专家里「不在 cache」的，从 host pinned 用 up_/PCIe 异步搬进「预取缓冲」
  ③ 本层 CPU 池继续算本层的 miss（搬运藏在这段时间里）
  ④ 到 l+1 时：预测命中的直接 GPU 算（miss→hit）；没预测中的仍走 CPU
```
**理论收益**：若预测准确率 = p，则下一层 miss 变为 (1−p)×原 miss。
- p=50% ⇒ CPU 腿 −50% ⇒ decode **+50%**（若固定开销不变）
- 老师的 `ForesightSwap` 报告 p≈72%（helgard 项目里也有类似数据）
- **代价**：PCIe 带宽占用（但它与 CPU 读共享 DRAM ⇒ 只有当 CPU 腿"算力受限"时才净赚 —— 这就是 builder3 正在做的微基准要回答的）

### 判据（预注册）
1. **预测准确率**（先零 GPU 量：用 `p_decode2`/`p_routing` 的历史路由算"用 l 层 h 预测 l+1"的 top-22 重合率）
2. 若准确率 ≥40% ⇒ 值得实现（3 跑判 decode）
3. ids：预取只改"谁在 VRAM"⇒ class-E（允许，与传统换槽同类）
4. 峰值：预取缓冲用闲置 staging ⇒ **不应增加峰值**（要自证）

## 5. 一句话

**我们用了老师的 6 条路线（chunk/MMQ/stage-ahead/up_/ring/borrow），没上的是 8 条**；
其中**真正还没开采的大件 = 1.6 RouterLookahead + 1.7 ForesightSwap**（"藏时间"的核心，且我们恰好有 3GB 闲置 staging 可当预取缓冲）；
其次是 1.9 Coverage Curve（指导 slot 分配）、1.11 head alias（+142 槽）、1.13 Batched DMA。
