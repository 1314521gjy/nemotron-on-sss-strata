## §1 borrow 移植的验收判据（**预先注册**，builder 交付后逐条勾）

### §1.0 口径（先钉死，否则数字不可比）

- 同一 prompt（700 token）、greedy、同一 profile（冻结）、同一 `--stage-mib/--stage-ahead/--cpu-share/--expert-swaps`。
- **性能每条 ≥3 跑取中位**；数值（ids/top-probs）**每条只跑 1 次**即可（确定性路径）。
- 两个"参照跑"必须先存在：
  - **REF-OFF**：`STRATA_PROMPT_BORROW=0`（旧行为）。
  - **REF-PB8**：pb=8（scratch 不成为瓶颈），只用来判"借槽是否把大 pb 拉回 pb8 的搬运量级"。

### §1.1 正控（borrow ON）

| 项 | 期望 | 依据/备注 |
|---|---|---|
| 驻留（prefill 期间） | **3640 → ≈6892**（+3,252 槽） | 队长给的移植目标；上游同型：11428 → 9041（−2387） |
| streamed 专家 | **应减少 ≈3,252** | 派生：+3,252 驻留 × 3.0966 MB = **−10.07 GB** |
| prefill | **必须 > 383.6**；据速率给区间 **~500–700**（派生） | −10.07 GB ÷ 8.9–19 GB/s = −0.53…−1.13 s；以 REF-OFF 的绝对秒数为基准 |
| 借槽回填 | 有明确读数（上游是 `lent slots refilled in 208.7 ms`）；**应计入 prefill 墙钟** | 若不计入，性能数偏乐观 |

### §1.2 负控（**必须能变红**）

| # | 臂 | 期望 |
|---|---|---|
| **N1** | `STRATA_PROMPT_BORROW=0` | 回旧数：**resident 3640 · prefill 383.6**（以及 pb 较小那档的 290） |
| **N2** | 同 N1 连跑 2 次 | 数值与性能都可复现（排除一次性缓存效应） |
| **N3** | borrow ON 但把**可借槽上限设为 0** | 行为 = N1（证明开关真的接了线，不是"改了也没差"） |

### §1.3 ★ 数值安全（**hard gate**）

| # | 判据 | 强度 | 说明 |
|---|---|---|---|
| **V1** | **ids 45 个逐位相同**（REF-OFF vs borrow ON） | **硬** | 借槽只改内存布局，不应改路由/算术 |
| **V2** | `--top-probs` | **见下** | ★ **不能无条件要求"逐位"**：借槽会**改变 prefill 期间的驻留集合**（上游 11428→9041，我们预计 7388→~6892）⇒ cached/staged 的划分与 MMQ tile 宽度都会变 ⇒ **top-probs 末位漂移是预期内的**（我们已有先例：profile 改变驻留集合时 **ids 相同、top-probs 全不同**，`KP-UNI-0244`）。 |
| **V2a（严格版，若可实现）** | 若 borrow **只借"空槽/scratch 槽"**、prompt 期间驻留集合**不变** ⇒ top-probs **必须逐位相同** | 硬 | 这是最干净的实现；若做不到，转 V2b |
| **V2b（现实版）** | 驻留集合改变时：**ids 逐位 + top-probs 单点最大 \|Δp\| ≤ 1e-5**（预注册阈值） | 硬 | 阈值在跑之前写死；若超阈，按"数值路径被改变"处理，不算通过 |

> ★ 建议先尝试 **V2a**（只借空槽）。若 cache 满（7388/7388）导致必须挤占，再走 V2b，并在回执里写明"驻留集合变化"这一事实。

### §1.4 ★★ 静默退化（**这条最关键**）

| # | 判据 | 做法 |
|---|---|---|
| **S1** | **prompt 之后再 decode 32–64 token，ids 与 REF-OFF 逐位相同** | 借出的槽**回填的专家必须是对的**；若回填了旧数据/半份数据，decode 会在头几个 token 就分叉 |
| **S2** | **回填后的槽内容抽检** | 对 **借过的槽**（至少 8 个）+ **未借过的槽**（对照 8 个）各算一次内容哈希/逐字节比对 pack；上游有 "slot 0 verified" 的先例 |
| **S3** | 回填耗时 | 与上游同量级（~200 ms/2387 槽 ⇒ 按比例）；若回填被跳过而 decode 仍对 ⇒ 说明借的是**空槽**（好事，记下来选 V2a） |
| **S4** | 二次 prefill | 连续两次 prefill（第二次用同一 session）ids 均与 REF-OFF 相同（确认回填后 cache 状态可复用） |

### §1.5 ★ 冲突判据（**必须响亮失败，不许静默**）

**判据 C1**：借槽需求 > 可借上限 ⇒ **抛异常、非 0 退出、错误文本含 `do not fit`**（或等价），**绝不允许**静默少借/静默降级。

**怎么人为制造一次冲突（负控，零 GPU 可先做代码级）**：
1. 加一个**只用于测试**的 env：`STRATA_PROMPT_BORROW_SLOTS=<n>`（覆盖自动计算）。
2. 跑 `n = 可借上限 + 1`（保守取 `n = cache_slots + 1`）⇒ 期望：**立即失败**，打印需求/可借两个数。
3. 跑 `n = 可借上限` ⇒ 期望：成功（证明边界判据不是"永远拒绝"）。
4. 跑 `n = 0` ⇒ 期望：等价于 `STRATA_PROMPT_BORROW=0`（三条互相咬合，任何一条不成立都说明判据没接线）。
5. **数据冲突的等价测法**：让可借槽**恰好覆盖 profile 前 100 名专家所在的槽**（构造一个把 borrow 起点指向槽 0 的测试开关），prompt 路由到这些专家 ⇒ S1/S2 必须仍然通过（证明"被借走的槽在 prompt 期间没有被当成 resident 使用"）。

### §1.6 通过/失败判定（汇总）

| 判定 | 条件 |
|---|---|
| **通过** | §1.1 全中 **且** §1.2 N1–N3 全中 **且** V1/V2a 或 V1/V2b 通过 **且** S1–S4 全过 **且** C1 能响亮失败 |
| **失败（必须回滚）** | 任一负控**不变红**（说明开关没接上）；ids 有一位不同；decode 分叉；冲突静默通过 |
| **降级（记录但可继续）** | V2b 的 \|Δp\| 超 1e-5；回填耗时明显高于比例；借槽数达不到 3,252 |

## §2 `--kv-resident` 值不值得移植（**结论：我们的默认上下文下不值得**）

### §2.1 我们的 KV 几何（已有账，A）

- **8 个 attention 层**；每层 `head_count_kv = 2`、`head_dim = 128`；**f16**。
- **8 KiB/token**（= 8 层 × 2(K,V) × 2 head × 128 × 2 B）。出处：`P3-20261016` 的显存三方账（`nemotronhmoe.cpp:246` `card_row_bytes`、`:197-204`，`engine.cpp:518`，`Options::max_context=8192` `engine.hpp:41`）。
- **KV 与专家缓存共用同一块 arena**（`cover()` → `shrink_cache()`，`engine.cpp:533-551`）⇒ **每 1 GiB KV 恰好挤掉 ~347 个专家**（3.0966 MB/专家）。

### §2.2 按上下文算（派生）

| max-context | KV 总量 | 挤掉/腾回的专家 | 少搬的 streamed 字节 | 相对 borrow（−10.07 GB） |
|---:|---:|---:|---:|---:|
| **8,192（我们的默认）** | **64 MiB** | **22** | **0.07 GB** | **~1/144** |
| 65,536 | 512 MiB | 173 | 0.54 GB | 1/19 |
| 262,144 | 2 GiB | 693 | 2.15 GB | 1/4.7 |
| 1,048,576（模型上限） | 8 GiB | 2,773 | 8.59 GB | 0.85× |

- 计算式：`KV GiB = ctx × 8192 B / 2^30`；`专家数 = KV GiB × 346.7`；`字节 = 专家数 × 3.0966 MB`。
- ★ **默认 ctx=8192 时，KV 只占 64 MiB —— 拿它去换专家（22 个）完全没有意义**。

### §2.3 代价（它那边实测的）

- 上游日志：`KV streaming: 32768 of 1048576 cells per QSA layer in VRAM, the K/V in **12.38 GiB of pinned RAM**`（`prof-warmup-base.txt:20`）——**1M 上下文要 12.38 GiB 的 pinned 主机内存**，且 decode 每 token 要跨 PCIe 读 KV。
- 我们若在 1M 上下文做同样的事：**8 GiB pinned**，decode 每 token 读 8 KiB（带宽可忽略，但锁页内存与页文件要够）。
- 与 borrow 对比：**borrow 是"零 pinned、零 PCIe、用完回填 ~200 ms"**；kv-resident 是"长期占 pinned + 每 token 稍微多一次读"。

### §2.4 ⇒ 一句话

> **默认 ctx=8192 下，`--kv-resident` 只值 0.07 GB（borrow 的 1/144），不值得移植；只有当工作负载固定在 ≥256K 上下文（尤其 1M）时，它才值 2–8.6 GB，届时再考虑。优先级：borrow ≫ kv-resident。**

## §3 未验 / 风险

1. **【未验】** borrow 的预期数字（+3,252 槽、−10.07 GB、500–700 tok/s）是**派生**，不是实测；最硬的判据是 **streamed 字节下降量**与 **ids/decode 逐位**。
2. **【未验】** 我们的 cache 是否真的满（7388/7388）——若还有空槽，borrow 可能走 **V2a 严格版**（top-probs 逐位），这比 V2b 好。
3. **【已核：不存在】** `--kv-resident` 在 poly 引擎里**不存在**（`grep -rn "kv-resident\|kv_resident" src/poly include/strata/poly` **0 命中**）⇒ 若要做是全新接线，移植面另算；本页判"值不值"：**默认 ctx=8192 下不值**。
4. **【口径】** "290 / 383.6" 对应不同 pb；回执里要写清各自 pb，别混。
5. 本件**只读、零 GPU、未改码、未碰 `E:\strata`**。
