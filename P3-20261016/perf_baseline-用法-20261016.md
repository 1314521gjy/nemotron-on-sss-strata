# 性能基线跑批脚本 · 用法（verifier）

> **★★ t13 折进之前，`--prompt-batch 1024` 档不可用** —— 非 gated 层 >8 token 会撞 `native MMVQ ncols<=8` 崩掉（`native_mmvq.cu:939/1768`）。脚本默认**只跑 batch=8**；1024 档须显式 `--allow-batch-1024`，**只有 t13 折进后才应使用**。
> **只读准备件**：本席**未跑 GPU、未编译、未改码**（红线）。脚本写好了交**有权跑 GPU 的人**执行。
> **AI：deepseek-flash[1m]** ⇒ **自验，不构成独立验收**。证据 **A** = 本机实测（语法/解析/离散度函数自测）。

---

## 1. 它做什么
把 t8 定死的性能口径落成**可复现跑批**：跑 N 次（默认 3）→ 解析引擎性能行 → 出中位 + **负控离散度**。

口径源：`src/poly/main.cpp:716-724`；`Stats` 在 `engine.hpp:135-140`。
- decode tok/s = `1000*(produced-1)/decode_ms`（★ 分子减 1，首 token 算 prefill）
- prefill tok/s = `1000*read/prompt_ms`
- 专家在卡比 / CPU 专家 ms/token / router wait ms/token / 换入次数 / 跳出 / 投机命中

## 2. 用法
```
python perf_baseline.py --model <gguf> --text perf_prompt_long.txt \
    --runs 3 --max-new 64 --threads 24 --exe build-p3/strata-poly.exe \
    --out perf_baseline_old.md --tag old

# 1024 档（★ 只在 t13 折进后）
python perf_baseline.py ... --allow-batch-1024 --out perf_baseline_t13.md --tag t13

# 关投机一档（与 llama-simple 同口径；性能基线**默认生产态=投机开**）
python perf_baseline.py ... --no-draft

# 只看命令、不跑：先核参数
python perf_baseline.py ... --dry-run
```
**跑批红线（脚本内建）**：必带 `--vram-reserve-mib 2500`（缺则 assert 拒绝）；**一次只跑一个 GPU 作业**；**跑前核 exe sha**。

## 3. 长 prompt（≥512 token）
- 现成文件：`perf_prompt_long.txt`（英文散文 **607 词** ⇒ 估 ~900+ token；**连贯多样**，避免重复导致的专家缓存假命中）。
- **分词**（缺省走这条）：脚本调 **`llama-eval-callback`（pin 同源、CPU-only、`-ngl 0`）** 拿 id 序列 —— evalcb 会把每个输入 token id 打进日志（`number of input tokens = N` 后逐行），脚本抓取。**CPU-only，不占 GPU 窗口**。
- 也可 `--tokens id,id,...` 直接给（跳过上面的分词）。
- 若 prompt <512 token，脚本**发警告**（prefill 会被单次调用开销淹没）。

## 4. 负控（★ 判据必须能变红）
**同参数重跑**的离散度 `max|x−median|/median` 应落在 **±29%**（t8 §3.2 实测噪声地板 26%/29%）：
- 落地板内 ⇒ **PASS，基线可用**；
- **超出 ⇒ 判「脚本或环境有问题，基线作废」**（不解释为"提速/退化"）。
脚本对 decode 与 prefill **各出一行**判定。

## 5. 已自测（A，零 GPU）
- 语法/`--help`/`--dry-run` OK；dry-run **打印真实命令**（已核 8/1024、生产态/关投机 四种组合的 flags）。
- **性能行解析**：用现成 `nodraft2.log` 的真实性能行自测 → 正确解出 `{pre 40.6, gen 19.01, vram 56.6%, cpu 30.2ms, route 6.5ms, swapped 934, ...}`；空输入返回 `None`。
- **离散度函数**：同值 → `0.0`；`[19.0,24.7,15.0]` → `0.30`（>29% ⇒ 会报红）。

## 6. 未做 / 边界（如实）
- **未跑 GPU**（本席红线）⇒ **基线数值本身尚未产生**，脚本仅备好。
- 口径默认 **tail-skip 0**；`--tail-skip 6`（提速档、会改答案）请**另记**，别与 0 混。
- 默认**生产态（投机开）**；`--no-draft` 是**另一档**，两档别混记。
- 「显存峰值」**仍无埋点**（t8 §1 U-显存峰值）⇒ 本脚本**不输出**该指标。

## 7. 分阶段耗时分解（脚本已内建，回答「为什么这么久」）

脚本在每次 run 前后用 `time.monotonic()` 测**整段墙钟**，并从引擎输出抽分项。**口径三要素（量 / 范围 / 分辨率）已逐行标注**：

| 阶段 | 量 | 范围 | 分辨率 | 数据来源 |
|---|---|---|---|---|
| **拉起+入卡** | 秒 | 进程启动 → 装载完 | **0.1 s**（日志 `loaded in %.1f s`） | 引擎启动行（**唯一覆盖该段的埋点**） |
| **prefill** | 毫秒 | 整段 prompt | **反推** `1000·read/prefill_tok/s`；tok/s 打 0.1 ⇒ 相对 ~0.3% | 性能行 |
| **decode** | 毫秒（整段） | `produced−1` 个 token | **反推** `1000·(produced−1)/decode_tok/s`；打 0.01 ⇒ ~0.05% | 性能行 |
| **decode/单token** | 毫秒 | 每生成 token | 同上 | 反推 |
| **其余（启动/退出/落盘）** | 秒 | 墙钟 − 上述三项 | ★ **无独立埋点，为差值** | 脚本实测 − 分项 |
| **整段墙钟** | 秒 | 本 run 全程 | 脚本 monotonic（~µs） | 脚本 |
| **专家入卡** | 个 / GiB | 载入 VRAM 的路由专家 | 引擎启动行 | 启动行 |
| **显存峰值** | — | — | — | **★ 无埋点**（如实标） |

**两档横向对比**：脚本自动算 `batch 1024 − batch 8` 的差，并**点名「相对差异最大」的一段** ⇒ 直接给出**提速第一靶**。
（预期：**prefill** 是 t13 折进的直接受益段；`拉起+入卡` 两档相同、`decode` 基本不变。）

**注意**：`拉起+入卡` **每次 run 都要付一次**（脚本每个 run 都新起进程）⇒ 这本身就是「跑测为什么久」的一大块：**3 次 × 2 档 = 6 次装载**，每次 ~10 s ⇒ 光装载就 ~60 s。
**已自测**（A，零 GPU）：用 mock 的性能行/启动行跑通全表渲染；**墙钟 < 分项和时「其余」显示「—（异常）」**（防 mock/异常时报负数）。

## 10. ★ `all`（全开）档：**定义待定 → 已禁用**；另修正一处语义
- `PRESETS["all"] = None` ⇒ 传了 `all` 会被**拒绝并提示**（不猜着跑）。
- **我此前拟的 `--tail-skip 6` 已撤**，理由（**A，源码**）：`--tail-skip N` **不是「跳过尾部 N 层」**，而是「**位次 ≥ N+1 的专家不算**」（`main.cpp:789-791`、`engine.cpp:1936` 的 `host_k[j] >= opt_.tail_skip`）。
  ⇒ **N=6 对 top-22 = 只留前 6 个专家、丢 16/22（≈73%）** = **牺牲正确性换速度**，**不是免费开关**，**不能当基线**（会让基线虚高，且与判据链 exe 行为不一致）。
  ⇒ 数值 `6` 的**来源** = `main.cpp:791`（**引擎给 Qwen3.6 的 setup 默认**），**非 Nemotron 实测** —— 来源已交代，**不用**。
- 现在可跑的是 **语义确定的两档**：`default`（batch 8）与 `batch1024`（脚本默认值即 `default,batch1024`）。
- `all` 等两个输入汇合再定：**scheduler 的「哪些开关实测有效」** + **builder 的 `--help` 完整开关清单**。

## 11. 开关分类护栏（队长 2026-10-16 裁定分界线，已写进代码；★ 方向已更正）

**★ 核心分界（别读反）**：近似开关 **可以进「性能档」，只是不能进「正确性档」** —— **不是禁用**。
- 需求中的"全开基线" = **实际使用时的最快配置**；若实际用时会开投机/裁剪，**基线就该开** —— 一律排除会让基线**虚低**（那是要避免的**另一半错误**）。

| 类 | 定义 | 例 | 进基线？ |
|---|---|---|---|
| **真·快** | **不改变计算结果** | `--prompt-batch`（大档 / t13 扩列） | ✅ 可全开 |
| **近似** | **用精度换速度**，改结果 | `tail-skip 6`、`lookup 3`、`window 8` | ✅ **性能档**；❌ 正确性档 |
| **关近似** | **把近似关掉**（**不是**近似开关！） | `--no-draft`、`lookup 0`、`tail-skip 0`、`window 1` | 正确性档用 |
| **未知** | 未实测 | `--cpu-share`、`--expert-swaps` | ⚠ 用前补实测 |

- 代码：`FLAG_CLASS` / `APPROX_VALUE` / `classify()`（**按语义 + 取值**判，见下）。每档输出打印类别，并给出结论：
  - 含近似 ⇒ **「本档是【性能档】…可作性能基线；不可作正确性档」**；
  - 不含近似 ⇒ **「本档兼可作正确性档」**。
- **同 flag 取值相反**：`--tail-skip 0`/`--lookup 0`/`--window 1` = **关近似**；取正数才是近似。⇒ 分类必须看**取值**，不能只看 flag 名。

## 14. 横向对比表升级（队长 2026-10-16 两条要求，已实现）

**(1) `命中率高 ≠ 快` 护栏**（台账 §9.2 封印：`--expert-cache` 吃满显存 ⇒ decode 85.0→21.6 t/s **−75%**，命中率反升 **98.4%**）：
- 横向对比表**命中率(专家在卡%) 与 decode tok/s 并排**；
- **命中率↑ 而 tok/s↓ 时单独告警**（真输出样例）：
  > ⚠ **`hoard` 命中率升（40.6%→98.4%）而 decode tok/s 降（18.20→5.10）** ⇒ 正是「命中率高 ≠ 快」的封印形态。**别把命中率当成绩。**

**(2) ★「智力影响」列 = 客观判（台账四取值的 ①）**：
- 各档生成的**贪心 token 序列** 与**基准档**逐位比：
  - 相同 ⇒ **`①逐位相同`（零智损，当场可判）** —— 把"无损失"**从主观变成客观**；
  - 不同 ⇒ **`≠ 首个分歧 @ token k`**（报首个分歧位置）；
  - **档内多次不一致** ⇒ 先报这个（比跨档比较更基础，说明该档本身不稳定）。
- 它同时**顺带测了投机的逐位等价性**（`all` 关投机 vs `all_approx` 开投机：若 ids 逐位同 ⇒ 投机校验正确）。

**(3) 参照量级（Qwen3.8 线，★ 不可直接移植）**：自适应层 开 vs 关 = 87.8 vs 70.0 t/s（关掉 −20.3%）；工作负载轴 1.39×，**机制几乎全在草稿接受率、命中率几乎不动** ⇒ 先验：**专家层/profile 通用、投机那层不通用**。

**(4) ★ 口径弱点（原文自陈，必须带）**：那批读数带 **~18% 顺序/会话效应**，且 **launch-flag 臂的第一臂被系统性罚慢** ⇒ **别当精确值用**。

## 15. ★★ 分类由**实测**判定（队长升格为最终依据）+ 比较器自身的负控

**规则（2026-10-16 定）**：
- **逐位相同 ⇒ 真·快（准进 `all`）**；**有分歧 ⇒ 近似（只能进 `all_approx`）**。
- ⇒ **`FLAG_CLASS` 人填表降级为「候选假设」**，只用来决定**先测哪些**；**结论一律以实测为准**。
- ⇒ 脚本横向对比表的 **`智力影响` 列已带准入结论**：`**①逐位相同**（零智损，当场可判）⇒ 可进 all` / `**≠ 首个分歧 @ token k** ⇒ 只能进 all_approx`。
- ⇒ scheduler 三条件的 **(c) 无损失** 从此**机器可判**，不依赖任何人的判断。

**★ 判据自身必须能变红（老规矩）**：
- 实现抽成独立函数 `ids_verdict()`，并入 `--selftest`，**现 13 项全过**，含**真实数据**双向控制：
  - **真实负控**：`eng_mt_8`（实跑 8 token）× `eng_mt_16`（实跑 16 token）⇒ 必须报 **`≠ 首个分歧 @ token 8`** ✅
  - **真实正控**：同一实跑 vs 自身 ⇒ 必须报 **`①逐位相同`** ✅
  - 另有 合成例（分歧位/长度不同/档内不一致/空输入）全覆盖。
- **跑批时的必做负控（需 GPU，未做）**：**加一档 `--tail-skip 6`**（已知会改输出）⇒ 横向表里**必须报出分歧**；若报不出 ⇒ **判比较器失效，本轮结论作废**。

**跑法（负控档用自定义串塞进同一次 GPU 作业）**：
```
python perf_baseline.py --model <gguf> --text perf_prompt_long.txt --runs 3 \
  --allow-batch-1024 \
  --presets "base=--prompt-batch 1024 --no-draft --lookup 0 --tail-skip 0,\
cand1=--prompt-batch 1024 --no-draft --lookup 0 --tail-skip 0 --<待测开关>,\
NEG=--prompt-batch 1024 --no-draft --lookup 0 --tail-skip 6" \
  --out perf_baseline_cand.md
```
⇒ **`NEG` 档必须报分歧**（比较器活）；**cand 档逐位相同才准进 `all`**。

## 16. ★★ 关键前提：`①逐位` 比较器的**跨运行**前提（来自候选表表头 §9.4）

**候选表表头第 2 条（引台账 §9.4 原文）**：同臂同提示 `temperature=0`，**kept 3 跑恒为 3 个不同 sha**（Qwen3.8 线）⇒
> **"逐位相同 = 数值没动"只能用于同一次运行内，不能跨运行；②类改动一律走 PPL/KL。**

**⇒ 对本脚本的直接影响（必须明说）**：`ids_verdict()` 比的是**不同档的输出**，而**每档是一个独立进程（= 独立运行）** ⇒
- **若本线跨运行确定** ⇒ 现设计**有效**；
- **若本线跨运行不确定** ⇒ 我的比较器会把「跨运行抖动」误报成「改动改结果」= **假红**，**准入结论全废**。
⇒ **在 builder 的确定性核实出结果之前：逐位结果【两个方向都不成立】—— 既不能证真、也不能证伪。**

> **★ 对称风险（队长补，我原漏）：不只"假红"，也有"假绿"。**
> - **假红**：跨运行抖动被当成"开关改了结果" ⇒ 把**该进的拦掉**（保守，可接受）；
> - **假绿**：跨运行本来就不确定、两跑"碰巧逐位相同" ⇒ 被误判为**真·快而放进 `all`** ⇒ **把不该进的放进去了** —— **比假红更危险**（假红会拦住，假绿会放行）。
> ⇒ 故核实前的正确表述 = **"逐位相同/不同"都不能作为准入依据**（**两个方向皆不成立**），不是泛泛的"不能当依据"。**这是当前最容易埋雷的一处：它不报错，只给错结论。**

**两条出路（等核实后二选一）**：
1. **本线跨运行确定** ⇒ 沿用现设计（每档一进程、跨档比）；
2. **本线跨运行不确定** ⇒ 必须改成「**同一次加载内**切开关比」（脚本做不到，需引擎加一个"一次加载里跑两套开关"的入口），或按候选表说的走 **源码级理由（只改"谁算"不改"算什么"）+ PPL/KL 兜底**。

### ★ 顺带：一条**支持"本线可能确定"的一手旁证**（A，本机实测）
我的比较器真实负控用的是 **两次真实跑**：`eng_mt_8`（`--max-new 8`）与 `eng_mt_16`（`--max-new 16`）——
**前 8 个 token 逐位相同**：`6993,2613,1256,1010,1045,2409,1395,1261`。
⇒ **跨运行（不同 `--max-new`）的前缀是重复的** ⇒ 本线**至少前缀是确定的**。
⚠ **但这不是直接证据**：直接证据要 **builder 的同参数两次跑**（同一档、同一 `--max-new`、比 sha）。**我不把旁证当结论。**

## 17. ★★ 教训升级（第三次同类 bug，根因同一个）

**事实**：`tokenize()` 连续三处错 —— ① 分词行正则（真实日志带 `<ts> I` 前缀）→ ② `-m None` 占位（靠调用方补，写法本身就是雷）→ ③ **`--ngl`**（evalcb 只认 **`-ngl`**，实测报 `invalid argument: --ngl`）。
⇒ **两档基线至今一次都没跑成**（`perf_t18.log` 全废）；builder 只好用自带分词绕开。

**根因（同一个）**：我上一轮说「**已用真实 `evalcb-pos0.log` 验证**」—— 但**我验证的是"拿真实日志喂解析器"，不是"真实跑一遍 evalcb 命令"**。
⇒ **参数名 / 调用形态的错误（如 `--ngl`）解析器再怎么测都测不出来**。

**★★ 教训升级（写死）**：
> **「用真实数据测」必须包括「真实跑一遍整条命令」**，不只是"拿真实日志喂解析器"。
> **交付脚本前，整条命令必须真跑一次**（哪怕只跑 1 个 token）—— **跑不通 ⇒ 判脚本无效**。
> 这与「判据必须能变红」同源：**"命令真的能跑通"本身就是一个必须先变红的判据**。

**已落实的护栏（不只改 bug）**：
1. `tokenize(text_path, model)` —— **`model` 显式传参**（删掉 `-m None` 占位写法）；`-ngl` 单横线。
2. ★ **硬失败**：分词得 **0 token ⇒ 打印 evalcb 的 rc + 输出尾 ⇒ `return 2` 立即中止，不再拿空 `--tokens` 去跑引擎**。
   —— 这正是三次事故的共同形态：**0 token 不报错，只是静静地传空**。现在它**必须响亮地失败**。

## 18. ★★ 通用规矩（队长裁定，由 verifier 立）：**沉默退化禁令**

> ### 凡可能「静默退化」的路径 —— 传空 / 返回空 / 吞异常 / 静默 `return` —— 都必须有**响亮的失败或告警**。

**理由**：本轮已撞见 **4 次同类**，**无一报错，全都"静静地给出错结果"**：

| # | 实例 | file:line（A，本机核） | 形态 |
|---|---|---|---|
| ① | `save_profile()` 的失败被**降级成一行 stderr**、不标记 | 服务路径 `main.cpp:670-675`（`catch` 里只 `fprintf`，**继续跑**） | **吞异常**（"下回缓存更差，这轮没事"） |
| ①b | 同一失败在**单次**路径把"跑成功"**错报成运行失败** | `main.cpp:937` 抛 → `:939 catch` → 打印 + **非零退出** | **错信号**（t2 观测的 `EXIT=1` 正是它：读者以为"跑挂了"，其实只是 profile 没存） |
| ② | `read_profile()` **文件不存在就静默返回** | `engine.cpp:176-177`：`FILE* f = fopen(...); if (!f) return;` —— **零告警** | **静默 return** ⇒ **profile 旋钮"静静地不生效"**（本线一直都在这个状态） |
| ③ | 台账 §9.4 的判据**静默不可靠** | 候选表表头第 2 条（引 §9.4） | **不报错，只给看似确定的结论** |
| ④ | 我的分词 **0 token 静默传空** | `perf_baseline.py tokenize()` 旧版 | **传空** |

**⇒ 制度化要求（对 t17 直接适用）**：
- **①/② 合起来 = profile 功能端到端"没有任何成功信号"**：写失败只在服务路径留一行、读失败**完全静默**。
  ⇒ **建议**：读写两端各加一行**显式信号**（如 `profile: loaded N entries` / `profile: saved N entries`），
  且 **`read_profile` 文件不存在时至少告警一次**（现在 `if (!f) return;` 是完全沉默）。
  **有了这两行，"旋钮到底有没有生效"才第一次可查** —— 否则每次实验都在猜。
- **④ 已落实**：0 token ⇒ 打印 rc + 输出尾 ⇒ `return 2` 中止。

**这条规矩的判据形态**：与「判据必须能变红」同源 ——
**"失败路径必须能被看见"，本身就是一条先要能变红的判据。**

## 19. ★ 测量窗口纪律（队长 2026-10-16 补明确 —— 写进本件，因本脚本会装载/扫盘）

> **窗口内的负载 = 任何吃 CPU / 磁盘 IO / 内存带宽的活** —— **包括"只读"扫盘、装载大模型、大量日志写入**。
> ⚠️ **「不占 GPU」≠「不占窗口」** —— **GPU 只是被独占的那一项，不是唯一的资源。**

**本脚本会触发窗口负载的地方（跑批前必须先确认窗口空）**：
1. `tokenize()` ⇒ 起 **`llama-eval-callback`（CPU 装载 70 GB 模型）** —— 实测工作集一度 **58 GB**、用户态满载 CPU + 连续 IO；
2. 跑批本身 ⇒ 起 `strata-poly.exe`（**占 GPU，独占**）；
3. `--selftest` / 解析 ⇒ **只读小文件，无窗口负载**（可随时跑）。

⇒ **实操**：跑 `perf_baseline.py`（非 `--selftest`）之前，**先向队长确认"此刻无测量窗口"**，**不是只看 GPU 空闲**。
（2026-10-16 一次实际事故：我的 evalcb 与 builder 的基线重叠 ⇒ 差点污染其 tok/s 读数；队长叫停。）

## 21. ★★ 教训最终精确版（队长裁定，由 verifier 落）：「真启动」的判据

**递进（每一格都在上一层修好后才暴露，不是重复犯错）**：
| # | 层 | 错在哪 | 代表的教训 |
|---|---|---|---|
| ① | 解析 | 正则认不出带前缀的行 | **mock 自测 ≠ 真实自测** |
| ② | 拼装 | `-m None` 占位 | 「真跑」要跑**整条命令** |
| ③ | 参数名 | `--ngl`（只认 `-ngl`） | 参数名只能真跑才暴露 |
| ④ | 环境/编码 | GBK 崩在 `print` | **在交付环境真跑** |
| ⑤ | 启动（路径） | 相对路径 ⇒ spawn 失败 | **dry-run 不 spawn** |
| ⑥ | 启动（DLL/PATH） | `rc=0xC0000135`、**stderr 空** ⇒ exe 没起来 | **spawn 成功 ≠ 能起来** |

### ★ 最终判据（写死）
> **「真启动」= 进程成功完成一次最小工作。**
> **不是**「`subprocess` 没抛异常」，**也不是**「`rc == 0`」—— **rc 可能是异常码而 stderr 为空**，
> 那种情况**伪装成"无输出"**，是最阴的一类。

**本脚本的落实**：
- **最小工作** = 5-token 单跑**出性能行**（`prefill … tok/s, generated … tok/s`）；**这才算"起来了"**。
- **响亮诊断**（§18）：`RUN_FAIL_RC` 把 `0xC0000135`(DLL 未找到) / `0xC000007B`(映像无效) / `0xC0000005`(访问越界) 翻成人话；**rc 是启动错且 stderr 空 ⇒ 直接报"多半是 PATH 缺 DLL"**。
- `PATH_PREPEND = [E:\llama-cpp, E:\cuda-13.3\bin]`（**存在才前置**；`.cmd` 跑法里有 `set PATH=…`，脚本此前没有）。

```
python perf_baseline.py --selftest --model x      # 解析/判据护栏（零负载）
python perf_baseline.py ... --runs 1 ... <短prompt>   # ★ 真启动冒烟：出性能行才算通
```
