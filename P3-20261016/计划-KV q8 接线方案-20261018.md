# 计划 · KV q8 接线到 Nemotron（poly 线）— 方案 + 暂缓裁决 — 2026-10-18

**裁决：暂缓，不进今天交付**（16K 交付形态下收益 ≈0）。以下为方案与"什么时候值得做"。

## ① 现有 q8 接口（主引擎线，已在树里）
- `include/strata/kernels/kv_q8.hpp`：
  - `kv_q8_bytes_per_cell()`（每 token/层字节 = n_kv·head_dim·2 + scales）
  - `kv_append_q8_steps()/kv_append_q8_step()`：量化 K/V 为 int8 codes + **每 64 值一个 fp16 scale**（scale=f16(max|x|/127)，`round-to-nearest`，clamp ±127），写 `[page][head][page_size][head_dim]`（+可选 host pools）
  - `kv_gather_q8_step()`：把选中 cells **反量化进 fp16 scratch**，attention 内核照旧读 scratch（"只改存储"）
- `src/kernels/cuda/kv_q8.cu`：`kv_append_q8_kernel`（每 64-group 一块、warp max→shared 合成）、`kv_gather_q8_kernel`（每线程 4 值，int8×scale→half4）。
- 测试：`src/kernels/kv_q8_parity.cpp`（另有 `kv_stream_parity.cpp`/`kv_hybrid_parity.cpp` 可复用骨架）。
- 主引擎的接法（参考）：`qsa_decode_attn.cu` / `qsa_prompt_attn.cu` 里 `kv_gather_q8_step(...)` → 原 `qsa_attend` 不变。

## ② Nemotron（poly）要改的几处（file:line 为当前树）
1. 存储：`src/poly/nemotronhmoe.hpp:61-62` 的 `keys`/`vals`（`uint16_t*` 连续 VMM 缓存，`kv_alloc(n_kv*head_dim, 1)`，见 `nemotronhmoe.cpp:206/212-213`）→ 增加 q8 双缓冲（int8 codes + f16 scales，布局 `[pos][kv_head][head_dim]`，每 64 值一 scale）。
2. 写入：`nemotronhmoe.cpp:318-319`（prompt 的 `store_f16_at`）与 `:321-322`（decode 的 `store_f16`）→ 换成新 `store_q8`/`store_q8_at`（新增 poly 内核）。
3. decode 读取：`:329` 的 `attend(...)` → 新 `attend_q8(...)`（内核内按 64-group 反量化 K/V，读 1B+scale 代替读 2B；需覆盖 window/ring/draft 变体参数）。
4. prompt 读取：`:326` 的 `attend_batch(...)` 走 cuBLAS 读 fp16 矩阵 ⇒ q8 需先 **chunked 反量化到 FP16 scratch** 再 gemm（读 1B+写 2B vs 直接读 2B，长上下文下**可能不赚**）或新增 q8 GEMM 路径（工作量大）；这是本方案主要工作量/风险点。
5. 其它触及点：`card_row_bytes()`/两处 KV 行拷贝（`:255/:261/:276`）要按 q8 字节数改；`snap_` 只存 recurrent state（与 max_context 无关，**不受影响**）；window 用 `attend` 的 ring 参数，需同变体。
6. 布局差异：主引擎 q8 按 **分页**（`page_table`、host pools）写，poly 是**连续 VMM**（`kv_alloc` + `cover()` 按需 map）⇒ 不能直接复用写/读内核，需为连续布局写一对新内核（量化/反量化逻辑可照抄）。
- 估计 **~250–400 行**（store_q8 ~60 · attend_q8 ~120 · attend_batch 反量化路径 ~80–120 · 接线/自证 ~40 · parity/精度测试 ~60）。

## ③ 为什么暂缓 / 何时值得做
- **16K（当前交付形态）**：KV=128 MiB → q8 64 MiB，只多 **+21 个专家槽 ≈ +0.36%**，收益 ≈0，不值得 250–400 行 + 精度门。
- **≥128K**：128K → 省 512 MiB（+165 槽，+0.8%，边际）；**1M** → 省 4 GiB（+1,322 槽，hit +6pp、miss 207→155、CPU 腿 −5.7 ms/轮）+ attention 读取减半（16.8→8.4 ms @500GB/s）⇒ decode 约 **+10–15%**，那时值得。
- 前置条件：用户真的要用 ≥128K（交付已改 `--max-context 1048576`，但 p6792 类短跑用不到）；且 **V 量化需要 flash-attn 支持**（llama.cpp 的已知约束，本机 `attend_batch` 的 cuBLAS 路径需自建反量化）。

## ④ 预注册判据（将来做时）
- **16K 臂（正确性）**：q8 on/off 的 **ids 逐位同** 且 **max|Δp| 无 >0.05 的跳变**（logits 概率差），性能不作门槛（预期 0）。
- **128K/1M 臂（收益）**：`miss/token` 下降 + **decode ≥ +5%**（目标 +10–15%）、峰值 ≤31,700、ids 记录（量化后可能非逐位同，class-E 记录）；prefill 不得退化 >2%（prompt 反量化路径是风险点）。
- 兼容性结论：**数值/几何兼容**（`n_head_kv=2` 的 GQA 由 shape 驱动，主引擎 q8 内核本身支持任意 kv heads），**布局不兼容**（分页 vs 连续）⇒ 需新内核而非直接复用。
