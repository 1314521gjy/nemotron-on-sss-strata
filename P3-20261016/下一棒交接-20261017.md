## §3 坑（★ 动任何东西之前先过一遍）

### 3.1 ★★ 三条"混杂臂"—— 以为在测 A、其实测的是 B
| 臂 | 实际发生了什么 | 后果 |
|---|---|---|
| **`--dump-layers`** | **把 `rows_` 强制设为 1** ⇒ `L.mmq=false` ⇒ **`batched()` 假 ⇒ `moe_rows()` 根本不跑** | 整跑变成 700 次单 token `moe()`；**还"看起来把 NaN 治好了"** |
| **`--no-gpu-experts`** | `L.mmq=false` ⇒ **绕过 `moe_rows()`** | 拿它当"CPU 路径"证据是错的 |
| **`tile_class(32)=0`** | pb=32 全程 class 0 | 对"class 混用"**零鉴别力** |

### 3.2 ★★ 假杠杆清单（都已实测否掉，**且每条都有差异归因**）
`top-k 22→10`（模型属性）· `PLE 跳过 MoE`（设计件说明 PLE 不改路由）· `PF_FUSED`（上游消融也只 +5%）· `KV_PREFETCH`（上游实测 8K 无改善）· `kv-resident`（我们 KV 只有 64 MiB）· 页缓存预填（65.3 GiB 在 96 GiB 机器上兜不住）· pinning 本身（热 mmap 已 21.9 GB/s）· "排序 ⇒ 大 DMA"（86/512 稀疏 id 展开会多搬 3–6×）· `--prefill-head-alias`（方向相反，对应 `--prompt-batch`）· IL 表 / `--no-vision` 存在 / `--expert-cache` 不存在。

### 3.3 ★★ 今天的两次"误判"—— 都是从残缺状态测出来就下了结论
- **单 chunk 判否两次**（`290 < 383.6`、`159.6 GB > 121.7 GB`）⇒ **真实原因都是 ours scratch 比上游大 1.6×、抢走 arena**。
- **609.6 也曾被判"复现不出来"** ⇒ 真实原因只是**漏了 `STRATA_M2_SCAN_SMEM=1`**。

### 3.4 ★★ ①b 里修掉的两个真 bug（下一个人可能会踩同款）
1. **pinned 表的竞态**：`h_rel_local_` 每批重写 + `cudaMemcpyAsync` ⇒ host 立刻写下一批 ⇒ **与在飞 DMA 竞争** ⇒ 后续批拿到别批的 bounds ⇒ **结果退化成 `1278,2879,1044` 循环**。
   **修法：整个 call 建一张表 + 一次 `cudaMemcpy`，call 内不再重写。**
2. **mmq 的 q8 布局是 `[K block][row]`**（`quantize.cu: ib = k_block*ne1 + row`）⇒ **`mq_ + r0*xq_row` 的切片根本不成立**，`total_rows` 也不能传批行数。
   **修法：每批把行重量化到 `mq_tile_`（`ids = d_tok + r0`），再用局部 bounds。**

### 3.5 其它坑
- **按宽度分配/清零必须用真实专家宽 `in_w`/`out_w`，不用 `n_embd_`**（今天因此出过两个 bug）。
- **`--stage-mib` 与 arena 同池**：调大 `sm` 会掉驻留，**两列必须一起报**。
- **profile 跨运行写回**：不冻结 `p_run.txt`，读数不可比。
- **MSVC 嵌构建时间戳** ⇒ 同源码两次构建 sha 不同 ⇒ 用「exe sha + 源码改动清单 + 构建命令」三件记账。
- **nsys 要求整条路径纯 ASCII**（cwd + exe + `-o`），否则 `std::range_error: bad conversion`。
- **Windows 命令行 32767 上限** ⇒ 长 prompt 必须用 `--tokens-file`。
