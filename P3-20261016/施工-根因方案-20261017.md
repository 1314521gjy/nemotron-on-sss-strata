## §0 三句话

1. **R-1（2.22× 重复）的根因不是"预取机制本身"，也不是 `--expert-swaps 64` / `--stage-ahead 128`**：是 **conversation-cache 的 checkpoint 每 2048 token 把 prompt 的 `read()` 切成 4 个 call**（默认值 `conversations.hpp:31` `every=2048`；`main.cpp:376-389` 把 checkpoint 位置当 marks 传给 `engine.read`；`engine.cpp:3139-3147` 按 mark 切 call），于是**每一层 `moe_rows()` 被调 4 次**，而每个 call 都会把 ≤341 个非驻留专家的 `L.ahead` 整表重搬一遍 ⇒ 45,538 个副本 = **3.12× 唯一集**。**68% 的字节是可消除的，且消除它不需要改码**（现成 CLI 旗标 `--prompt-cache-every 0`）。
2. **R-2（st_ 10.1 GB/s）**：这个读数的形态是 **`--stage-mib 48`、走非 pin 的 host-gather 路径、整块 15.48/24.77 MB 拷贝**；**A 臂（`STRATA_PIN_ARENA_GIB=59.1`，pin，每拷贝 1.548 MB、每专家 2 次）的拷贝形态完全不同**，10.1 不能直接算到 A 臂头上。A 臂上能**静态证死**的只有结构：**单 `stage_` 缓冲 + `up_`/`st_` 事件互斥 ⇒ 同时在飞的 DMA ≤ 1**。真速率必须由 **D 跑 nsys 的 H2D busy/墙** 决定（盘上没有，情报A §7-U1 同判）。
3. **R-3（借槽）**：**"我们自携 scratch ~10.8 GiB" 是 ①b 之前的旧数**（`方案-prompt缓存借缓存槽-20261017.md:22`）；①b 之后非 arena 实测 **5.334 GiB**（情报A §3.2，我复核其公式与之自洽）。**借槽对 prefill 的收益 ≈ 0（§4.4 有结构论证）**，只在 decode 侧有 +546~+1,845 槽潜力 ⇒ **不是拉平 2.22× 的最短路，建议排在去重之后**。

### 2.1 机制链（A：逐行可复核）

**① checkpoint 位置 → 把一次 prompt 切成 4 个 read call。**

| 步 | 事实 | 出处 |
|---|---|---|
| 1 | `CacheOptions::every = 2048`（默认）；`checkpoints = 6` | `PolyStrata\src\poly\conversations.hpp:29-31` |
| 2 | CLI 的 `--prompt-cache*` 默认不设 ⇒ D 跑用默认 2048（脚本 `C:\sp3\run_pb6912_D.cmd` 里没有这些旗标） | A：脚本全文 |
| 3 | `kept.inside(0, 6791, due)`：`for (p = 2048; p < 6791; p += 2048) due.push_back(p)` ⇒ **due = {2048, 4096, 6144}** | `conversations.hpp:106-127`（`:112-113`） |

**② 每个 call 里，`moe_rows()` 都重做一次"预取（ahead）+ 轮内拷贝"。**

| 步 | 事实 | 出处 |
|---|---|---|
| 1 | `ahead = opt_.stage_ahead > 0 && (n >= opt_.stage_ahead || shared_ahead_)`；4 个 call 的 n 都 ≥128 ⇒ 全部 `ahead=true` | `engine.cpp:2323` |
| 2 | `plan_ahead()`：把**该层全部非驻留专家**按 profile 排序，**截到 `stage_bytes_/(2·gu_bytes+d_bytes) = 341`** —— 注意它是"全部非驻留"，**不是"这次路由到的"** | `engine.cpp:1306-1315`（cap 在 `:1314`） |
| 3 | 早拷贝：`stage(L, L.ahead.data(), n_ahead, up_)` —— **每个 call、每一层都做** | `:2380-2389` |
| 4 | 预取清单**无条件并入 `group_`**（哪怕这次没路由到） | `:2450` |
| 5 | 轮结构：`round_ = [n_cached, n_cached+n_ahead, …]`；**call 内**轮 0 = ahead（直接用早拷贝，不重拷），轮 1… = 其余路由到的非驻留专家（"others"，每 call 拷贝） | `:2484-2488`、`:2699-2711` |

**③ 结果：每个 call 的拷贝量 = `512 - c_l`（c_l = 该层"有行的驻留专家数"，全部驻留专家在 6792-token prompt 上都会被路由到），4 个 call 里只有 1 个是"唯一必需"，其余 3 个是重拷。**

### 2.3 三条必须查清的问题，逐条回答

**① 预取重复（`engine.cpp:1314, 2450`）—— 是，但只占一半；真因是"每个 call 重做一次预取"。**
- 每个 call 的 ahead 拷贝上限 **341 专家/层**（`:1314`；本靶 `stage_bytes_/(2·gu+d) = 1,585,446,912/4,644,864 = 341.4` → 341）。
- 预取清单"全部非驻留、按 profile 排序"⇒ **它不依赖本次路由**，所以 4 个 call 的 ahead 列表**几乎相同**（same 341）。
- 复用检测（`kept`，`:2693-2696`）要求 `staged_`（**上次 call 结束时缓冲里的"最后一轮"**，`:2777-2779`）与本次的某一轮**逐元素相等**；而 call 内最后一轮通常是把 ahead 画在最后才 stage 的——**它按 `from`/`kept` 的轮序交替**：实测模型 = call1 拷 365（ahead+others）、call2 拷 341（ahead）、call3 拷 24（others）、call4 拷 341（ahead）⇒ **341 的 ahead 表被拷了 3 次**（一次在 call1 的早拷贝里 + call2 + call4）。
- **⇒ 预取本身保留（它是把 copy 藏到 attention 下的机制），要修的是"跨 call 把已经搬过的 ahead 表再搬一遍"。**

**② 跨轮重拷（`--expert-swaps 64` / `--stage-ahead 128` 是否强制多轮）—— 不是重复来源。**
- `--expert-swaps 64` 是 **decode 侧**的换入（`start_swaps()` `engine.cpp:1150-1164`；`follow()` `:1355-1452`；prefill 走 `follow(0)`，`engine.cpp:2826` 在 n≥32 时传 0 ⇒ **prefill 期间不换专家**）⇒ **对 91,076 无贡献**（那些换入走 `swap_st_`，也不计入 `pin_dmas_`）。
- `--stage-ahead 128` 只是**开启 ahead 的门槛**（`:2323`），不是"强制多轮"。真正的多轮来自 **chunk 数**（每 call 每层的 chunk 数 = ⌈m/173⌉，`chunk_bytes_=512 MiB`，`runtime.hpp:37` → `per=173`，`engine.cpp:2259`）。
- **⇒ 91,076 次 DMA / 373 chunk 的分解**：4 call × 40 层 = **160 次 `moe_rows`**；每层 call1=3 chunk（ahead 341 → 173+168，others 24 → 1）、call2=2、call3=1、call4=2–3 ⇒ **≈8–9 chunk/层 ⇒ 320–360 chunk**，实测 373（+4~16%，层间 `c_l` 不均）✔。

**③ 为什么"≤200 次"的推算对不上 —— 因为推算默认了"1 个 call"。**
- 若 `read()` 只有 1 个 call：每层 stage() = 1（ahead 341）+ 0–1（others）⇒ 80–120 次，chunk 80–120，副本 = Σ(512−c_l) = **14,590**（= §2.2 的 A 项）。
- **⇒ "373 ≠ ≤200" 不是预取次数异常，而是"prompt 被切了 4 刀"的直接指纹。**

### 2.4 为什么"单 chunk"的优势没兑现（与交接件 §2.3 对齐）

`--prompt-batch 6912` 只把 `rows_`（一次 read 的**上限**）提到 6912；**checkpoint marks 又把实际 call 砍回 2048** ⇒ **"单块 6792" 实际是 4 个 2048/647 的块**。这解释了：
- 为什么 D（pb=6912）只比 B（pb=1024，7 个 call）快 0.2%（652.6 vs 651.2）——**两者都不是单块**；
- 为什么 2.13×/2.6× 的单块体积优势从未出现——**它需要 1 个 call**。

### 4.3 ★ 借槽对 prefill 的收益 = 0（结构论证，A）

1. **借不创造显存**：借出的槽在 prefill 期**仍然不能放专家** ⇒ prefill 期驻留 = (arena − 借出量)/slot，与"单独分配 scratch"**完全相同**。
2. **本靶没有"尾部可省"**：6792-token prompt 每层路由 ~152,064/512 ≈ 297 次/专家 ⇒ **每层 512 个专家全部被路由到**（P(某专家未被选) ≈ e^−297 ≈ 0）。所以"驻留的专家"每个恰好省 1 次拷贝，"不驻留的"每个必拷 1 次 —— **借槽把哪 1.5 GiB 专家挤出去都无所谓：它们本来也会被拷**。⇒ **prefill 的拷贝量与借不借无关**。
3. **arena 无 spare**：`fill_expert_cache()` 的候选是全 20,480 专家、`room` 一路放到尽（`:1120-1142`）⇒ 当前 5,890 槽已是"free − reserve"吃满 ⇒ 借区只能"挤掉专家"，不能"白拿空槽"。
4. **⇒ 借槽的真实价值在 decode 之后**：prompt 结束后把借区还给专家（+~0.96–1.54 GiB 可借集 ⇒ **+310–500 槽**；若再把 `arch`/token 这类 `rows_` 缩放缓冲在 prompt 后重分配为 `rows=1`（这是"缩"不是"借"，**另做**）⇒ 总共可到 +1,700–1,845 槽，52.7% → 76–82% 的专家来自 VRAM）。
5. **★ 知识库判据**：`KP-UNI-0218` = 借槽让 prefill 快 2–5%，但 **decode 慢 10–23%** ⇒ **borrow 的任何验收必须带 decode 负控**；`KP-UNI-0250` = 动 prefill 的机制不许伤 decode。⇒ **本靶如果借槽只换到 decode 收益（甚至可能按 KP-UNI-0218 为负），就不该排在 R1 的最前面。**

**⇒ R-3 结论：借槽不是拉平 2.22× 的短路径；它是 decode 侧杠杆，建议在"去重 + R-2"之后单独排一臂。**
