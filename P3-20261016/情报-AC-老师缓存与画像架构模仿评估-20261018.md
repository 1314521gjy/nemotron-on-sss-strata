## §0 一句话结论

**A. per-layer 槽配额：不建议照抄。** 老师上这套是因为它**按"到达顺序"填缓存**（一个共享计数器），256 槽被 ~26 层的位置 0 吃掉（2.97%）；**我们的填充已经是"全局按计数排序"（`fill_expert_cache`，`engine.cpp:1429-1500`）**——给定权重下全局 top-N 就是最优，配额只能收紧不能变好。用 `p_decode2.txt`+6745 槽离线模拟：**等分/按层等比例/贪心相对现状仅 +0.10~0.11 pp 命中（噪声级）**，且把排序换成 decode 最优后配额反而 **−0.08 pp**；本机硬证据（`回执\IW-20261018-命中率硬证据.md:7`）per-layer 倾斜 **≤0.4 点**。⇒ **有条件不抄**（保留条件：若将来改成未排序/到达序填充，或 profile 失效时的防御；届时 30–60 行、需重过 class-E）。
**B. profile 学习闭环：值得有条件模仿，且已有今天的实测锚。** 老师的闭环是 **rank 语义（resident→heat→prior）** + 二进制 rank 表 + **换请求间隙/QUIT 每 10 min** 写盘；我们是 **计数语义（prior+use）** + 文本计数 + **10 s** 写盘，且 **use_ 混了 prefill（98.26%）**。今天已经用手工"decode 主导表"验证了 B 的兑现量：**R48 命中 +5.5 pp / miss −9.1%；R50 命中 43.3→51.8%（+8.5 pp）/ miss −14.7% / per-token +4~5%**（A 级，但 ids 漂 43/64 = class-E）。⇒ **有条件模仿（三件：decode-only 计数、rank+resident-first 写回、写盘节奏按老师 10 min/QUIT）**；改动合计 **~60–120 行、零新 kernel、1 编译**；代价是 **class-E（缓存组成变 ⇒ ids 可能漂）**，需 opt-in 或接受重过 ids 门。

### §1.2 我们现在怎么做
- **填充是全局计数排序，不是到达序**：`fill_expert_cache()` 对全部 (层,专家) 建 `Cand{il,e,bytes,value=(prior+use)/bytes}`，`stable_sort` 降序，然后按 arena 能装多少取多少（单计数器）——`PolyStrata\src\poly\engine.cpp:1429-1500`（`Cand`/value `:1480-1493`、sort `:1497-1500`）。
- 因此等价问题（到达序偏斜）**在我们这里不存在**；残留的"偏斜"只是"计数排序的合法结果"。
- **偏斜要重算（今天口径）**：用 `p_run.txt`（=p_master，20,275 条，交付表）在 6745 槽下推：**每层槽数 min=102 / max=231、CV=0.204**（10-17 的 0.161 是旧槽数/旧表口径；老师 CV 0.116 是 lead 给的参考值）。

### §2.2 我们现在怎么做（当前源码，行号已漂）
- `save_profile()`：把 **`prior_ + use_` 计数**按 `"层 专家 计数"` 文本写回（tmp+rename），**必须 `--expert-profile-write`**（默认只读）——`PolyStrata\src\poly\engine.cpp:2682-2712`（写回逻辑 `:2689-2707`）。
- `use_` 计数 **同时被 prefill 与 decode 累加**：decode 路径 `moe()` 中 `++use_[...]`（`engine.cpp:2922`），prefill 路径 `moe_rows()` 批量路由中 `++use_[...]`（`:3496`；`情报-W:127` 的旧行号 `:2800-2802` 对应同一处）。
- **写盘节奏**：`kProfileSaveMs = 10000`（10 s，`main.cpp:62`）；serve 循环里**每个请求结束后**若距上次 ≥10 s 就写（`main.cpp:780-788`），退出时再写一次（`:1215`）。⇒ **比老师频繁 60×**，且计数是"累加型"（`prior` 已含上次 `use`）。
- **无 rank / 无 resident-first 语义**：读侧 `read_profile` 只认计数（`engine.cpp:198-217`）；填充按 `(prior+use)/bytes` 排序（`:1429-1500`）。
- **已知实测问题**：`情报-W:127` 硬证据：88 个写过 profile 的请求里 **prompt 65,793 tok vs decode 1,167 tok ⇒ prefill 占 98.26%**；`p_master` 的计数 98% 来自 prompt 路由，却用来预测 decode。`优化表-重订-20261018.md:73` 直接记 "24.1 表采自 prefill（98.26% 计数来自 prompt token）"。
- **今天的"手工版闭环"已证明这条线的价值**（R48/R50，A 级）：decode 主导表 ⇒ 命中 **43.3→51.8%（+8.5 pp）**、miss **496.7→423.6（−14.7%）**、per-token **+4~5%**、覆盖 100% trunk（+431 blk.88 行）；但 **ids 漂 43/64（class-E）**，R1==R2 重复逐位同（表本身确定性 ✓）。表线的下一瓶颈是**槽位容量/路由浓度**（R50 结论）。

### §2.4 B 的"预期总账"
- **已实测锚（A）**：手工 decode 主导表 = **命中 +8.5 pp / miss −14.7% / per-token +4~5%**（R50；R48 为 +5.5 pp / −9.1%）。
- **自动闭环的兑现区间**：B1（decode-only 计数）是在运行中把表逐步推向"服务负载"，**上限 ≈ R50 的 +8.5 pp / +4~5%**；如果服务负载比 R50 的 4 类 64-token prompt 更集中，可望接近模拟"过拟合上界"（+22.6 pp）的中间值 ⇒ **给区间：+4~7% per-token（A/C，需 1 跑验证）**。B2 的 tok/s 增量 ≈0，但把"每次换表 ids 漂 43/64"收窄为"**收敛后重启可复现**"（需 1 跑验证）。
- **不做的代价**：表继续被 prefill 主导（98.26%），命中停在 ~52%，miss/token ~423 而非表的潜力（模拟 decode 最优 62% ⇒ miss ~340）。

## §4 结论（一句话）
**A 不抄**（我们的全局计数填装已经优于它的到达序+等分，配额模拟只值 +0.10 pp = 噪声；只在"将来改回未排序填装"时才装）；**B 有条件地抄三件**：**decode-only 计数（20–40 行）是必做**，它把 98.26% prefill 污染去掉、实测锚 **+8.5 pp 命中 / −14.7% miss / +4~5% per-token**；**rank+resident-first 写回（40–80 行）**把"每次换表 ids 漂 43/64"收窄为"收敛后重启可复现"（tok/s ≈0，需 1 跑验证）；**写盘节奏对齐 10 min/QUIT（3–5 行）**只是降 churn。总改动 ~60–120 行、零新 kernel、1 编译；**代价是 class-E，必须作 opt-in 或重过 ids 门**。
