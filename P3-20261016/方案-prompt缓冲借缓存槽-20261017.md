# 方案（只方案、未改码）· prompt 缓冲借专家缓存槽 — 2026-10-17

- **背景**：单 chunk（`--prompt-batch 6912`）实测 **290.0 tok/s < 373.5（pb=1024, sm=2048）** —— **scratch 单独分配、吃走 ~10.8 GiB VRAM ⇒ 驻留 7388→3640 ⇒ 净负**。
- **3.8 的做法**（`E:\strata\_staging\dec-pool2.txt`）：`prompt path borrows 2387 cache slots (4.55 GiB)` ⇒ **借、不额外占**。
- **本件 = 把"借"落成可施工的方案，未改一行码。A 级读码。**

## 1. 现状（`file:line`）

### 1.1 分配顺序（scratch 先于 arena，故 1:1 扣 arena）
- `alloc()`（`engine.cpp:1591`）→ `shared_scratch()`（`:1561`）**两遍计数/落地** → `scratch_ = dmalloc(scratch_at_*4)`（`:1641`，`dmalloc` 见 `:406`，**cudaMalloc 单独**）
- `moe_rows` 的 scratch：`gu_ = fbuf(rr*2*n_ff_exp_)` / `hx_ = fbuf(rr*n_ff_exp_)` / `dx_ = fbuf(rr*n_embd_)`（`:1584-1586`），`rr = rows_*n_used_`
- mmq scratch：`mq_/mq2_/mqx_/xq_/q8_/d_ids_/d_wts_/tab_/iota_`（`:1647-1670`）
- **`fill_expert_cache()`（`:995`）在之后**，它按 **`free_b - reserve`** 定 arena（`:1044`）⇒ **scratch 占多少，arena 就少多少**。

### 1.2 本靶的 scratch 账（pb=6912 ⇒ rr=6912×22=152,064）
| 缓冲 | 公式 | 字节 |
|---|---|---|
| `gu_` | rr·2·2688·4 | **3.27 GB** |
| `hx_` | rr·2688·4 | **1.63 GB** |
| `dx_` | rr·4096·4 | **2.49 GB** |
| 其余（mq_/mq2_/xq_/q8_/tab_/…） | ∝ rr | ~3.4 GB |
| **合计** | | **≈10.8 GB**（与实测 arena 21.3→10.5 GiB 吻合） |
- **对照 3.8 的借出量：4.55 GB** ⇒ **我们的 prompt scratch 是它的 ~2.4×**（`n_used_=22` vs 10；`dx_` 用 `n_embd_=4096` 宽）。

## 2. 目标
**把"prompt 期才需要、且 ∝ rows_"的缓冲放进专家缓存 arena 的地址空间（借），prompt 算完归还；不再从 arena 1:1 扣。**

## 3. 方案（按 3.8 的语义）

### 3.1 借哪些槽
- **只借 `moe_rows` 的 `gu_/hx_/dx_` 与 mmq 的 `mq_/mq2_/mqx_/xq_/q8_/d_ids_/d_wts_/tab_/iota_`**（即"只在 prompt 批内存在"的）**；`state_/snap_/wlogits_/logits_/d_/moe_*/rl_/…` 不动**（decode 也用的，不借）。
- 借出量 = 上述合计（本靶 ~10.8 GB，实际按 `rows_` 算）。**若借出量 > arena 可借出的槽，就少借/报错（见 3.3）。**

### 3.2 怎么保证不冲突（★ 防静默重叠）
1. **借出的槽【不放进专家填充序列】**：`fill_expert_cache()` 在 `vmm_map`/`dmalloc` 前先 `vmm_reserve` 出"借区"，**借区的槽号从 `chan_/L.slot` 的候选里剔除**（等价于"这些槽这次不放专家"）。
2. **借区与专家区在同一 `arena_` VMM 里，物理不重叠**（`vmm_reserve` 已保证地址不交叠；`arena_.pieces` 记录）。
3. **take 序列一致**：借用前后，`arena_.pieces`/`L.slot` 的映射必须一致；**不一致就 `std::runtime_error("prompt buffers do not fit the expert cache")`** —— **绝不静默叠放**（§5 静默退化禁令）。
4. **不借用 `staged_`/`stage_`**（那是 stage 缓冲，另有语义）。

### 3.3 归还时机与谁等谁
- **借区在 prefill（`n >= kStageRows` 的 `moe_rows` 调用）期间存在；prefill 结束、decode 开始前归还**（`rows_` 从 chunk 大小变回 1 时，或首个 `n < kStageRows` 的调用前）。
- **归还 = 把这些槽重新放回专家填充的候选**（不重新 `vmm_map`，只改 `chan_`/`L.slot` 的候选集）；**等 prefill 最后一次 `moe_rows` 的 `st_` 与 `up_` 都完成**（`cudaStreamSynchronize(cs(st_))` + 等 `ev_ahead_`）—— **这一步会牵动 `ev_free_`/`ev_ahead_` 的时序**（见 §4）。
- **谁等谁**：**归还前必须等"最后一次读借区"的 kernel 完成**；用 `cudaEventRecord` + `cudaStreamWaitEvent` 保证，**不靠 sleep**。

### 3.4 碰不碰 §7（`engine.cpp:2189/2191/2374/2390`）？
- ★ **很可能牵动**：借/还发生在 `moe_rows` 的 `card()`/`stage()` 边界，**与 `ev_free_`/`ev_ahead_` 的配对（那四处）相邻**。
- **若必须碰 ⇒ 按纪律整组改，并重跑确定性判据（母本 5 跑逐位）**；**不单改其中一处**。

## 4. 改动面与风险
- **改动面**：`alloc()`（借区预留）· `fill_expert_cache()`（剔除借区槽）· `moe_rows`（借/还时机）· 可能 §7 的事件配对。**估计 60–120 行**，**不是"10 行"**。
- **风险**：
  1. **静默重叠**（借区被专家覆盖）⇒ **最危险**，用 3.2 的"take 序列一致否则报错"防。
  2. **驻留仍会掉**：**借出量 = 10.8 GB，本靶 arena 21.3 GiB** ⇒ **即使"借"，专家能用的槽仍少 10.8 GB**（借 ≠ 变出显存）。**唯一能"驻留不掉"的前提是"借出的槽本来就是空的"** —— 这需要 `arena_` 有**未用的 spare**。**本靶 arena 7388/20480 已基本用满**（`full_bytes_`），**没有 spare** ⇒ **借了照样掉驻留**（≈3640）。
  3. ⇒ **★ "借"本身不解决本靶的问题**：**真正的差是"我们的 scratch 10.8 GB 比 3.8 的 4.55 GB 大 2.4×"**（`n_used_=22`、`dx_` 用 4096 宽）。

## 5. ★ 更可能兑现的一刀（诚实提出，供队长判）
**先把 prompt scratch 缩小**（不借也能赢）：
- **`dx_` 用 `out_w`（1024）而不是 `n_embd_`（4096）** ⇒ 2.49 GB → 0.62 GB（**与 latent 修复同一族，可能已经该改** —— 当前 `dx_` 仍是 `rr*n_embd_`）。
- **`gu_/hx_` 分块**：按 `kSumRows` 分块算专家，别一次开 `rr` 行 ⇒ 可降到 ~1/10。
- **这刀不碰 §7、不碰事件配对**，且 **ids 应逐位不变**（只改缓冲大小/分块，不改算术）。
- **预计**：scratch 10.8 GB → ~2–3 GB ⇒ pb=6912 的驻留从 3640 回到 ~6000+ ⇒ **单 chunk 的收益才可能翻正**。

## 6. 验收预案（若施工）
1. **单 chunk 下驻留不掉**（3640 → ≥6000）· prefill 明显上去（290 → >373.5）。
2. **ids 逐位不变**（同 prompt 的 pb=1024 参照）。
3. **负控**：新旗标关掉 ⇒ 回旧（290 / 3640）。
4. **无静默重叠**：take 序列不一致必须报错（构造一个"装不下"的 pb/arena 组合验）。
5. **确定性**：母本 5 跑 ids 逐位（若碰 §7）。
