## §0 三句结论

1. **本模型没有"潜空间的注意力"**：注意力是**标准 GQA**（32 个 query 头 × head_dim 128，**2 个 KV 头** × 128，n_embd 4096；无 RoPE、无 q/k norm）；**全模型没有 MLA**（51 个元数据键里无 `q_lora_rank`/`kv_lora_rank`；453+328 个张量里无 `attn_k_b`/`attn_v_b`/`kv_a`/`q_a`/`compress`）。模型里唯一的"潜空间"是 **MoE 的 1024 维 latent**（`moe_latent_size=1024`，`ffn_latent_down` 4096→1024 / `ffn_latent_up` 1024→4096）——那是**专家计算**的潜空间，与注意力、与 MTP 的取法都无关。
2. **MTP（blk.88）该"从主模型的隐状态取"——这一点我们做对了；但它的注意力和 KV 必须自己算一套，不能复用主模型 KV**：llama.cpp 的 MTP 图（`E:\strata\third_party\llama.cpp\src\models\nemotron-h-moe.cpp:9-160`）把 `il = hparams.n_layer() = 88` 当独立层，输入是 `eh_proj([hnorm(主模型最后 hidden), enorm(下一 token 的 embedding)])`，注意力用**它自己的** Q/K/V 权重、写**它自己的** KV（`build_attn_inp_kv()` `:59` + `build_attn(..., il)` `:122`），且 KV cache 的层数口径是 **`n_layer_all`=89**（`llama-kv-cache.cpp:102`）⇒ **MTP 层有自己的一层 KV 槽**。NeMo 的 `mtp_hybrid_override_pattern:"*E"` 也是这个意思：`*`=Attention、`E`=Expert(MoE)（`conversion/nemotron.py:239-246` 注释原文；`:268-276` 把 MTP 块**同时**登记成 attention 层与 MoE 层）。
3. **我们没有取错**：`nemotronhmoe.cpp:371-381` 的 `block_rows()`/`block_attend()` 就是"自己写自己的 K/V、自己在自己的 KV 上做注意力"；`engine.cpp:3900-3922` 的 `draft_input()` 才是"从主模型隐状态取"的那一步（`hnorm(h)` + `enorm(embed)` → `eh_proj`），与 llama.cpp 逐行对应。**若改成"复用主模型 KV"会算错**；而且即使能复也只省 per-guess 流量的 **≈3.4%**（注意力 20.3 MB / 591 MB），**MTP 的钱花在别处**：共享输出头 **440 MB/次**（占 75%）+ MTP 自己的 MoE **≈107 MB/次**。

## §2 ② MTP（blk.88）的注意力应该从哪取（C 级：llama.cpp 逐行）

### §2.1 blk.88 是"自带 attention + 自带 MoE"的完整块（A 级：GGUF 张量）
```
blk.88.attn_norm.weight      (4096,)        F32
blk.88.attn_q.weight         (4096, 4096)   Q4_K     ← 自己的 Q
blk.88.attn_k.weight         (4096, 256)    Q4_K     ← 自己的 K（2 KV 头）
blk.88.attn_v.weight         (4096, 256)    Q6_K     ← 自己的 V
blk.88.attn_output.weight    (4096, 4096)   Q4_K
blk.88.post_attention_norm.weight (4096,)   F32      ← 只有这个块有（FFN 前 norm）
blk.88.ffn_gate_inp.weight   (4096, 512)    F32      ← 完整 MoE（512 专家）
blk.88.exp_probs_b.bias      (512,)         F32
blk.88.ffn_latent_down/up    (4096,1024)/(1024,4096) Q4_K
blk.88.ffn_up_exps/down_exps (1024,2688,512)/(2688,1024,512)
blk.88.ffn_up_shexp/down_shexp (4096,5376)/(5376,4096)
blk.88.nextn.enorm.weight    (4096,) F32             ← 下一 token embedding 的 norm
blk.88.nextn.hnorm.weight    (4096,) F32             ← 主模型最后 hidden 的 norm
blk.88.nextn.eh_proj.weight  (8192, 4096) Q4_K       ← 两半拼起来(8192)→4096
blk.88.nextn.shared_head_norm.weight (4096,) F32     ← 共享输出头前 norm
```
⇒ **它有自己的 attn_k/attn_v** ⇒ 它的 KV 只能由**它自己的**输入算出来，**不可能**"从主模型 KV 里取"。

### §2.3 KV cache 的层数口径（C 级）
- `E:\strata\third_party\llama.cpp\src\llama-kv-cache.cpp:102`：**`const uint32_t n_layer = hparams.n_layer_all;`**（89）⇒ **KV cache 给第 88 层（MTP）也留了槽**。
- `llama-hparams.cpp:348`：`return n_layer_all - n_layer_nextn;` ⇒ 主干 `n_layer()=88`、`n_layer_all=89`。
- `llama-context.cpp:1419` 注释：*"MTP hook batches carry both token (next-token id) and embd (h_nextn row)"* ⇒ MTP 的输入确实是**主模型 hidden 的一行**。

### §2.4 NeMo 的 `mtp_hybrid_override_pattern:"*E"` 语义（C 级：llama.cpp 转换器原文）

⇒ **`*E` = 一个"Attention mixer + Expert(MoE) FFN"的块**；`*` = Attention（不是"潜空间"，也不是 Mamba；`M` 才是 Mamba2）。

### §2.5 结论（② 的回答）
**MTP 的取法 = (a) 自己算一套 KV，且输入融合里取主模型最后的 hidden（h_nextn）**——不是 (b) 复用主模型 KV，(c) 也不是复用某个注意力层的 KV。
**为什么 (b)/(c) 不成立（读码理由）**：MTP 的 K/V 由它**自己的** `attn_k/attn_v`（(4096,256)，GGUF 里独立张量）作用于**它自己的输入** `eh_proj([enorm(emb), hnorm(h)])` 得到；主模型任何一层的 K/V 是**另一组权重**作用于**另一输入**（该层 attn_norm 后的 hidden）的产物，二者不相等。llama.cpp 的实现（`il=88` 自己的 KV 槽）也证明这一点。

## §4 ④ 结论：错没错？该不该改？代价多少？

### §4.1 "潜空间注意力"到底指什么
- **不是 MLA**（§1.1 已查无命中）；
- **不是**"对 latent 做注意力"（模型没有这种层）；
- 模型里唯一的"latent"是 **MoE 的 1024 维**（`moe_latent_size`，`ffn_latent_down/up`），它只属于**专家分支**；注意力始终在 4096 维上；
- 用户这句话在实现上**最接近的正确答案**是：**"MTP 的输入应当取自（主模型最后一层的）隐状态"** —— 这一点模型设计与我们的实现都是这样的（§2.2/§3.2），**没有取错**。

### §4.2 若"复用主模型 KV/latent 缓存"会怎样（回答"代价"）
- **语义上不成立**：MTP 的 K/V 是它自己的 `attn_k/attn_v` 作用在 `eh_proj([enorm(emb), hnorm(h)])` 上的产物；复用主模型某层 KV 等于用错权重/错输入 ⇒ 输出必错。
- **即使能复用，省的也很少**（我们尺寸，A 级计算）：
  - MTP 的 KV：**16 MiB**（`2×128×2B = 512 B/token` × 16384 行 × K/V，`max_context=16384`；`engine.cpp:541-548` + `nemotronhmoe.cpp:211-213`）
  - MTP 注意力每 guess 的权重读：`attn_q 9.44 + attn_k 0.59 + attn_v 0.86 + attn_output 9.44 ≈ 20.3 MB`
  - ⇒ 20.3 MB / 591 MB ≈ **3.4%** ⇒ 不是杠杆。
- **MTP 每次 draft 的真实开销**（按 GGUF 类型/行宽逐项算，D 级）：
  | 项 | MB/guess | 占比 |
  |---|---|---|
  | **共享输出头**（`output.weight` Q6_K 131072×3360 B；`draft_vocab` 默认 -1 ⇒ `guess_vocab()`=0 ⇒ 全词表，`engine.hpp:205-211`） | **440.4** | **74.5%** |
  | MTP 自己的 MoE（22 专家 ×(1.548+1.548) + shexp 12.39+18.06） | 98.6 | 16.7% |
  | `nextn.eh_proj`（8192×4096 Q4_K） | 18.9 | 3.2% |
  | 注意力（q/k/v/o） | 20.3 | 3.4% |
  | router `ffn_gate_inp` F32 4096×512 | 8.4 | 1.4% |
  | `ffn_latent_down/up` | 4.7 | 0.8% |
  | **合计** | **≈591 MB/guess** | 100% |
  另加：`state_` 里给 draft 的 `hn_` 行缓冲 = `rows_ × n_embd × 4 B`（`engine.cpp:1757-1761`；`rows_ = min(prompt_batch, max_context)`，pb=6912 ⇒ **113 MB**）+ 16 KiB 状态。
### §4.3 若要提速 MTP，该改哪（按收益/风险排序；不改注意力取法）
1. **`--draft-vocab N`（已实现，`main.cpp:953`，默认 -1=全词表）**：把输出头从 131072 行砍到前 N 行。N=76,938（上游 Qwen 的实测常用值）⇒ 头 258 MB（省 182 MB/guess ≈ **0.21 ms@864GB/s**）；N=32,768 ⇒ 省 330 MB。**风险**：只影响"能不能猜中"，猜错只丢窗口位、不丢 token（`engine.hpp:205-206` 注释）；但**我们的 tokenizer 是 `pixtral`（GPT2-BPE），词表是否"常用在前"未验**（上游只对 Qwen 词表序验证过）⇒ 必须先测 acceptance（A/B：45 token 逐位 + acceptance 计数）。
2. **MTP 的 MoE（≈107 MB/guess）**：这是设计的一部分（`*E`），要省只能换更小的 draft 头/共享专家策略——属线 B 的取舍，不是"取法"问题。
3. **不要动**：KV（16 MiB）与注意力（20 MB，3.4%）——不是瓶颈。
4. 顺带一个**免费清理**：`block_attend()` 里 `attn()` 重算并重写一次 K/V（§3.3-1），可加一个"只算 Q、不重写 K/V"的分支，省每 guess ≈1.4 MB 权重读（≈1.5 µs，可忽略；但能去掉一次冗余写，正确性不变）。
