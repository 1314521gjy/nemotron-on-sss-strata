## §1 ① helgard 到底怎么做的（本地 clone 逐行）

### §1.1 布局：离线把 **down 按神经元位级转置**（同尺寸）
`C:\sp3\upstream-hist\nemotron8gb\` 的 `repack_T.py`：
- 每个专家块 3,096,576 B = `up_w(1,376,256) | up_s(172,032) | dn_w(1,376,256) | dn_s(172,032)`（`qmoe_ns.py:16-19`：`O_UW=0, O_US=1376256, O_DW=1548288, O_DS=2924544, BLOCK=3096576`）。
- `repack_T.py` 的 `to_T_batch()`：把 down 的 4-bit 值从 `(LAT=1024 行, INTER=2688 列)` **位级转置为 `dnT_w [2688 神经元, 512 B]`**（每个神经元在 1024 个输出行上的 nibble 连续排成 512 B）；把 down scale 从 `(行, 组)` 转成 **`dnT_s [168 组, 1024 行]`**（每 16 神经元一组的 scale 在 1024 行上连续，1,024 B/组）。**总尺寸不变**。
- 生成 `experts.layout = "T"` 标记；`from_T_batch()` 可逆；文件末尾对 **200 个专家**逐字节比对原始 checkpoint（`СВЕРКА С ОРИГИНАЛОМ: 200 экспертов, расхождений 0`）。
- 走 `--back` 可退回原布局；一次重排按 64 专家/批、`preadv/pwritev` 流式改写。

### §1.2 运行时：活神经元索引 + 只读活字节
`qmoe_ns.py`：
- `:136` 注释：**"пропуск нулей relu² (#399, пункт 1)"**（ReLU² 零跳过）。
- `:145 _down_live(...)`：`out[j,r] = coef_j·ws2d_j·Σ_{n 活的} W[r,n]·S[r,n//16]·h[j,n]`；**逐专家读 `cnt` 与 `idx[j*2688+kk]` 活神经元列表**，按神经元取 `base + O_DW + n*512 + r2`（该神经元 1024 行的 nibble 连续）与 `base + O_DS + (n//16)*1024 + 2*r2`（该 16 组在 1024 行的 scale 连续）。
- `:175 _down_live2(...)`：把活列表按 NB 交错分给 KS 个 program，分摊。
- `:198 _down_groups(...)`：**按 16 神经元组**：组 scale 一次连续读 `[BR]`，组内再按 `h>0` 掩码只取活神经元的 4 bit。
- `LIVE_CFG = dict(BR=256, NB=8, KS=8, num_warps=4)`（`:216`）。
- 激活 **h 是 fp32、无量化**（W4A16：`qmoe_ns.py:1-6` 明写"Активации не квантуются (W4A16)"）⇒ 零是精确 0，跳过无近似。
- 活索引怎么来：`nem_super.py:345` `hh = torch.relu(F.linear(X[tok_idx].float(), u)) ** 2`（prompt 路径）；decode 走 `moe_decode_groups(...)`（`:383`），索引由 down kernel 前的 `h>0` 掩码/列表提供（`_down_groups` docstring "маска h>0"）。

### §1.3 他们的收益与代价（原文）
- README：**92.5% 的 ReLU² 中间神经元恰为 0**（"live 7.5% on average, **1–16.5% by layer**"）；**ReLU² 零跳过是最后一步、+12% 端到端**（6.5 → **7.3–7.6 tok/s**）。
- 代价：down **不走拷贝、直接从 pinned RAM 经 PCIe 随机读**（地址表），所以他们省的是"PCIe 字节+随机读次数"；当前 decode 137 ms/token 的构成：GPU busy 92 ms（含 up 拷贝 49 ms、**`_down_groups` 读 down 17 ms**、稠密 19 ms）、host 等盘 50–55 ms 等。
- ⇒ **他们的 +12% 是"down 读从 ~34 ms 降到 17 ms"的端到端结果**（down 相占 ~25%），不是"expert 字节 −46%"的全额。

### §2.1 我们的 down 布局与激活（A 级，`PolyStrata\src\poly\cpu_experts.cpp` 当前版）

|---|---|---|
| down 矩阵 | IQ4_NL（type 20），GGUF dims `(2688, 1024)`：**1024 个输出行、每行 2688 个输入值**（行主序、连续） | GGUF 实测（本机解析）；`cpu_experts.cpp:201,356`（`d_row`、`down + r*d_row`） |

### §2.2 实测：down 相占每 token 墙的 **40.8%**（A 级，现成日志，零 GPU）
`C:\sp3\R49-L1-20261018.log:223`（`STRATA_DEC_LEDGER` 默认开，`main.cpp:833-835`）：
```
ledger: router_wait=981.7 cpu_pool=6238.0 (gate/up=3210.9 quant=22.2 down=3415.6, 31.1 GB/s) host/launch=432.9
        commit=711.0 ms | sum/wall=0.91 | rounds=127 ... ms/round=65.9 tokens/round=1.00
```
- 127 轮/127 token ⇒ 每 token：**down = 26.90 ms（墙 65.9 的 40.8%）**；gate/up = 25.28；quant = 0.17；**cpu_pool = 49.1 ms = 1.53 GB ÷ 31.1 GB/s ⇒ 纯带宽**（和 `情报-L` 的 32.2 GB/s 一致）。
- ⇒ **down 相是第二大项、且完全是带宽**：这是"零跳过"能碰到的全部钱。

### §2.3 块级 / cache-line 级全零率（公式 + s=0.925 代入）
设 ReLU² 后每个中间神经元为零的概率 s（helgard 实测 s≈0.925；我们**未测**）。
- **IQ4_NL 32-值块全零**：`P32 = s^32 = 0.925^32 = 8.24%` ⇒ 每行 84 块里约 6.9 块可跳（8.24% 字节）。
- **x86 cache line = 64 B**：IQ4_NL 是 0.5625 B/值 ⇒ 一条 64 B 行载 ≈ **113.8 个值**；一行 down（1512 B）≈ 23.6 条 line。**行全零**：`Pline = s^113.8 = 0.925^113.8 ≈ 1.4e-4 = 0.014%`。
- ⇒ **就地跳块的 DRAM 字节收益 ≈ 0**：跳过 18 B 的块并不能少取它所在的 64 B line；只有"整条 line 全零"才省，而 i.i.d. 下该概率是 0.014%。**这个结论对"16-半块拆分"也一样**（拆完仍 18/20 B 粒度、仍被 64 B line 罩住）。
- **只有把"活数据变连续"才能把 s 变成字节**：neuron-major 后每条 64 B line 都被活神经元的 512 B 连续值填满（见 §3-b）。
- 若 s 不是 i.i.d.（成块/成段零）⇒ P32/Pline 会更高，但**必须先测**（§4）。

### §2.4 重排后的读数（算账，D 级）
neuron-major 布局：值 `dnT_w`（2688 神经元 × 512 B = 1,376,256 B，同尺寸）+ scale 按块跨行（84 块 × 1024 行 × 2 B = 172,032 B）。读一个专家：
- 值：活神经元 7.5% × 1,376,256 = **103.2 KB**（512 B/神经元，整 cache line 用满）；
- scale：块内至少一个活神经元 ⇒ `P(块有活) = 1−0.925^32 = 91.8%`，读 91.8% × 172,032 = **157.9 KB**；
- 合计 **261 KB / 1,548 KB = 16.9%** ⇒ **down 字节 −83.1%**；
- expert 字节 **3,096,576 → 1,809,000 B（−41.6%）**；每 token 字节 1.53 GB → **0.899 GB**；
- 同带宽 31.1 GB/s ⇒ cpu_pool **49.1 → 28.9 ms**；墙 **65.9 → 45.6 ms** ⇒ **21.9 tok/s（+35%）**；
- **天花板**：gate/up 25.3 ms 不可省（稠密读 769 MB/token）；即使 down 免费，墙 ≈ 25.3+7.7+3.4+5.6+~4 = **45.9 ms ⇒ 23.3 tok/s（+44%）**。⇒ **lead 预估的 28–30 到不了**（那要求 gate/up 也省）。

## §3 ③ 三个候选实现（改哪里/多少行/新 kernel?/ids?/收益/风险）

| # | 方案 | 改哪里 | 行数 | 新 kernel? | ids 逐位? | 省多少 | 风险/代价 |
|---|---|---|---|---|---|---|---|
| **(a)** | **就地 32 块掩码**：down 循环里按 hq 的 32-块是否全零跳过 `vec_dot` 的该块 | `cpu_experts.cpp:348-383`（把 `td->vec_dot` 换成自写的"按块循环 + 掩码"版本；或先算 84-bit 掩码再逐块 dot） | ~40–60 | 否（可在 TU 内写 per-block 小 dot；或调用 ggml 内部的 q4_K? 不暴露 ⇒ 自写 ~40 行） | **是**（跳过的项在整数域恰为 0 ⇒ 和逐位不变；但需保持块序） | **≈0 字节**（64B line 罩住，§2.3）；只省整数计算，而 CPU 腿是带宽受限 ⇒ **≈0** | 分支开销/破坏顺序预取；**不推荐** |

| **(c)** | **只重排 down 列顺序（按神经元活跃频率）+ 行对齐** | 离线统计（需 1 跑采激活频率）+ 同步置换 up 行；把 down 行 pad 到 1536 B（24×64B）以启用"整 64B 线跳过" | 统计/repack ~100 + 加载 ~30 | 否 | 否（列置换 + pad 改变求和顺序/地址，需重测） | 取决于活跃频率偏斜：若把低活神经元聚块使 P(64B 线全零) 升到 20% ⇒ down −20%；**需先测频率分布，先验未知** | 复杂、收益不确定、64B 线需 ~114 值全零（极强聚类才有用）⇒ **不推荐先做** |

**备选简化（如果 (b) 的 sidecar 太重）**：只对 **CPU 实际读到的专家**做"首次访问时转置缓存"——但专家 miss 是随机的、每 token 496.7 个 miss，转置开销（1.55 MB 随机读写）会吃光收益；**不建议**。

## §5 结论（一句 + 第一步）
**这条能做、且是今天最大的无损单点，但不是"就地跳块"：必须离线把 down 重排成 neuron-major（helgard 同款：值 512 B/神经元连续 + scale 按块跨行连续，同尺寸），再写一个"活神经元列表"down 内核；理论收益 down 字节 −83%、expert −42%、墙 −31%~−35%（16.2 → 20–22 tok/s，天花板 23.3），代价是 31.7 GB sidecar + 加载/内核 ~300–450 行 + ids 重测（求和顺序风险）。第一步：① 已完成的零 GPU 账（down=26.9 ms/token，占墙 40.8%）已确认值得做；② 加 `STRATA_PROBE_RELU2=1`（1 编译 + 1 跑）测我们自己的 s、32 块全零率、64B 行全零率——它决定"就地跳块有没有 0 以外的可能"以及 (b) 的真实收益。**

## §6 未验 / 边界
- **U1**：helgard 的 **92.5% 零率是 NVFP4 检查点 + fp32 激活**的测量；我们 **Q4_K_M GGUF + relu2 实现**的 s **未测**（§4.2 的打点就是为它）。
- **U2**：我们的激活是 Q8_0 量化后进 dot：0→0 精确（`ggml-quants.c:276-296`），但"非零小值被量化成 0"会**额外增加**零率、而"非零值量化误差"会影响 (b) 的 ids；实测时要同时报 float 零率与 q8 零率。
- **U3**：31.7 GB sidecar 的**盘位/RAM 预算未核**（本机模型盘剩余空间未查）；page-cache 被挤会影响其它阶段（prefill 也读同一 GGUF）。
- **U4**：(b) 的 **+36% 是"31.1 GB/s 原样保持"的乐观值**；neuron-major 后是 gather（512 B/神经元）而非顺序流，实测带宽可能 ≤ 顺序流的 80% ⇒ 现实 +20~30%（20–22 tok/s）。
- **U5**：天花板 23.3 tok/s 的前提是"gate/up 25.3 ms 不可省"（稠密 769 MB/token @31 GB/s）——若 P1 打点（`情报-K` §5）证明 gate/up 不是纯带宽，则天花板会上移。
- **U6**：helgard 的 +12% 与"down 读 17/137 ms"是**其 NVMe/PCIe 架构**下的数；我们的 down 是 DRAM 顺序读，相对收益会更大（这也是本件算 +36% 而非 +12% 的原因），但 gather 开销未实测。
