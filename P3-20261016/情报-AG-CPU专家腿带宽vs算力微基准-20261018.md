# 情报-AG · CPU 专家腿「带宽 vs 算力」微基准 — 2026-10-18 · builder3

**问题**（用户思路）：选错专家可"边搬边算、PCIe 搬入正确的、其余 CPU 原地算"，用调度藏时间。此思路有没有理论窗口，取决于 CPU 专家腿是**带宽受限**还是**算力受限**。

**答：带宽受限（算力被隐藏），PCIe 分流没有额外 DRAM 带宽窗口 ⇒ 预期 ≤5%，与 R39 实测 +5.6% 吻合。**

## 1. 测法（零 GPU、零编译、零改码；未 spawn 子代理）

| 量 | 方法 | 读数 |
|---|---|---|
| 单线程原生顺序读 | `copy /b E:\sp3-sidecar\downT.bin NUL`（29.53 GiB，native 读+丢弃） | 冷 6.4 s / 4.92 GB/s；**热 6.1 s / 5.20 GB/s** |
| 多线程读（参考，不作结论） | 自写 `C:\sp3\bw_microbench.py`（FileIO.readinto，1 MiB 块，4 GiB/组） | 1 线程 2.18、8 线程 8.04、**16 线程 15.77 GB/s**（受 Python 读路径限制，明显低于原生；**仅作量级参考**） |
| **引擎 16 线程实际聚合**（结论采用） | 交付跑 ledger：`down=2009 ms / 128 tok`；uses=516/tok、1.548 MB/use | **≈51 GB/s 聚合**（= 516×1.548MB / (2009ms/128)） |
| **纯算力（16 线程）** | 现成 `C:\sp3\stageC-parity-topt.exe` bench（数据已驻留、"compute only, no I/O waits"） | 1 线程 171.8 µs/use；16 线程 **5.54 ms/token ÷ 516 = 10.7 µs/use** |

## 2. 三条关键比较

1. **带宽时间 / use**：引擎 ledger 自报 `down=2009.4 ms … 41.3 GB/s`（`C:\sp3\R69-P0-20261018.log`，128 tok）⇒ down 相每 token 15.7 ms。按引擎自报的 41.3 GB/s 折算，一个 use 的 1.548 MB 需 **37.5 µs**；若按 parity bench 的 uses=516/token 折算则是 30.4 µs/use（与自报 41.3 GB/s 存在口径差，两者都远大于算力时间，结论不变）。
2. **算力时间 / use（16 线程）**：**10.7 µs/use**（`stageC-parity-topt.exe` bench：1 线程 171.8 µs/use，16 线程 5.54 ms/token ÷ 516 uses/token）。
3. ⇒ **带宽时间 ≈ 3–3.5× 算力时间；down 相的时间基本全部由内存读解释（30–37 µs/use vs 算力 10.7 µs/use），算力被线程级重叠隐藏**。

## 3. 判决

- **带宽受限**（不是"vec_dot 算力打满"）。52 GB/s 不是"只用到理论 89.6 的 58% 所以还有 40% 空间"——该读路径的实测单线程上限 5.2 GB/s、16 线程聚合实测 51 GB/s（≈3.2 GB/s/线程，含多线程共享内存控制器的常规折损），**51 已接近可达到的读上限**；Python 15.8 GB/s 与"5.2×16=83 GB/s"都不构成可实现上限。
- **PCIe 边搬边算结论：无窗口（≤5%）**。理由：正确的专家无论怎么来，其数据都在同一块 host DRAM 里；CPU 原地算要读它、PCIe 搬入也要从 host 端读出（或该专家本来就在 RAM）⇒ **不产生额外带宽**。可重叠的只有"调度空档"，而算力本来就被隐藏 ⇒ 最多蹭到 PCIe 与 DRAM 的少量并行空档，量级与 R39 的 +5.6% 一致。
- **唯一潜在空间不在 PCIe，而在读路径本身**：若能把 51 GB/s 抬高（例如更大的预取/连续读、线程亲和/内存通道均衡），down 相才可能下降；但按本机实测上限判断空间有限（≤10–20% 需专项验证，且属于 CPU 读优化，与 PCIe 无关）。
