## §0 结论速览（三条任务令各一句）

1. **★ 谱系已定**：本靶 **Nemotron 3.5 Super VL 120B-A12B** 的**直接前代 = `NVIDIA-Nemotron-3-Super-120B-A12B`（2026-08-25）**，**架构逐项一致，只多一个 VL 外壳** ⇒ **同族同架构**（§1）。
2. **★ 架构相近度**：3-Super-120B-A12B 与本靶**逐项相同**（88 层 / hidden 4096 / 512 专家 / top-22 / latent 1024 / shared 5376 / relu2 / vocab 131072 / MTP 1 / head_dim 128 / KV 头 2 / ssm_state 128）；**同族但几何不同**的是 Nano/Lightning（128 专家、top-6、**无 latent**）与 Ultra（hidden 8192）⇒ **"借鉴"要分院线**（§2）。
3. **★ NVIDIA 侧重（第 3 问）：有干货，但方向与预期相反**（§4）：
   - **官方三栈（vLLM / SGLang / TRT-LLM）都给了 recipe**，但**全是"把整模放进大显存"的路子**（≥ B200/DGX Spark 档），**没有任何 offload / 专家驻留 / CPU-GPU 协同建议**；
   - ★★ **NVIDIA 对小卡的官方答案是"改模型"不是"改调度"**：**Bolt-74B-A9B-24GB** = 用 **Star Elastic 剪枝**（router-guided）把 120B-A12B 压到 74B-A9B、**top-K 22→9**、专家 **IQ2-XXS 2-bit**（QAD）、再配 **dflash 投机** ⇒ **目标硬件 = RTX 5090 / DGX Spark / RTX Spark（24–128 GB）**。
   - ⇒ **我们想靠调度（profile 驻留）拿的东西，NVIDIA 选择在模型侧解决** ⇒ 这解释了**为什么官方 recipe 里没有"专家驻留/offload"**（§5 的"不能搬"）。

## §4 ★★ NVIDIA 侧重调优（第 3 问；C，但全部来自官方模型卡）

### 4.1 官方三栈的**可直接看的**旋钮（把原文抄在下面，供判"可否搬"）

| 旋钮（官方原文） | 出现在 | 与本靶关系 |
|---|---|---|
| **`--kv-cache-dtype fp8`** | vLLM（Super 与 Bolt **都开**） | ★ **KV 量化被官方当一等旋钮**；我们 t16 因 `max_context=8192` 得出"KV 只 64 MiB、省不出肉" ⇒ **该结论只在短上下文成立**，与 `上游适配侦查` 里 strata 新增 `--kv q8_0`（仅挂 qwen35）呼应 |
| **`--mamba-ssm-cache-dtype float32`**（Super）/ `bfloat16`（Bolt）· **`--mamba-cache-dtype`** · **`--mamba-cache-mode align`** | vLLM | ★ **Mamba state 的 dtype/对齐是官方显式旋钮**（我们 `state_` 恒 fp32、165 MiB）|
| **`--enable-expert-parallel`**；**B200 用 `--tensor-parallel-size 2` 并去掉它** | vLLM | "卡间怎么分专家 vs 分张量"的官方取舍 ⇒ 对应我们 `--layer-split` |
| **`--gpu-memory-utilization 0.9`** / **`kv_cache_config.free_gpu_memory_fraction: 0.8`** | vLLM / TRT-LLM | ★ **官方明确"留 10–20% 余量"**；我们默认 reserve = 768 MiB ≈ 32 GB 的 **2.3%** ⇒ **量级差一个数量级**（见 §5 可测假设） |
| **`--speculative-config '{"method":"dflash", "model":"…-LiLiCorr", "num_speculative_tokens":7, …}'`** | Bolt | ★ 官方在**24 GB 卡**上**开投机**（dflash + 专门的 draft 模型）⇒ 与我们 `--no-draft`（为正确性）是**相反取向**，但**方向值得记** |
| **`use_mamba_kernels: true`** · `moe_shared_expert_overlap`（Lightning **true** / Super false） | config | 两个"内核/重叠"开关我们**没有对应物** |

### 4.2 ★★ 官方对"小卡"的答案：**改模型，不是改调度**

**`Nemotron-3.5-Bolt-74B-A9B-24GB` 的官方做法（原文）**：
- **一句话**：「designed to run everyday agentic tasks **locally**, using a **native 2-bit quantization** to fit in **24GB** of memory」；目标硬件 = **RTX 5090 / DGX Spark / RTX Spark**。
- **手段**：**Star Elastic**（router-guided 结构化剪枝）把 **120B-A12B → 74B-A9B**；★「**budget-conditioned router heterogeneously selects routed-expert counts and MoE intermediate widths across layers, while expert top-K is fixed at 9, down from 22 in the parent**」；**专家量化到 2-bit（IQ2-XXS）+ QAD**（用 Modelopt）。
- **⇒ 对照**：NVIDIA 面对"小卡装不下"的**官方解 = 把模型变小**（剪枝 + 降 top-K + 异构专家宽度 + 2-bit）。
- **⇒ 我们面对的是相反问题**：模型**已经在手上、不许改权重**（正确性目标已达成）⇒ 只能在**运行期**做（`--expert-profile` 驻留 / `--vram-reserve-mib` / stage / swap）。**两条路线的目标函数相同（在 24–32 GB 里跑好一个 120B-A12B），但手段正交。**

**⇒ 一个重要的负面结论**：**官方三栈的 recipe 里没有任何 `offload` / "expert residency" / "CPU-GPU 协同"建议**（全卡 grep 未见）——因为它们的**目标硬件不是 32 GB 消费卡**（120B-A12B 的官方口径是 **2×B200 / DGX Spark / 单 B200（NVFP4）**）。⇒ **第 3 问的期待（"历史版本有侧重 N 卡的 offload 调优"）在官方材料里没有得到支持**；能拿到的只有 §4.1 的**旋钮清单**与 §4.2 的**路线对照**。

### ★ 由 B3 得到的一条**可测假设**（D，须实测）
官方留 10–20% 显存余量，我们只留 2.3%（768 MiB）⇒ **"把 reserve 提到 0.1×卡（≈3.2 GB）会不会更稳/更快？"**
⚠️ **但与我们的已知规律冲突**：`反组设计`/`batch-arena` 已证 **reserve↑ ⇒ arena↓ ⇒ 命中↓**（1 MiB ≈ 0.338 对）。⇒ **这正是需要"成套配比"实验去判的张力**（不是单独调 reserve 能定的）。

## 8.0 ★ 先说最重要的负面结论（省掉别人重找的时间）
