## ③ 老师代码里的缓存准入/换出策略（决定 96.5% 的机制层）

### 3.1 准入：**decode 期间不 admit**（与日志 `0 admitted` 一致）

- 运行期应用：`E:\strata\src\program\generate.cpp:1761-1775` —— profile 只在这**一次**填入 `xcache`：
  ```cpp
  const int64_t want = std::min<int64_t>((int64_t) profile.size(), xcache.slots());   // :1767
  for (int64_t i = 0; i < want; ++i) {
      const int32_t slot = xcache.admit(profile[i].first, profile[i].second);        // :1769
      ... fill_slot_blocking(...)                                                    // :1772
  }
  ```
  注释原文（`:1761-1764`）："This is the only place the plan is applied, and it runs ONCE: with slots pairs and slots slots the cache is full when this returns, so the decode-time admission finds no room and every non-profiled expert stays a CPU miss. **That is what makes the profile the policy rather than a hint.**"
- decode 的 verify-window 路径：`src\core\expert_source.cpp:397-402` 只记 `cache_hits`/`cache_refused`，**没有 admit 调用**；日志 `dec-pool2:87` `(0 admitted, 4176 refused, cache 100.0000% full)` 与之逐字吻合。
- 单 token 路径才有 compulsory-miss 的 `cache_admitted`（`expert_source.cpp:455-495`，`::485 ++d.cache_admitted`），但本 run 走 verify window，admitted=0。

### 3.2 换出：**没有淘汰**；只有 adaptive tier 的"换入换出"（fill-only + 每 4 轮 ≤96 个）

- 引擎不淘汰：`49c50f4` 的 commit 正文 = "**ExpertCache::admit never evicts because eviction policy is a measured question** (R4.1's LFU-decay vs LRU sweep)"；实验工具 `tools/bench_eviction.py` 回放 fill-only/LRU/LFU-decay/oracle **只是测量**，没有变成默认。
- 唯一的动态性 = **adaptive tier**（Plan v0.3 P6）：
  - 默认 `--adapt-every 4`、`--adapt-swaps 96`（`generate.cpp:248/260`）；
  - 语义（`generate.cpp:2651-2690`）：每层把**非驻留且 decayed count ≥ 2** 的候选按计数降序、驻留者按计数升序；只换 **gain > 1.5** 的（`:2670-2672`），全局取前 96，`cudaMemcpyAsync` 在独立 `adapt_stream`，`pending` 落地后改 `host_res`；最后全部 counts ×0.7（`:2689`）。
  - 日志 `dec-pool2:74`：**818 experts swapped / 76 rounds（every 4 rounds, 0.175 ms/round）** ⇒ 整个 decode 只换了 818 次（24,576 distinct 的 **3.3%**）。
- **关键推论（有界）**：在"不 admit + 只换 ≤818 个"的前提下，**96.5% 只能靠初始表已经足够好**：
  - 初始表 11,428 槽（46.5%）；若表与本次流量无关，命中率不可能显著高于它 46.5%；要出现 96.5%，初始 11,428 槽里必须已经含有本次 decode 绝大多数的热专家；818 次换入最多再补 3.3% 的 distinct。
  - 定量上限：从"表质量=我们的 67.4% 理想覆盖"开始，要靠换槽到 96.5% 需要改掉 ~30% 的槽（≈3,400 个），**远超 818 的上限** ⇒ 老师的 96.5% **不是自适应换出来的，而是初始表与流量匹配**（adaptive 只做微调/漂移补偿）。
- **表从哪来**：`data/expert-profile.bin` 是**随发行版发布的文件**（`git log --all -- data/expert-profile.bin`：`01529aaa` 初始加入 2026-09-24、`9253c92a` 扩到全 24,576；`E:\strata\docs\DETAILS.md:93-95`：**"Since 0.1.14 the expert profile ranks all 24,576 experts … `tools/make_profile.py` builds a profile from your own prompts: run the engine once with `--dump-routing trace.bin`"**；`09e3ba42/8cb26e6` 给出维护者的做法：`make_profile_mix.py` + `bench/profile_corpus.json` 的 45 条多样化 prompt + 8 个文档摘要）。**"随包发行的表是不是从 NVIDIA 训练/评测流量生成"——仓库里没有明写**（`未查到`；只有 SYCL 表有明确 45-prompt 来源）。
- **老师本次 run 是否用了"自己的流量表"**：不是（`dec-pool2:19` "profile E:\strata\data\expert-profile.bin: 24576 ranked pairs, built for 24576 slots" = 发行版表）；而且它跑在 0.1.40.2，`make_profile --reorder`（2026-10-03）尚未发布 ⇒ **即使想用 trace 重排也不会生效**（`--base` 已被完整 base 排满 ⇒ trace no-op，`90d32517` 正文）。因此 96.5% 的合理解释 = **发行版表本身就是维护者按"类似 benchmark 的 prompt 集"做的，而这次 decode 的流量与它同族**。
- **老师自己的证据链（A 级日志）**：`bench/local/a1-verdict-0124.log:34/67/100` = **97.35% / 97.23% / 97.01%**；`bench/local/arms/20261013-011157-B1-learnedprof.log:76` = **97.06%**；`profile-gen-stats.log` 尾 = **95.95%**（111,231/115,932）⇒ 96–97% 是它**跨 prompt（4,170–6,845 token prompt、1,000 decode）稳定复现**的水平，不是单次侥幸。
- **表质量是杠杆的直接证据**：`8cb26e6`：SYCL 表（45 prompts+8 docs）在 **12 条未见 prompt 上 decode +5..64%（均值 +21%）**；`abba-r2profile.ps1`（老师自己的 A/B 模板）："**A = the profile-rebuilt arm (--expert-profile = the ranking learned from our OWN decode routing), B = the live arm (the shipped data\expert-profile.bin)**"；A/B 结果（`bench/local/results/r2prof-*.json`）：decode 86.6/101.6（A1/A2）vs 85.2/85.4（B1/B2）⇒ **自流量表最高 +16.2 tok/s**（hit 已饱和 97% 所以变化小；对我们 43% 的场景杠杆更大）。

### 4.3 我们的 24.1 点：层间不倾斜 vs 表采集自 prefill

- **层间不倾斜：≤0.4 点**（§4.2 反事实）。
- **表采集自 prefill：≈23.7 点**（=24.1−0.4）。硬证据：
  - 代码：`use_` 在 **prefill**（`moe_rows`，`PolyStrata\src\poly\engine.cpp:2800-2802` `++use_[il*n_expert+ids[i]]`）和 **decode**（`moe`，`:2260`）**都计数**；`save_profile()` 写 `prior_+use_`（`:2020-2047`）⇒ 表是"prompt 路由 + decode 路由"的混合物。
  - 数据：把 `P3-20261016` 下所有**写过 profile 的日志**（含 `profile: saved` 的 88 个请求）的 token 数加总：**prompt 65,793 vs decode 1,167 ⇒ prefill 占 98.26%**（脚本见 §6）。⇒ **p_master 的计数 98% 来自 prefill 路由**，却被用来预测 decode 路由。
  - 另一硬伤：`p_master` 只有 **40 个 trunk MoE 层**，**没有 blk.88（MTP 块）**；对应 R40 开 draft 的臂命中从 43.3% 掉到 28.6%/29.4%（`C:\sp3\R40-W1/-W2-20261018.log`）。
  - 自适应能从这 24.1 里捞回多少：我们 R43/R44 臂（更多 swap）命中已到 **60.5–62.7%**（`R43-A1/B1`、`R44-C4`）⇒ 约 **17–19 点可被自适应收回**，剩 5–7 点是静态表本身。
