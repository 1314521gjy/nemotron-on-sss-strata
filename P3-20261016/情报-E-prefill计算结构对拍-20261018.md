## §0 结论速览（给队长的一屏）

1. **上游 prefill 的段序列**（`src/prefill/prefill.cpp:2004-2010` 的 `PfPhase`，A）：`embed+steps → hc read → [GDN: gdn/gdn conv+gates/gdn recurrence/gdn out proj | QSA: qsa proj/indexer/select/attn + kv stage] → router+shared → (fused: GPU grouping→fused experts | MMQ: host grouping→gather→wait copy→dequant→gemm gate/up→gemm down→combine) → 下一层`。**它不把层拆成可并行段**；并行只发生在"拷贝流 vs 计算流"、"CPU 池 vs GPU"、以及"下一层专家预取 vs 本层计算"（`m.cs` 计算流 + `m.copy` 拷贝流，`prefill.cpp:1119`）。
2. **`--gpu-stages` 不是 prefill 的东西**：它是**一个 decode token 的 per-layer 图**的三段测量（`session_capture(..., split=true)` 捕 3 组图，`generate.cpp:5970,6149-6181`；打印 "one token over 48 layers" 后 **prints and exits**）。help 原文 `C:\sp3\help.txt:162-164`。**上游 prefill 全程没有 CUDA graph 捕获**（`src/prefill/` 下 `cudaStreamBeginCapture` **0 命中**，全树 `src/**` 的捕获点只在 `core/session.cpp:204`、`core/mtp.cpp`、`core/verify.cpp` —— 都是 token/decode 侧）。
3. **我们 poly 的 prefill 也没有图**：`replay = opt_.graphs && n <= opt_.window && (windowed_ || n == 1) && !opt_.dump`（poly `engine.cpp:3007`）⇒ 6792 token 的 prefill 永远走逐层 launch。`--no-graphs` help 原文 "launch a **token's** kernels one by one"（poly `main.cpp:767`）。⇒ **"图"这个机制两边都只服务 decode；上游 prefill 快不出在图。**
4. **最高性价比的一条**：上游把 **router 的 top-k 放在 GPU**（`src/prefill/kernels.cu:2016-2023` 的 `route()` + `:1491-1528` 的 `route_kernel`），host 只收 ids/weights（T×K）；我们的 `moe_rows` 每 MoE 层 **D2H 整张 T×512 分数（6792×512×4 = 13.9 MB/层）** 再在 24 线程上做 sigmoid+bias+top-22+归一（`nemotronhmoe.cpp:362-412`、`engine.cpp:2436/2505-2509`）——这正对得上 nsys 的 **40 个层边界气泡 7.2–12.2 ms（合计 0.400 s，占墙 12%）**。**A 级**：气泡与 D2H/host 代码；**D 级**：归因。工作量：中（top-22 的 GPU 内核要自写：现成 `native_router_topk_supported` 只支持 (512,10)/(256,8)，`src/kernels/cuda/native_router.cu:236`）。
5. **两个"不可搬"的坑（先钉死）**：`wmma_gemm.cu` 是 **AMD RDNA3 (gfx1100) HIP intrinsics**（`wmma_gemm.cu:1-19`）⇒ NVIDIA 不可用；`mmq_nvfp4_w4a8/w4a4.cu` 是 **Blackwell sm_120 FP4 MMA**（`mmq_nvfp4_w4a8.cu:1-9`）⇒ 4080S (sm_89) 不可用；`STRATA_PF_FUSED_KQ` 的 K-quant 融合 **只在 `#if defined(__HIPCC__)` 下编译**（`moe_fused_iq.cu:1076-1089`）⇒ **CUDA 上 Q4_K 不在融合覆盖内**。**不许把上游任何"卡注释值"当我们读数**（§5 每条都标了机器）。

### §2.3 我们 poly 的图现状（A：当前 sha 的代码）

- `replay` 判据（`engine.cpp:3007`）：`opt_.graphs && n <= opt_.window && (windowed_ || n == 1) && !opt_.dump` ⇒ **只有 decode/verify 窗口（n ≤ window、n==1）会走图**；prefill 的 `n` 是 6792。
- 图再捕点：单层 `replayed(...)`（`:3009-3013`，按 `(layer, tokens, rec)`）、`whole` 全层一张图（`:3143-3166`，条件含 `replay`）、logits `tail()`（`:3242-3243`）。
- `--no-graphs`（`main.cpp:767, 848`）原文："launch a **token's** kernels one by one (default: a layer's are recorded once…)"。
- ⇒ **和上游一样：图只服务 decode。我们的 0.400 s 层边界气泡若要靠图解决，是"新增 prefill 图捕获"，不是"照抄上游 prefill"。** 上游口径（`generate.cpp:6142-6147`）正好说明：这种气泡就是"host 逐 kernel enqueue 的间隙/等待"，与 kernel count 成正比 ⇒ 图对它是直接对症的；**但上游自己在 prefill 没这么做**，说明它的 prefill 气泡靠"流水线（双流 + ring + 异步 PLE + CPU 池重叠）"压掉了。
  - **能证伪这条的两个读数**：① 若把 0.400 s 按 layer 打标签，发现气泡在 **MoE 层**（40 个）⇒ 指向 router 的 host 往返（§5-A 方案）；若在 **mamba 层**（40 个）⇒ 指向 mamba 段之间的 host 依赖，图捕获/GPU 路由也不是直接解（需另查）。
  - ② 若用 `--no-graphs` 跑 **decode** 墙钟差 < 1% ⇒ 我们图上没有收益空间，prefill 加图同样应悲观（负控）。

### §3.3 "我们没用但重要"（本席挑 3+1 个，按可搬性）

1. **GPU 侧 routing**（不是这 11 个文件里的，但同一上游思想）：`src/prefill/kernels.cu:2016-2023` 的 `route()`（GPU 内核）+ `route_kernel:1491-1528`（warp-per-token、top-10 硬编码、softmax 口径）。我们**在链接面里已有** `src/kernels/cuda/router_top10.cu` / `native_router.cu`，但 `native_router_topk_supported` **只支持 (512,10)/(256,8)**（`native_router.cu:236`）⇒ 我们的 **top-22 + sigmoid + bias** 语义（`nemotronhmoe.cpp:360-412`）**没有现成的**，要自写/扩一个。这是"最可能直接吃掉 0.400 s 气泡"的一条。
2. **fused int8 专家**（`moe_fused.cu` / `moe_fused_iq.cu`）：把 grouping+激活量化+GEMM+SwiGLU/relu2+down 量化**融成一条**；上游 **A 级数字（RTX 5070 12GB）**：Q2_0 prompt 4K 1294→1570、32K 2170→2653 tok/s（`DETAILS.md:22-23`，+16~22%）；老师在我们机器上 **A 级只有 +5%**（`回执\长prompt-3.8对拍-20261017.md:24`：2805.87 vs 2670.68）。**CUDA+K-quant 不可搬**（见 §3.2），但"relu2+quantize 融进 GEMM epilogue"是能自写的方向。
3. **`gemm.cu` 的 dense 大 tile GEMM**：prompt 的 dense 投影走 cublas（CUDA）/ hipBLASLt（HIP）+ bf16 路径，而不是逐 token GEMV。我们的 `mul_mat_q type12` 0.844 s 里 dense 占多少**未验**；若占比可观，这是 tensor-core 化的入口。
4. **（附加）`moe_mmq.cu` 的组 gather**：`MMQ_GROUP=16` 专家/launch 的设备侧 gather（`gather_native_group`，`prefill.cpp:3829-3899`）。我们 DMA 已 85.2% 重叠（队长 nsys）⇒ **收益只在"少 launch / 少 host 参与"**，不在搬运。

## §5 结论：哪些上游结构最可能压我们的 compute（按"收益/工作量"排序）

**前提（队长给的 A 级拆账）**：prefill 墙 3.631 s = compute **2.941 s（77.5%）** + 层边界气泡 **0.400 s**（40 × 7.2–12.2 ms）+ 未藏副本 0.289 s；DMA 45.23 GB @ 23.2 GB/s、重叠 85.2% ⇒ **DMA 不是瓶颈**。
> **口径注意**：3.631 s 是**队长 nsys 的拆账口径**（与 `C:\sp3\pair_D_pb6912.log:87` 的 10.406 s 不是同一跑/同一窗口）⇒ 本表一律用**队长口径的相对数**（占墙 %），不与 D 跑绝对值混算。
**我们的 kernel top（占 compute 2.941 s 的比例）**：`mamba2_scan` 0.845（28.7%）· `mul_mat_q type12`(Q4_K) 0.844（28.7%）· `type20`(IQ4_NL) 0.254（8.6%）· `quantize_mmq` 0.228（7.8%）· `relu2` 0.199（6.8%）· `mamba2_conv` 0.139（4.7%）· `native_mmvq_slots` 0.113（3.8%）· `axpy` 0.077（2.6%）· `attn_softmax` 0.061（2.1%）。

## §6 未验 / 需要什么读数才能定

- **U1（决定 #1 是否成立）**：0.400 s 气泡的**层标签**。队长给的是"40 个、一 mamba 层一个"，但 **mamba 层数 = MoE 层数 = 40**，仅凭计数分不开。需要 nsys 里气泡附近的 layer 标记（或把 `moe_rows` 的 host 段用时单独打点）。若气泡在 MoE 层 ⇒ #1 直击；若在 mamba 层 ⇒ 需另查 mamba 段的 host 依赖（本件未找到候选）。
- **U2**：`mul_mat_q type12` 的 **MoE vs dense 占比**（决定 #4/#5 的量级）——需按 call-site 打标签或分开跑（零 GPU 不可得）。
- **U3**：我们 `route()` 的 host 耗时**实测值**（本件是按 3.5M sigmoid/层估的，未打点）——这与 7.2–12.2 ms 的气泡是否对得上，需一次计时钩子（属于改码，本件不做）。
- **U4**：上游 `moe_mmq` 组 gather / `mmq_resident_sort` 在 **RTX 4080 SUPER + Q4_K** 上的收益**无任何上游数字**（`mmq_resident_sort` 的数字是 4×P100；fused 数字是 5070/5090/R9700）⇒ 一律 D 级，**不许当我们的读数**（任务单点名的坑）。
- **U5**：`src/prefill/kernels.cu`（prefill 专用 kernel 库，2,225 行）只读了段/route 部分；其余（qsa/gdn/combine 族）未逐行读。
- **U6**：`GraphRegistry`（`graph.cpp`）无调用者这一点是**grep 结论**（`GraphRegistry` 全树只在 graph.cpp 出现）；若有宏/模板间接引用本席未覆盖，需复核。
- 本件未跑 GPU、未编译、未起进程、未改任何 src。
