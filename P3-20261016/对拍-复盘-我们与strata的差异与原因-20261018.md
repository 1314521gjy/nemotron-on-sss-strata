# 对拍复盘：我们 vs Strata 老师 — 哪里不一样，为什么

> 依据：`对拍-我方与老师-差异总表-20261017.md`（唯一归属处）· `情报-O/Q/U/AA/AB/AC/AD` · `情报-W`（命中率硬证据）· R49/R51（真计时）· R58/D2a（Stage D）· R60/R62/R67（今天）
> 老师读数来源：`E:\strata\_staging\dec-pool2.txt`（**A 级：同一台 4080S 32GB 上跑的**，engine 0.1.40.2）
> 证据等级：A=本机自实测 / B=同机另一线 / C=外部 / D=推断

---

## 0. 一句话

**硬件相同（同一台 4080S），差距不在"引擎快慢"，在「每 token 要搬的字节数」**：
我们用同一块卡、同一套 CPU/内存，每 token 的 CPU 专家字节是老师的 **≈12.6×**，于是 decode 写成
`per-token ≈ miss/token × cpu_us/miss + 固定开销`，两边套同一公式，结果就是 24.3 ms/轮 vs 65.9 ms/轮。

**差距 ≈ 12.6× 字节 = 2.74×（几何：top-22 vs top-10）× 1.52×（专家大小：3.10 vs 2.04 MB）× ~3×（miss 率：42% vs 3.5%）。**

## 1. 差在哪 — 五张表

### 1.1 模型几何（**不可改**）

| 项 | 老师（3.8-Flash） | 我们（Nemotron-120B-A12B） | 倍率 |
|---|---|---|---|
| 层 | 48 | **88**（40 mamba + 8 attn + 40 MoE） | 1.83× |
| 专家数 | 24,576（48×512） | **20,480**（40×512） | 0.83× |
| 每专家 blob | **2.0379 MB** | **3.0966 MB**（up Q4_K 1.548 + down IQ4_NL 1.548） | **1.52×** |
| **top-k** | **10** | **22** | **2.20×** |
| 每 token 激活专家 | 480 | **880** | 1.83× |
| 专家库总量 | ~50 GB | **63.4 GB** | 1.27× |

### 1.2 常驻（命中）率

| 项 | 老师 | 我们（今天交付） |
|---|---|---|
| VRAM 槽数 | **11,428 / 24,576 = 46.5%** | 5,721 + 1,025（借槽）= **6,746 / 20,480 = 32.9%** |
| hit | **96.5%**（45 miss/token） | **58.4%**（373 miss/token，p6792） |
| 每 token CPU 专家字节 | **91.7 MB** | **1,155 MB** ⇒ **12.6×** |
| 每 miss 成本 | ~130 µs（15.4 GB/s） | ~110 µs（**52 GB/s 安静机实测**） |
| CPU 腿 / 轮 | **7.3–9.9 ms** | **49.1 ms** |

**为什么槽少**：同 32GB VRAM，我们的 blob 大 1.52× ⇒ 同样显存装得少；且我们额外要放 borrow 区、staging。
**为什么 miss 多**：top-22 vs top-10 ⇒ 单 token 激活专家多 1.83×；且**每 token 需要的"覆盖"更大**。
**为什么 hit 差**：我们的表历史上被 prefill 污染（98.26% 计数来自 prompt token）；今天 B1 修好后 p6792 到 75.3%、但异构 alt/qa 只有 57–68%（**表是负载专属的**，见 §13）。

### 1.3 一轮的时间结构（A 级，同一台机）

| 段 | 老师（24.3 ms/轮，2.63 token/轮） | 我们（65.9 ms/轮，1.0 token/轮） |
|---|---|---|
| ring / router 等待 | **12.378 ms**（GPU 在门铃上等 host，**图内**） | 7.7 ms（host D2H + event） |
| CPU 专家池 | **7.269 ms** | **49.1 ms** |
| host / launch | **0.101 ms** | 4.9 ms（实测） |
| commit / sync | **0.037 ms** | 1.1 ms（实测） |
| MTP / tail | 2.360 / 2.17 ms | 无（`--no-draft`） |
| **有效每 token** | **9.24 ms** | **65.9 ms** |

⇒ **CPU 腿 7.27 vs 49.1 = 6.8×，几乎就是总差距的全部**（其余段我们并不差，router 段还更小）。

### 1.4 架构成熟度（我们的"缺件"）

| 老师有 | 我们用 | 影响 |
|---|---|---|
| **device 侧路由 + 门铃 + 整图**（只在"全驻留 token graph"成立） | host 路由（40×512 sigmoid+top-22）+ 88 层逐层 launch | 我们**永不全驻留** ⇒ 主体不可仿；可仿部分只值 +3~7% |
| **resident 补集 + exchange 架构** | pin 死全部 63.4 GB | 省不出 RAM（Stage D 实测证实） |
| **per-layer 槽配额** | 全局计数排序（已最优） | 我们更彻底，+0.10pp 不值得 |
| **profile 学习闭环**（rank 学习） | 今天 B1 才有（默认关） | **真实价值 = 负载自适应 +16~38%**（自建表） |
| **MTP 512 专家专属常驻 675 MiB** | MTP 与主 cache 抢槽（−212 槽 ⇒ ids 漂） | 老师 **2.63 token/轮**，我们 1.0 |
| `PCIE_BALANCE` / `PF_FUSED` / `ADAPT_NOWAIT` / `EXCHANGE_ROTATE` | 无/半 | 各自 5~10%，未验证 |
| **482 个 env+CLI 旋钮** | 18 | 调度面厚一个量级 |

### 1.5 我们比老师**强**的地方（不是全面落后）

| 项 | 我们 | 老师 |
|---|---|---|
| CPU 专家读带宽 | **52 GB/s**（安静机实测 29.7 µs/use × 1.548MB） | 15.4–18.4 GB/s |
| prefill 有效 DMA | 17.7 GB/s | 13.97 GB/s |
| ring 流水 | 自研 round-slot（−19% 墙） | 上游默认 N 槽（未打印槽数） |
| prefill 去重 | 我们把 2048-token 切 4 call 的重复 ahead 砍掉（141→44.58 GB） | 它单 chunk、无此坑 |
| 借槽 | 今天做了（+11.3%） | 它有（2387 槽 / 4.55 GiB / 回填 208.7 ms） |

**⇒ 我们输的不是"读得慢"，是"要读的太多"。**

## 2. 原因分析（按贡献排序）

### 原因 1（≈60%）：**每 token 激活的专家多 + 专家大 ⇒ 字节多**
`top-22 × 3.10 MB` vs `top-10 × 2.04 MB` ⇒ 单 token 的"活跃专家字节"天然 3.35×。
这是**模型选择带来的**，不是引擎能改的；只能靠"更多常驻"或"更少每专家字节"来抵消。

### 原因 2（≈30%）：**常驻率低 ⇒ miss 率高**
- 同 32GB，blob 大 1.52× ⇒ 槽数上限低；
- 我们的路由浓度其实和老师**几乎一样**（`情报-W`：46.5% 覆盖处 84.0% vs 84.1%）⇒ **不是模型差异，是"槽数 + 表质量"**
- 表质量：历史表被 prefill 污染（98.26%）；今天 B1 修好 ⇒ p6792 75.3%，但**表只对建表负载有效**（跨 alt −16% miss、跨 qa +19% miss）

### 原因 3（≈10%）：**MTP 没做成**
老师 2.63 token/轮 靠 MTP（且把 512 个 MTP 专家单独常驻 675 MiB，不吃主 cache）。
我们的 MTP：仅 +2.2%（还吃 626MB ⇒ −212 驻留 ⇒ ids 漂）⇒ 收口 opt-in。
**根因不是 MTP 不行，是"没有专属驻留"** —— 但我们算过：1.585 GB 专属区 + 626MB draft 本体 ⇒ 峰值 33.2GB > 31,700 ⇒ 只能从借槽区划 ⇒ 主 decode −6% vs MTP ≤+8.4% ⇒ 净 ≈+2% ⇒ 不值。

### 原因 4（<5%）：**引擎形态差**（device plan / 门铃 / 整图）
老师 decode 的一轮是"GPU 算路由 → device 表 → 门铃 → host 拿环 → CPU pool → GPU 收尾"，**且只在全驻留 token graph 时用整图**。
我们命中 58% ⇒ 永远到不了全驻留 ⇒ **它的主体对我们不适用**；可仿部分（device top-k + mapped 门铃）预期只 +3~7%，且风险高。

### 原因 5（几何以外的"看起来像原因但不是"）
- ❌ **不是带宽**：我们 52 GB/s > 老师 15–18 GB/s
- ❌ **不是内核**：共用 `strata_core/kernels/spec/gguf_reader`
- ❌ **不是 ring/借槽缺失**：今天都补了
- ❌ **不是"教师机更强"**：dec-pool2 就在本机 4080S 上跑的

## 3. 要追平，必须动什么（量化）

| 手段 | 能把字节降到 | 现实性 |
|---|---|---|
| 提到老师同级命中（46.5% 覆盖 ⇒ 84% hit） | miss 373→143 ⇒ 约 **+8% decode**（不是 +80%，因为专家大） | 需 VRAM 多装 ~2,400 槽 ⇒ **不可能**（32GB） |
| **ReLU² 让每专家字节 −42%**（Stage D） | miss 不变、字节 1.155→0.67 GB | **今天实测不可行**：T 内核延迟受限（8.3 GB/s）、prefill 2.2×、净慢 3~5% |
| **MTP 做成**（2.63 token/轮） | 每 token 成本 ÷2.63 | 需专属驻留（+1.585GB）⇒ 峰值破门 ⇒ 只能牺牲主 cache ⇒ 净 ≈+2% |
| 关掉 `--lookup 3` 在异构场景 | 省 2.8% | 已判 opt-in |

**⇒ 结论：在 4080S 32GB + 96GB RAM + 这个 120B-A12B 模型上，我们已接近这套几何/硬件组合的天花板。**
**剩下的真实空间在"负载自适应"（B1：+16~38%，自建表）+ 小修（refill 异步 3%、二期借槽 5~15% prefill）。**

## 4. 复盘纪律（今天新增，防再犯）

1. **对拍是为了模仿**：差异不是否决理由；判否只能写"模仿了也不划算（带算式）"
2. **模板 prompt 的自拟合陷阱**：p6792 上的 +44%/+77% 都在 alt/qa 上崩过；任何"表/学习"类增益必须跨 prompt
3. **host-load 混淆**：同代码换窗口 `cpu_pool` 差 33% ⇒ A/B 必须交错 + 记 load + **相级读数为主**
4. **两段 pin 后，所有依赖总 pin 量的地板/阈值都要同步改成"当前段"**（今天 P1 就是踩这个）
5. **"省字节"在该 regime 收益有限**：CPU 腿已带宽打满（52 GB/s），T 内核若不能到 ≤10 µs/use 就是负收益

### 5.2 ★ 固定开销 18 ms 的结构 → **speculation 的天花板被算死了**
```
per-token = 18 ms 固定 + miss(373) × 110 µs ≈ 18 + 41 = 59 ms
若 token/round = 2.63（老师水平）：成本/轮 = 18 + 2.63×41 = 125.8 ms ⇒ 47.8 ms/token ⇒ 仅 +23%
但 R40 实测：窗口 2–3 token 时 miss/token +35% ⇒ 41→55 ms
    ⇒ 成本/轮 = 18 + 2.63×55 = 162.6 ⇒ 61.8 ms/token ⇒ 反而更慢
```
⇒ **即使做出老师的 2.63 token/轮，我们也拿不到它的 9.24 ms/token** —— 因为我们的"边际成本/ token"是它的 12.6×，摊薄固定开销救不了。
**这就是 MTP 只 +2.2% / draft-vocab 只 −8.4% 的最终解释。**

### 5.4 ★ 新挖出来的三个方向（计划表里没有）

**① 固定开销里 router 段占 43%（7.7/18 ms），Phase 5 完全没碰它**
- Phase 5 只图化了 `moe_add`/`moe_latent`（C1）与激活内联（C3），动的是 160 个 launch；
- **router 段是 40 次 `cudaEventSynchronize(ev_)`（每 MoE 层一次 D2H 等路由）**，是固定开销的最大单项；
- 仿老师的"device top-k 写 mapped memory + host 每轮 poll 一次"⇒ 把 40 次同步压成 1 次 ⇒ 预期 **+3~7%**（这是"可仿部分"的真正落点）

**② 48 个 mamba/attn 层可**整段图化**（它们不含 host 决策）**
- 88 层里 48 层是 mamba+attn+norm，**输入输出都在 GPU**，理论上可一次性捕获成图；
- 现在它们各层单独 launch + event ⇒ 48 次/round 的 host 开销；
- 预期：把 host 4.9ms + 部分 router 等待压掉 ⇒ 与 ① 合计可能到 **+5~10%**

**③ B1 表 + 自适应层（`--expert-swaps 64`）的组合**
- 自适应层当时是 **+3.5% 且失确定性**，判据在那张**prefill 污染表**上做的；
- 今天 B1 把表修好（p6792 hit 75.3%），自适应层的换槽候选来自 use 计数 ⇒ **两者叠加可能把 hit 再抬**；
- 需要 1 编译 + 4 跑验证；若确定性仍破 ⇒ 仍不进交付

### 5.5 挖掘结论

**计划表里的"未做项"分两类：**
- **只影响 prefill**（#4 refill 异步 +3%、#6 二期借槽 +5~15%、#12 Q1）—— 对 agent 负载有实际意义（每轮 turn 一次 prefill），但不是 decode 缺口
- **decode 侧只剩小钱**（#3′ 0–6%、#14 的 3~7%、① +3~7%、② +5~10%、③ 待验）

**⇒ 两条轴（字节 / 固定开销）都已接近这套几何+硬件的极限；"大杠杆"在今天被逐个证伪。**
**真正还没被开采的唯一一块 = "让引擎按当前负载自适应"（B1）**：它今天在 alt +15.9%、qa +38.3%，而交付默认还没用上它 —— **这是从"研究结论"到"产品化"的唯一缺口**（要解决的是"何时建表/何时加载/如何跨请求"）。
