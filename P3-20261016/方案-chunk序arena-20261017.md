# 方案（只方案、未改码）· chunk 序 arena 合并大 DMA — 2026-10-17

- **背景**：pin 便宜版实测 **56 GiB / 37 层 = 603.7 tok/s（+52.8%）**；**direct DMA 平均 1.48 MB、次数 74,564** ⇒ 命中"小 DMA 是拖累"判据。
- **60 GiB 顶满被拒**（本次 free 74.3 GiB，需 60+16=76）⇒ **40 层（59.1 GiB）在 ≥16 GiB 线附近，本机经常被拒** ⇒ **便宜版天花板 = 56 GiB / 37 层**。

## 1. ★ 先说一个可行性结论：**"load 时按 chunk 序摆好 arena"【做不到】**
- `stage()` 的 chunk 组成 = `group_[round_[r] .. round_[r+1] ..]`，而 `group_` 是 **每次调用按【本次路由计数】排序**出来的（`count_` → `cands` 按 `value`）⇒ **是运行时量**，**load 时不知道**。
- ⇒ **没法在 load 时把 arena 摆成"chunk 序"**。**3.8 的 arena 也不是这么做的**（它只是把专家 blobs 拷进 RAM，staging 仍按自己的顺序取）。
- ⇒ **"chunk 序 arena"这个提法本身要改**。

## 2. ★ 真正能把 1.48 MB 小 DMA 合并的做法：**按专家 id 排序本轮**
- 关键观察：**`L.exp_up` 是【按专家 id 连续】的数组**（`n_expert × gu_stride`），`L.exp_down` 同理。
- 现在 `stage()` 拿到的一轮专家是**按路由 value 排的**（id 散）⇒ 只能逐专家 DMA（1.48 MB）。
- **若把本轮专家【按 id 排序】**：id 连续的一段 ⇒ `L.exp_up + e0*gu_stride` 在源上**连续** ⇒ **1 次 DMA 覆盖整段的 ups**（downs 同理）⇒ **每轮 2 次 40–80 MB 的大 DMA**。
- **代价/难点**：排序后**目标 `stage_` 的布局与行表（`d_bounds`/`d_rel`/`d_place`）必须同步置换** —— 否则专家与行错位。**每行独立 ⇒ ids 应逐位不变**（可判）。
- **不需要**：额外 arena、不需要 17.7 s 拷贝、不需要额外 RAM。**只是在 `stage()` 里多一次 sort + 置换行表。**

## 3. 另一种"合并"（更小改动、收益有限）
- **把当前 chunk 的专家按 id 分组**：连续的 id 段各 1 次 DMA，散的单专家各 1 次。**平均单次会上升，但达不到"每 chunk 2 次"**。
- 改动最小（只改 `stage()` 的 DMA 循环），**风险低**；收益是"部分合并"。

## 4. 冲突/失败/旗标
- 旗标 **`STRATA_STAGE_SORT_IDS=1`（默认 0 = 旧行为）**；负控用它。
- **不碰 §7**（`ev_free_/ev_ahead_` 与排序无关）。
- 排序/置换失败 ⇒ 响亮报错。
- **ids 逐位不变**是硬判据。

## 5. 验收
- **平均单次 DMA > 20 MB**、次数从 7.4 万降到 **~640**（每轮 2 次 × ~320 轮）
- **prefill 从 56 GiB 档的 603.7 明显上升**（按 23.5 GB/s 估，DMA 8.6 s → ~4.7 s ⇒ 有望 ~900–1000）
- **ids 逐位不变**；负控回 603.7 / 395.0

## 6. 未验 / 风险
- **排序 + 行表置换是本方案的全部风险**（错一列就整层错位，ids 会变，可判）。
- 未核：`d_bounds`/`d_rel`/`d_place`/`d_cb` 的置换是否一处即可覆盖（需读 `moe_rows` 的调用链）。
- **未改码**。
