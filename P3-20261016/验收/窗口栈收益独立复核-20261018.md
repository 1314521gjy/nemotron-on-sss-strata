## §0 结论速览

1. **p6792 的 +57.4%（128）/ +77.1%（256）无法拆成"窗口多 token/轮 + lookup 跳过计算"两笔加法**；它是**乘法**：`倍速 = tokens/round ÷ (每轮墙钟/单 token 墙钟)`。实测：128 为 `8 / 5.044 = 1.586`（实测 1.574）；256 为 `8 / 4.453 = 1.796`（实测 1.789）——误差 <1%。
2. **"lookup 直接命中跳过计算"假设被数据否定**：若命中即跳过计算，每轮成本应≈1 个单 token，倍速应≈8×（128：112.8 tok/s；256：114.0 tok/s）；实测只有 22.19/25.23 ⇒ 被接受的 token **仍在批量验证里被计算**；真正省的是"8 个 token 的批量验证只花 5.04/4.45 个单 token 的成本"（窗口栈的批处理摊薄）。lookup/draft 的独立贡献：lookup3 比 draft 只快 **+4.1%**（22.19 vs 21.31）。
3. **alt prompt 上窗口栈没有收益**：R37 同 exe 同 config（`1bafa78d…`）16.63 → 16.17 = **−2.8%**；窗口确实开了（accepted 1/4 offered），但 63 轮只提案 4 次 ⇒ tokens/round 仅 **1.016**；R30（`547cab54…`）draft 开窗也只 +2.2%（tokens/round 2.065），且两臂驻留不同（5509 vs 5721 槽）⇒ 不能称"最大杠杆"，只能称"**p6792 模板上的大杠杆**"。
4. **判决实验的 15% per-token 门有假绿/假红风险**（§4）：p6792 模板必绿、单跑噪声可达 ±8%、tokens/round 是**推算**（盘上 6 份日志 **DONE 行 0 条、窗口自证 0 条**）、draft 吃 VRAM、draft 在 alt 上改 ids。建议补 3 条（§5）。

## §2 ① p6792 拆分（+57% / +77% 从哪来）

### 2.1 推导（★ 标"推算"：盘上**没有 DONE 行**，6 份日志全 0 条；tokens/round 与每轮墙钟均为推算）

- 口径：`rounds = generated − accepted`（每轮至少写 1 个 base token + 被接受的提案）；`tokens/round = generated/rounds`；`每轮墙钟 = decode_ms/rounds`，`decode_ms=(generated−1)/decode_tok_s`（summary 的 `generated N tokens X tok/s`）。
- 派生表：

| 臂 | tok/s | accepted/offered | rounds（推） | tokens/round（推） | ms/token | ms/round（推） | r = 轮/单token | 8/r 预测 | 实测倍速 |
|---|---|---|---|---|---|---|---|---|---|
| B0 128（无窗） | 14.10 | 0/0 | 128 | 1.000 | 70.92 | 70.4 | 0.99 | — | 1.000 |
| B1 128（draft） | 21.31 | 112/112 | 16 | 8.000 | 46.93 | 372.5 | 5.252 | 1.523 | 1.511（+51.1%） |
| B2 128（`--window 8`） | 21.57 | 112/112 | 16 | 8.000 | 46.36 | 368.0 | 5.189 | 1.542 | 1.530（+53.0%） |
| **B3 128（lookup3）** | **22.19** | 112/112 | 16 | 8.000 | 45.07 | **357.7** | **5.044** | **1.586** | **1.574（+57.4%）** |
| B0 256 | 14.25 | 0/0 | 256 | 1.000 | 70.18 | 69.9 | 0.99 | — | 1.000 |
| **B3 256（lookup3）** | **25.23** | 224/224 | 32 | 8.000 | 39.64 | **315.8** | **4.453** | **1.796** | **1.789（+77.1%）** |

### 2.2 拆分结论（乘法，不是加法）

`倍速 = tokens/round × (1/r)`：
- **tokens/round 因子 = 8.0**：来自"提案被 100% 接受"（`112/112`、`224/224`）。p6792 是重复模板 ⇒ 重复草稿几乎必然命中；这是**模板红利**。
- **批处理因子 = 1/r = 0.198（128）/ 0.225（256）**：8 个 token 的验证轮只花 5.04 / 4.45 个单 token 的成本 ⇒ 相对"8 个串行 token"省 **37%/44%**。这是**窗口栈（批量验证/摊薄）**的净贡献。
- 合成：1.586 / 1.796（预测）≈ 1.574 / 1.789（实测，误差 <1%）。

**对"lookup 直接命中跳过计算"的判决**：
- 若成立：被接受的 token 不进模型 ⇒ 每轮成本≈1 单 token ⇒ 倍速应≈tokens/round=**8×**（128：112.8 tok/s；256：114.0 tok/s）。
- 实测：22.19 / 25.23 ⇒ **轮成本 5.04/4.45 单 token ⇒ 被接受 token 仍在批量验证中被计算**，省的是"批量摊薄"，不是"跳过"。
- 唯一可分离的"提案来源"差：lookup3 22.19 vs draft 21.31 = **+4.1%**（且 draft 臂 fill 少 203 槽，有驻留混杂）⇒ lookup 的相对贡献 ≤~4%，不是主要项。
- ⇒ **回答**：+57%/+77% 的主要项是"**窗口栈批处理摊薄**"（×0.198/×0.225）与"**接受率 100% 带来的 8 token/轮**"（×8）的乘积；**没有可独立列出的"lookup 跳过计算"份额**。且两者都依赖 p6792 模板，**不可外推到异构 prompt**（§3）。

## §3 ② alt prompt 的 −2.8%：窗口开了，但 draft 不命中（与机制一致）

### 3.1 R37 同 exe 同 config 对（`sp_donly.exe 1bafa78d…`，仅 lookup 0/3）

- 窗口**确实开了**：D3 有「1 of 4 guessed」⇒ `most>1` 且确有提案/接受；但 **63 轮里只有 4 次提案**（alt 只有 293 token，重复草稿找不到 ≥3-token 的重复）⇒ `tokens/round = 64/63 = 1.016`，几乎等于 1。
- 每轮成本：61.8 ms（推）vs 无窗 59.2 ms ⇒ r=1.03；倍速预测 `1.016/1.03=0.988`（−1.2%）；实测 `16.17/16.63=0.972`（**−2.8%**）⇒ 方向一致。
- **per-token 没降的原因（CPU 实测变化）**：`miss/token` **496.7→519.3（+4.5%）**、`cpu_us/miss` **96.1→94.2 µs（−2.0%）** ⇒ CPU 腿 **47.7→48.9 ms/token（+2.5%）**；其余部分 12.4→12.9 ms。⇒ **−2.8% 主因是 CPU 腿 +2.5%**（验证多走了一点专家路），不是"窗口没开"。
- 结论：alt 上"窗口开 + draft 不命中"的读数与机制预期一致：**提案太少 ⇒ tokens/round≈1 ⇒ 只剩开销**。

### 3.2 R30 同 exe 对（`sp_mtp1.exe 547cab54…`，draft 开/关，threads 24）

- tokens/round = 64/(64−33) = **2.065**（33/39 = 84.6% 接受），decode 11.45 vs 11.20 = **+2.2%**。
- CPU 腿：D2 703.3 miss/token × 112.3 µs = **79.0 ms/token**；D3 496.7 × 150.6 = **74.8 ms/token** ⇒ **+5.6%**（miss/token +41.5%，被 cpu_us/miss −25.4% 部分抵消）。
- 非 CPU 部分：D2 `8.3 ms/token` vs D3 `14.5 ms/token`（**−43%**）⇒ 窗口/流水线确实把非 CPU 部分摊薄了；但 CPU 腿 +4.2 ms 把省的 6.2 ms 吃掉大半 ⇒ 净 **+2.2%**。
- ⚠️ **不是纯窗口对照**：两臂驻留不同（fill **5509 / 16268.77 MB** vs **5721 / 16894.83 MB**，draft 吃 ~212 槽），miss/token 的上升有一部分可能来自驻留下降而非窗口本身。**必须在报告里两列同报**。
- 与交接件数字的出入：交接件 §53 写"D2 每轮 203 ms×2.07 token"，本席从同日志 summary 复算为 **177.5 ms/轮**（5502 ms ÷ 31 轮）；差 **12.6%** ⇒ 口径需统一（可能来自未落盘的 DONE 行/另一个 D2 版本），该读数目前**不能作为结论**。

## §5 我建议补的 3 条（给判决实验）

1. **同批 CTRL 首尾配对 + 预热剔除**：每块前/后各 1 跑 CTRL（同 prompt 同 config），**首尾差 >5% ⇒ 该块作废**；每臂先跑 1 跑丢弃（或只统计第 2 轮之后），并按配对差的中位判 15% 门——单跑绝对 tok/s 不作采纳依据（G2/G7）。
2. **三列同报 + 异构 prompt 口径**：`tokens/round（标"推算"）+ accepted/offered + per-round ms（拆成 CPU 腿=miss/token×cpu_us/miss 与非 CPU 部分）`；必须在 **qa/code/zh 至少 2 条 + alt** 上复现，p6792 只作历史对照——p6792 上的 +57%/+77% 一律不认（G1/G3）。
3. **质量 + 自证捆绑**：采纳门 = ① 新 exe sha 绑定 ② 启动自证 `most/window`（或每轮 window tokens/accepted）③ ids 逐位（≥2 prompt）④ 全位置 max\|Δp\| + near-flip 清单 ⑤ copy-ledger 两列 fill + R21 峰值 ⑥ ids/文本一致；任一项红 ⇒ 不得采纳（G4/G5/G6/G8）。

## §6 "我读到的" vs "我推断的"

- **读到的（A 级）**：summary 的 `generated N tokens X tok/s`、`N of N guessed tokens right`、`load`、`copy ledger`、`decode: miss/token/cpu_us/miss/cpu_busy_us/miss`、`*.peak.txt` 采样、run script flags、日志头 exe sha、源码行号与公式。
- **推断的（B/D 级，已在表中标"推"）**：`rounds = generated − accepted`；`tokens/round`；`ms/round`；`r`；倍速预测；"lookup 跳过计算被否"的推理（依据：轮成本 5.04≫1）。**盘上没有 DONE 行**，任何把 tokens/round 写成"盘上读数"的说法都缺字段。
