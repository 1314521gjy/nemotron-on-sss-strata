## §1 三个"命中率"的确切定义

数据源：`E:\models\Nemotron-3.5-Super-VL-120B-A12B-Q4_K_M\p_run.txt`（20,275 行 `层 专家 计数`；Σc=**53,957,200**；非零 20,275 / 总 20,480 ⇒ **205 个零路由专家**；md5 `8daab2075333937889dec3a7e99f22fd`；p_master.txt 同 md5，冻结）。帧字节 **3,096,576 B/专家**（20,480×3,096,576 = 59.06 GiB）。

| | A | B | C |
|---|---|---|---|
| 名称 | profile 计数份额（scout-a 的口径） | 日志 `experts from VRAM X%` | 去重命中（交接件 §5.1） |
| 分子 | Σ_{e∈R} c_e（常驻槽的 profile 计数和） | `gpu_experts`（本次运行 decode 期命中的专家-事件数） | Σ_{(l,e)∈D∩R} b（去重命中专家字节） |
| 分母 | Σ_e c_e（全部 profile 计数） | `gpu_experts + cpu_experts`（decode 期全部专家-事件） | Σ_{(l,e)∈D} b（去重路由集字节） |
| 单位 | 路由事件（×3,096,576 B 即字节） | 专家-事件（token×层×专家） | **去重专家**（×3,096,576 B） |
| 作用域 | **冻结 profile 的全历史**（不是某次跑） | **本次运行的 decode 段**（45 token） | **本次运行 prompt 的去重路由集 D** |
| 数据源 | `p_run.txt` + 常驻集 R | 日志 summary 场（`main.cpp:715-724`；计数 `engine.cpp:2122-2123`） | D（需引擎去重计数/dump，**日志未打印**）+ `loaded … R of 20480` |
| 本机实测值 | **68.2985%**（5,890 槽） | 5,890 槽：**52.0–53.4%**；7,388 槽：**77.7%** | **38.5%**（7,388/19,198，7,388 槽/700 token） |
| 复算等级 | **A**（逐行复算一致） | 字段 A；**换算不可独立复算**（缺绝对计数器） | 模型 **D** 复现 38.42%；单 call 可由 DMA 反推（R25，A 级） |

**为什么 A≠B**：A 的总体是"历史 profile 的全部 53,957,200 个路由事件"，B 的总体是"本次 45 个 decode token 的 39,600 个专家-事件"，且 B 的分母只含 decode（prompt 批路径不累加这两个计数器：`engine.cpp:3138/3164` 要求"该层全部路由专家都在 VRAM"的 card 路径；本靶 prompt 批是 staged，不计数）。
**为什么 C≠A**：A 按频率加权（热门专家被算很多次），C 每个 (层,专家) 只算一次 ⇒ 同容量下 C 只有 A 的 ~45%（5,890 槽：30.6% vs 68.3%）。

## §2 复算（原始数据 → 数值）

### 2.1 A 口径（可 A 级复现）

本席从 `p_run.txt` 独立排序取 top-5,890：Σcount = **36,851,956**；`36,851,956 / 53,957,200 = 0.682985` ⇒ **68.2985%** ✓；字节 36,851,956×3,096,576 = **114.115 TB** / 53,957,200×3,096,576 = **167.083 TB** ✓（与 scout-a 报数逐位一致）。
其余容量：7,388 → 75.7376%（126.544 TB）；5,551 → 66.4160%；5,213 → 64.4565%。
（复算命令：读 p_run.txt → 按计数降序 → 前缀和 / 总和。）

### 2.2 B 口径（字段 A 级；换算缺字段）

- 实测分布（按驻留槽）：5,890 槽 → **52.0–53.4%**（69 个日志，含本轮全部 A3/CP/R6/R7/R8/R9）；7,388 槽 → 53.8–97.1%（25 个日志，含历史异类）；8,010–8,185 → 76.2–77.7%。
- **77.7% 的出处已定位**：`C:\sp3\pf_off_{1,2,3}.log`、`pf_on_*.log`、`warmcache_on.log`（驻留 **7,388**）与 `C:\sp3\dlc_pb32.log`/`dlc_pb8.log`（驻留 8,185，77.7%）⇒ **77.7% 是 7,388–8,185 槽时代的 decode 每 token 命中**，与 5,890 时代的 52.4% 是同一口径的不同容量，**不能与 38.5% 混算**。
- 缺哪个字段：日志只打印最终百分比，**不打印 `gpu_experts`/`cpu_experts` 绝对值**，也不打印逐 eval 路由 ⇒ 无法从其他字段重算，只能当引擎自报字段（A 级"字段"、B 级"可复核性"）。

### 2.3 C 口径（模型 D 复现；单 call 由 DMA 反推 A 级）

- 模型（与 `机制对拍-触达率与命中率-20261017.md` §8 同式）：`p_{l,e} = 22·c_{l,e}/Σ_{e'}c_{l,e'}`（层内归一），`E_touch = Σ [1−(1−p)^{T}]`。
  - T=700：E_touch = **19,230.3**（实测 19,198，−0.17%）；top-7,388 去重命中 = **38.42%**（实测 38.5%，−0.08 pt）⇒ **C 可复现（D 级模型）** ✓。
  - T=6,792（本靶）：E_touch = **20,045.4**。
- **单 call 的 A 级反推（R25）**：DMA 28,792 ⇒ streamed 份数 = 14,396；C = 1 − 14,396/E_touch ⇒ **28.18%**（E=20,045.4）/ **29.71%**（D=全 20,480）；模型 T=6,792、R=5,890 给 **29.38%** ⇒ 三者 28.2–29.7%，一致 ⇒ 单 call 时 C ≡ DMA 计数器（无需 dump D）。
- 真正的 A 级直算仍缺字段：**D（本次 prompt 的去重路由集）没有打印**。⇒ 多 call/异常情况下必须由引擎补去重计数或 dump，否则只能"模型 D + DMA 反推"。

## §4 唯一准用口径（已写入判据表 R23 / R25）

1. **一切"命中率 / 字节账 / DMA 效率"门 ⇒ 只用 C（去重字节）**；单 call 下用其计数器形式（R25）：`streamed 份数 = DMA/2`，`字节 = 份数×3,096,576`，`命中 = 1 − streamed/D`（D 由引擎去重计数/dump 或模型 D 级补）。
2. **A 只允许当"profile 覆盖份额"诊断**（例如判 profile 放置/排序），**不得当本次运行命中率**，不得进字节账。
3. **B 只允许解读 decode 的单 token 搬运占比/延迟**，**不得进字节账、不得算 DMA 体积、不得当"命中率↑"门**。
4. **R25（甲）唯一准许做"涨驻留 ⇒ prefill 收益"投影**：`DMA = (20,480 − 205 − R)×2`；体积 = DMA/2×3,096,576 B。**乙禁用**。

## §5 R25 复核：单 call"每专家只搬一次"（66 个日志全量）

- 公式：`copies_pred = 20,480 − 205 − R`；`residual = (DMA/2 − copies_pred)/copies_pred`。
- 结果（节选 + 全量统计）：R=5,890 → 14,396 vs 14,385 = **+0.08%**；5,721 → 14,566 vs 14,554 = +0.08%；5,551 → +0.03%；5,213 → −0.02%；5,377 → +0.11%；5,653 → +0.12%；5,889 → +0.17%。**66 个单 call 日志最大 |residual| = 0.17%**，恒为正（≤0.17% 与 decode 换入副本一致）⇒ **无额外重复，甲（每个 routed 专家单 call 搬一次）成立（A 级）**。
- 反例检查：**多 call 日志不满足**该式（4-call 时 91,076 DMA ≈ 2.22× 唯一专家）⇒ 甲**只适用于单 call**；多 call 必须直接用实测计数（R25 已写）。
- ★ **lead 投影的算术更正**：驻留 6,900 ⇒ 份数 = 20,480−205−6,900 = **13,375** ⇒ DMA **26,750** / 体积 **41.42 GB = −7.1%**（不是 27,160 / 42.05 GB / −5.7%）。**prefill 增益目前未定**：R8 边际（DMA +2.3% ⇒ prefill −2.15%；+4.6% ⇒ −4.1%）≈0.9 prefill%/DMA% ⇒ 按 −7.1% 推 **+6~7%**，与 lead 的 +3~4% 不一致且 R8 单跑含漂移风险 ⇒ 只许写体积 −7.1%，prefill 增益写"未定"。

## §6 reserve 探针（R8 两跑）自洽性复核（只核算术，不跑 GPU）

### 6.1 斜率：✓（A 级，本席从原始日志重算）

| 臂 | reserve MiB | 驻留（日志 `loaded`） | DMA（日志 `pin chunks`） |
|---|---|---|---|
| R6-OFF 基线 | 2,500 | 5,890 | 28,792 |
| R8-RS3500 | 3,500 | **5,551（−339）** | **29,456（+664）** |
| R8-RS4500 | 4,500 | **5,213（−338）** | **30,118（+1,326）** |

- 每 +1,000 MiB reserve 少 **339 / 338** 槽 vs 理论 `1,000×2^20/3,096,576 = 338.62` ✓（差 ≤1 槽）。
- DMA 交叉核对（按"仅被路由专家会被搬"折算）：期望 +2×339×(20,275/20,480)=+671 / +2×677×0.990=+1,340；实测 +664 / +1,326 ⇒ **−1.0% / −1.0%** ✓ 自洽。
- **缺字段**：R8 的**峰值 29,059 / 28,098 MiB 在盘上找不到原始采样件**（`C:\sp3` 无 R8 vram CSV/summary；只有日志）⇒ 这两条峰值读数**无法独立复核**（B 级，需补落采样 CSV）。
- **读数标签错位（必须改标注）**：R8 回执把基线写成"R6-OFF 峰值 30,063–30,691"——这组数实际来自 **R5**（R5-OFF3=30,063、R5-CTRL1=30,691，且 R5 block 因 CTRL 漂移已作废）；R6-OFF 的真实峰值是 **30,119–30,185**（`R6-arms-summary-20261017.json`；含 CTRL 为 30,092–30,308，与 IB3 一致）。**结论不变**（reserve 2000→3500→4500 峰值下降、驻留斜率对），但标注必须更正。

### 6.2「ring ON 需 reserve ≥3000 才过 R21」——**算术方向对，但不是最小值**

- 要求：峰值 ≤ 32,760−1,024 = **31,736 MiB**。
- ring ON 实测（R6 同 block 配对）：ON−OFF 峰值差 = 31,720−30,119=1,601；31,691−30,185=1,506；31,702−30,159=1,543；31,814−30,162=1,652 ⇒ **+1,506..+1,652 MiB**（与 ring 第二缓冲 1,512 MiB + graph/工作区一致）。
- 现状（reserve 2,500）：ONtop 31,814 ⇒ 余量 946 <1,024 ⇒ **RED**；其余三跑余量 1,040/1,069/1,058（高出阈 16–45 MiB，按 R21 临界带须复采）。R5 ON1 32,109（作废 block，旁证）⇒ 651 = RED。
- 需要的最小 Δreserve：按 R6 最坏 31,814 ⇒ **+78 MiB**（reserve ≥ 2,578）；若把 R5 的 32,109 计入 ⇒ **+373 MiB**（≥2,873）。**⇒ 3000 是"安全但非最小"的选择**：reserve 3,000 时预计峰值 = OFF(3,000) + ring ≈ (30,119..30,185 −500) + (1,506..1,652) = **31,125..31,337** ⇒ 余量 **1,423..1,635 MiB ≥1,024**（比 R8 回执写的 1.45–1.57 GB 同量级，✓ 算术自洽）。
- 结论：**R8 回执的 3000 推论可以用来做决定（安全），但"需要 ≥3000"的措辞过强；最小值按已观测峰 ≈ 2,580–2,880。** 若下一轮真跑 ring ON + reserve 3000，R21 应能过（预计余量 1.4–1.6 GB），但须实测确认（D 级推论 → 待跑）。

## §7 怎么变红（本件四类）

1. **R25 验证**：任一单 call 日志 residual >0.5% ⇒ 判"重复搬运被重新引入" ⇒ RED（本轮 max 0.17% ⇒ GREEN）。
2. **口径混算**：字节账/预填收益用 A 或 B ⇒ RED（见 §3 表：差 2.5×/4.7 GB）。
3. **A 口径复算**：若有人报的 A 值 ≠ 36,851,956/53,957,200（例如换了槽集合/换了 profile）⇒ 必须重列集合；本席复算一致才能用。
