## 4. 三个决策的隐藏风险（Lead 点名）

**① sidecar on 禁用 CPU-share（R63 #8）**
- 交付 `--cpu-share 0.55` 让 prompt 的 staged 专家一半走 CPU、一半走 staging；禁用后 **全部 staged 走 GPU staging**。按交付 `prefill staging 29,106 DMA / 41.97 GB`（cached 之外的 staged 部分里 GPU 占 45%）估算：**GPU staging 量 ≈ 41.97→~93 GB**（×2.2）。
- 量级：R54 P1（stage-mib 减半）已测 staging 敏感 ⇒ **prefill 预计 −10~20%**（不能排除更多）；再叠加 ②的冷页 fault，**批② 的 prefill 可能 −20~40%**。
- **补法（批③）**：`moe_rows` 的 CPU-share `host_` 构造处（R63 #8 那行 `L.exp_down + e*L.d_bytes`）改填 `downT`（sidecar 指针），CPU 腿即可保留——这与 decode CPU 路径（`CpuExpert.downT`）同构，属于 Stage C 已有能力的复用。
- **要求 builder3 先给**：批② 的 prefill 期望区间 + **中止门**（见 ②）。

**② map_pages 去 down 预热 + pin-only-up ⇒ prefill 首读 GGUF down = NVMe 冷页 fault**
- 批② 后：GGUF down **不 pin、不预热**（#13 删 span、#11 pin 只 up），而 `stage()` #5/#6 仍读它 ⇒ **prefill 的每个 staged expert 的 down 第一次读 = 磁盘 page fault**。
- 量级（派生）：alt 293 tok 的 staged 唯一专家若 ~2–5k 个 ⇒ down 3–8 GB ⇒ NVMe ~2–4 s（当前 alt prefill ~0.3 s，会变 10×；**可跑**但要设门）；p6792 类 6792 tok 会读 ~29.5 GB ⇒ **15–30 s 级 + 抖动**，就是 R57-E1 那种"fault 到死"的量级（E1 是 63.4 GB/1.59 tok/s）。
- **要求**：**B2 只跑 alt/qa，禁止 p6792 臂**；每个 prefill 加**中止门：prefill 墙钟 > 3× 基线（或 >30 s）⇒ 立即中止**，否则 ids 门可能根本跑不出来。若要跑 p6792 级，批② 得保留 down 的 map_pages 预热（与 D4 省 RAM 冲突）或先做批③。

**③ load 末尾 pin+touch sidecar 的判据不够硬**
- F1 实测：29.53 GiB sidecar fault-in 时 **avail 只降 16.9 GiB**（边 fault 边回收旧 page cache）⇒ 若沿用"avail 降 ≥20 GiB 才认"，会**误拒**。
- 改三硬门：**① 进程 WS 增量 ≥27 GiB**（R57c 已打印 WS +）；**② 随机读探针**：sidecar 内随机 1000×4 KiB 读，平均延迟 <200 µs（证明真驻留，不是反复 fault）；**③ 时长**：fault-in ≤40 s（否则中止）。另：load 从 14 s→~40 s，预算要含。

**附（MTP，已由 R63 #18 覆盖）**：sidecar 只含 40 主层（`relu2_down_open` 只统计 `il<n_layer_`），开 draft 后第 41 个 MoE 层会被 `fill/stage` 读 GGUF down ⇒ **必须启动即拒 `--draft` × `STRATA_RELU2_DOWN=1`**（成交付 `--no-draft` 不触发）。

- **P1（配置级存疑，会响不静默）**：`pin_expert_arena()` 的 RAM 地板仍在 `:1369-1378` 用**全额** `budget = STRATA_PIN_ARENA_GIB(59.1)+8 GiB`，而 load 顺序是先 `relu2_down_open()`（`:2359` pin 走 sidecar 29.53 GiB）后 `pin_expert_arena()`（`:2552`）⇒ `ram_before ≈ 84−29.5 ≈ 54 GiB < 67.1` ⇒ **up 半会被 REFUSED**（日志会有 `STRATA_PIN_ARENA_GIB=59.1 REFUSED: only ~54 GiB … needs 59.1 + 8`）⇒ D4 的"29.53+29.53 分半 pin"实际不成立、`stage()` 回退 host gather（prefill 变慢，**ids/正确性不变**）。1 行修法：r2d 模式下 floor 用 `29.55 GiB + 8`（即 `budget - 29.53`）。**若这批也要验 pin/RAM 结论 ⇒ 先修；只验 ids/miss ⇒ 可先跑**。
- **P2（低风险顺序项）**：fill(`:1650-1652`)/grow(`:2012-2014`) 的 `materialize_down(..., nullptr)` 落在 **默认流**且函数返回前无收尾 `cudaStreamSynchronize(0)`；st_ 是 NonBlocking 流，首次 prompt 理论上可能读到未 materialize 完的 down（实际窗口 <0.1 ms vs load 后续数十 ms，概率≈0；且失败会以 ids 漂暴露，不会假绿）。建议 fill/grow 末尾各加 1 行 sync（或改用 `r2d_scratch_for(cs(st_))` 并同步）——非阻塞项。

### §补-教训（2026-10-18，P1 的根因归档）
**引入"两段 pin"（GGUF up+down → up 一段 + sidecar 一段）时，所有依赖"总 pin 量"的地板/阈值/预算都必须同步改成"当前段"** —— 本批 `pin_expert_arena()` 的 RAM 地板仍按全额 `59.1+8 GiB`，而 load 顺序已是先 pin sidecar（29.53 GiB）再进它 ⇒ 实际只剩 ~54 GiB 可用却要求 67.1 GiB，**up 半被响亮 REFUSED**（D4 分半 pin 不成立、prefill 回退 host gather；ids 不受影响）。修法：floor 用 `budget − 已 pin 的另一段 + 8 GiB`（或直接以"本函数将要 pin 的字节 + 8"为地板），并让判据同时核对**两条 pin 自证行**都在场。
