## 0. 先答三问

### 问 2：「`38.5%` 是什么？default 档为空 `—`」→ **不是口径不同，是真差异；而"空"是我的报告缺陷**
- **基准档 `default` 的命中率 = 65.8%（不是空）**，见报告「档位 `default`」表的 `卡上专家%` 列：65.9 / 65.8 / 65.8。
- 你看到"空"，是因为**我的「横向对比表」只列了候选档、没列基准行** ⇒ 读者会以为基准的 decode/命中率缺失。
- **已修**：横向对比表现在**必出基准行**（`| **`default`（基准）** | 18.71 | 65.8% |`）。
- ⇒ **`38.5%` vs `65.8%` 是运行期真实差异**（≈1.7×），**不是口径不同**。

### 问 1：先分清「真效应」还是「档不稳」→ **方向是真效应**
| 档 | 3 跑 decode tok/s | 区间 |
|---|---|---|
| `default` | 18.56 / 18.82 / 18.71 | **≥18.56** |
| `batch1024` | 9.19 / 11.30 / 9.73 | **≤11.30** |
⇒ **两档区间完全不重叠**（11.30 < 18.56）。
⇒ **档内 ±16% 只影响"幅度"（9.1–11.3），不影响"方向"** —— **`batch1024` 确实慢，约 1.6–2.0×**。**复跑能收紧幅度，但方向基本不会再翻。**

### 问 3：为什么慢？→ **机制指向「缓存里放的是不是 decode 要用的那批」，不是"换入更多"**
| 量 | `default` | `batch1024` | 变化 |
|---|---|---|---|
| decode tok/s | 18.71 | 9.73 | **−48%** |
| 单 token decode | 53.4 ms | 102.8 ms | **+92%** |
| 命中率（专家在卡%） | **65.8%** | **38.5%** | **−27 点** |
| CPU ms/token | 32.6 | 40.6 | **+25%** |
| **换入次数** | **5644–5728** | **1806–2770** | **反而少得多** |
| 入卡数 | 7989 | 7775 | **仅 −2.7%** |
| prefill | 26.2 | 23.3 | −11% |

**两条关键读数**：
1. **builder 猜的"大 batch 触发更多换入 ⇒ 污染 decode"——方向不成立**：`default` 的换入(5644)反而**是** `batch1024`(1806)的**3 倍**。所以**不是"换入太多"**。
2. ★ **入卡数只差 2.7%（7989 vs 7775），运行期命中率却差 1.7×（65.8% vs 38.5%）** ⇒ **差异不在"装了多少"，而在"装的是不是 decode 要用的那批"**。
   ⇒ 这正好指向已被锁定的杠杆 **`--expert-profile`（在容量里选哪些专家）**。
   ⇒ **合理假设（待验）**：大 batch 让 prefill「一次性、大范围」地摸过大量尾部专家，把这些**用一次就再也不用的**专家塞进/留在缓存里，挤掉了 decode 反复要用的那批 ⇒ decode 命中率崩、CPU 顶上。

**⇒ 对 B3/扩列方向的直接含义**：**"解锁大 batch"本身未必是收益** —— 大 batch 有**隐性代价**（把缓存搅坏）。若坐实，则正解不是"无脑放大 batch"，而是**"放大 batch + 让缓存只装 decode 常客"**（即 `--expert-profile`），二者是**一套**。

## 1. ★★ 附带发现（比上面更要紧）：**跨运行确定性出现反例**
`default` 档 3 跑：
| run | 完成 | 换入 |
|---|---|---|
| 1 | **length**（跑满 64） | 5728 |
| 2 | **stop** | 5644 |
| 3 | **stop** | 5644 |
⇒ **同档同参、3 跑里 1 跑跑满、2 跑提前停** ⇒ **输出序列长度不同 ⇒ 输出不同** ⇒ **本线在该负载下【不是】跨运行确定**。
⇒ **这与"确定性 = 确定"的结论冲突**，**必须回 builder 复核**。
- 注意区分：builder 核的是**节点级** 176 行 dump 逐位相同；**节点级相同 ≠ 端到端 token 序列相同**（**停止点不同 ⇒ 序列不同**）。
- 可能来源（**未验，仅列可能**）：run1 是**冷启动/首次 IO**（换入 5728 vs 5644 也支持"run1 不同"）；或投机路径**有时序依赖**（`window()`/`took_way` 带 timing）。
⇒ **建议**：**同 `--max-new`、比 `生成的 id 序列` + `完成原因`**，跑 3–5 次；若长度仍漂，**确定性结论要收回**。

## 2. 我这一轮的两处自身缺陷（已修）
1. **编码**：脚本含 `⇒/≠/①` ⇒ Windows stdout 默认 GBK ⇒ **末尾 `print` 崩、报告没写、读数全丢**。
   **根因（比 bug 本身重要）**：**我此前测试时 shell 里带着 `PYTHONIOENCODING=utf-8`** —— **测试环境与交付环境不同 ⇒ 测试不算数**。
   已修：两脚本加 `sys.stdout/stderr.reconfigure(encoding="utf-8", errors="replace")`；**并已在【不设 env】下裸跑复验通过**。
2. **比较器**：把「提前 `stop` 导致两次跑长度不同」**误报成"档内多次不一致"** ⇒ `batch1024` 那行"3 种"里，**可能有一部分只是长度不同**。
   已修：改为**按共同前缀判** —— 互为前缀 ⇒ 报 `档内仅长度不同（共同前缀 N 个 token 逐位相同）`；并新增 **`长度不同`** 档间判定。
   另：**每跑的生成序列已落进报告**（新列，前 8 个），否则"不一致"事后无法诊断。

## 3. 建议下一步（按优先级）

## 5. ★ 一条"有信息的空缺"：**至今没有「共同前缀分歧」的真实样本**（队长要求入档）

**观察**：把所有现有真实日志过一遍「共同前缀」口径 ⇒ **没有任何一例"共同前缀真的分歧"**。
- `eng_mt_8`（`--max-new 8`）vs `eng_mt_16`（`--max-new 16`，**两次独立真实跑**）⇒ **共同前缀 8 个 token 逐位相同**；
- t18 的 `default` 3 跑 ⇒ 差异只出现在 **`length` vs `stop`（长度/停止点）** 这一层；
- t18 的 `batch1024` 3 跑 ⇒ **全 `stop`**，是否前缀相同**因旧报告无 per-run 序列而无法回算**（已作废，未定）。

**⇒ 它意味着什么（谨慎表述）**：
1. **"没观察到"≠"不存在"** —— 这**不能**推出"本线一定确定"。
2. **但它把怀疑范围缩小了一层**：目前所有"不确定"的迹象**都停在「计时/停止点」层，没有穿透到「数值/token 序列」层**。
   ⇒ 若确定性问题真存在，**目前证据指向"timing 依赖（停止点漂）"而非"数值路径不确定"** —— 这是**方向性线索**，不是结论。
3. **⇒ 需要什么才能升级为结论**：一个**真实的共同前缀分歧样本**。
   - 计划里的 **`NEG` 档（`--tail-skip 6`）** 就是为此设的：它**应当**造成前缀分歧 ⇒ **它是当前唯一的"真红源"**；
   - **若 NEG 报不出前缀分歧 ⇒ 判比较器失效、本轮结论作废**（判据自身没变红 = 没有负控 = 装饰品）。

**⇒ 结论**：**「无前缀分歧样本」这条空白本身是证据**（缩小了范围），但**不足以定案**；
**定案只有两条路**：① `NEG` 档证明判据能红 + 各档共同前缀逐位相同；② 或抓到一例真实分歧。
