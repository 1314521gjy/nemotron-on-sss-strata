## 0. 一句话结论

**不采纳（类 E 两项不过）**：① ids 不是逐位同（1/64 在 near-flip 处翻转，文本随之不同）；② 跨臂 `max|Δp| = 1.081e-1 > 0.05` 跳。

## 4. 关键机制 / 必须转告

1. **交付配置在这个异构 prompt 上不可复现**（与 R26 p6792 的 G0/G4 三跑逐位同相反）：冷缓存 ⇒ 63 轮 decode 里 2738/2680 次专家换入 ⇒ adaptive tier 的到达时序决定驻留集 ⇒ 同配置重复跑概率差到 0.06/0.97、ids 翻 1/19。**这本身是判据级发现：换 prompt（冷缓存）时，交付配置的 decode 不是逐位可复现的。**
2. 因此 **交付配置层的 class-E 比对无效**：A0 vs A0b（同为 frac 0）也翻同一个 idx63，说明"跨臂翻"与"同臂翻"在同一量级。**要把"路径变化"单独隔离，必须关掉 adaptive tier**（`--expert-swaps 0`）；那样两臂各自确定，跨臂差异才是可归因的——结果就是上面 §3：**路径变化在 near-tie 处确定性改输出**。
3. 所以按判据原文：**不采纳，停**。若 lead 仍想要 v1，需要放宽的就不止 `max|Δp|`，而是"near-tie 可翻 token"这一条（3.15% margin 处翻转，属可预期但真实的输出变化）；**反之，若要求"实际输出不变"，v1 在本 prompt 上不成立**。
4. 附带：这条 prompt 上 v1 的 decode 收益很小（12.57→12.96 = +3.1%）且在同配置噪声内（交付配置重复跑 12.57/12.28；12.96/12.35），因为冷缓存下 CPU 专家 11.5–13.4 ms/token、router wait 6.7 ms/token 主导，**decode 主要不是 CPU-miss 瓶颈** ⇒ v1 的 +11% 只在 p6792 那种"缓存已贴合、CPU phase 主导"的场景成立。
