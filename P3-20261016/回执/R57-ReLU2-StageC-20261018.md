## 4. 根因（已三重隔离）

1. **计算不是瓶颈**：内核纯 bench 155.9 µs/use ⇒ 16 线程 **5.03 ms/token**（预算内）；即使 ×2 也到 10 ms，远小于观测 112 ms/token。
2. **I/O/page-fault 是差额**：T 内核每 use 只读 242.4 KB（活神经元 512 B + 活组 scale 2048 B），但 sidecar **29.53 GiB 未 pin**（R53 §0.3 按 RAM 口径禁止 pin）⇒ 在 59.06 GiB pinned arena + 模型页缓存下，sidecar 页被挤出；每 token 重读 ~125 MB（496.7 miss × 242 KB）于同一块 E: NVMe，等效 ~1.1–1.2 GB/s（随机 4K 级）⇒ ~110 ms/token。首跑 67.7 s 是纯冷启动（8 GB 全从盘读），C2/C3 部分暖机后 6.3–7.7 s。
3. **RAM 贴门槛**：性能档 avail RAM 最低 8.785 GB；C0 17.8 GB。`bytes/token` 反而比原路径少（125 MB vs 799 MB），但**未驻留**是硬伤。

## 5. 结论与选项（**交 lead 决策**）

- **位精确 T 内核已证明可行**（parity 0 差 + GPU ids 逐位同 + 字节读数 15.66%）——**正确性不是障碍**。
- **障碍是内存/不可驻留**：sidecar 是第二份 29.53 GiB 副本，在现有 `STRATA_PIN_ARENA_GIB=59.1` 的交付形态下无处常驻。选项：
  | # | 方案 | 代价/风险 | 预期 |
  |---|---|---|---|
  | A | **pin sidecar**（cudaHostRegisterReadOnly 29.53 GiB） | 59.06+29.53+8 > 96 GiB ⇒ **不可行** | — |
  | B | **换 pin 预算：pin up 半（29.53）+ pin sidecar（29.53）= 59.06 不变** | prefill staging 的 down 段失去直接 DMA（host gather，参考 R54 P1 −11% 级）；需改 `pin_expert_arena`/`stage()` | decode down → RAM 速率，**预计 +30~40%**，prefill −5~15% |
  | C | **降 pin arena 到 ~40 GiB + pin sidecar** | 部分层预填走 host gather；页面压力再平衡 | 折中，待测 |
  | D | sidecar 移到 **C: 盘**（另一块 NVMe，现 E: 两者同盘） | 只是减盘争用，若页仍被挤出仍会 fault | 小幅，不确定 |
  | E | 放弃 Stage C（回到只做 Stage A/B 的 sidecar 备用） | 0 改动 | 无收益 |

- **建议先做 B 的 1 跑量级验证**（改 pin 分配 + 跑 1 臂，≈30 s+1 编译）再定是否交付；若 lead 同意，下一步我出 B 的补丁（`pin_expert_arena` 只 pin up；sidecar pin；`stage()` 混合路径）。

## 7. 追加：方案 B（pin 预算重分配）量级验证 — **失败，按判据停手**

lead 批准 B 后实现并验证（一次编译 + D0/D1/D2 三跑；exe sha `2008ADCB962748E7A5DEAEC4C647A348573F499EFD680D7D950BBD99B7F4C46E`）：
- `pin_expert_arena`：`STRATA_RELU2_DOWN=1` 时只 pin **up 半**（29.53 GiB）
- `relu2_down_open`：sidecar `cudaHostRegisterReadOnly` pin（29.53 GiB）+ RAM 断言（sidecar + 8 GiB，否则 REFUSED）
- `stage()`：混合路径（up 直接 DMA；down 从**未 pin 的 GGUF** gather 到 pinned staging 再 DMA）
- 自证行：`relu2-down: sidecar PINNED (29.53 GiB), up pinned (29.53 GiB), avail 76.1 GiB, ...`

| 臂 | decode tok/s | down ms/64tok | wall ms/round | **prefill tok/s** | avail RAM 最低 | 峰值 |
|---|---|---|---|---|---|---|
| D0（默认，pin 59.06 全量） | 16.35 | **1,568.1** | 61.2 | **127.3** | 18,151 MB | 31,036 |
| D1（B：up+sidecar 各 29.53 pin） | 10.77 | **2,234.0**（+42.5%，34.9 ms/token） | 92.8 | **12.7（−90.0%）** | **240 MB** | 31,282 |
| D2（重复） | 6.17 | 6,629.5 | 161.9 | 14.0 | 679 MB | 31,207 |

- **ids：D1/D2 与 D0 逐位同（64/64）**；`sidecar PINNED`、`up pinned 29.53`、ON-LOAD 4/4 全按预期打印。
- **判据失败**：D1 down = **34.9 ms/token > 20 ms** ⇒ 按 lead 判据**停手**。
- **根因（两条，都是 RAM 硬约束）**：
  1. **prefill −90%**：B 把 GGUF down 从 pin 区拿走 ⇒ prefill staging 的 down 段要从**未驻留的 GGUF** gather（每次 prefill 全量 31.7 GB 从盘流），实测 12.7–14.0 tok/s（原 127.3）。
  2. **decode down 仍慢**（+42.5%）：avail RAM 最低 **240 MB** ⇒ 系统级内存耗尽（59.06 pinned + dense/缓冲后只剩极少页缓存），整个进程被换页拖慢；pin 了 sidecar 也救不回来。
- **结论：96 GB 里放不下"up 29.5 + GGUF down 29.5（prefill 要全量高速）+ sidecar 29.5（decode 要常驻）"三份。方案 B 与方案 A 一样是 RAM 死路。**

### 建议（交 lead/用户）

- **最省事的收口**：Stage C **不进交付**；保留本回执的位精确成果（parity 全绿 + ids 逐位同 + 内核源 `relu2_down_t.hpp`），作为"正确性已验证、受内存约束未启用"的登记项。
- **唯一自洽的下一步（大改造，需单独立项）**：让 **GPU 侧也吃 T 布局**（改小批 `native_mmvq_ids` 的 down、prompt-batch 的 MMQ down、slot/staging 布局），然后 **GGUF 里的 row-major down 就不再需要**（可从 70.1 GB 裁到 38.4 GB；或直接重打成 T 内嵌版）⇒ pin 预算 = up 29.53 + sidecar 29.53 = 59.06 GiB 闭合，prefill staging 的 down 也来自 sidecar 直接 DMA（同布局、无反变换），decode CPU 同源。代价 = 2 套 GPU down 内核 + 槽/staging + 全套 v3 门；收益 = 预计 +35~40% 且 RAM 闭合。
- 不建议再做"pin 预算微调"类实验（已证两个极端都失败）。
