## ★★ §0 先纠正一条**关键推理前提**：「全 CPU 正常」**不能证明**"bug 在 GPU 分支"

```
// engine.cpp:1622
L.mmq = opt_.gpu_experts && rows_ >= kStageRows && Mmq::fits(...) && ...;
// engine.cpp:1877
bool Engine::batched(const Layer& L, int n) const { return mmq_ && L.mmq && n >= kStageRows; }
```
⇒ **`--no-gpu-experts` ⇒ `L.mmq = false` ⇒ `batched()` = false ⇒ `moe_rows()` 根本不会被调用**（`eval` 走 `moe()`，`engine.cpp:2708-2709`）。
⇒ ★ **所以"全 CPU 正常"只证明【`moe_rows` 是罪魁】，并不证明"bug 在 GPU 分支而不在它的通用部分"**。
★ 真正的"通用 vs GPU 分支"判别臂应当是 **`--expert-cache` 极小 / `--vram-reserve-mib` 很大（`n_cached = 0` 但 `L.mmq` 仍为真）** —— 见 §4 的臂 2。

## §1 你点名的四处，逐条读数

| # | 查什么 | 读数 | 判 |
|---|---|---|---|
| **1** | **`stage()` `:2242` 在 n≥32 与 n<32 的入参/假设差别** | **没有 n 相关差别**：`stage(L, L.ahead.data(), n_ahead, up_)`（`:2242`）与 `stage(L, group_.data()+g0, m, st_, …)`（`:2428`）**入参是"专家数 `m`"，不是 token 数 `n`**。`stage()` 内部：`per = chunk_bytes_/(gu2+d)`（`:2161`）、`down_at = pad(m*gu2)`（`:2159`）、**末尾 `cudaMemsetAsync(stage_ + down_at + m*d_bytes, 0, kTail)`**（`:2185`） | ✅ **n<32 时 `moe_rows` 根本不跑** ⇒ 无"两种 n 下的 stage"可比 |
| **2** | **`per_round` 会不会为 0** | `per_round = (int)(stage_bytes_/(gu2 + L.d_bytes))`（`:2342`）；而 **`stage_bytes_ ≥ one_expert = slot_down()+d_bytes = gu2+d`**（分配 `:1668`：`max(min(sm<<20, …), one_expert)`）⇒ **`per_round ≥ 1`** ✅ | **不会 0 除、不会"不搬运"** |
| **3a** | **`d_`（32 行）在 `card()` 里怎么用** | ★ **`d_` 在 `moe_rows`/`card()` 里【一次都没出现】**（我把 `:2194-2500` 全扫了 `d_\b`，命中均为 `d_xxx` 变量名）⇒ **`card()` 的输出是 `gu_/hx_/dx_`**，`d_` 只服务 `moe()` 的 `add_scaled` | ✅ **`((i0+j)%kSumRows)` 是 `moe()` 的事，与 NaN 无关** |
| **3b** | **`tab_` 拷贝 `:2361` 在 `n≥32` 时与 alloc 是否一致** | alloc（`:1650`）用 **`rr = rows_*n_used_` = cap**；拷贝（`:2362`）用 **`cap = rows_*n_used_`** ⇒ **逐字一致**。★ **`rows_ = min(prompt_batch, max_context)`**（`:1591`），**`read()` 的每次调用 `n ≤ read_rows_`**（`:1593`：`read_rows_ = max(rows_, most/rows_*rows_)`）⇒ **`n ≤ read_rows_`，而 `cap` 用的是 `rows_`** ⇒ ★ **若某次 `n > rows_`，`rr > cap` ⇒ 溢出** ⇒ **但 `read_rows_` 可能是 `rows_` 的整数倍 ⇒ 我【未核】`read()` 是否会把 `n` 发成 `> rows_`**（见 §4 臂 3） | ⚠️ **未核（潜在）** |

## §2 另外两处我顺手排掉的
- **`route_tmp_`**（并行路由的 per-thread scratch）**尺寸正确**：`assign(threads * 2 * n_expert_)`（`:1529`），每线程用 `+ p*2*n_expert_`（`:2268`）；`route()` 用 `probs[0..n_expert)` + `pick = probs+n_expert_`（`nemotronhmoe.cpp:365-366`）⇒ **2×n_expert 恰够** ✅。
  （★ 顺带：`parts = min(threads, ceil(n/32))` ⇒ **n<32 时 parts=1**、n≥32 时 parts≥2 —— **本来是一个"和 32 同界"的可疑点，但它的 scratch 尺寸是对的**，排除。）
- **`rel` / `cb` / `d_cb` 的偏移**：`rel` 分配 `2*n_expert+2 = 1026`，实际最大 ≈545；`d_cb = (int32_t*)(d_w + cap)`，`cb_row = n_expert+1`（`:2254`）与 alloc 的 `kClasses*(n_expert+1)` 一致 ✅。

## §3 剩余首疑（**未定案**）

| # | 嫌疑 | 为什么它只在 `n_cached>0` 且 **n≥32** 时发作 | 判别 |
|---|---|---|---|
| **★ H1** | **`staged_` / `holds` 的跨调用记账**（`:2411-2419`、`:2472-2474`）：`kept` 从 `staged_` 与 `group_` 的**子区间相等**推断；`holds` 记录"调用结束时缓冲里是哪一轮" ⇒ **若 `kept` 误判**，下一调用会**跳过 `stage()`** 而直接用缓冲里**残留的别层/别轮数据** ⇒ **读到脏数据 ⇒ NaN** | `mine = ahead && staged_il_ == il && (staged_ == L.ahead || 2*route_ms_ < ahead_ms_)`（`:2236`）**只在多轮（`round_.size()>2`）且 `ahead` 时**有意义 ⇒ **n≥32 + `sa>0`**；`sa=0` 时 `mine=false` ⇒ 不发作（**与 `sm48` 的 canonical `sa=128` 吻合**） | **pb=32 + `--stage-ahead 0`**：若 NaN 消失 ⇒ **H1 坐实** |
| **H2** | **`n > rows_` 导致 `rr > cap`**（§1-3b） | `read()` 的 `read_rows_` 可能把 `n` 抬到 `rows_` 之上（`:1593` 的 `max(rows_, most/rows_*rows_)`）⇒ **`ids_/w/mq_/mq2_/dx_/gu_/hx_` 全部按 `rr=rows_*22` 分配** ⇒ 若 `n` 更大 ⇒ **全部越界** | **核 `read()` 实际发出的 `m`**（`PP` 行数/日志），或 **pb=1024 时看 `read_rows_` 是否 > rows_**；也可**用 `--dump` 对比** |

★ **我倾向 H1**：它同时解释"**n≥32（多轮）** + **有 GPU 专家（`n_cached>0`）** + **`sa>0`**"三个条件，且**全 CPU 时 `moe_rows` 不跑 ⇒ 当然正常**。

## §4 给 builder 的判别臂（零改码，按成本）
1. **pb=32 + `--stage-ahead 0`** ⇒ 判 **H1**（**最便宜、最可能**）。
2. **pb=32 + 把 `n_cached` 压到 0 但保留 `L.mmq`**（`--vram-reserve-mib` 极大 / `--expert-cache` 极小）⇒ 若正常 ⇒ **bug 只在"有 cached 专家"时**（进一步锁 GPU 分支）。
3. **看 `read_rows_`**：pb=1024 跑一次，**读日志/加一次只读打印**（`rows_`/`read_rows_`/每次 `eval` 的 `n`）⇒ 判 **H2**（需一次改码，得你批）。
4. **pb=32 + `--cpu-share 0`** ⇒ 排除 CPU 份额分支（`n_cpu>0` 时 `card()` 会先 memset `dx_`，`:2376`）。
