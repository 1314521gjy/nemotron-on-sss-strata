## §0 ★ 先立一条设计约束（它决定甲/乙的天花板）

**状态布局与快照是【同一套偏移】写死的**：
- **state**：`float* sp = s + (size_t) ii * d_state;`（`kernels.cu:2558`），`ii = h*head_dim + i1` ⇒ **布局 = `[h][i1][st]`**，本靶 = **128×64×128 floats = 1,048,576 floats = 4 MiB/层** ⇒ ×40 层 = **160 MiB** ⇒ ★ **与 `显存三方账-20261016.md` 的 "SSM state S(f32) 160.00 MiB" 逐字吻合** ✅（互证）。
- **快照**：`mamba2_scan(…, snap = snap_at_ + (B.ssm_state - state_), stride = rec_n_, snaps = snap_bits_)`（`nemotronhmoe.cpp:287-289`）⇒ 内核里 `snap_of(snap, stride, snaps, t)` = `snap + popc(...) * rec_n_`（`kernels.cu:1750-1752`）⇒ ★★ **`snap` 是"整段 `state_` 的若干份完整副本"**，**用 `(B.ssm_state - state_)` 这个【同一内部偏移】对齐** ⇒ **`mamba2_scan` 只写自己那层那一段，但坐标系是全模型 state**。
**⇒ ⇒ 设计约束（写死）**：**凡改动 `sp` 的 `(ii, st)` 映射，必须同时改快照的写法**；否则 `snap_ok_`/`keep()` 回滚会把状态恢复到**错位置** ⇒ **静默错误**（`nemotronhmoe.cpp:290` 的 `snap_ok_ = true` 还会让它看起来"快照成功"）。

## §1 两种切法对比

### (甲) **d_state 维切线程**
| 项 | 内容 |
|---|---|
| **怎么做** | launch 从 `<<<n_head, head_dim>>>`（`kernels.cu:2688`）改成 `<<<n_head, head_dim * S>>>`（S=4 ⇒ **256 线程**；S=8 ⇒ 512）：`i1 = threadIdx.x % head_dim`（值维，**不变**）· `seg = threadIdx.x / head_dim`（state 段）· 每线程负责 `st ∈ [seg*d_state/S, (seg+1)*d_state/S)` ⇒ **本靶 128/4 = 32 个 st/线程** |
| **★ 要不要跨子段归约** | ★ **要** —— `y` 要的是 **`sumf = Σ_{st<d_state} state*C[st]`**（`:2576`），切成 S 段后 S 个部分和**必须再相加** ⇒ **每 token 一次跨段归约**（S≤32/64 ⇒ 用 **warp shuffle** 或 shared + 一次 `__syncthreads`）⇒ **barrier 从 2/token 变成 3/token**（**代价明确**）；★ 也可把现有两次 barrier 合并成两次（读写 sB/sC 一次、归约与快照合并）⇒ **净增 ≈0–1 次** |
| **数值影响** | ★ **只改【结合顺序】**：同 128 个加数，从"1 条 128 长链"变"S 条 32 长链 + S 项合并" ⇒ 相对误差量级 **≈ 128×6e-8 ≈ 8e-6**（与 verifier 的判据同阶）⇒ **不是换算法**（**低风险**） |
| **并行度** | **8,192 → 32,768（S=4，占用 5.3%→21%）/ 65,536（S=8，→42%）** |
| **快照对齐** | ★★ **天然对齐**：`st` 仍是**全局 st 索引**、`sp[st]` 的写法不变 ⇒ **`snap_of` 完全不用改** ✅ |
| **改动面** | ★ **小—中**：**纯 kernel 内**（`i1/seg` 推导 + 段内和入 shared + 一次合并）+ **launch 的 block 维改 1 个数**（`:2688`）；**不动 state 布局、不动快照、不动调用方** |

### (乙) **chunked scan**（块内并行 + 块间前缀合并）
| 项 | 内容 |
|---|---|
| **怎么做** | 经典三阶段：**①** 每 chunk 独立算"局部 scan + 块末状态"；**②** 对 `N/C` 个块末状态做一次**小的前缀 scan**；**③** 每 chunk 用"进状态"修正局部结果。**切多少 token 一块**：`C ∈ {32, 64}`（**C 越大并行度越低、块间合并越小**） |
| **块间合并怎么做** | **① 第二 kernel**（最简单，但多一次 launch + 一次全量中间结果落盘）**或 ② 单 kernel 内两 pass**（要用 cooperative groups / grid sync，或把 ② 串行放在 1 个 block 里 —— `N/C` 最多几十项，**串行代价小**）⇒ ★ **我倾向 ②**（把 ② 做成 1 个 block 串行，因为块末状态只有 `head_dim×d_state×(N/C)` = 64×128×22 ≈ 180 K floats，**很小**） |
| **多出来的 global 往返** | 每 chunk 要存"局部 y"与"块末状态" ⇒ **≈ rows×dim×2×4B + (N/C)×head_dim×d_state×4B** ⇒ 本靶 ≈ **45.9 MB + 0.7 MB / 层** ⇒ ×40 ≈ **1.9 GB**（★ 相比 state 串行往返的 ~235 GB **很小**） |
| **数值影响** | ★★ **真的换算法**：**两级累加**（块内 32–64 项 + 块间 N/C 项），**且"块末状态 → 进状态 → 再乘"多一条乘法链** ⇒ **误差同阶（仍是改序 + 多一级）但风险更高** ⇒ **必须过 `--top-probs` 逐位判据**（verifier 的 Q 判据正是为此） |
| **并行度** | ★ **能真正打开**：`<<<n_head × (rows/C), head_dim>>>` ⇒ rows=700/C=32 ⇒ **128×22 = 2,816 blocks** ⇒ **远超容量**（不再受 8,192 线程限制） |
| **★★ Q4 快照（致命点）** | ★★ **`snap_of` 要的是"某个特定 token 之后的状态"**（`row < 32` 的位图，`kernels.cu:1750-1752`）⇒ **块中间的那个 token 的"之后状态"在 chunked 方案里【不能直接拿到】**（要先有"进状态"+块内重放到该 token）⇒ **必须额外处理**：**(a)** 在 chunk 内按 `snaps` 位**重放一小段**（≤C 步，代价小）**或 (b)** 改变快照点的语义（**= 错，会让 keep() 回滚到错状态**）⇒ ★ **这是乙最容易漏、也最贵的一处** |
| **改动面** | ★ **大**：新 kernel/两 pass + **快照路径重写** + 多一份中间缓冲（显存 +~46 MB/层 的峰值，若按层流水则更小）+ 与 `snap_at_`/`rec_n_` 的坐标对齐要重推 |

## §2 算术影响量化（预期）

| 切法 | 误差性质 | 预期相对误差 | 判据建议 |
|---|---|---|---|
| **(甲)** | ★ **只改结合顺序**（同 128 项，分组变） | **≈ 1e-5 量级**（`128×6e-8 ≈ 8e-6` 上界；实际往往更小） | **`--top-probs` 逐位**（末位可能漂）；**ids 应完全相同** |

## §3 会不会碰 §7 那四处？

**⇒ 不会（两条都是纯 kernel 内 / launch 维度）。**
- 那四处是 **`stage_` 与 `up_`/`st_` 的配对**（`engine.cpp:2189/2191` 的流注释 · `:2374` 的 `card()` · `:2390` 的分组）⇒ 与 `kernels.cu` 的 mamba 段**无交集**。

## §4 ★★ Q4 专项：state 的持久化语义 + 快照（**最易漏**）

| 问 | 答（`file:line`） |
|---|---|
| `sp` 是跨 kernel 调用的状态吗 | ★ **是** —— `s` = `B.ssm_state`（`nemotronhmoe.cpp:287` 传参），指向 `state_` 里属于该层的那一段（`alloc_caches` `:205-210` 按层累加切分）⇒ **每层的 state 常驻，跨 token/跨调用递推** |
| 切维/分块后**状态在 global 里的布局要不要改** | ★ **(甲) 不用改**（`st` 仍是全局索引，`sp[st]` 写法不变）；★ **(乙) 要改**（要么引入"局部结果"缓冲、要么把"进状态"也放进 state 区） |
| 改了会不会影响 `snap_of()` | ★★ **会** —— `snap` 用 `snap_at_ + (B.ssm_state - state_)` 与 `stride = rec_n_` **对齐到同一个坐标系**（`nemotronhmoe.cpp:286/289` + `kernels.cu:1750-1752`）⇒ **只要 `sp` 的映射变了，快照的写点也必须在同一新映射下**；否则 **`keep()` 回滚到错位置（静默）**，而 `:290` 的 `snap_ok_ = true` 仍会宣称成功 |
| 快照点在 chunk 中间怎么办 | ★ **(乙) 必须专门处理**：(a) **块内按 `snaps` 位重放 ≤C 步**（推荐，代价小）或 (b) 把快照点后移 —— **❌ 错**（语义变了） |
| 额外风险 | ★ **`snap_places_ = min(window−1, kSnapPlaces=3)`**（`engine.cpp:1603`）⇒ **最多 3 个快照点**，且**只在前 32 个 token**（`snap_of` 的 `row < 32`）⇒ ★ **⇒ 快照点全部落在【第一个 chunk 内】**（C≥32 时）⇒ **乙的"块内重放"只需处理【第 1 块】** ⇒ **代价可估且很小** ✅（这条是个好消息，值得写进方案） |

## §5 ⇒ 一句话推荐

> **先做 (甲)（d_state 维切线程，S=4 或 8）** —— **改动小（纯 kernel 内 + 1 个 launch 维度）、数值只是"改结合顺序"（≈1e-5，低风险）、快照天然对齐（`sp[st]` 映射不变）、并行度 5.3%→21%–42%**。
> **(乙) 留作第二刀**：它**能真正打开并行度**，但**换了算法 + 要重写快照路径 + 中间缓冲**，且★**它的"块内快照"只需处理第 1 块**（因快照点全在前 32 token）⇒ **第二刀比看起来便宜，但仍是"大改动"** ⇒ **在 (甲) 之后若 ncu 仍显示该 kernel 独占关键路径，再做 (乙)**。
