# R32 · draft 链长：为什么 alt prompt 每轮只提 1.26 个 — 2026-10-18

- **席位**：builder2 · **线 B 后续** · **零 GPU**（本轮未跑：没有旗标能改链长/期望门，验证必须改码，见 §5）
- **状态**：**问题已定性**。三个串联原因：① `kBlockWindow=4` 硬上限 ⇒ **每轮最多 3 个 draft**；② 真问的轮里 `Guesses.takes()` 的期望规则在 p≲0.8 时拒第一个 draft；③ 更主要的是 `Gate` 判定"问 block 不划算"后按 8 轮/次节流 ⇒ 多数轮**根本不问**。
- **要害更正（与 scout-b 分解的衔接）**：decode 的 CPU 腿**并不随 window 内 token 数摊薄** —— R30 实测 D2（2.065 token/轮）与 D3（1 token/轮）的**每 token CPU 腿 79.0 vs 74.8 ms（+5.6%）**，每 token 总时 86.0 vs 87.9 ms（就是 +2.2% 的来源）。⇒ **"8 个 token 共享同一次专家读取"在本引擎不成立**：不同 token 的路由几乎不重叠（22/512，期望重叠 <1 个专家），CPU 腿 ∝ (token,expert) 使用数，**是线性工作量，不是可摊薄的固定开销**。所以把链拉到 4–8 个也不会翻倍。

## 1. 逐条回答（附 file:line）

### Q1：一轮最多能提几个？什么条件让只提 1 个？
- **上限 = `min(most, kBlockWindow) − 1`**：`main.cpp:478` `for (from = t; n_d < std::min(most, kBlockWindow) - 1 && guesses.wants(n_d); from = d[n_d++])`。
  - `most = min(engine.max_window(), DraftPolicy::kMaxT=8)`（`main.cpp:329`，`draft_policy.hpp:24`）；本模型 `opt_.window=8`（snaps_spread → 8）⇒ `most=8`。
  - **`kBlockWindow = 4`（`main.cpp:66`，constexpr）** ⇒ `min(8,4)−1 = **3 个 draft/轮**`（block 猜测链的**独立硬上限**，与 `--window` 无关）；`std::min(most,kBlockWindow)` 也用于 `widest`（`main.cpp:464`）。
- **实际 1.26**（R30-D2：39 joined drafts / 31 rounds）是**两个闸门串联**（都不是"验证被拒"）：
  1. **`Gate::ask()`**（`guesses.hpp:48-68`）：前 16 轮必问，之后按"问 block 的 tokens/ms" vs "不问的"比较；**输的一方只每 8 轮问一次**（落后超 10% 时每 96/24 轮才轮到一次）。R30-D2 的 block 轮 2.065 token/177.5 ms，**每 token 86.0 ms vs 不问的 87.9 ms**——Gate 只看每轮 tokens/ms ⇒ 它判断"问不划算"并节流。**这是 1.26 的主因**。
  2. **`Guesses::takes()`**（`guesses.hpp:100-110`）：第一个 draft 要加入窗口需 `p × round_ms(1) > tokens_ × more_ × one_`，其中 `tokens_=1`、`more_` 实测被 clamp 到上限 **0.8**（`wants()` 里 `clamp((ms_[to]-round_ms(to-1))/one_, 0.2, 0.8)`）⇒ **p ≲ 0.8 就直接拒第一个 draft**；`wants()`（`:88-96`）同样用期望值挡。
- **旁证（R30-D1 dump，前 8 轮）**：offered = 1,1,3,3,3,2,3,3 = 19/8 = **2.4/轮**（前 8 轮 Gate 未节流，链能到 3）；其后 23 轮只剩 20 个（0.87/轮）⇒ **前段到上限、后段被 Gate 节流**，与上面的机制一致。

### Q2：`--window` 的真实语义
- `engine.hpp:68` `window` = "**一轮里同时过模型的 token 数上限**（已知 token + 猜测）"；`most = min(max_window, kMaxT=8)` 是**每轮窗口最多 token 数**，**不是"最多提几个"**。draft 数 = 窗口 token 数 − 1。
- **`kBlockWindow=4` 是 block 猜测的额外硬上限**（lookup 链可到 `most−1=7`，block 链只能到 3）。所以 **`--window 8` 对 MTP 链长没生效**——被 `kBlockWindow` 压住。这是当前设计的意图（lookup 比 MTP 便宜/准），但对"靠 MTP 摊薄 CPU 腿"的路来说是硬墙。

### Q3：alt prompt 与 p6792 的差别（**不是 bug**）
- p6792 的 **8 token/轮来自 `--lookup 3` 的"抄 prompt"**（重复模板，R28 里 112/112 全中），**不是 MTP**；alt prompt 无重复 ⇒ lookup 只 1/4 中（R28-B/D：tokens/round 1.016）。
- 我们在 alt 上用 `--lookup 0` 时，offered/accepted 全部来自 MTP（R30：84.6–94.9%），链长 1.26 是**策略的期望值闸门**在起作用，不是实现 bug。
- ⇒ **"每轮提更多"本身不是目标**：见下面的经济学。

### Q4：可执行改法（1–2 个）+ 预计
1. **`main.cpp:66` `kBlockWindow = 4 → 8`**（一行常量）：上限 3→7 个 draft。
2. **`guesses.hpp` 放宽期望门**：`Guesses::wants()` 里 `more_` 的 clamp 上限 `0.8 → 0.5`，并把 `takes()` 的首 draft 门相应放宽（或让 `Gate` 对"每 token 更快"而非"每轮更快"计费；当前 `gate.saw(asked, wrote, ms)` 用 `tokens[asked]*ms[other]` 比的是每毫秒 token 数）。
   - **预计 tokens/round**：2.07 → **3–5**（取决于 MTP 链上 p 的衰减；R30 dump 显示前 8 轮已有 2.4–3，若 Gate 不节流+上限 8，估 3–5）。
   - **预计 decode**：**不升，可能 −2~5%**。依据：D2（2.065 token/轮）每 token 86.0 ms vs D3 87.9 ms 只 +2.2%；而每 token CPU 腿 79.0 vs 74.8 ms（**+5.6%**，因为被拒的窗口 token 也算 CPU 工作）。再拉长链只会放大"被拒 token 的沉没成本"（p 衰减 ⇒ 兑现率下降）。
   - **验证跑法**（若 lead 批）：改完一次编译 → alt prompt、`--max-new 64 --expert-swaps 0 --lookup 0`、开 draft，3 跑：量 tokens/round（guessed/rounds）、兑现率、decode；判据 decode 相对 no-draft ≥5% 才留。
3. **真正能降 decode 的杠杆（与 scout-b 的 A 级分解一致）**：decode ≈ `miss/token × cpu_us/miss`（74.8 ms = 496.7 × 150.6 µs）。要降它只能**降 miss/token**（提高驻留/命中、降 top-k、pcie 分流减 CPU miss）或**降 cpu_us/miss**（CPU 点积更快/更多线程）；**加 token/轮不改变这条乘法**。

## 2. 关键实测支撑（全部来自已有日志，零新跑）

| 量 | D3（no-draft） | D2（draft） | 比值 |
|---|---|---|---|
| decode | 11.20 tok/s | 11.45 tok/s | **+2.2%** |
| 每轮 | 87.9 ms / 1 token | 177.5 ms / 2.065 token | — |
| **每 token** | **87.9 ms** | **86.0 ms** | −2.2% |
| CPU 腿每 token（miss/token × cpu_us/miss） | 496.7 × 150.6 µs = **74.8 ms** | 703.3 × 112.3 µs = **79.0 ms** | **+5.6%** |
| tokens/round | 1.000 | 2.065 | ×2.065 |

⇒ 窗口内 token 的 CPU 腿**没有摊薄**：token 数翻倍、CPU 腿每 token 反升 5.6%（被拒窗口 token + block MoE 的沉没工作），只是把"每轮固定开销"摊了一点点 ⇒ 净 +2.2%。**scout-b 的"8 token 共享一次专家读取"不成立**（22/512 路由重叠期望 <1 个专家）。

## 3. 结论（一句话）

**每轮最多提 3（`kBlockWindow=4` 压住 `most=8`）；实际 1.26 = `Gate` 节流（主因）+ `Guesses.takes` 的 p≲0.8 期望门；这不是 bug。即使把上限/门放宽到 3–5 token/轮，decode 预计也不升——本引擎的 CPU 腿是按 (token,expert) 线性计费的，不是可摊薄的固定开销。真杠杆是降 miss/token（或 cpu_us/miss）。**
