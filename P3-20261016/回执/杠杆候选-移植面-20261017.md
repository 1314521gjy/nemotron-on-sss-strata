## ★★ 先答"你担心的混淆"（**本件的重点**）：**是两个不同的量，不是同一量的相反结论**

| 量 | 上游（`strata`/program 线） | 我们（`poly` 线） | 两边方向 |
|---|---|---|---|
| **chunk**（一次读多少 token） | ★ **`--prefill auto`** = 「**the largest chunk whose buffers fit in the expert-cache slots it borrows**」（`docs/DETAILS.md:332-336`）⇒ **按容量反推上界，然后在装得下的前提下【往大选】**；实测 **chunk 4096 比 1024 快 1.8×**（`pp4096 427.5 vs 240.8`，设计件 `:3039`）；社区 `auto32k` 在 28.9K 上 **+14~25%** | **对应物 = `--prompt-batch`**（我们的实测：`8 → 1024` 巨幅；**`1024 → 2048` 到平台**：126.0 vs 120.6） | ★ **两边都"大→快"（同向）** ⇒ **不是相反结论** |
| **预取环形缓冲** | ★ **`ring_slots()`**：**按 pack 与 pinned 比例导出**（`prefill.cpp:214-230`；`STAGE = 8` 固定槽 `:122`）⇒ **没有用户旋钮** | **`--stage-mib`**（我们实测：**越小越快**，`2048→48` = **+192%**） | **上游没有这个量** ⇒ **无可比** |

**⇒ 判决**：
1. **"它选大的、我们实测选小的"= 选了【两个不同的量】**（它选 **chunk**、我们选 **stage**）⇒ **不矛盾**，**也说明 (a) 不是"把我们的 stage 调大"**。
2. ★★ **⇒ (a) 对我们不是"往大选"，而是"按可用缓冲反推一个【安全上界】"** ⇒ **价值 = 鲁棒性（不手填、不 OOM），不是提速**。
3. ★★ **社区那条 +14~25% 的来源是 chunk `8192 → 32768`**（`auto32k`）⇒ **我们 `--prompt-batch` 被校验卡在 `≤4096`**（`engine.cpp:1399`）⇒ **要吃到那条得先放开上限**；**而 `1024→2048` 已无收益** ⇒ **预期很小**（4096→32768 是否非线性 ⇒ **未验**）。

## (a) `--prefill auto` 式 chunk 扫描

| 项 | 内容 |
|---|---|
| **① 落在哪** | **上游**：候选扫描在 `src/program/generate.cpp:6681-6744`（`Prefill::set_ring_budget` `:6729/:6740/:6744` · `ring_cap_for` `:6709` · `bytes_needed*` `:6720`）+ **`--prefill auto` 的解析与上界** `:2043-2049`（`auto:32768` 会取到 **32768**）。**我们**：对应物是 **`opt_.prompt_batch`**（`engine.hpp:50`；校验 `engine.cpp:1399` **≤4096**；`rows_ = min(prompt_batch, max_context)` `:1591`） |
| **② 量级** | ★ **小**（**不动流**）：在启动时**按"scratch/stage/arena 预算"扫几个候选档**，把选中的值写进 `opt_.prompt_batch` ⇒ **约 20–40 行，纯决策，不碰任何 event/流** |
| **③ 碰 §7 四处吗** | ★ **不碰** —— §7 的四处（`engine.cpp:2189/2191` 的 `up_` 注释、`:2374` 的 `card()` 里 `st_` 上的 memset/quantize、`:2390` 的 `runs_` 分组）都是**运行期 `stage_` 与 `st_` 的配对**；chunk 选择只改**一个整数值**，不改变它们的语义 |
| **④ 收益依据** | ★ **上游有实测**：`chunk 4096 vs 1024 = 1.8×`（设计件 `:3039`）· `auto32k` 28.9K **+25%**（本席 iq3s 表）。**但我们这边【没有】**：**1024→2048 = 无收益（126.0 vs 120.6）** ⇒ **⇒ 我们的 chunk 已到平台** |

## (b) 借专家缓存槽当 prompt buffer（借了还）

| 项 | 内容 |
|---|---|
| **① 上游机制** | ★ **默认就是"借"**：`generate.cpp:549-550` 的 help 原文「the prompt (**default**); **`--no-prefill-borrow` reserves the buffers' VRAM for the whole session instead**」（解析 `:2069`）· **借的接口** = `Prefill::relayout(chunk, borrow, borrow_bytes, err)`（`prefill.cpp:1343`）· **借谁的** = **专家缓存的槽 1..N（slot 0 留）**，**溢出的自己分配**（`docs/PREFILL_HEAD_ALIAS.md:34-37`）· **何时还** = **读完之后**（该文档 step 3「**Refill the lent slots and free the prompt path's own buffers**」）；储备件 §2.1-D 亦记「一个请求只借**它自己提示**需要的那点」· **谁保证不冲突** = **① 借出去的槽在提示期内不放专家**；**② 共用 scratch 的安全性靠"计数用与 `init` 完全相同的 `take` 序列"，对不上就 `init` 报 `do not fit`，绝不静默重叠**（储备件 §2.1-D）；**A/B 臂** = `--no-prefill-borrow`（`:2069`）· 与 `--prefill auto` 绑定（`:2523`） |
| **① 我们对照** | ★ `stage_` **从 arena 扣**：`engine.cpp:1668-1670`（`stage_bytes_ = max(min(sm<<20, n_expert×one_expert), one_expert)` → **`dmalloc`**）；canonical `sm=1024` ⇒ **扣 1024 MiB**；且 `alloc()` **早于** `fill_expert_cache()`（`:1487-1489`）⇒ **扣得早、扣得死** |
| **② 量级** | ⚠️ **中—大**：要"借"就得让 `stage_` **能在 prompt 期间拿走、之后还给专家** ⇒ 要么走 **VMM 映射**（我们已有 `vmm_`/`arena_`/`shrink_cache`/`grow_cache`），要么**把它挪进 arena 的同一段地址空间** ⇒ **必须改 `stage_` 的生命周期** |
| **③ 碰 §7 四处吗** | ★★ **必碰** —— `stage_` 的"何时空闲"正是 `ev_free_` 的语义（`up_` 等 `ev_free_` 才能复写 buffer，`:2440-2443`；`st_` 等 `ev_ahead_`，`:2426`）。**借/还会改变"buffer 何时归还"** ⇒ **四处配对逐条要重核**（`:2189/2191` 的流语义 · `:2374` 的 `card()` · `:2390` 的分组 · 以及 `:2426/:2442` 的 wait/record） |
| **④ 收益依据（★ 先按你的算术给上界）** | ★ **我们已实测：prefill 对 arena 的灵敏度 = ≈0.5%/GiB**（`sm归因-判决-20261017.md:18-19`：只动 reserve +1000 MiB ⇒ arena 21.3→20.3 GiB ⇒ prefill **378.0→376.2 = −0.5%**）。⇒ **上界算术**：<br>· **只借 `stage_`（canonical 1024 MiB）** ⇒ 净多 **1 GiB** ⇒ **+0.5%**；<br>· **连 prompt 路径的 scratch 一起借**（我们 `batch-arena` 件：**~1.7 MiB/token × 1024 ≈ 1.7 GiB**）⇒ 净多 **~2.7 GiB** ⇒ **+1.35%**。<br>★ **⇒ (b) 的收益上界 ≈ +0.5% ～ +1.4%（且是上界）** —— **它不是"提速"，而是"省显存"**（换来的 arena 若用在命中上，也同量级：`batch-arena` 件 **+1 GiB ≈ +338 对 ≈ +0.5 点**） |
| **⑤ 风险** | ★ **中—高**：① **改 `stage_` 生命周期 = 直接动 §7 的跨流配对**（最容易引入"偶发慢/偶发错"）；② **静默退化的可能**：若"借"失败（装不下）而不报错 ⇒ **会退化成"提示期没 buffer"**（上游的对策是 `init` 报 `do not fit`，**我们必须照抄"响亮失败"**）；③ 我们的 `--expert-swaps` 在**解码期**还在动缓存 ⇒ **"借出去的槽"在提示期必须被冻结**（多一条状态） |
| **★ 结论** | **收益上界 ≤1.4%（且是省显存不是提速）· 改动面中—大 · 必碰 §7** ⇒ **不建议进 D3 的高 ROI 档**；**只有当"arena 逼近不够/要长 ctx"时才有意义**（那时它是"腾空间"的手段，不是"提速"手段） |
