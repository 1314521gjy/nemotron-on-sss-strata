## §0 一句话

> ★ **源缓冲是 pinned（不是 pageable）** —— 代码 `cudaMallocHost`（`engine.cpp:418-433`）+ nsys `srcKind=1=PINNED`、`dstKind=2=DEVICE`（`ENUM_CUDA_MEM_KIND`：0=Pageable / 1=Pinned / 2=Device）双重确认。
> ★★ **同一份 trace 里有现成的正控**：**同样 15.48 MB、同样 pinned、同样的源/目的缓冲**，在 `up_`（早拷贝）上 **22.1 GB/s**，在 `st_`（轮内拷贝）上 **10.1 GB/s**；24.77 MB 的轮内拷贝 **8.8 GB/s**。
> ⇒ **pageable 与"每次拷贝间同步"两条都否掉了；问题在"轮内拷贝的执行形态"，不在内存类型。**

## §1 四问逐条

### 1. `stage()` 的源缓冲是 pinned 还是 pageable？—— **pinned**

| 证据 | 读数 | 分级 |
|---|---|---|
| 代码 | `h_stage_[b] = hmalloc(chunk_bytes_)`（`:1673`）；`hmalloc` 用 **`cudaMallocHost`**（`:418-433`） | **A** |
| nsys 字段 | 1511 次 H2D 全部 `srcKind=1`，`dstKind=2`；`ENUM_CUDA_MEM_KIND` = {0:Pageable, 1:**Pinned**, 2:Device} ⇒ **源 pinned、目的 device** | **A** |
| 对照：谁才是 pageable | 模型加载那批：**15,134 次 `srcKind=0`（pageable）**，1–2 MB，**7.85 GB/s** —— 这是另一条路，不是 `stage()` | **A** |

⇒ **builder 可以省掉"pinned vs pageable"的 benchmark**（结论已定：pinned）。

### 2. 1511 次拷贝之间有没有同步/事件等待？—— **拷贝之间没有；每个 `stage()` 调用入口有一次 CPU 事件等待**

- `stage()` 内：**两次 `cudaMemcpyAsync` 背靠背**（up 区 → down 区，`:2185-2188` 一带），**两者之间无同步**；调用入口 `ck(cudaEventSynchronize(left), …)` 等的是**同一缓冲两轮之前**的完成事件（`:2175`）。
- 量级（A）：整段 prefill 里 CPU 侧同步 **817 次 / 合计 154.3 ms / p50 0.014 ms**（`CUPTI_ACTIVITY_KIND_SYNCHRONIZATION`，`syncType=1`）⇒ 只占 5158 ms 的 **3.0%**，**不是排队饥饿的原因**。

### 3. 能不能多流并发？—— 结构上是**单流串行**，但已有一条现成的第二条流

| 事实 | 读数 |
|---|---|
| 轮内拷贝（stage 的 `:2450` 调用）用的流 | **`st_`（stream 13）**：1472 次 H2D |
| 早拷贝（`stage(..., up_)`，`:2260` 一带） | **`up_`（stream 14）**：**80 次**，每次 15.48 MB（`n_ahead=10` × 2） |
| 两条流都是 `cudaStreamCreateWithFlags(cudaStreamNonBlocking)`（`:1417`、`:1680`） | 同优先级、非默认流 |
| **任意两次 H2D 在时间上重叠的次数** | **0 / 17,473** ⇒ 拷贝引擎全程串行（连 `up_` 与 `st_` 之间也不并发） |

★ **正控（A，同一 rep、同尺寸、同缓冲）**：
| 流 | 尺寸 | n | p50 | 速率 |
|---|---|---|---|---|
| **`up_`（14）** | **15.48 MB** | 80 | **0.701 ms** | **22.1 GB/s** |
| `st_`（13） | **15.48 MB** | 10 | **1.540 ms** | **10.1 GB/s** |
| `st_`（13） | 24.77 MB | 1,358 | 2.831 ms | **8.8 GB/s** |
| `st_`（13） | 7.74 MB | 10 | 0.983 ms | 7.9 GB/s |
| `st_`（13） | 3.10 MB（另一条流 16） | 494 | 0.218 ms | 12.8 GB/s |

- **同一尺寸、同一源类型、同一目的缓冲，`up_` 比 `st_` 快 2.2×** ⇒ **不是链路、不是内存类型、不是尺寸**，而是**流/入队形态**。
- 与"是否与 kernel 重叠"无关：`up_` 的拷贝 **overlap=True 48 次 / False 32 次，两组都是 ~21 GB/s**（本人按 kernel 区间做的重叠判定）。
- 与"GPU 此刻是否空闲"也无关：`st_` 的 1469 次拷贝里 **只有 46 次**与任何 kernel 重叠。

## §2 ★ 两条**新的、可能会改变结论**的读数

### 2.1 这份 trace 是 **`--stage-mib 48`**，不是 1024

- 轮内 stage 调用数 = 679（= 1358 次 up 拷贝 / 2）⇒ **16.975 轮/层**；`per_round = stage_bytes_/(slot_down+d_bytes) = 48 MiB / 2.953 MiB ≈ 16` ⇒ **sm=48** ✓。
- 每轮 16 专家 ⇒ 16 × 2.95 MB ≈ 47 MB/轮，679 轮 × 2 次 ≈ 34.9 GB ✓ 与 H2D 总量吻合。
- ★ **⇒ 这个 74% 的画像属于 `sm=48`**。若正确路径 canonical 用 `sm=1024`：每层非缓存约 271 专家 × 2.95 MB ≈ 0.8 GB **一轮装得下** ⇒ **每层 1 轮、每轮 ~0.8 GB 的大拷贝**（40 次而非 679 次），形态完全不同。
  - 所以：**H2D 占比必须在"正确路径实际用的那个 sm"上重测**；在 sm=48 上得出的 74% 不能直接外推到 145.6 那一跑。
  - 另：每层 ~0.8 GB 的**单次**拷贝也超过 `chunk_bytes_/(gu2+d_bytes)` 的 173 专家分片上限 ⇒ 会拆成 2 片（`stage()` 的 `j0` 循环，`:2170`），仍是每片 0.4 GB 级别的大拷贝。

### 2.2 暂存量本身是"命中率的函数"，不是拷贝次数

- 34.87 GB / 700 token ≈ **49.8 MB/token**；每层约 271 个非缓存专家（7388/20480 驻留 ⇒ 每层约 327 个非缓存，其中 83% 被本 prompt 用到）。
- ⇒ **不换更大 cache，就降不下来**（每专家 2.95 MB 是权重本身）。所以杠杆只有两个：**速率**与**重叠**。

## §3 建议的一击 benchmark（builder，10 分钟；按"能否复现 22 GB/s"分组）

> 目的：把"链路/机器"与"引擎的入队形态"分开。

| 臂 | 内容 | 期望/判读 |
|---|---|---|
| **B1** | pinned，24.77 MB × 300 次，**一条流背靠背**，无 kernel | **≈22–25 GB/s ⇒ 机器没问题**；**≈9 ⇒ 机器/链路/驱动**,改法只有"少传/重叠" |
| **B2** | 同上，但**每次拷贝前插一个 0.04 ms 的 kernel**（复刻 `st_` 的"小 kernel→大拷贝"节奏） | 若掉到 ~9 ⇒ **kernel/拷贝交替是根因**（引擎可改成"先攒多轮再拷"或换流） |
| **B3** | 同上 + **双缓冲 + 每 2 次拷贝一次 `cudaEventSynchronize`**（复刻 `stage()`） | 若掉到 ~9 ⇒ **CPU 事件等待/队列浅**；若仍 22 ⇒ 不是它 |
| **B4** | 同上，但拷贝发在**第二条流**、与一段长 kernel 重叠（复刻 `up_`） | 应 ~22 ⇒ 证明"重叠"可行，是最终修法方向 |
| **B5**（可选） | 把 up+down **合成一次拷贝**：`j0==0 && m==c` 时目的区是连续的（`down_at = pad(m*gu2)`，本靶 m*gu2 是 256 的倍数 ⇒ 无间隙）⇒ 1 次 49.5 MB 替代 2 次 24.8 MB | 若 B1/B2 显示"每次拷贝有固定成本" ⇒ 立省一半次数 |

## §4 给修法的**方向排序**（等 benchmark 定）

1. **把轮内拷贝挪到第二条流并加事件**（`up_` 已被证明能跑 22 GB/s）：H2D 与 MMQ kernel 重叠 ⇒ 即使速率不变，也能把 3.8 s 藏掉一部分；若速率也回到 22 GB/s ⇒ 3.8 s → 1.6 s。
2. **合并 up+down 两次拷贝为一次**（条件见 B5）：若每拷贝有固定成本，直接省一半。
3. **增大 `--stage-mib` 让每轮更大**（少轮次、大拷贝）：但要注意 `plan_ahead` 的 cap 与显存；且在正确路径上要重新量。
4. **不指望"缩小传输量"**：每专家 2.95 MB 是权重本身；除非提高命中率（arena 不够）或专家压缩。

## §5 未验 / 边界

1. **【未验】** 22 vs 10 GB/s 的**机制**（队列深度、引擎唤醒、驱动分块）——B1–B4 可定；**本件只给出"不是链路/不是 pageable/不是同步"**。
2. **【未核】** 145.6 那一跑的 `--stage-mib` 实际值（我只有 nsys 跑的；从轮数反推是 48）。**若两者不同，74% 不可直接搬**。
3. **【未核】** 拷贝引擎与该流的绑定关系（为何同尺寸在两流上差 2.2×）——属驱动行为，代码层不可见。
4. 本件**只读、零 GPU、未改码、未碰 `E:\strata`**；nsys 的 sqlite 查询与 `nvidia-smi --query-gpu`（Gen4 x16、当前=最大）都是只读查询。
