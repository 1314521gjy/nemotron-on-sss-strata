## 6. 关键发现 / 必须转告

1. **16 槽会饱和，三档 frac 不可分辨**：每层每窗 distinct miss ≈82、每 token miss uses = 443、每 8-token 窗每层 n_host ≈88。`m_uses` 按 uses 算、再按 distinct 复制，**16 槽在 frac≈0.18 处就顶满**（0.2/0.3/0.4 全会拿满 16 槽）⇒ 三档变成同一档。**G1–G4 改用 `--pcie-slots 48`**（141.8 MiB），三档才拉开（实移 uses/token = 139 / 200 / 245）。**若采纳：`--pcie-slots` 必须 ≥40–48，默认 16 只够 frac≤0.18。**
2. **frac→实际搬迁份额不是 1:1**：按"取最后 m 个 use、复制其 distinct expert、该专家的全部 uses 都搬"的口径，名义 0.2/0.3/0.4 ⇒ **实移 uses 31%/45%/55%**。这解释了为什么 0.3 与 0.4 几乎同速（老师成本模型的平衡点在 0.43 附近，0.4 已过冲）：**G2(0.3) 24.54 略优于 G3(0.4) 24.44**。若要 frac 精确等于搬迁份额，Compile #3 可把 m 改成**按 distinct misses 计数**。
3. **代价（confound，未控）**：staging 141.8 MiB 从 arena 扣 ⇒ 驻留 **5721→5673（−48 专家，−0.84%）**，prefill staging DMAs 29132→29238。G0 vs G 臂的差异里含这 −0.84% 的驻留损失（按 Compile #1 口径 ≈1% 级别，远小于 +11%，但严格说未隔离）。**隔离实验（staging 分配但 frac=0）未做 ⇒ 未验。**
4. **max|Δp| 超门的原因**（供裁定）：分流把约 45% 的 miss uses 从"CPU ggml int8 点积"改为"GPU mmvq"，两条路径末位不同 + Mamba 循环状态放大，到 pos103 概率差 1.3e-2，但 **argmax 全程未翻 ⇒ ids/文本 128/128 不变**。同类现象在 R1 的 reserve 变化里是 2.84e-4，这次大 45×，但性质仍是"驻留/谁算"改变 ⇒ 建议 lead 明确：**分流 v1 的数值门是否改用"ids + 文本 + 全位置 max|Δp| 记录（不设 2e-3）"**。
5. **CPU phase 与 cpu_busy 拆行生效**（G4）：`cpu_us/miss` 墙 145.5–149.2 µs、`cpu_busy_us/miss` 106.8–108.8 µs ⇒ **每 miss 有 ~40 µs 是交接/等拷贝**；按 token 折算 CPU phase 36.8 ms，cpu_busy 26.7 ms。pcie 流量：200.12 uses/token，30,494 DMAs，47.21 GB（≈0.372 GB/token），与 23.2 GB/s 链路一致，可与 CPU 重叠。
