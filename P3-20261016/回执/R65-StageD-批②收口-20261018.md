## 2. 归因三条（file:line + 读数）

1. **T 内核逐 use 收益有限（down 只 −13.2%）**：字节数已确实减少（`relu2-down-summary: uses=31294, active_avg=219.94/2688, bytes_per_use=242.4 KB vs 1548.3 KB = 15.66%`），但 decode 里 **CPU 专家只占 ~10% 调用**（自证 `relu2-down: sidecar on, active=2/2688, uses=10`，首层），且 CPU 专家的 down 时间上界本来只有 R57 全专家 bench 的 5.03 ms/token 量级 ⇒ **down 相的主导项是 GPU/填槽侧，不是 CPU T 内核**。⇒ T 内核已不是带宽瓶颈（242 KB/use 的 gather 进入 compute/延迟区，`cpu_experts.cpp` 的 T 分支 + `relu2_down_t.hpp`）；**"预期 −80% 字节 ⇒ −70%+ 时间"的换算不成立**。
2. **prefill 2.2×（2.39 → 5.30 s）**：`stage()` 每个专家走 `Engine::materialize_down`（`engine.cpp:395`）= **cudaMemcpyAsync(T 块→scratch) + T→row kernel 两次 launch/专家**，两个 stage 分支各调用（`engine.cpp:3498` pinned / `:3526` 非 pin），p6792 量级 prefill 约 1.4 万专家 ⇒ 数万次 launch + 额外 T DMA；**修法明确：per-chunk 批量反变换（一次 launch 处理 c 个专家，c≈chunk 内专家数）**，今天不做。
3. **router_wait +46%（468.8 → 685.1 ms/run）**：最可疑的是 **fill/grow 的默认流物化 + 尾部 `cudaStreamSynchronize(nullptr)`**（`fill_expert_cache` 尾 `engine.cpp:1659` 附近、`grow_cache` 尾 `:2022` 之后）与 decode 图流争用；以及每个 miss 的 fill 现在多一次 kernel launch（`materialize_down` `:395-398`，per-stream scratch 池 `:404`）。**待查项**：把默认流 materialize 移到专用流/或用事件串行化再测 router_wait。
