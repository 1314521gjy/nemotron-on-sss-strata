- **状态**：**根因已定位（代码级）**：**draft 的输入融合与链式递归都是对的，但 Nemotron 的 MTP 块（blk.88）根本没被正确接线** —— 它被 `kind_of()` 误判成纯 MoE 层，**attention 子层从未加载/从未运行/从未有 KV 行**，且 **attn_post_norm 从未加载**（draft 的 FFN 前 norm 用的是空权重=无权重 RMS norm）。⇒ **acceptance 0–4% 是实现缺失（少移植），不是"MTP 弱"。**

## 0. 一句话

GGUF 里 `blk.88` = **attention 子层 + MoE 子层 + 4 个 nextn 张量**（llama.cpp 参考实现原文："NextN/MTP draft head: each predict layer folds an attention sub-layer and a MoE sub-layer into a single trailing block"，`E:\strata\third_party\llama.cpp\src\models\nemotron-h.cpp:142-181`）。我们的 Nemotron 架构（`nemotronhmoe.cpp`）**没有为这个块实现 attention**：`kind_of` 把"有 ffn_gate_inp"的块先判成 `kMoe`（`nemotronhmoe.cpp:48-54`），于是 attention 权重不加载、KV 缓存不分配、`block_attend()/block_rows()` 走基类空实现（`engine.hpp:394-396`，只有 glm5next/qwen35 覆写）。draft 每步都在"**无 attention + 无 post_attention_norm**"的块上算 ⇒ 输出近似随机。

## 1. 逐条回答 lead 的四个问题

### Q1：draft 的输入 hidden state 来自正确的层/正确的 norm 吗？→ **是（这一环没问题）**
- `hn_` 由 `output_rows()` 写入：`NemotronHMoe::output_rows()` = `rms_norm(r_ + first*n_embd, fp(out_norm_), h, ...)`（`nemotronhmoe.cpp:356-358`），即**最后一层残差过了模型 final norm 的 hidden**。
- 参考实现同口径：llama.cpp 在 trunk 末尾 `cur = build_norm(cur, model.output_norm, ...); cb(cur, "h_nextn", -1); res->t_h_nextn = cur;`（`nemotron-h.cpp:246-249`）——**我们的 hn_ 就是它的 h_nextn** ✓。
- 写入点：`engine.cpp:3412-3417`（eval：`float* h = draft_ ? hn_ + n_embd_ : xn_; output_rows(n-m, m, h)`）、`:3606`（read）、`:3711`（window）。

### Q2：`eh_proj / enorm / hnorm / shared_head_norm` 四个张量是否都真参与？→ **四个都参与，且加载正确**
- 加载：`engine.cpp:1668-1678`（`load_drafter()`）：`d_proj_ = nextn.eh_proj.weight [8192, 4096]`、`d_enorm_ = nextn.enorm.weight`、`d_hnorm_ = nextn.hnorm.weight`、`d_head_ = nextn.shared_head_norm.weight`。
- 融合：`engine.cpp:3805-3808` `rms_norm(cur_=embedding, d_enorm_)` → `r_`；`rms_norm(h=hn_, d_hnorm_)` → `r_+e`；`lin(d_proj_, r_, x)`（concat 后投影）✓。
- 输出头：`engine.cpp:3845-3848` `rms_norm(x, fp(d_head_), own)` 后 `lin(output_, own, logits_, 1)`，`head.n_out = draft_rows()`（共享输出矩阵）✓。
- 张量形状与 GGUF 实测一致（下面 §2 的读数）。

### Q3：链式第 2/3 个 draft 的输入是否用上一步 draft 的输出（递归）？→ **是，递归写对了**
- `main.cpp:471-479`：`for (int32_t from = t; n_d < std::min(most, kBlockWindow) - 1 && guesses.wants(n_d); from = d[n_d++]) { d[n_d] = engine.draft(from, n_d, &p); ... }` —— 第 2 次起 `from = d[n_d-1]`（上一个 draft token）✓。
- `engine.cpp:3830-3833`：`draft_step(token, i)` 中 `i == 0 ? hn_ : own`，`own = hn_ + n_embd_`（块上一步的输出）✓。
- 位置用法：每次 draft 在 `pos_ + i`（同一个尚未 feed 的窗口位置）——与 llama.cpp 的 MTP 多步 draft 用法一致（未在参考里找到内置 MTP 前向，见 §5 未验）。

### Q4：draft 是不是系统性错位/乱码？→ **不是错位，是块少了一半（无 attention、norm 错）**
- `draft_step()`（`engine.cpp:3830-3850`）的顺序是：`draft_input`（融合）→ `block_attend(pos+i, 1)` → `axpy(ao_, 1.f, x, ...)`（加 attention 残差）→ `rms_norm(x, fp(L.ffn_norm), ...)` → `moe_router/moe/moe_add/moe_latent`（MoE 子层）→ `axpy(fo_, 1.f, x, ...)` → `rms_norm(x, fp(d_head_))` → `lin(output_)`。
- **但 `block_attend()` 对 Nemotron 是空操作**（`engine.hpp:394-396`；覆写只有 `glm5next.cpp:562-563`、`qwen35.cpp:372-373`）⇒ attention 不算，`ao_` 里是**上一层注意力/混合器留下的旧数据**，被 `axpy` 当 attention 输出加进残差。
- **`block_rows()` 同样是空操作**（`engine.cpp:3817-3825` 调它）⇒ 块 attention 的 KV 行从不写入。
- **而且根本没有地方可写**：`NemotronHMoe::alloc_caches()` 只给 `B.kind == kAttn` 分配 `B.keys/B.vals`（`nemotronhmoe.cpp:196-213`），blk.88 被判 kMoe ⇒ **没有 KV 缓存**。
- **`L.ffn_norm` 在 Nemotron 架构里从未赋值**（全仓 grep：`L.ffn_norm = ...` 只出现在 deepseek4/gemma4/glm5next/lfm2moe/qwen35，`nemotronhmoe.cpp` 一条都没有）⇒ `Dev{}` 默认空指针 ⇒ `engine.cpp:3836` 传给 `rms_norm(x, fp(L.ffn_norm), ...)` 的是 **nullptr**；`kernels.cu:169` 是 `w ? xr[i]*scale*w[i] : xr[i]*scale` ⇒ **静默退化成一个无权重 RMS norm**。而 MTP 块真正该用的 `blk.88.post_attention_norm.weight`（GGUF 里存在，仅此块有）**全仓没有任何地方加载**（grep `post_attention`：只有 gemma4/qwen35 用，Nemotron 没有）。

## 2. GGUF 实测（零 GPU，用 `P3-20261016\gguf_u43.py` 读两个 shard；脚本 `C:\sp3\_kinds.py`）

- 两个分片合计 **781 个张量**；块 **0..88 共 89 个**（`block_count=89`），所以 `nextn_predict_layers=1` ⇒ 模型 88 层 + **MTP 块 = blk.88**。
- `blk.88` 的张量（**决定性**）：
  - nextn 输入融合：`nextn.eh_proj [8192, 4096]`、`nextn.enorm [4096]`、`nextn.hnorm [4096]`、`nextn.shared_head_norm [4096]` ✓ 四个都在
  - **attention 子层**：`attn_norm`、`attn_q [4096,4096]`、`attn_k [4096,256]`、`attn_v [4096,256]`、`attn_output [4096,4096]`、**`post_attention_norm [4096]`（89 个块里只有 blk.88 有）**
  - **MoE 子层**：`ffn_gate_inp [4096,512]`、`exp_probs_b [512]`、`ffn_latent_down/up`、`ffn_up/down_exps`、`ffn_up/down_shexp`
- 参考实现（vendored llama.cpp）对 MTP 块的字段定义逐条对上：`nemotron-h.cpp:159-180`（enorm/hnorm/eh_proj/shared_head_norm + attn_norm + qkv + wo + **attn_post_norm** + ffn_gate_inp + exp_probs_b + latent + exps + shexp）。
- **运行日志的硬证据**：开 draft 的 R28-C/D 显示 **`5518 of 20992 routed experts`**（20992 = **41** × 512），关 draft 的 R28-A/B 显示 **`5721 of 20480`**（20480 = **40** × 512）⇒ **blk.88 被当作第 41 个 MoE 层加载**（`nemotronhmoe.cpp:141-143` 的 `else ++n_moe_`），即 `kind_of(88)==kMoe` 在运行中确实发生了；它的 attention 分支（`nemotronhmoe.cpp:146-155`）从未执行。

## 4. 若要修（**本轮不动手，等 lead 裁定**；预计一次编译）

正确接线需要（对照 `nemotron-h.cpp:142-181` 的字段与我们的引擎结构）：
1. **种类**：MTP 块要能表示 "attention + MoE"（新增 `kAttnMoe`，或 `kind_of(il)` 在 `il == n_layer_` 时按 `attn_q` 判；`load_layer` 对块同时走 attention 分支 + MoE 分支）。**注意不能简单把 ffn_gate_inp 顺序调前/调后**：前 88 层里没有"attention+MoE 同层"的块，只有 blk.88 是两者都有。
2. **KV 缓存**：`NemotronHMoe::alloc_caches()` 为 blk.88 的 attention 分配 `B.keys/B.vals`（`kv_alloc(row, 1)`），并把它计入 `card_row_bytes()/save_rows()/load_rows()` 的单卡口径（当前单 GPU 只是行数，不影响数值；多卡要一致）。
3. **`block_attend()/block_rows()` 覆写**：`attn(blocks_[n_layer_], pos, n)` / `attn_store(blocks_[n_layer_], pos, n)`（照 qwen35.cpp:372-373 的写法）。
4. **`L.ffn_norm`**：MTP 块加载 `blk.88.post_attention_norm.weight` 到 `L.ffn_norm`（普通层没有此张量；引擎的 `draft_step` 已经用 `L.ffn_norm`，正好对上）。
5. **`check_draft_block()`**：覆写为"块必须有 attn_q + ffn_gate_inp + nextn 四件"，否则响亮失败（防静默半支持）。
6. 然后才做 lead 的第 2/3 步：`--draft-dump N`（打 target vs draft 逐位）+ 3 跑验收（判据 acceptance ≥30%）。
7. 修之前**保留 evidence**：R28-C/D 日志、本回执的 20992 vs 20480 对照。

**风险**：`moe()`/`moe_shared()` 的 `tok_` 用法、`card_moe` 的 slot 表、`moe_router` 的 `h_rl_` 拷贝都按"层"处理块层——`draft_step` 已按普通层调用，接线后要重验 ids/文本（draft 只影响 draft 路径；**关 draft 时数值必须逐位同**）。
**另一个待核**：参考树里 MTP 的**前向图**没有实现（vendored llama.cpp 只加载 MTP 张量、只暴露 `h_nextn` 给外部 hook，见 `llama-graph.cpp:1328-1373`、`llama-context.cpp:1499-1572`）；因此"对照 llama.cpp 的 acceptance"这条（lead 第 4 步）**这批二进制可能做不到**，需要用更新的上游/Unsloth 口径另找（见 §5）。

## 5. 未验 / 边界
