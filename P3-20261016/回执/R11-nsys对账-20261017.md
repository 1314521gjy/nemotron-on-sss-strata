# 回执 · R11：nsys 轨迹对账（1.54× 副本 / 流映射 / 气泡归因）— 2026-10-17

## 任务
lead 令：**零 GPU** 用现有 `C:\sp3\nsysR10.sqlite` 对账 R10 的两条矛盾读数（H2D 43,550 次/74.50 GB vs 引擎 29,132 次/45.10 GB；窗口 4.638 s vs copy 流空闲 1.929 s），回答窗口口径、14,418 次差额归属、2,174 整帧拷贝来源、流 id 映射、11 ms 气泡时刻、H2D 尺寸分布；给"prefill 窗口内 H2D 归因表 + 气泡归因表 + 74.5 GB 里真假构成"。

## 状态
**达成（零 GPU、零编译、零改码；纯 sqlite 复算 + 代码核对）。**

## 第一行结论
**"1.54× 副本"是伪影（假绿），不是隐藏重复拷贝。** 多出的 **14,418 次**= **load 期专家填充 11,402 次（17.65 GB）**+ **decode 段整帧 swap 2,174 次（6.73 GB）**+ **load 权重上传 764 次（4.89 GB）**+ **78 次舍入**；**prefill 窗口内真实副本 = 29,210 次 / 45.23 GB ≈ 引擎自印 29,132 / 45.10 GB（差 0.3%）**。同时 R10 的"nsys 开销 +21.3%"与"重叠只 61.4%"也一并修正（见下）。

## 证据（A：sqlite 全量；D：推断处已标）

### 1) 采集窗口口径（A）
- trace 首个 GPU 事件 → 末事件：**19.052 s**；分三段（全部为 GPU 事件时间轴，相对 trace 起点）：
  - **load 期**：0.103–11.739 s（含权重上传 4.89 GB、专家填充 17.65 GB；引擎自印 `loaded in 11.9 s`）；
  - **prefill 期**：**11.862–15.493 s = 3.631 s**（首 staging copy 11.862；首个 `mul_mat_q` kernel 11.817）；
  - **decode 期**：15.802–19.052 s（整帧 swap 2,174 次，无单列 kernel —— decode 走 CUDA graph）。
- ⇒ R10 的"4.638 s 窗口"= 首个 1–2 MB copy 到最后一个 copy，**把 load 填充期（10.87–11.74 s）也算进去了** ⇒ 窗口口径错，已修正为 **3.631 s**。

### 3) 2,174 次 × 3,096,576 B 是谁（A）
- 3,096,576 B = `L.slot_down() + L.d_bytes`（1,548,288+1,548,288）= **一整帧专家的上下投影一次拷**；
- 唯一发出点：**`engine.cpp:1342`** `cudaMemcpyAsync(s->slot, s->pinned, L.slot_down()+L.d_bytes, H2D, cs(swap_st_))` —— **swap（follow()）路径**，流 = `swap_st_`（`:1160-1161`）；
- 时间跨度 **15.802–19.052 s = decode 期**，不在 prefill；引擎自印 **2,041 个不同专家**，2,174 次拷贝（+133 次重复/回填，**未解释**，D）。

### 5) 真实重叠与气泡（A）
- **prefill 窗口 3.631 s**：`st_` kernel busy **2.941 s（81.0%）**；staging 副本 **1.952 s，与 st_ kernel 重叠 1.663 s = 85.2%**（⇒ **未隐藏 0.289 s**）；GPU-any-busy 3.230 s（89.0%），**气泡 0.400 s**。
- **气泡归因表**：**40 个、总 0.400 s、每个 7.2–12.2 ms，恰好每个 mamba 层边界一个**（`mamba2_scan` 完成数 = 2…39），位置在**每层最后一个 kernel 之后、下一层首个 `mul_mat_q` 之前**；最大 **12.19 ms**（@mamba done=30）、11.67/11.64/11.12 ms… **不是每轮 swap-轮边界**（每层都有）。
- **修正后的墙构成**：`2.941（compute）+ 0.289（未隐藏副本）+ 0.400（层边界气泡）= 3.630 s` ✓ = 真窗口 3.631 s。
- **对 lead 模型（DMA 2.55 / compute 2.4 / 重叠 1.0 / 墙 3.92）的修正**：真实 DMA 只有 **1.95 s**（45.23 GB @ 23.2 GB/s，不是 17.7 GB/s），且 **85% 被藏住**；**真正的差距在 ① compute 2.941 s（比估算高 0.54 s）② 层边界气泡 0.400 s ③ 未藏副本 0.289 s**。
- **nsys 开销修正**：真窗口 3.631 s vs 无 nsys 对照 3.8250 s ⇒ **约 −5%（在单跑噪声内，未测出正开销）**；R10 的 +21.3% 撤销。

### 7) "74.50 GB 里真假构成"（问题 6 的答案）
- **真且必须在 prefill 窗口内**：**45.23 GB**（ahead 42.20 + others 3.03），全部不可去（是流式专家本体）。
- **真但可去/可省（改机制才有意义）**：**0 GB**（窗口内没有重复拷贝；R10 的"1.54×"是伪影）。
- **真但在窗口外**：load 填充 17.65 GB（load 期一次性，不进墙）+ load 权重上传 4.89 GB（load 期）+ decode swap 6.73 GB（判据外）。
- **伪影**：0 GB（多出的次数全是时间分段口径造成的，不是重复发行）。

## 未验 / 边界
1. **decode 段（15.80–19.05 s）的 kernel 不可见**（CUDA graph 内），swap 2,174 与引擎 2,041 的 +133 差异未解释。
2. **层边界气泡的宿主侧原因未定位**：候选是每层 routing 的 host 同步（`engine.cpp` 里 `cudaEventSynchronize(ev_)` 一带）与"下一层预取/启动"的时序；需插桩（每层 NVTX + host 时间戳）才能钉死（本轮禁改码）。
3. 764 次 load 上传里极少数（≤0.01 GB 量级）落在 prefill 窗口尾部，按 D 级忽略。
4. nsys 开销"−5%"是单跑对照，噪声 ±5% ⇒ 只能说"未测出正开销"，不能说 nsys 免费。
5. 本次结论全部基于 R10 的同一份 sqlite。**给 lead 的编译建议**：①**不要做"去重修复"**（重复不存在）；②计数器应改成分段打印（`fill_copies / prefill_copies / swap_copies` 各自 bytes），避免再对账；③下一步值得做的是"层边界 0.40 s 气泡"（每层 ~10 ms，属 host/依赖时序，不是 kernel 优化）。
