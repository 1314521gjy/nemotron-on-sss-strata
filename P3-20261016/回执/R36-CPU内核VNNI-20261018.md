## 4. 为什么不赚（与上游一致的物理解释）

我们的 decode window 只有 2–4 个 token，top-22/512 的路由重叠极小 ⇒ 一个专家的"uses 段长"平均 ≈1.2 ⇒ 行内核对单 use 没有多 token 摊薄；`kq256_rows` 省下的是"每 use 重复解码权重"，而这段在 window 里本来就只有 ~1.2 份。上游 `native_expert.cpp` 对同一内核的实测也是 "in-engine 1.01–1.13×（parity 工具里 1.0–1.45×）"。**该杠杆在 decode 上不存在，只在长 uses 段（prefill 的 CPU share）可能有用**——但 B3 prefill 本批被负载污染，未能定论（未验）。

## 5. 对 lead 计划的直接影响

1. **"接上已有 VNNI 行内核"这条路被位精确硬门挡住**：`iq4nl256_down_rows`（含 VNNI）对 ggml 非逐位（max rel 1.12e-2）。若 VNNI 要上，必须写**新的位精确 VNNI 行内核**：Q4_K up 的 `vpdpwssd`（K-quant 的 q4_K×q8_K，逐 int32 累加后可逐位对齐）+ IQ4_NL down 的 `vpdpbusd` 位精确版——这是 Compile #2 该做的**单变量**，且必须先过本 parity 工具（可复用/扩展）。
2. **本包代码留在树里（默认开、可 env 关）无害**：ids 逐位同；建议下批一次编译时**把它改回默认关**（或保留，等你定），并同时上 Compile #2。
3. **下一批先控环境**：本批 B0 比 R35 −24%（外部 AweSun/多 DSH/qoderwake 仍在），decode 判据建议每批都带"旧 exe 同批对照臂"（B0 这种），否则跨批不可比。

## 6. 未验 / 边界

- B2/B3 无同批旧 exe 对照（预算 4 跑，B0 只覆盖 alt）⇒ qa/交付形态的**相对**性能未验（绝对值见上表，本批环境慢 24%）。
- 任务粒度 32→64 的单独贡献未拆（与 up 内核同包，且数值中性）。
- prefill 的 CPU-share 长 uses 段是否有收益：未验（B3 被负载污染，需干净批再跑一次交付形态 + 旧 exe 对照）。
- `kq256_rows` 的 1-use 路径未单独压测；按上游 `native_expert_parity` 口径单 token 无优势。
