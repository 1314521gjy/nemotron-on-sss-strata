## 红臂（本席怎么验、怎么变红）

- **"没人读 down"断言**：全树 grep `exp_down` 28 命中逐条分类（§3），不是只看 builder3 的 4 处；任何一条仍读且未改 ⇒ 断言红。本席发现 **9 条 builder3 未列**，其中 **borrow refill（交付 borrow=1）** 与 **prefill stage** 是硬伤。
- **map_pages 跳过**：只删 :2312 不够——fill/stage/borrow 一读就 fault，页仍回 RAM ⇒ **RAM 不降**（判红条件：Stage D 只改内核就宣称省 31.7GB）。
- **RAM 闭合**：算术 95.13 = 63.42+31.71（A）；post 75.2（含 OS 估算）⇒ 余 20.8；若 OS 实际 14–16 或 housekeeping 3–4 ⇒ 余 11–14（仍闭合）；**若把 scout-b 的 42.5 当额外副本再加一次 ⇒ 91 ⇒ 余 ~5**（但 42.5 已含在 63.4，属重复计）。
- **冷页**：sidecar 不 prefault ⇒ R57-E1 实测 1.59 tok/s 是硬负控；up 不预热 ⇒ CPU miss/prefill 冷读。

## 关键决定（给 lead 的答复）

1. **论断判定：条件成立**——Stage D 必须按"数据源切换包"实施（D2+D4+D5+D6a + borrow refill/CPU-share/on-load 检查/MTP/pcie 边界），不能只做 GPU down 内核。
2. **RAM 对账：lead 的 68.1 方向对，需两处修正**：① 4.7GB "dense" 中 output+other 是 load 一次读、上传 VRAM（硬驻留仅 token 表 0.30GB）；② 68.1 未含 OS ~10GB ⇒ 本席 post ≈**75.2GB**，余 **≈20.8GB**（仍闭合；pin 预算 67.06GiB ≤96）。
3. **scout-b 的 42.5 是"63.4 里的非驻留页"，不是额外副本** ⇒ 其 91/96 是 pre-Stage-D 账；若拿它给 Stage D 判死，属于**重复计 down 读集 + 把一次性读当驻留**。
4. **冷页风险可控**，但前提写死：`map_pages` 必须保留 up span 预热 + sidecar 必须 prefault/touch（R57c-fix）；否则 R57-E1 的页错风暴重演。
