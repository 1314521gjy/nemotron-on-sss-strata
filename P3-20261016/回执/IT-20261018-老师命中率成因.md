## 1. 任务

## 3. 结论（一句话）
**老师 96.5% 不是口径骗局、也不只靠"表好"：① 口径先纠正——decode 驻留是 11,428 槽（46.5%），不是 9,041（36.8%，那是 prefill 借出 2,387 槽后的瞬时值 11,428−2,387=9,041；streamed 15,535+resident 9,041=24,576 全专家数吻合）；命中分母是 decode verify window 的 **expert uses**（76 轮×48 层=3,648 dispatches，119,845 entries，32.85/层/窗；窗口 T=3.3×k=10=33 ✓），distinct 口径几乎同值（96.52% vs 96.53% 推算）⇒ (c) 不是原因。② 它的路由远比我们集中：同 46.5% 槽比例下我们的理想表只能覆盖 83.9%，它实测 96.5%（(a) 差 12.6 点，不可抄）。③ 我们的表确实吃亏且可修：表在当前 27.9% 槽位下"同分布"应覆盖 67.4%，实测 43.3%（无 swap）/51.7%（交付）/60.5–62.7%（R43/R44 自适应臂）⇒ 24 点丢在**表在 prefill 负载上采、decode 分布不匹配 + 缺 blk.88**（(b)）。分解（线性近似，D）：43.3 实测 +24.1（b）+16.5（槽位比例 27.9→46.5%，受每专家 2.95MB 限制）+12.6（a）= 96.5%。**

## 5. 建议（(b) 可执行建表步骤）
1. **采集负载换 decode 为主**：3–5 条同族 prompt（agent/问答/代码），prompt ≤64 token、`--max-new 512–1024`、顺序单请求，目标 **2–5 万 decode token**（uses 1.8–4.4 千万，与现有 5.4 千万同量级）。
2. **从空表开始**：新路径作 `--expert-profile` + `--expert-profile-write`（poly `main.cpp:943-944`；缺失文件=无表，`engine.cpp:182-199`）；**不要**用 p_master 当起点（`save_profile` 会 prior+use 叠加旧 prefill 计数，`:2020-2047`）。
3. **把 blk.88 采进来**：采集时开 `--draft`（draft 前向 `moe(L,n_layer_,1)` 会把 uses 计入 `use_`，`:2260`）。
4. **（小改）decode-only 计数**：`use_` 分 prefill/decode 两个计数（`moe_rows:2802` 不进 profile），1 个计数点改动。
5. **验证（能变红）**：alt prompt 64 token：`experts from VRAM` ≥60%（理想 ~67%；<55% 红）、`decode: miss/token` ≈350（>450 红）、ids 45/45、tok/s ≥17；长跑 256 token 复核命中不随长度掉。
6. **现实收益**：命中 43.3→~67% ⇒ CPU uses 496.7→~290/token，按 96µs/miss 省 ~20ms/token（75ms 的约 27%）；补到 96.5% 不可能（(a) 12.6 点 + 槽位/VRAM 限制）。
