## 2. 结论（S3）

1. **首 token 翻转的因 = VRAM 代价**：X2 把 block 计算完全关掉（`drafts()`=false、不跑 `draft_rows`），只保留它的 VRAM（驻留 5721→5509）——**首 token 一样翻到 1957**，与全量 draft（D2）一致。⇒ 不是 `block_rows/block_attend` 的计算污染。
2. **reserve 补偿能救"首 token"，但救不到逐位**：
   - 精确补偿量：`212 专家 × 2.9531 MB = 626.06 MB`（**不是计划里估的 ~212 MB**；按此 reserve 需 3000→2403，再微调到 **2376** 才让驻留精确回到 5721）。
   - X3（5712 槽）首 token 已回 6421，但 idx45 漂；X4（5721 槽、峰值 31,660 仍过门）**首 token 同、idx43 漂（1046 vs 1044）**。
   - 残余差异不再来自"槽数"，而来自 **投机本身的 window/batch 算术**（一轮里 2–4 个 token 一起过 88 层，kernel 形状与逐 token 不同 ⇒ 末位不同 ⇒ 在近平分处翻 token；兑现 95% 时也在 idx43 翻）。⇒ **ids 门在"补偿 VRAM"这一步救不回逐位**。
3. **峰值门的真实余量**：X4 峰值 31,660 = 门 31,700 只剩 40 MiB ⇒ 即使"救首 token"也不宜作为交付默认（余量太薄，且仍未逐位）。

### draft 机制的精确 VRAM 账（§S3 要求）
| 项 | 计算式 | 字节 | 折合 |
|---|---|---|---|
| `state_` 扩容 | `(n_embd_ + rows_*n_embd_)*4` = (4096+6912×4096)×4 | 113,262,592 | **108.0 MiB** |
| `r_` 扩容（3 路 ×2 半） | `(3−1)*(read_rows_>rows_?2:1)*rows_*n_embd_*4` = 2×2×6912×4096×4 | 452,984,832 | **432.0 MiB** |
| blk.88 稠密权重（GGUF 实测：eh_proj/attn_q/k/v/o/latent down/up/shexp up/down/gate_inp/5 个 norm/probs_b） | 按类型块大小逐张量求和 | 82,839,552 | **79.0 MiB** |
| blk.88 attention KV | `2 × max_context(16384) × n_kv(2)×head_dim(128) × 2 B` | 16,777,216 | **16.0 MiB** |
| **计算合计** | | 665,864,192 | **635.0 MiB** |
| **实测净占**（缓存差：16894.83 → 16268.77 MB） | 5721→5509 专家 × 2.9531 MB | 626,060,000 | **597.1 MiB** |
| 差 | 38.0 MiB | | 归因 `free_b`/CUDA 上下文跑间差（本批 X1/X2 峰值本身差 99 MiB），未单独测 |

⇒ 交付含义：**开 MTP 的代价 ≈ 600 MiB VRAM ⇒ −212 驻留专家（−3.7%），换来 decode +2~4%**；要补偿回驻留则峰值余量只剩 40 MiB ⇒ **不划算，MTP 保持 opt-in，不采纳默认**（与 R30 结论一致，现在有了因果证明）。
