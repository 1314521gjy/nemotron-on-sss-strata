## 结论（一句话）
**A 值得做、B 不值得做**：mamba2_scan 的 6.87% occupancy 由"并行度只有 8,192 线程（grid 128 blocks=0.08 wave/SM）+ 每线程 6,791 步串行递推"决定（smem 33 KiB 只是上限次因）；改法 #1（d_state 切给 warp + state 入寄存器）**可做逐位等价**、预计 2–4×（0.87→0.22–0.4 s，墙 +5~8%，D）。FP16 专家路径**DMA 字节不变**（上游 Q4_K 仍在飞、FP16 只是小环 scratch）但算力峰值只有 int8 一半，预期 **−10%~−30%（更慢）**，不建议移植。

## 证据（要点）
### A（mamba2_scan）
- **ncu 出处已复核（不是未验）**：`P3-20261016\计划-分环节定位杠杆-20261017.md:73`：0.08 wave/SM、Achieved Occupancy **6.87%**（理论 79.17%）、1 warp/调度器、No-Eligible 98.67%、长记分板 80.6%、Compute 2.98%、DRAM 0.84%、非合并 load 4.1/32 B。**注意它是旧/非 SMEM 版本**（Duration 38.62 ms/层 vs 现配置 nsys 21.79 ms）⇒ 只用 occupancy/stall，不用其 Duration。
- **现配置 launch（A，R13 nsys）**：grid=(128,1,1)、block=(64,1,1)、regs 40、static smem 4,112 B + dynamic **33,024 B**、**40 次/0.872 s（21.79 ms/层）**；几何反推 d_state=128、head_dim=64、n_head=128（`kernels.cu:2719` 的 `head_dim×(d_state+1)×4`）。
- **手算 occupancy（C 级规格）**：每块 2 warp、37,136 B smem ⇒ smem 允许 **2 blocks/SM=4 warps=8.33%**；实际 grid 128/80=1.6 blocks/SM ⇒ **≈6.7%** —— 与 ncu 6.87% 闭合。
- **根因排序**：①并行度只有 8,192 线程（GPU 可跑 ~163,840）②每线程 6,791 步串行递推 ③warp 太少不能藏延迟（No-Eligible 98.67%）④smem 33 KiB 是上限次因（加 grid 后仍需先腾掉）⑤非 SMEM 版有非合并 state load。
- **改法**：#1 d_state 切 warp + state 入寄存器（2–4×，可逐位，中工作量）· #2 token 分块两遍 scan（再 1.5–2.5×，非逐位，高工作量，scratch ~29 MB）· #3 只挪 smem **单做≈0**（只是前提）。**Mamba2 ≠ GDN：上游 `gdn_rec_chunked` 代码不可搬，只搬"分块并行 + 对拍"方法**（与 `情报-E-prefill计算结构对拍-20261018.md:164` 一致）；判据台已有 `正确性判据-mamba2scan改动-20261017.md`。

### B（FP16 prompt 路径）
- **我们路径**：量化 dense `engine.cpp:2031-2034` int8 MMQ；MoE staged/cached `:2687/2696/2771/2780/2858/2863/2873/2879` 全 int8 MMQ；F32/BF16 dense 走 `gemm_f32`＝**cuBLAS SGEMM FP32**（`src/poly/kernels.cu:2082-2102`）。链接面 `strata_poly_mmq`（`CMakeLists.txt:1803-1805,1829`）**不含 `gemm.cu`**（属 `strata_prefill`，`:612`）。
- **上游数据流**：`UP/docs/QUANTS.md:37`（Q4_K CUDA prompt 默认 FP16，MMQ 需 `STRATA_MMQ_KQ=1`）+ `:43-44`（专家反量化 FP16 再 BLAS，~10 MB/专家）；`UP/include/strata/prefill/gemm.hpp:1-6`（BF16 权重或 `dequant_bf16` scratch + BF16 激活 + cuBLAS）；**DQ=2 环** `UP/src/prefill/prefill.cpp:315,1307`（`dq_gu` 1280×2560 u16、`dq_d` 2560×640 u16，×2 ⇒ ≈19.7 MB）。⇒ **关键：上游 DMA 在飞仍是 Q4_K 字节，FP16 只是小环 scratch。**
- **最小移植面**：①Q4_K→FP16 反量化 kernel（我们的链接面**没有** ggml `dequantize.cu`，需加或自写 ~60–80 行）②FP16 环 22 MB（我们几何：半帧 5.5 MB×2×2）③`mmq_f16` cuBLAS HGEMM 入口（可抄 `kernels.cu:2059` 的 `cublasGemmStridedBatchedEx`，~50–80 行）④旗标默认 0 ⑤数值门 = ids 45/45 + pos0 容差（上游自己写"changes the prompt's rounding"，不可能逐位）。**需要 A/B 对照跑 + ncu**。
- **收益判断（D）**：DMA 45.1 GB **不变**；额外 VRAM 流量 ~160 ms 级；FP16 TC 峰值 165 TFLOPS vs int8 330 TOPS（C）⇒ **FP16 峰值只有一半**；我们 MMQ MoE 有效吞吐反推 ≈180–220 TFLOPS 等效（D，±40%）⇒ **FP16 要反超需效率翻倍，没有理由** ⇒ 预期 **−10%~−30%**。若真要 GEMM 侧杠杆，先做 MMQ 的 ncu、或 dense F32/BF16 混合精度（`gemm_f32` 现为纯 FP32 SGEMM），别动专家流。
- **type12 拆分（D，±30%）**：MoE ≈ **0.35 s**（grid 1728/2268/2940/3024/3780 + type14）· dense/shared ≈ **0.31 s**（grid (7830,1)×40 占 0.277 s + (80,1)/(432,1)）· **未归因 ≈0.28 s**（多种 grid，未逐 launch 对 call site——**查不到精确归因**）。
