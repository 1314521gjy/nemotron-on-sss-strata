## 3. 为什么 decode 没赚到（数据）

- D3（无 draft）每轮 1 token、**75.0 ms/round**（63/11.20/64）。
- D2（draft）**tokens/round 2.07**，但 **~203 ms/round**（63/11.45/31）⇒ 每 token 98.2 ms vs 89.3 ms，**反而贵 10%**。
- 机理：window 一次过 2–4 个 token 时，**代价≈随 token 线性**（decode 是"每层专家缺失 + CPU 计算/等待"主导：miss/token 703 vs 497、CPU experts 14.2 vs 13.5 ms/token、router wait 5.8 vs 6.6），批内没有摊薄；而 MTP 每轮还多 1–3 次整块前向 + 同步。⇒ **在这条引擎的 decode 结构里，投机只提高 tokens/round，不降低每 token 成本**；D4 短 prompt 13.98 是冷缓存特例（无同 prompt no-draft 对照，未验）。

## 4. ids 门为什么不过（关键发现，未完全定因）

- **不是近平分末位漂**：P1（开 draft）pos0 分布 `1957:0.2105 6421:0.1576 10736:0.1167 1032:0.0933…`；P2（关 draft）`6421:0.1825 1957:0.1483 1032:0.1090 10736:0.1033…` ⇒ **max|Δp| = 6.215e-2 @token1957，且 top1 直接互换**。prompt 端 hidden state 真的不同。
- **可复现**：D1/D2 两跑首 token 都是 1957；关 draft 的三次跑（R28-A 旧 exe、D3 新 exe、P2）都是 6421 ⇒ 系统性差异，不是噪声。
- **不是 D3 侧被本 build 改变**：`D3 ids == R28-A（旧 exe，同 config）` 逐位同 ⇒ 无 draft 路径未被本轮改动影响（一次编译的默认行为保持不变 ✓）。
- **候选机制（未逐个隔离，需下一轮开关）**：
  1. **draft 机制的 VRAM 代价**：`state_`(+113 MB) 与 `r_`(3×2 缓冲，+454 MB) + block 权重/KV ⇒ 驻留 **5721 → 5509 专家（−212）**；prompt 293 token × 88 层 → 数万次"GPU↔CPU 谁算"变化 → 末层 logits 漂 6e-2（同一量级在 R1 reserve 实验里只有 2.8e-4，但那时只 45 token）。
  2. **block_rows 在 prompt read 里新增的真工作**（k/v 投影 292 行 + 写 KV）；R28-C 旧 exe（block 载入但未接线、block_rows 空转）首 token 未漂 ⇒ 这条嫌疑最大之一。
  3. 其它（draft_input 在 prefill 后对 r_/xn_/xq_ 的复写、`card_row_bytes` 8→9 层对 conversation-cache 行口径）——**均未验**。
- **下一步隔离建议（未做，等令）**：加 `STRATA_DRAFT_LOAD_ONLY=1`（载入并接线 block、但 `block_attend/block_rows` 空转）⇒ 把"VRAM/缓存代价"与"block 真工作"分开；再决定 ids 门是否可用"reserve 补偿"（把 −212 专家用 `--vram-reserve-mib 2600` 之类换回来）恢复逐位同。

## 5. 结论与建议

1. **R29 根因判断正确、修复有效**：acceptance 84.6–94.9%，dump 语义正确，峰值安全，**默认值一个没动**。
2. **但投机在这条引擎上不划算**：tokens/round 2.07–2.37，decode +2.2%（<5% 门），且 ids 因 draft 的 VRAM 代价在 prompt 端漂 6e-2 ⇒ **不采纳为交付默认**（保持 `--no-draft`；MTP 保留 opt-in）。
3. **若还想救 ids 门**：先做 §4 的隔离开关 + reserve 补偿实验（separate compile/run）；否则按"投机在 CPU-miss 主导的 decode 上无收益"记档。
4. 交付口径建议：**decode 用 `--no-draft --lookup 3` 的 alt-prompt 实测（11.2–13.4 tok/s）**，不要用 p6792 的 22.19/25.23；MTP 的能力读数（acceptance 85–95%）单独作为架构能力报，不与 tok/s 混。
