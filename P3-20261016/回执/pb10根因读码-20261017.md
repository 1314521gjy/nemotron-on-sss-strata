## §0 先说两条**结论级**的（能立刻用于排错）

1. ★★ **9→10 的断崖有一个严格的代码边界，但它不是"n_run 越界"**：**`kCpuRows = 8`**（`src/poly/runtime.hpp:26`，"tokens whose CPU experts one call computes"）⇒ `moe()` 把一次调用**按 8 个 token 分块**：`for (int at = 0; at < n; at += kCpuRows) { const int m = min(kCpuRows, n-at); … }`（`engine.cpp:1917-1918`）。
   ⇒ **pb=8：块 = {8}** · **pb=9：块 = {8,1}** · **pb=10：块 = {8,2}** ⇒ ★ **9→10 的唯一结构变化 = "第二个块第一次拿到 ≥2 个 token"**（不是"第一次分块"——那发生在 9）。
   ⇒ ★ **⇒ 任何"需要同一块内 ≥2 个 token 才会发作"的 bug，都会【恰好】在 pb=10 首现、而 pb=9 正常** ✓ 与实测吻合。
2. ★★ **pb≥32 的 NaN 很可能【不是同一个 bug】**：`batched(L,n) = mmq_ && L.mmq && n ≥ kStageRows`（`engine.cpp:1877`，**`kStageRows = 32`**，`runtime.hpp:29`）⇒ ★ **pb 跨过 32 时【换了一条路径】**（`moe_rows()` 的 MMQ 批路径，`:2194`）⇒ **NaN 的签名（0xFF 解成 float）更像"批路径读了未初始化/越界的 buffer"** ⇒ **⇒ 请把 pb=10–16 与 pb≥32 当【两个 bug】分别定位**（除非后面证明同源）。

## §3 你第 3 问：`n_run` 会不会在 9→10 越过某个界？（**从代码算**）

- **`n_run` 的定义**（`cpu_experts.cpp` 的分组）：一次调用里**不同专家**的数量。在 `moe()` 的**一块**（≤8 token × top-22）里，理论上限 **min(512, 8×22) = 176**；**实测**在 pb=8 时已可达 ~176（因为每 token 22 个、几乎不重复）。
- ★ **⇒ `n_run` 从 pb=8 起就可能到 170+，并没有在 9→10 才"越过"某个 ≤8/≤9 的界** ⇒ **⇒ "n_run 越界"这条假设，在 `moe()` 里【不成立】**（它只影响**分组粒度**，而分组是 `std::stable_sort` + 逐 expert 的，**没有定长上限**——这点我在 `cpu_experts.cpp:190-199` 只读到分组键，**未逐行读上限**，标 **未验**）。
- ★★ **⇒ 但 `kCpuRows=8` 给了一个【不同】的 9→10 边界**（§0-1）：**"第 2 块 ≥2 token"**。⇒ **这是目前与 9→10 断崖最吻合的结构特征。**

## §4 你第 4 问（反假设）：哪些地方按 `rows` 定尺寸但有 ≤8/9 的常量
- **`kCpuRows=8` 的 `m` 循环**（`:1917-1918`）⇒ **正是"按 n 切块、块大小 8"** ⇒ ★ **如果 bug 需要"块内 ≥2 token"，它就在 pb=10 出现**。
- **`chunk_`（注意力分块）**：`chunk_ = clamp(kScoreFloats/(n_head*max_context), 1, rows_)`（`nemotronhmoe.cpp:212`）⇒ 本靶 = `clamp(64, 1, rows_)` ⇒ **pb≤64 时 `chunk_ = rows_ = pb`** ⇒ **不构成 8/9 边界**。
- **`__launch_bounds__` / warp 数**：poly 侧 `kernels.cu` 的 mamba/attention 段**未设 `__launch_bounds__`**（grep 只在小内核 `:113` 有）⇒ **不是**。

## §8 ★★ 追加（本轮最后 10 分钟的**更锋利候选**）：`d_` 的**两套索引**在同一块里混用

**读到的两处（A）**：
- **卡上专家**写 `d_` 用 **槽序号**：`down.y[j] = d_ + (size_t) ((i0 + j) % kSumRows) * e_row;`（`engine.cpp:1982`）⇒ 索引 = **`(i0+j) % 32`**（"第几个 cached 专家"）。
- ★ **CPU 专家**写 `d_` 用 **token 行号**：`sum.acc[k] = acc + (size_t) c.row * e_row;`（`:2065`）⇒ **`c.row = at + t`**（`:1937`）⇒ 索引 = **token 行**。
- 两者最后都由 `add_scaled(sum, k+1, out_w, st_)`（`:2067`）加进 `y`。

**⇒ 机制（候选 D，未验）**：**同一层、同一块里若一个 token 既有 cached 专家又有 host 专家**，两条路会把行写进 `d_` 的**不同坐标系**（一个按"第几个专家"、一个按"第几个 token"）⇒ **互相覆盖 / 少加一项**。
**⇒ 为什么是 9→10**：`kCpuRows=8` 分块 ⇒ **pb=9 的第 2 块只有 1 个 token**（且若该 token 全 cached 或全 host，不会撞）；**pb=10 的第 2 块有 2 个 token** ⇒ **"混合 + ≥2 行"第一次出现**。
**⇒ 为什么 pb=8/9 正确、且旧 exe 同错**：`kCpuRows=8` 是老常量（`runtime.hpp:26`），**与我们的改动无关** ⇒ 符合"pre-existing" ✓。
**⇒ 一击定案（零改码）**：**`--no-gpu-experts`（全 CPU）或让全部专家驻留（`--vram-reserve-mib` 极小 + 大 arena）** 各跑 pb=10：
- **全 CPU ⇒ 只剩一个坐标系 ⇒ 若变正确 ⇒ 候选 D 成立**；
- **全驻留 ⇒ 只剩另一个坐标系 ⇒ 也应正确**；
- **两者都正确而混合时错 ⇒ 就是"混用"**。
**⇒ 修法方向（未实施）**：让 CPU 侧也用 `(k) % kSumRows` 的**槽序号**（`sum.acc` 用连续的 `k` 而不是 `row*e_row`），或让卡侧也用行号 —— **但行号会超过 32 行（`d_` 只有 32 行）⇒ 只能用"槽序号 + 单独的 row 表"** ⇒ 改动面待评估。
