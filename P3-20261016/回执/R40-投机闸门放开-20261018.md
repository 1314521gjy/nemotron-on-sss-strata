## 3. 判据

| 判据 | 结果 |
|---|---|
| tokens/round > 2（窗口真的开了） | **✓ 3.05 / 3.20**（旧 R30 是 2.07；闸门放开生效，兑现率还升到 93.5%/97.8%） |
| per-token 时间相对 W0 改善 ≥15% | **✗ W1 +3.2%、W2 +0.9%（反升）** |
| 判红后停手 | **✓ 未跑 W3/W4**（预算 3/5 跑） |

**为什么反升（与 R32 的预测一致，且这次有直接账）**：
- 窗口 token 的 CPU 专家工作**不摊薄**：miss/token 496.7 → **670.5 / 644.8（+35% / +30%）**（窗口里被拒/多算的 token + draft 块自身的 MoE 都记进 CPU 腿），`cpu_us/miss` 只降 13%（88.1/88.9 vs 101.1）⇒ **CPU 腿每 token 50.2 ms → 59.1 / 57.3 ms（+17.7% / +14.1%）**。
- 即：MTP 的兑现率不是问题（93.5%/97.8%），**每多测一个 token 就要多付一份 CPU 专家读取**（top-22/512 路由几乎不重叠，权重读不共享）；窗口只摊薄了很小的每轮固定开销，堵不上 CPU 腿的线性增长。
- 本机 decode 的 75–80% 时间就是这条 CPU 腿（R37/R33 已定论），所以窗口栈没有可赚的空间。
