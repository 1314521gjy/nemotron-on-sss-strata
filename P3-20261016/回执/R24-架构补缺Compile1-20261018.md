## 6. 必须转告的两条实测修正

### 6.1 ② 默认 pinning 掉 decode ⇒ 默认已改为 off（与任务单"默认 first=现状"相反，附归因）
- 第 1 次编译（默认 `first`）：同机同配置 decode **21.91（旧 exe）→ 19.39（新 exe）**，prefill 不变（1900.9 vs 1909.5）⇒ 掉的是 decode（host/CPU 侧）不是 GPU-bound 的 prefill。
- **结构归因（回答"为什么和老师不同"，不是判否）**：上游 pool worker = **物理核数**，host 独占一物理核、SMT 兄弟可给 aux（`--no-host-worker` 语义）；我们 `--threads 24` = **24 个逻辑 CPU 全用**（23 worker + host 自己也是第 24 个 worker，`Workers::threads()=spawned+1`），

  ⇒ 把 24 条线程钉死在 24 个逻辑 CPU 后，OS/Thread Director 没有空闲逻辑 CPU 可把 latency-critical 的 host 线程挪到空闲 P 核，也没有余量给 CUDA 驱动线程；V2 的 `aux auto` 只能从 worker 手里拿走 2 个（21 cpus / 23 workers，2 share）。
- 因此**默认改为 `off`**（不 pin = 不变量）；`--host-core first|last|<n>` 保留为显式 A/B 开关。
- **静默重复的零精度证据**：`V1r`（pinned，静默）128 行概率逐位同 ⇒ host/worker pinning 本身不改算术；但 **aux pinning 不满足"零精度风险"**：V2 概率行 pos65 起漂（见 §6.2）。交付配置**不要默认开 aux**。
- **性能判决（明确不给）**：默认 off 5 跑 20.72/21.21/21.68/22.01（+旧 exe 21.63/21.91/22.31），V1 两跑 19.82/19.87，V2 一跑 18.86；decode 单跑噪声本机 ±8% ⇒ **n=1/2 不足以判"pinning 一定更慢"**，只能说两臂方向一致偏低；要判需 ≥3 跑中位、同窗口。

### 6.2 decode 概率级**时序敏感漂移**（预存在嫌疑；"pos0 概率"判据抓不到）
- 同 exe、同配置、同 flags 的重复跑出现**两条离散轨迹**：
  - **静默跑 5/5**（V0、V0r2、new3、V1r、旧 exe×3）⇒ 128 行概率**逐位同**基线；
  - **带 VRAM 采样器（每 200 ms spawn 一个 nvidia-smi）的 3 跑**：V0r 与 V1 出现**完全相同**的另一条轨迹（pos97 起 31 行不同，**max\|Δp\|=0.1099 @pos103**），V2 是另一条（pos65 起 63 行，max 0.0187@76）；**ids 全部仍 128/128**。
- 归因（待查/倾向于预存在）：引擎里有**计时择路**（`pick_way`：两路先各测 3 次再选快的一路）与 **adaptive tier 的到达时序**（`follow()` 用 `cudaEventQuery` 决定何时发布槽表），都会随机器负载改选择；但同样带采样器的 V0/旧 exe 对照没漂 ⇒ 触发条件不止采样器，**未定**。
- **对判据的影响（重要）**：任务单的"pos0 概率逐位同"**恒真**（pos0 在所有跑都同，因为它算在任何 swap 之前），抓不到这种漂移。建议 R25/Compile #2 的负控升级为 **ids + 全位置 `max|Δp| ≤ 2e-3`（R1 §7 门）**，且在**静默窗口**跑（不要边跑边采）；逐位判改用 `--expert-swaps 0`。
