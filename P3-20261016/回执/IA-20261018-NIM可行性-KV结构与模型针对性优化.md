## 3. 结论（三句）
1. **NIM 卡两条：主因=显存，次因=卡型。** 本模型 **NVFP4 ≈75 GB**（BF16 249 GB），NIM 官方 profile NVFP4=**1×B200/1×H200/2×H100**；**32 GB 装不下，2×4090=48 GB 也不够**；且 **GeForce 不在 NIM verified 列表**（verified 全是 A100/A10G/B200/B300/GB200/GH200/H100/H200/L40S），多卡还要求同型号受支持卡。⇒ "没有 B300"不准确（H200/L40S/A100 也支持），我们卡的是 **75GB>32GB + 消费卡不受支持** 两条同时成立；**32GB 无任何官方 recipe**。
2. **我们的 KV 是 F16（不是 BF16）**：@16384 = **128 MiB（8 个 trunk attn 层）/ 144 MiB（含 MTP blk.88）**；48 层全 attn 才 768 MiB（6×）。**Q8 只省 64 MiB≈21 slot（0.36%）、Q4 省 96 MiB≈31 slot（0.54%）⇒ 按 <300 MB 判据不值得**（attention 不是瓶颈）。mamba state = **164.7 MiB fp32**；窗口快照 `snap_` 上界 3×=494 MiB（交付 window=1 ⇒ 0）。**要省 VRAM 应动快照/MTP，不是 KV。**
3. **结构针对性优化 Top-3**（本件 §3）：**T1 GPU 侧 routing（sigmoid+bias+top-22）**（prefill −0.2~0.35 s=+6~10%，decode −2~4 ms/token=+3~6%；D）＞ **T2 Hybrid prefill CUDA graph + shared expert 独立流**（SGLang PR #44518；折中只图化 40 个非 MoE 段=+1~3%，先 T1 后整图 +5~10%）＞ **T3 mamba-state 感知 window/spec 管理**（vLLM PR #33726 已合并；tok/s 0~+2%，但**可能修掉我们 MTP 的 ids 漂**，state bf16 省 82 MB）。**"mamba 段与 MoE CPU 腿跨层重叠"不可行**（残差链）；**"40 mamba 整段图化"必须先有 T1**（非 MoE 段只有 40 段，32 段仅 1 层）。

## 5. 三问细节
- **① NIM**：见 §3.1；**显存是硬约束（75 GB>32 GB；48 GB 也不够）**，**卡型是第二道门（GeForce 不在 verified、多卡需同型号数据中心卡、无 NVFP4 消费卡内核）**；"没有 B300"不准确（H200/L40S/A100 也支持）；**32 GB 无官方 recipe**，官方单卡档是 H200/B200 或 DGX Spark（128 GB）。
- **② KV/state**：KV=F16，128/144 MiB@16K；mamba state=164.7 MiB fp32；snap 上界 494 MiB（window>1）；**KV 量化不值得（Q8 省 21 slot/0.36%，Q4 省 31 slot/0.54%）**；attention 8 层非瓶颈（decode GPU kernel busy 2–4%）。
- **③ Top-3**：T1 GPU routing（最值得，D 级 +6~10% prefill / +3~6% decode）＞ T2 hybrid prefill graph+shared 流（+1~3% 折中 / +5~10% 整图）＞ T3 mamba-state 感知 spec（tok/s 0~+2%，但可能修 MTP ids 漂）。**跨层 mamba↔CPU 重叠不可行（残差链）**；**整段图化要先 T1**（40 非 MoE 段，32 段仅 1 层）。
