# 回执：`mamba2_scan_kernel` 为什么慢（读码）

```
状态: 达成（4 问全答；判决 + 三个改法 + 一个"上游也没并行"的克制）
席位: scheduler（引擎后端-调度）
时间: 2026-10-17 11:4x 起，约 30 分钟
任务单 version: 队长消息（无盘上任务单）
```

## ★ 一句话判决

> **它慢是因为【跨 token 完全串行 + 每 token 两次 `__syncthreads`】—— 而这正是"一个为单 token 优化的实现"**：`grid = n_head`（**128 个 block**）× `block = head_dim`（**64 线程**）⇒ **总并发 8,192 线程**，而 4080S 容量 ≈ **155,648**（76 SM × 2048）⇒ **占用率 ≈ 5%**；**`for (t = 0; t < rows; ++t)` 在 kernel 里串行**，**rows=700 ⇒ 1400 次 barrier 串行**。
> **⇒ 能靠"给 prefill 走一条并行度更高的 scan 路径"压下来吗？—— 能，但有三档改法，且【上游自己也没做跨 token 并行】**（见 §5，这条很重要，防我们走错路）。

## §2 ★★ 是串行还是并行 scan（**核心**）

```cuda
for (int t = 0; t < rows; ++t) {                       // ← kernels.cu:2561 ★ 跨 token 完全串行
    if (threadIdx.x == 0) { … sdt = softplus(dt…); sdA = expf(sdt*A[h]); }
    for (int st = threadIdx.x; st < d_state; st += blockDim.x) { sB[st]=…; sC[st]=…; }
    __syncthreads();                                   // ← :2571  每 token 第 1 次 barrier
    const float x_dt = xbc[…]; float sumf = 0.0f;
    for (int st = 0; st < d_state; ++st) {              // ← :2574 每线程串行 128 步（依赖链）
        const float state = sp[st]*sdA + sB[st]*x_dt; sumf += state*sC[st]; sp[st] = state;
    }
    … snap … y[…] = sumf + xbc[…] * D[h];
    __syncthreads();                                   // ← :2584  每 token 第 2 次 barrier
}
```

| 问 | 答（A） |
|---|---|
| **串行还是并行 scan？** | ★★ **跨 token 完全串行**（`:2561` 的 `for t` 在 kernel 内），**没有 chunked / Blelloch / 分段并行**；**没有"先算块内、再合并前缀"的两阶段** |
| **跨 token 的串行依赖有没有被并行化？** | ★ **没有**（这正是它慢的根因） |
| **每条 channel 一个 thread？** | ★ **一个 thread 一个 value 维（`i1`）**，而 **该线程负责 `st = i1, i1+blockDim.x, …` 的所有 `d_state` 分片**（`:2567`）⇒ 本靶 `d_state=128 > blockDim=64` ⇒ **每线程 2 个 state 分片** |
| **shared 用多少 / bank conflict？** | `__shared__ float sdt, sdA`（2 个标量）+ **`sB[M2_MAX_DS]`、`sC[M2_MAX_DS]`**（`:2559-2560`）⇒ 访问是 **`st` stride 化（`st = threadIdx.x; st += blockDim.x`）** ⇒ ★ **无 bank conflict**；**state `sp` 不在 shared，而在【全局内存】**（`s + ii*d_state`，`:2558`）→ 见 §3 |

## §3 ★ 一个独立可查的嫌疑：**state 在全局内存**（每 token 一次全局往返）

- `float* sp = s + (size_t) ii * d_state;`（`:2558`）⇒ **state 住在全局内存**（不是寄存器、不是 shared）。
- 每 token：**`d_state` 次全局 load + `d_state` 次全局 store**（`:2575-2577`），**并且有串行依赖**（`sp[st] = state` 下个 token 还要用）⇒ ★ **每 token 一条 128 长的"load→FMA→store"依赖链**。
- **量级（算术）**：每层每 token 的 state 往返 = `dim × d_state × 2 × 4B = 8192×128×8 = 8.4 MB` ⇒ **rows=700 ⇒ ≈5.9 GB/层** ⇒ **×40 层 ≈ 235 GB**；在 ~700 GB/s 下 ≈ **0.34 s**（与实测 kernel 总 **1.237 s** 同量级）⇒ ★ **它可能同时是 latency-bound（串行依赖链）与 bandwidth-heavy**。
- ★ **⇒ C2（ncu）要判的第一件事**：**`smsp__warp_issue_stalled_long_scoreboard` 高 ⇒ latency-bound；`dram__throughput` 高 ⇒ bandwidth-bound**。**两者对应的改法完全不同**（见 §5）。

## §4 `mamba2_conv` / `mamba2_gated_norm` 是否同族同病？（**不同病**）

| kernel | 并行结构 | `file:line` | 判 |
|---|---|---|---|
| **`mamba2_conv_kernel`** | **grid = channels/256、block 256**，**`for (t = 0; t < rows; ++t)` 串行**（`:2599`） | `:2589-2600` · launch `:2671` | ★ **同族同病**（token 维串行；且 `channels=10240` ⇒ **40 个 block**，占用也低）—— 但它只占 **0.8%** |
| **`mamba2_gated_norm_kernel`** | ★ **`<<<dim3(rows, n_group), M2_NORM_BLOCK>>>`** ⇒ **grid.x = rows（每 token 一个 block）、grid.y = n_group** ⇒ **token 维【已并行】** | `:2616` · launch `:2700` | ★ **不同病**（它反而是三者里结构最健康的）—— 占 **0.5%** |
| ⇒ 结论 | **真正的病只在 `scan`**（51.4%）与 `conv`（0.8%）**两处**；★ `gated_norm` **可以当作"我方向对了"的对照臂**（同一个模型、同样每层每 token，**它并行了 ⇒ 它不慢**） | —— | —— |

## §5 ★ 能不能靠"prefill 并行 scan"压下来？三档改法 + **一条重要的克制**

| 档 | 改什么 | 改动面 | 预期 | 依据 |
|---|---|---|---|---|
| **① 最小** | **把 state 从全局内存搬进 shared**（每 block `head_dim × d_state` = 64×128 = **8192 floats = 32 KB**，放得下）⇒ 去掉**每 token 的 128 次全局往返** | **小**（kernel 内改，不动 launch 结构） | 若 §3 判为 **bandwidth/latency 由 state 往返主导** ⇒ 收益大 | `:2558` / `:2574-2578` |
| **② 中** | **chunked scan（两阶段）**：把 `rows` 切成若干 chunk、块内并行 + 块间前缀合并（经典 associative/chunked scan） | **中**（要引入块末状态与合并 kernel/循环） | 把"700 步串行"变成"ceil(700/C) 步串行 × 并行度 C" | —— |
| **③ 大** | **按上游那样做"分段并行 + 软件流水载入"**（上游 `strata` 有 `chunked GDN scan (WY form, chunks of 32)`、`software-pipelined loads in the column-split GDN recurrence`，见提交 `272bbbbd`/`18106b1c`） | **大**（GDN 与 Mamba-2 算术不同族，**只能借思路不能搬码**） | —— | 上游提交（**C 级**） |
| ★★ **克制（防走错路）** | ★ **上游自己也没在 token 维并行 scan**：`include/strata/prefill/prefill.hpp:4-5` 原文「the recurrences **walk the chunk inside one kernel**」⇒ **它也是"一个 kernel 里走完 chunk"** ⇒ ★ **所以"并行化 scan"未必是上游快的来源；它更可能靠"① 两层预取/重叠 + ② chunk 大"把这段时间藏住** | —— | —— | `prefill.hpp:4-5`（A） |

**⇒ 判**：**先做 ①（最小、可测）**；**② 只有在 ① 之后 ncu 仍显示"该 kernel 独占关键路径"时才做**；**③ 暂不做**（跨族）。★ **并且**：在决定改 kernel 之前，**先看 C2 的 ncu 反证** —— 若这个 kernel **本身只占 GPU 时间的 51% 但被"其他 kernel 等它"** ⇒ **真正的杠杆可能是"把它与其他层重叠"（= 我们已证的预取/重叠族）**，而不是把它单点加速。
