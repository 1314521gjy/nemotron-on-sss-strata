## §0 一句话

> ★★ **56% 不能由 top-k 解释（两者在 700 token 下都饱和到 ~512/层）；它要么是"统计口径的 T 不是 700"，要么是"它只有 27 层在饱和"—— 两者都指向口径，不是"它真的只用 288 个专家"。**
> ★ **真正可改的是命中率对齐**：我们把 19,198 个触达里的 **61.5%** 送去搬运（命中 38.5%，而缓存容量占 36.1% ⇒ **≈随机**）；它把 **34.8%** 送去搬运（命中 65.2%，容量占 31.8% ⇒ **2.05× 随机**）。**streamed 比例的 3.5× 差里，几乎全部来自"放置质量"，而不是槽位数。**

## §1 候选 1（top-k 直接效应）—— **排除**

均匀路由下 `E[触达] = 512 × (1 − (1 − k/512)^700)`：

| k | (1−k/512) | ^700 | E[触达] |
|---|---|---|---|
| **22（我们）** | 0.95703 | 4.4e-14 | **512.0** |
| **10（它）** | 0.980469 | 1.0e-6 | **512.0** |

⇒ **两者都饱和**。top-22 与 top-10 在 700 token 下都必然触达几乎全部 512 个专家 ⇒ **56% vs 94% 与 top-k 无关**（候选 1 否）。

## §2 反解：288 与 480 分别相当于多少个 token 的饱和量

`T_eff = ln(1 − E/512) / ln(1 − k/512)`

| 观测 | k | 反解 T_eff |
|---|---|---|
| **我们 480/层** | 22 | **≈ 63 token** |
| **它 288/层** | 10 | **≈ 42 token** |

⇒ 我们的 480 在 700 token 下是"接近饱和但不完全"（路由器略有集中）；它的 288 只相当于 **42 token** 的饱和量。

**能产生 288 的三种口径（按可能性）：**

| # | 解释 | 依据/检验 |
|---|---|---|
| **a ★** | **统计的 T 不是 700**（按 chunk/子窗口统计，或只统计了一部分调用） | 反解 T_eff=42；请核那组 `9018/2428/2382` 是**一次 chunk**还是整个 prefill、chunk 多大 |
| **b ★★** | **只有 27 层在饱和**：`13,828 / 512 = 27.008` —— 恰好 **27×512 ≈ 13,824**（差 4） | 设计件说 48 层都有 MoE（`:180-182`），但若那组数只覆盖 27 层（或 21 层非 MoE），56% 就是平均出来的假象；**请给逐层触达直方图** |
| **c** | **路由高度集中**：7,000 次抽样只落到 288 个专家（224 个专家 0 命中） | 需要 Zipf 截断/专家特化；**请给每专家计数分布**（0 命中的专家数） |
| **d** | **PLE 替代路由** | **否**：设计件 §2 的 PLE 是"每 token 注入 16 行（≈2.5 KB）"，不改变 MoE 路由；全引擎无"跳过 MoE"路径 |

⇒ **一句话：先别把 4.87× 当定论。** `11,810 / 2,428 = 4.87` 里，`1.39×` 来自触达数（19,198 vs 13,828，本身可能是口径），`3.50×` 来自命中率（61.5% vs 34.8%）。**后者才是可复核、可改的部分。**

## §3 可改的部分：命中率对齐（**这是杠杆**）

### 3.1 账（A，用你给的四元组）

| | 我们 | 它 |
|---|---|---|
| 触达（distinct 层-专家） | **19,198** | **13,828** |
| 驻留命中（用于触达的） | 7,388 ⇒ **38.5%** | 9,018 ⇒ **65.2%** |
| 缓存容量占总专家 | 7,388/20,480 = **36.1%** | 7,808/24,576 = **31.8%** |
| **命中 / 容量**（放置质量） | **1.07×（≈随机）** | **2.05×** |
| streamed | **11,810** | **2,428** |
| streamed 占触达 | **61.5%** | **34.8%** |
| 字节（×3.0966 / ×2.11–2.77 MB） | **36.6 GB**（实测 34.87） | **5.1–6.7 GB** |

⇒ **我们的 profile 放置对本 prompt 几乎不产生集中收益**（1.07× 随机），而它的排名放置是 2.05× 随机。**同一容量下，把放置做到 2× 随机，streamed 从 11,810 → 6,681（−43%），字节 36.6 → 20.7 GB。**

### 3.2 「驻留 7,388 → ~10,000，streamed 降多少」——给数

| 情形 | 命中率 | streamed | 字节 | 相对现在 |
|---|---|---|---|---|
| **现状**（7,388 槽，放置≈随机） | 38.5% | **11,810** | 36.6 GB | —— |
| **只加槽**（10,000，放置仍≈随机） | 48.8% × 1.07 ≈ **52.0%** | **9,215** | 28.5 GB | **−22%** |
| **加槽 + 放置对齐到 2.05×**（10,000 槽） | ~**72–75%**（容量 48.8% × 2.05，受长尾饱和折减） | **~4,800–5,400** | 14.9–16.7 GB | **−54%~−59%** |
| 只修放置（仍 7,388 槽，2.05×） | **65.2%** | **6,681** | 20.7 GB | **−43%** |

★ **结论：槽位从 7,388→10,000 只值 −22%；而"放置对齐"值 −43%，两者叠加值 −54%~−59%。** ⇒ **先修 profile 对齐，再谈加槽/换格式。**

### 3.3 为什么我们"≈随机"（可查）

- 引擎**确实**按 profile 填 cache（`fill_expert_cache()`，`engine.cpp:1026-1080` 一带），但那份 profile 是**跨运行累积/全局热度**（`p_run.txt`，20,275 条）。
- 本 prompt 的触达命中 38.5% ≈ 容量 36.1% ⇒ **profile 排名与本次 prompt 的实际路由几乎不相关**（1.07×）。
- ⇒ 要么 profile 过期/来自别的 workload，要么我们的路由分布本来就平（那更需要"按 prompt 重排"或在线 adapt）。**这两者可用同一份数据判**：拿本 prompt 的实际专家计数和 profile 排名做一次秩相关/命中曲线。

# ★★ 追记（2026-10-17 18:4x）：**放置已经是最优 —— 撤回"−43%"**

## §8 用 `p_run.txt` 自己的分布复算（模型 vs 实测）

把每层计数归一成"每 token 选中概率" `p_e = 22·c_e / Σc`，再用 `E=Σ[1−(1−p_e)^700]`：

| 量 | 模型算 | 实测 | 差 |
|---|---|---|---|
| 触达总数 | **19,230** | **19,198** | **0.17%** |
| 去重命中（7,388 槽） | **38.4%** | **38.5%** | 0.1 pt |
| streamed | **11,842** | **11,810** | **0.3%** |

⇒ ★ **我们的 cache 放置对 profile 分布而言已经是 top-K 最优**。38.5% 不是"放置没做好"，而是**长尾的固有属性**：61.6% 的触达专家在 top-7,388 之外，且大多只被碰 1–3 次。
⇒ **上一轮的「1.07× ≈ 随机 ⇒ 可到 2.05× ⇒ −43%」作废** —— 它把"去重命中"误读成"放置质量"。

★★ **3.8 的"2.05×"同样是分母假象**：它触达 288/层、缓存 7,808/48 = **162.7/层** ⇒ **"触达集内均匀"的基线 = 162.7/288 = 56.5%**，实测 65.2% ⇒ **只有 1.15×**，不是 2.05×。
⇒ **两边放置几乎一样好；差的是"触达集大小"（480 vs 288/层）—— 路由分布/T，调度改不了。**

### 9.2 ★ CPU assist（它用，我们在 prefill 里关掉了）
- 它：`2,382 / 13,828 = 17.2%` 的触达专家**交给 CPU**，省 ≈ **5.0 GB PCIe**（2,382 × 2.11 MB）。
- 我们：`spare = !ahead && …`（`engine.cpp:2208`）⇒ canonical 带 `--stage-ahead 128` 时 `ahead=true` ⇒ **CPU 路径整段关闭**；`moe_rows` 的 `host_/cpu_experts/moe_add` 代码全在（`:2303` 的 `use_` 照记），只被这一行挡住。
- ★ 不能直接开：现有策略 `n_cpu = round(share × n_spare)`（`:2318`），canonical `--cpu-share 0.55` ⇒ 会丢 55% 给 CPU，**必炸**。需改成**只给薄专家**（按 `count_[e]` 升序，取到"CPU 时间 ≈ 拷贝时间"，设计件 §13 的做法）。
- 量级（**未跑**）：我们专家 3.10 MB 比它大 1.47×、CPU GEMV 也更慢 ⇒ **17% 的份额未必划算**。薄专家（n_e≤8）每专家 11–88 MFLOP，2,000 个 ≈ 44–80 GFLOP（24 线程 ≈ 0.4–1 s），对 6.2 GB / 22 GB/s = 0.28 s ⇒ **大致打平或略亏**；须小样本实测。
